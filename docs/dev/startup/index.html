Start: first paint and loading state

On this page
  1. Where the window opens
  2. The view from earlier
  3. What the window shows while loading
  4. The start panel
  5. Shimmer
  6. Measuring

The window is never empty after a start. It shows the last known state at once and replaces it part by part as the accounts and repositories answer. "Synced" only shows once every account has answered.

Where the window opens#

The window opens on the start page: the statistics overview (src/views/overview/OverviewView.tsx, docs/metrics.md, "Overview dashboard"), with what only the user can fix above the figures. The way back to it from anywhere is the first entry of the navigation, "Überblick" ("Overview", key 1), marked like every entry while the start page shows. The header shows the same full wordmark on every view, never a view title (each view names itself in its own heading), so the top of the window does not change when a repository or a page opens. The wordmark is a second way to the start page: a button named "Gitoodo, zum Überblick" ("Gitoodo, go to the overview"), reachable with Tab and pressed with Enter or Space. The introduction tour points at the navigation entry.

What the next start opens (src/state/lastView.ts, kept in the window's local storage, never in start-view.json):

Before the window closedNext start
Nothing kept (first start, private mode, damaged entry)The start page.
The start page, a tab ("All repos", "Asked of me", Chat)The start page.
A repository's page, or a question or the settings opened on itThat repository's page; Back leads to the start page.
A repository that is gone sinceThe start page.
The onboarding handed over to the setup assistantThe setup assistant over the start page.

Why not the tab of earlier: the start page answers "is everything running?" in one look, which is the question at every start, and a list from earlier can have changed meanwhile. A repository is the exception: whoever closed the window inside one was in the middle of its work. "All repos" keeps its subpage, so the tab shows the page used last. A kept "Overview" subpage of earlier versions opens the start page.

The view from earlier#

  • What is stored: a compact copy of what the window showed: the accounts (id, kind, label, address, login), each account's last good snapshot (questions and tasks, dashboard rows, repo list), the orchestrator's repositories (state and issues) and the counts. Errors are not stored; they belong to the moment.
  • Where it lives: start-view.json in the app's state folder (the folder that also holds settings.json). It is local only: it is not part of the settings export, and it is never sent anywhere.
  • Who writes it: the window composes the view (src/state/startView.ts). The core stores it (crates/core/src/store/start_view.rs):
    • fields whose names suggest a secret (token, password, secret, cookie, credential, authorization, api_key, private_key, auth) are dropped;
    • every text passes the log redaction: registered tokens, token prefixes and URL credentials are replaced;
    • the file stays under 4 MiB. A bigger view first loses issue bodies and comments, and a view that is still too big is not stored at all.
  • When it is written: at most every 3 seconds while the window shows data that arrived since the start. The view from earlier alone is never stored again.
  • Version: a view with another version, or a damaged one, is ignored whole, never shown in part. The next save replaces it.

Rules:

  • Synced: "Synced" (with its age) only shows once every account that the core polls has answered at least once since the start. A failed poll is also an answer; the error bar says why it failed. Until then the status bar counts the repositories that have answered.
  • Unknown is not zero: a repository whose data has not arrived is a placeholder, never missing, "Empty" or a count of 0. "Only with work" keeps such repositories in the list until their data is known.
  • A failed first poll keeps the data from earlier, still marked as from earlier.
  • Repository by repository: the core reports each repository's progress as it is fetched (the repo-progress event: the account's listing first, then for each repository the start of each read and one event once it is through, with its dashboard row). The sidebar and the counts fill in as the events arrive, without waiting for the whole account.

The start panel#

While the content shows nothing but placeholders (the first-sync skeleton of "Asked of me" or the issues list), a card in the middle of the content says what loads right now (src/views/shell/LoadPanel.tsx, model in src/state/loadPanel.ts):

  • a title, a bar with "12 of 32" (without a value while a repo list is still open), the current step in plain words ("Reading issues and pull requests of owner/name and 3 more …"), and the four phases: accounts, lists, issues and pull requests, questions;
  • a repo whose read takes 5 seconds or more is named as slow; a repo or an account that failed is named once, with the note that loading goes on with the others.

It never blocks: it lies over the content only, takes no pointer or focus, and the sidebar and header stay usable. It shows only after 400 ms (a fast start never flashes), fades out once the first useful view is there and never comes back in this window: later refreshes only use the status bar. A start with a view from earlier shows that view at once, so the card appears only where the view from earlier has nothing to show. Screen readers hear the progress at most every 5 seconds; reduced motion drops the fade and the running band.

The core reports the reads as part of repo-progress: reading (with pass: questions or issues) when a pass starts a repo, and failed on a repo that could not be read. Names only.

The browser demo adds a slow and a failed repo with ?stagger&trouble.

Shimmer#

Placeholders use the shared .shimmer class (src/ui/tokens.css): the grey --color-skeleton with a light band (--color-skeleton-shine) that runs across it every 1.8 seconds. With reduced motion the band is off, and the placeholder only fades slowly. It uses design tokens only, never a meaning colour.

Measuring#

The window logs its start once, when every account has answered, as the start_timings event (docs/logging.md). It records milliseconds since the page began loading:

  • firstContentMs: first content shows, either from earlier or from the core;
  • sidebarMs: the sidebar names every repository with data, with no placeholder left;
  • allLoadedMs: every account has answered;

plus the number of accounts and repositories, and whether a view from earlier was shown. The values are also on globalThis.gitoodoStartTimings while the window runs.

The browser demo simulates a slow start with ?stagger (or ?stagger=<ms>, the base step, default 400). It works like this:

  • every account starts unsynced;
  • each account lists its repositories after one to four steps, reports them one by one at its own pace and then sends its full snapshot;
  • the orchestrator answers after two steps;
  • the demo keeps its view from earlier for the tab, so a reload shows the second start.

Measured in the demo (4 accounts, 60 repositories, ?stagger=400, Vite dev server, headless Chrome):

StartFirst contentSidebar completeAll loaded
First (nothing earlier)481 ms9605 ms10115 ms
Again (view from earlier)139 ms139 ms9797 ms

In both starts, placeholders show from the first frame. On the second start, the sidebar shows all 60 repositories from earlier at once.
