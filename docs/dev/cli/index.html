Every subcommand of the gitoodo command line, generated from the text gitoodo --help prints (the USAGE constant in crates/cli/src/main.rs). The app installs the command with its background services; the daemon reference covers configuration and tokens.

Synopsis#

usage: gitoodo <command> [options]   (gitoodo <command> --help shows one command)
docs: https://gitoodo.com/docs/dev/cli/

Everyday:
  gitoodo status [--changed] [--json] [--ack]
      queue picture of all configured accounts: what waits for you and what the workers do
      --changed  exit 0 when the lines that wait for a person changed since the last --ack, 1 otherwise
      exit 3 when the last poll could not read an account (the summary counts it) or the config
      --json     machine-readable output; --ack remembers the current lines as seen
  gitoodo stop-all
      emergency stop: no new work, running workers are stopped and released (worktrees kept), no
      merges and no classifier writes until `gitoodo resume`; survives restarts
  gitoodo resume
      lift the emergency stop; every repo continues in the state it had before
  gitoodo attach [--host <name>] <issue>
      terminal of a worker, raw mode, detach with Ctrl-]; the worker keeps running
  gitoodo usage [--refresh] [--json]
      usage limits of the coding agents (5-hour and weekly window, paused until); --refresh checks
      every agent on every machine now (at most every 30 s), a lifted limit starts workers at once
  gitoodo --version
      print the CLI version (the app compares it with its own)

Diagnosis:
  gitoodo doctor
      diagnostics: where the daemon takes tokens from (systemd credentials, service environment, system keyring or memory only)
      and, per account, whether this terminal reads the token; when the keychain wants approval it
      names the ways on: the app's System check, token-access --grant, or GITOODO_TOKEN_<ID>
  gitoodo restore-config
      replace a broken orchestration.json with the last valid copy Gitoodo saved
      (orchestration.json.bak); the broken file is kept as orchestration.json.corrupt
  gitoodo trace <owner/repo#n | run-id> [--local] [--output]
      timeline of one issue or run from the logs: every step from the classifier's decision over
      host choice, worktree, worker, pull request and checks to merge and cleanup, with durations;
      also asks the worker machines for their lines (--local: this machine only); read-only,
      redacted; names the worker transcripts kept on this machine (--output: prints them)
  gitoodo diagnose [--hours <n>]
      summary of the last 24 hours (or n): runs, count and p50/p95 per step, top wait reasons,
      errors by kind, the log folder against its budget and the cleanup state (leftover worktrees
      and branches, disk, errors); read-only, redacted
  gitoodo token-access --account <id> [--grant]
      whether the background services read the account's token without a keychain prompt; prints
      readable, needsPrompt, missing or failed; --grant asks once so "Always Allow" can be chosen
  gitoodo clean [--dry-run]
      remove what coding agents keep of Gitoodo's runs whose worktree is gone (session transcripts,
      project and state folders), as the dispatcher does every round; --dry-run only lists it. The
      user's own sessions and the data of runs that may resume stay
  gitoodo autoclean [--plan] [--disk-low]
      one pass of the automatic disk cleanup the dispatcher runs on its schedule (caches of
      installed tools, build output of managed repositories, old temp files); --plan checks
      everything and removes nothing, --disk-low applies the rules for a full disk

Releases and setup:
  gitoodo release [--repo <owner/name>] [--json]
      release planning: open, in-progress and merged items of the next release
      (https://gitoodo.com/docs/dev/release-planning/)
  gitoodo release-version --repo <owner/name> [--account <id>] [--json] [--check]
      suggested next version from the next release's issues and the last released version, with
      its reason; a script scheme runs the repo's script in the local checkout without a token;
      --check only checks the stored version config
  gitoodo release-rules --repo <owner/name> [--account <id>] [--json]
      release assignment rules in effect, their problems and the suggestions waiting for
      approval; read only, the rules are edited in the app
  gitoodo release-runs [--repo <owner/name>] [--account <id>] [--json]
      completed releases and the state of their automation steps; read only, releases are
      completed and steps retried or skipped in the app
  gitoodo labels migrate <account> <owner/repo> [--yes]
      switch an active repo from legacy label names to the catalog by renaming (issues keep their
      labels); prints the preview and changes nothing without --yes; same in the app: Settings ›
      Repos › <repo> › Migrate old labels… (when this terminal may not read the token: token-access
      --grant, or GITOODO_TOKEN_<ID> in the command's environment)
  gitoodo account add --forge forgejo|gitea|github|gitlab --url <url> --token-stdin [--label <name>] [--id <id>] [--store keyring|credential]
  gitoodo account token <account> --token-stdin [--store keyring|credential] | list | remove <account>
      forge accounts without the app (a server without a desktop): the token comes on stdin only
      (typed hidden on a terminal), is checked with the forge and kept in the system keyring or,
      where none answers (headless Linux), as a systemd credential both services load (a file
      only you can read in the state folder plus a drop-in per service, which this writes)
  gitoodo repo list <account> | activate <account> <owner/repo> [--backlog ask|ready|new] [--paused]
  gitoodo repo pause|observe <account> <owner/repo>
      the repository switch without the app: list shows each repository's state; activate shows
      the label changes and what happens to open issues per backlog choice and writes nothing
      until --backlog is given, then creates the labels and switches the repo on (--paused:
      labels and comments, no workers); an account is named by id, label or login
  gitoodo host add <name> <ssh-target> | list | remove <name>
      configure worker machines (satellites: other computers that run workers for this one over
      SSH); ssh target only, no secrets
  gitoodo memory list [--repo <owner/name> [--account <id>] | --global] [--kind <kind>] [--status active|proposed|disputed|archived|all] [--json]
  gitoodo memory show|archive|remove <id> [--json]
  gitoodo memory add --kind fact|procedure|preference|location [--repo <owner/name> [--account <id>]] [--origin human|worker|optimization] [--status active|proposed] [--pin] (<text> | --text-stdin) [--json]
  gitoodo memory edit <id> [--text <text> | --text-stdin] [--kind <kind>] [--repo <owner/name> [--account <id>] | --global] [--status <status>] [--pin|--unpin] [--json]
      knowledge Gitoodo keeps across repositories (memory.sqlite in the config folder): facts,
      procedures, preferences and where things are found, global or per repository; list shows
      what applies (with --repo: global and that repository's), each with a token estimate; show
      prints the history of every change; texts that look like a token, key or password are
      refused (keep where a secret is, never the secret); entries from a worker wait as proposed

Services:
  gitoodo service install|uninstall|start|stop [classifier|dispatcher|all]
      background services with the system service manager (restart on crash and reboot);
      default classifier; install copies this CLI to a stable per-user folder first
  gitoodo classifier
      run the classifier daemon in the foreground (what the service starts)
  gitoodo daemon
      deprecated alias of `gitoodo classifier`
  gitoodo dispatcher
      run the dispatcher in the foreground: one coding agent worker per ready issue
      (https://gitoodo.com/docs/dev/dispatcher/)
  gitoodo satellite [--stdio | --restart-idle | --drop-carried]
      worker machine service: runs workers for a main host (https://gitoodo.com/docs/dev/satellites/);
      --stdio is the SSH bridge, --restart-idle lets an idle service take up the installed build
      after an update, --drop-carried removes every main host's carried setup and credentials from
      this machine
  gitoodo mcp [--scope all|<account>/<owner>/<name>[#<n>]]
      MCP server over stdio: the ledger and the dispatcher as read tools plus change proposals
      that wait for the human's OK (https://gitoodo.com/docs/dev/orchestrator-chat/); --scope
      narrows them to one repository or item
  gitoodo token-purge
      remove every Gitoodo token from the data protection keychain (the uninstaller runs it through
      the service helper, which shares the app's keychain group); prints removed or unavailable

Used by workers (run inside a worker session, not by hand):
  gitoodo ask [--issue <key>] [--check]
      post a question block (JSON spec on stdin) to the issue and wait for a human;
      `--check` only tests the spec and prints the block, nothing is posted;
      `gitoodo ask --help` shows the spec's fields and a complete example
  gitoodo worker context
      print compact assigned issue context as JSON; requires GITOODO_ISSUE (local workers only)
  gitoodo worker push | pr [--title <t>] [--body <text>]
      push the branch and open the pull request that closes the issue, through the account
      connected in Gitoodo (the worker never holds a token)
  gitoodo worker follow-up --title <t> --body-file <path|-> [--label <kind>]
      propose a follow-up issue for work outside the own issue; the dispatcher creates it
      with a back-reference, and a maintainer approves it before a worker picks it up
  gitoodo worker split --plan <path|->
      split an issue too big for one run into parts (JSON plan) before writing code; the
      dispatcher creates them, and the issue waits until all parts are closed
  gitoodo worker blocked --on <#n[,#m]> --reason <text>
      the issue cannot go on before other issues land; the dispatcher records the
      dependency on the issue, ends the run, and the issue waits until they are closed
  gitoodo worker close --summary <text>
      close the issue without a pull request: an umbrella whose child issues are all
      closed delivered what it asks, or the issue needs no change (delivered already,
      obsolete); the dispatcher checks the children, or refuses while your branch or
      worktree changes a file, then posts the summary and closes the issue
  gitoodo worker needs --tool <name[,name]> --reason <text>
      the issue cannot be done without a command this machine lacks; the dispatcher
      labels it tool:<name>, ends the run, and a machine that has the command takes it
  gitoodo worker needs --data <path[,path]> --reason <text>
      the issue cannot be done without local files that cannot come to this machine;
      the issue goes to the main machine, which has them (never a tool: label)
  gitoodo worker needs --desktop <name[,name]> --reason <text>
      the issue needs a test desktop of this Gitoodo that this worker computer cannot
      reach (push your work first); the issue goes on from its branch on the main
      machine, which reaches every test desktop (never a tool: label)
  gitoodo worker input <path>
      copy a further local file or folder of the main machine (relative to the
      repository, a session transcript <id>.jsonl, or a log file of Gitoodo such as
      log:dispatcher.jsonl with its older generations) into the worktree
  gitoodo worker remember --scope global|repo --kind <kind> --text <t> [--from-answer]
      propose a memory entry (fact, procedure, preference, location) later runs need and
      cannot read from the code, never a secret; one that says the same is merged; it is
      used once a person approves it or workers of 3 issues proposed it
  gitoodo worker dispute <id> --reason <text>
      report memory entry <id> as wrong or outdated: it is kept, marked disputed and no
      longer given to workers until a person looks at it
  gitoodo desktop [--on NAME] <command> [args]
      Agent Desktop (desktop control through the accessibility tree) as Gitoodo installed it; in a
      worker it takes turns at the test desktop; --on reaches another machine's desktop over SSH
  gitoodo desktop-turn [--on NAME] "WHAT" | --done
      wait in line for a test desktop (prints OK, BUSY or PERSON) or give it back
  gitoodo hook status-line|stop|stop-failure|activity|tool-start|tool-end|needs-you
      Claude Code or Codex hook ping to the dispatcher (silent without one)
  gitoodo next --worker <id> --host <host> [--repo <owner/name>] [--account <id>] [--json]
  gitoodo done --worker <id> --lease <id> [--result <text>] [--json]
      take the next ready issue (a lease: a time-limited claim so no other worker takes it) and
      give it back when done; the dispatcher uses them, from the command line they are refused in
      an automation session and for repositories whose autopilot is on (it works that queue)

wait in line for a test desktop (prints OK, BUSY or PERSON) or give it back

gitoodo hook#

gitoodo hook status-line|stop|stop-failure|activity|tool-start|tool-end|needs-you

Claude Code or Codex hook ping to the dispatcher (silent without one)

gitoodo next#

gitoodo next --worker <id> --host <host> [--repo <owner/name>] [--account <id>] [--json]

gitoodo done#

gitoodo done --worker <id> --lease <id> [--result <text>] [--json]

take the next ready issue (a lease: a time-limited claim so no other worker takes it) and give it back when done; the dispatcher uses them, from the command line they are refused in an automation session and for repositories whose autopilot is on (it works that queue)
