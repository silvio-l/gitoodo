Gitoodo orchestrates coding agents as workers. A worker reads forge text (the issue, its comments) and runs code on the machine. This page says whose text may steer a worker, how a worker runs, and how the forge token stays out of the worker's reach. It answers the release-gate review findings H1 (untrusted forge text steering an unattended worker) and H2 (token-carrying git calls in worker-writable folders).

Who is trusted#

A login is trusted for a repository when any of these holds (intake::Intake::is_trusted, one rule for intake, answers, briefs and worker context):

  • it is trusted automatically (#337, #916, acting::auto_trusted): the token owner of the connected forge account, the worker account Gitoodo writes as, and every login Gitoodo wrote as before on that forge (earlier worker accounts, kept in orchestrator_writers). All are derived at runtime from the accounts set up in onboarding and the write history, never copied into trusted_authors (so no migration is needed), and follow a token renewal or an account switch; Settings → Dispatcher shows them as "Automatically trusted" (own account, worker account, earlier worker account) and they cannot be removed there. Other bots, Ghost (a deleted account) and agent accounts are not trusted automatically;
  • it is the repository's configured human (human);
  • it is listed in Settings → Dispatcher → Trusted authors (trusted_authors); an entry that opened no issue or pull request and wrote no comment in any configured repository for 90 days is marked "not active" there with a remove button (#943). The check reads at most 20 repositories and 4 pages per listing, is cached for 6 hours and marks nobody when it cannot read everything (for example on GitLab, which has no repository-wide comment listing); an entry is never removed automatically. An approval card of an untrusted author offers "Trust this author" (#916), never for system or bot accounts: the app adds the login to this list through its settings write path (the dispatcher never writes orchestration.json), the author's open approvals leave the card and their issues turn ready on the next pass, and "Undo" takes only this login back for ten seconds;
  • the forge reports write, maintain or admin permission on the repository, or membership in the organisation that owns it.

A failed lookup counts as untrusted. Everyone else is untrusted, including anyone who can comment on a public repository.

What reaches a worker#

  • Issue: only issues of trusted authors (or approved by a trusted person, spec 5.3) become ready and are dispatched. Title and body of a dispatched issue reach the worker.
  • Comments, start brief (orchestration::brief::worker_brief) **and gitoodo worker context**: only trusted people's comments appear as discussion, Gitoodo questions or answers. A comment of an untrusted person is never labelled "Answer" or "question", whatever markers it carries. Depending on the repo's worker mode (below) it is left out with a count (unattended) or quoted in a fence that its own backticks cannot close, under a heading that marks it as untrusted data (guarded; untrusted quotes have their own, smaller size budget, so they cannot push a trusted answer out). When trust cannot be judged (forge unreachable), every comment is left out.
  • Logs of failed checks (failed_checks::excerpt, #1568): a worker restarted for failed checks gets the end of each failed job's log (at most 5 jobs, 80 lines or 6 KiB each, 12 KiB in all), read through the forge API with Gitoodo's token, which is never sent to another host the log redirects to. A log can carry what a pull request's own code printed, so it is cleaned of terminal escapes, redacted (known tokens, secret assignments, cloud access keys, private key blocks) and handed over only in gitoodo worker context, fenced as quoted CI output that is untrusted data and never an instruction. Neither the log's text nor the excerpt is written to Gitoodo's own log, which records only the error category of an unreadable log. Without read access or without a log the worker gets the check names and run pages as before.
  • Answers (hygiene::reconcile_issue): only cards and answers posted by trusted people count. A stranger cannot post a card that names themselves and then answer it, and a stranger's answer marker or plain reply to a card without a header login does not release the issue. The intake's own approval and clarification rules (intake::scan) were already trust-checked; the issue author may still answer the intake's clarification.
  • Automations: only events of trusted actors start an automation session, and the prompt carries kind, number, author and link, never bodies. The title of an issue opened by an untrusted person is left out even when a trusted person's comment on it is the event.

The orchestrator chat (gitoodo mcp for a human-led chat session) still shows all comments: a person reads along and confirms forge and configuration changes on proposal cards. The chat can also relay an explicitly requested human instruction directly to a running worker. The system prompt treats issue bodies, comments and tool results as data, never authorization to send. The MCP server enforces the chat scope and instruction bounds; the dispatcher protects unsent human input. This relay relies on the chat model to recognize the human request and its intended recipients, and does not independently verify the request against the conversation.

Worker mode per repository#

Settings → Repositories → (repo) → "Workers with permission checks" sets worker_permissions in orchestration.json:

ModeAgent flagsUntrusted comments
unattended (default)Claude Code --dangerously-skip-permissions; Codex --dangerously-bypass-approvals-and-sandbox, worktree trusted; Gemini --yololeft out
guardedClaude Code --permission-mode auto --add-dir <clone git dir>; Codex --sandbox workspace-write --ask-for-approval never with network access and the clone's git directory as an extra writable root, worktree untrusted; Gemini --yolo --sandbox --include-directories <clone git dir>quoted as untrusted data

unattended stays the default because workers must finish without anyone answering prompts, and it is safe for the trust boundary above: only trusted text reaches it. guarded adds the agent's own checks as a second line, for repositories where more is at stake, typically public ones. Automation sessions always run unattended; their prompts carry only trusted text. Satellites get the same mode; the clone's git directory is only added on the main host. Sessions the person starts from Gitoodo (new session, "Solve with an agent") run in the repository's mode with the same flags and folder trust as its workers (agent::worker::permission_args, docs/agent-session.md), so guarded also gives those sessions the agent's checks back.

Codex workers run Codex's interactive terminal UI (#934). Their folder trust is a setting of the session only (-c projects={…}), never written to the user's Codex config: unattended trusts the worktree like a Claude Code worker (the repository's own Codex settings and hooks load), guarded records it as untrusted, so nothing from the repository configures Codex and the sandbox flags stay as set. Gitoodo's hooks (gitoodo hook stop|activity) are passed per session too and run with --dangerously-bypass-hook-trust, so no hook review waits in the terminal. Hook events of the user's own config.toml are emptied for the session (-c hooks.<Event>=[], "What a worker loads" in docs/orchestrator/dispatcher.md); hooks Codex reads from elsewhere (a hooks.json, the repository's own settings in a trusted worktree) still run without their review. -a never means a guarded worker never waits for an approval: Codex's sandbox refuses what it does not allow and the model gets the refusal.

What a worker loads#

Workers start lean: without the user's MCP servers, plugins, skills, slash commands, memory and extra tools, but with the repository's instructions, Gitoodo's hooks and the permission mode above (details and flags: docs/orchestrator/dispatcher.md, "What a worker loads"). Besides the tokens, this keeps a worker that reads untrusted text from reaching the user's personal connectors (mail, calendars, other accounts). A repository can allow named MCP servers ("MCP servers for workers", worker_mcp_servers, none by default); everything a server can reach is then within a worker's reach too. Settings that come with the user's agent configuration itself (login helper, provider environment, deny rules, and for Claude Code the user's own hooks) still apply.

Sub-agents and nested agent sessions (#952)#

Settings → Repositories → (repo) → "Workers may use sub-agents" sets worker_sub_agents in orchestration.json (off by default). A worker is one agent session; off keeps it that way, so its work, its usage and its permission mode stay in the session the user can see:

AgentOff (default)On
Claude Code--disallowed-tools Agent: the sub-agent tool (older name Task) is denied for the sessionthe agent's own choice
Codex-c features.multi_agent=false -c features.multi_agent_v2=false -c agents.enabled=false: the multi-agent features (names from codex features list) and the multi-agent role text are offthe user's features
Gemini CLI--policy ~/.gemini/policies --policy <state>/gemini-worker-policy.toml: a policy denies the sub-agent tool invoke_agent and the built-in agents' names (#1555); left out where the user's Gemini settings name their own policyPathsthe user's policies

The switches are settings of that session only; nothing is written to the agent's own configuration (the Gemini policy file lies in Gitoodo's state folder). In both modes the start brief tells the worker never to start another coding agent session or agent command-line program from its shell, and the dispatcher (a satellite for its own workers) looks at each issue worker's process tree every 15 seconds: a claude, codex or gemini below the worker's own agent process (its own helper processes of the same agent excepted) is logged as dispatch.nested_agent (issue, run, agent, process id, never the command line), and with the setting off it is ended (SIGTERM; Windows taskkill /T). The check lists processes with ps (Windows: Get-CimInstance Win32_Process); where that fails, the round is skipped. Satellites of older versions only get the flags.

Residual risk: the check finds the three agents by program name, every 15 seconds; a renamed binary or a session shorter than that is not caught, and other agent programs are not known by name. The flags and the brief are the first line; the check catches what slips through.

Automation sessions belong to no repository; they keep the agent's own features and are not checked.

Public repositories#

On a public repository anyone can open issues and comment. Untrusted issues wait for a trusted person's approval and are never dispatched on their own. Untrusted comments never steer a worker in either mode. What remains is the code and data in the repository itself (a trusted person merged it) and whatever a worker fetches from the internet while it works; for that second line, use guarded.

Review feedback on a worker's pull request follows the same line (#1567, docs/orchestrator/dispatcher.md, "Review feedback"): only reviews and comments of trusted people start a follow-up run and reach the worker, fenced as quoted text; everyone else's are only counted, in both modes. The worker's answers to them go through the main host, only to the open points of its own pull request.

Worker follow-up issues#

A worker may propose a follow-up issue (gitoodo worker follow-up, spec 8.3); the dispatcher's broker creates it with the connected account's token. The worker's text is treated as untrusted data, although the worker account is its author:

  • Mediated: the proposal needs the worker's capability, a live lease of that worker on its issue and the repo setting worker_follow_ups (on by default; switch it off where workers should never write to the issue tracker). The worker gets no token and no forge client.
  • Bounded: one-line title up to 200 characters, body up to 16 KiB, at most dispatch.max_follow_ups_per_run per run (default 3) and 10 per repository and hour; a title that matches an open issue refuses the proposal. Chains stop at depth 3: a follow-up of a follow-up of a follow-up may not propose another one (follow_up::MAX_DEPTH, the depth is in the marker). Refusals name only fixed reasons, never forge errors.
  • Approval is opt-in: the issue carries the gitoodo:follow-up marker in the footer Gitoodo appends; <!-- in the worker's text is defused, so it cannot forge that or any other Gitoodo marker. By default the intake makes a follow-up the worker account opened ready like the account's own issues, so another worker may pick up its body without a human reading it first; the bounds above are what limits a worker that runs wild. A repository's human who wants to read every proposal first switches on "Approve each follow-up before it is worked on" (repository settings → Workers, stored as follow_up_approval in its orchestration.json entry; the default for repositories without their own choice is dispatch.follow_up_approval, Settings → Dispatcher). Then the intake asks for approval like for an issue from outside (a "no" closes it), the read model never counts it ready without the ready label, and with the intake rule for outside issues switched off such follow-ups wait untouched. Switching approval off again releases the follow-ups still waiting, as if approved. A marker in an issue by anyone else always counts as an outside contribution.
  • Labels: besides the intake label gitoodo, only an existing label that is no workflow, priority, host or release label may be added, so a worker cannot route, prioritise or release its own proposals.

Residual risk: the text is public on the forge as soon as it is created, and @mentions in it notify the people named, like any issue the worker account opens. Without approval, a worker that runs wild can have at most the budget and depth above worked on before a human sees it; switch on approval, or switch proposing off, for repositories where that matters.

Parts of a split issue#

A worker may split an issue that is too big for one run into parts before it writes code (gitoodo worker split --plan <file>, #1012); the dispatcher's broker creates the parts with the connected account's token. Each part's title and body come from the worker, so a part is treated exactly like a follow-up:

  • Mediated: the same capability, live lease and repo setting worker_follow_ups as a follow-up; never on a satellite. The worker gets no token.
  • Bounded: 2 to 8 parts per plan, each checked like a follow-up (title, body up to 16 KiB, kind label); the plan file is at most 32 KiB. A part may only wait for earlier parts and never for the issue being split. At most 5 splits per repository and hour; splits do not use the follow-up budget. A split run again reuses the parts that exist (by index), so a restart creates no duplicates.
  • Not ready on its own: each part carries the gitoodo:part marker (parent and index) in the footer Gitoodo appends; <!-- in the worker's text is defused, so it cannot forge it. The intake treats a part opened by the worker account like a follow-up: it becomes ready by default and asks the repo's human for approval only where follow-up approval is on.
  • The parent waits: an issue waits while an open issue carries a part marker naming it, but only issues the account Gitoodo writes with opened count; a marker in anyone else's issue neither holds the parent nor is reused as a part. A part is never split again. Nothing is closed by a split: the parent closes only through its own pull request after its parts are closed and integrated.

Residual risk as for follow-ups: the text is public as soon as it is created, and a worker that runs wild opens at most the bounds above before a human sees it.

A recorded dependency#

A worker whose issue cannot go on before other issues land says so with gitoodo worker blocked --on <#n> --reason <text>; the dispatcher's broker writes it with the connected account's token, which the worker never gets:

  • Mediated: the same capability and live lease as a pull request; never on a satellite.
  • Bounded: at most 10 references, each one #n, repo#n or owner/repo#n, never the issue itself, at least one still open; the reason is at most 1000 characters.
  • Only its own issue: the description of the worker's issue gets a Depends on … line for each reference it lacks; nothing else changes. The reason goes into a note Gitoodo signs as its own (so it declares no dependency itself), quoted, with <!-- defused so it cannot forge a marker.
  • Ends the run: the worker is stopped once the reply is out; the issue waits in the queue until its dependencies are closed. A person removes the line to release it earlier.

Residual risk: a worker can hold its own issue back by naming an open issue it does not really need; the note says which and why, on the issue, for everyone to see.

A command a machine lacks#

gitoodo worker needs --tool <name> --reason <text> hands the worker's issue back because its machine lacks a command (docs/orchestrator/satellites.md, "Commands a worker machine lacks"):

  • Bounded: at most 8 names of letters, digits and _ - . + (no leading . or -), at most 64 characters each, a reason of at most 1000 characters; anything else is refused before it is sent.
  • No forge write by the worker: the broker (this computer) or the satellite (worker machine) only records the request and ends the run; the dispatcher sets the tool: labels with the account's token, which the worker never gets.
  • Probes run nothing: a machine looks for the names as files on its search path and never starts them.

Residual risk: a worker can hand back an issue it could have done; it then waits for a machine with the command or for the person's "Run without".

Local inputs on worker machines#

The files an issue names that git does not carry go to the worker's machine (local inputs):

  • Only what the issue names: paths in inline code inside the main host's working copy of the repository, and agent session transcripts by their id. No absolute path, no .., no symlink, no .git, nothing outside the repository but a named transcript. Only the issue body counts, which only trusted authors bring to a worker.
  • No credentials: files named like one (.env*, keys, key stores, sign-in files, .ssh) are never sent, unless the person lists that exact path under "Files for every worker" of the repository (#1583); the brief names what was left out.
  • The worker machine only receives: it checks size, SHA-256 and every path of the archive, writes below its staging folder and then into the worktree, never over an existing file. Nothing lands where git would commit it (.gitoodo-inputs/ ignores itself).
  • **Fetching more (gitoodo worker input):** a worker can name one more path by the same rules; the main host answers only for a machine that holds the issue's lease, and only with what those rules allow (inside the repository's working copy, untracked, no credential, or a transcript by its id). A refusal names the path, never a path of the main host.

Residual risk: a trusted author can name a file inside the repository that should stay on the main host; it then reaches the worker machine like the repository itself.

A person's setup on worker machines#

"Take my setup along" (docs/orchestrator/satellites.md, "Taking this computer's setup along") copies part of this computer's home folder and some credentials to worker machines:

  • Only what is named. Files come only from what the git configuration, the agents' user instructions and hooks, and the scripts they reference name, below the home folder, at most 256 KiB each, text only. Anything that looks like a credential by name or content, private ssh keys, binaries, state files and anything outside the home folder (also through a link) stays here.
  • Only to the same person's machines by default. The default is on only when the machine's user name or git user.email matches this computer's; the machine sends SHA-256 fingerprints of both, never the names. The user can switch any machine on or off.
  • Never the machine's own configuration. The carried setup lives in the state folder there and reaches only Gitoodo's workers, through their environment (GIT_CONFIG_GLOBAL, PATH) and arguments. The person's own git, agent and shell configuration there is not written, and the machine's own setup wins unless the user chooses otherwise.
  • Credentials by reference, by name, revocable. Only credentials the carried texts reference go along (an env file they source, a variable they read, gh's login as GH_TOKEN); ssh keys never do. Values travel only over the authenticated, encrypted satellite connection, are stored in the machine's system store (a user-only file where that cannot be written, as for the transferred agent sign-ins), never in a log, an error text, the status or the app, which shows names only. Each one can be switched off per machine; switching it or the machine off, or removing the machine, revokes it there. Workers get them in their environment; an env file a carried shell script sources becomes a per-worker temporary file (user-only) deleted when the worker ends. An env file a script in another language (Python, Node, PowerShell) reads is written user-only at its place in the carried tree only while a worker of that main host runs, and deleted when the last one ends.

Residual risk: a carried hook or script runs with the worker's rights on the machine, as it does here. A credential handed to a worker can be read by that worker, like any other in its environment; the person decides per machine and per credential.

  • Nothing stays on a machine that left (#1416). A machine switched off or removed while it is unreachable gets the drop at its next contact: the main host records the drop of a removed machine (carry-revocations.json in its state folder: name and address, never a password) and retries it every minute until the machine confirms it; the machine's card says "Will be removed at the next contact." until then. The drop also takes back the sign-ins handed to that machine. Independently, the satellite service drops the setup and credentials of a main host that has not been in touch for 7 days, at its start and every hour, without any message. gitoodo satellite --drop-carried removes everything carried to a machine by hand, the stored Claude Code sign-in included; the service also empties that store at its start and its end (#1406). User-only files are mode 0600 on Unix and carry a protected DACL with the user as the only entry on Windows. Residual risk: a machine that stays powered off keeps the stored values until its service runs again or the main host reaches it.

Keychains and dialogs on worker machines (#1607)#

A worker never opens a keychain, password or administrator dialog on the computer it runs on (docs/orchestrator/keychains.md): its builds sign ad-hoc, git never asks for credentials, and on macOS its security and codesign calls go through gitoodo keychain-guard, which refuses what would open a locked keychain or ask a person and stops a call that still waits for a dialog. The guard only reads which keychains are locked; it never unlocks one, never reads a password for the worker, and never changes a keychain or the search list.

Worker account created by Gitoodo (#764)#

On Forgejo/Gitea and self-managed GitLab an administrator can let Gitoodo create the worker account (crates/core/src/forge/worker_setup.rs, commands in src-tauri/src/worker_create.rs):

  • Nothing is written before the user confirms a summary (login, email, repos, token scopes).
  • The account is limited: Forgejo/Gitea restricted (sees only repos it is added to), GitLab external, no own projects, no groups. Access is per repo (collaborator with write, GitLab Developer; Maintainer only where a protected branch requires it), never a team or organisation role.
  • Passwords: the account gets a random 44-character password from the operating system's random source. Forgejo/Gitea's token endpoint accepts only basic auth, so Gitoodo sets a fresh random one-time password, uses it for that one request and replaces it right after with another random one. No password is stored, logged, returned to the frontend or shown; error texts from the forge are scrubbed of it. Nobody can sign in with a password; an administrator resets it if a person ever needs to.
  • The new token goes the normal account way (system keychain only). Logs name host, step and counts, never logins, passwords or token values. If replacing the one-time password fails, that is logged by category only; the password was never kept, so it is as unknown as the next one.
  • A retry only touches accounts carrying Gitoodo's marker (Forgejo/Gitea full name "Gitoodo worker", GitLab admin note); a login owned by someone else stops the setup.
  • A token created by a run that then failed to store it remains on the forge (named gitoodo-<time>); the next run creates a new one. The administrator can delete stale ones on the account's token page.
  • Admin rights lent once: when the own token lacks the admin scope, the user may confirm with the own password (plus one-time code). The core sends it only as basic auth to the own forge to create one short-lived token (write:admin, write:repository, write:user), uses that token for this run and deletes it afterwards, also after a failure. Password, code and short-lived token live only in the core's memory (zeroized when dropped), are never stored, logged, sent to the frontend or put in error texts; forge error texts are scrubbed of them. The short-lived token never reaches the keychain. If deleting it fails, only its name is shown so the user can delete it. A pasted temporary admin token is handled the same way (used once, never stored).
  • GitHub: Gitoodo creates no accounts. It invites the user-provided worker account with the own token and accepts with the worker token, only after the user presses the button.

Deleting a repository on the forge#

The removal dialog can delete a repository on its forge for good (crates/core/src/forge/repo_delete.rs, src-tauri/src/repo_remove.rs):

  • No request without consent: the core builds a Confirmation only from the text the user typed (the exact owner/repo, for several repositories the count or "löschen") and checks it again in the command; without one, delete returns not_confirmed and sends nothing. Each delete is a single request, never repeated.
  • Only the user's own account deletes. An account that is a worker account (orchestrator_accounts in orchestration.json) is refused before its token is read.
  • The token is read from the system keychain inside the core and lives only in the HTTP client's sensitive header; it never reaches the frontend, a log, an error text or the result (the outcome carries deleted, missing_scope, missing_role, not_found, token_rejected or an error category).
  • The rights check before the delete only reads (user, repository permissions, GitHub's x-oauth-scopes, GitLab's personal_access_tokens/self).
  • Every attempt is in the audit trail as repo.deleted_on_forge (audit: true) with account, repository and result, and in the forge write log; never with token or forge answer.
  • The browser demo never deletes anything.

Forge token and git (H2)#

A worker controls its worktree and, through the shared git directory, the clone's configuration and hooks. No token-carrying git process runs there:

  • Every token-carrying git call (fetch_base, push_branch, push_assigned_branch, the leased push of a branch update, the backup push of the hygiene, remote prune of the maintenance, the first clone, the prefetch of missing objects before a worktree is cut) runs through crates/core/src/token_git.rs: GIT_DIR is a scratch bare directory under Gitoodo's temp root with a configuration Gitoodo writes (hooks off, no fsmonitor, the explicit remote URL), objects come from the clone's object store (GIT_OBJECT_DIRECTORY), the refs it needs are seeded. The clone's own config, hooks, insteadOf/pushInsteadOf rewrites, filters, credential helpers and includes are never read.
  • On top: GIT_CONFIG_NOSYSTEM=1, GIT_CONFIG_GLOBAL=/dev/null, every inherited GIT_* variable removed (except GIT_SSL_CAINFO/GIT_SSL_CAPATH), -c core.hooksPath=/dev/null -c core.fsmonitor=false -c credential.helper= -c core.askPass=, submodule recursion and auto-maintenance off, and GIT_ALLOW_PROTOCOL limited to the remote's scheme (https, http).
  • Local steps in the checkout (update-ref, rebase or merge of an update, worktree add) run without any token in their environment; they may run the worker's hooks, which then see nothing secret.
  • gitoodo askpass answers only prompts that name the forge host of the push or fetch (GITOODO_ASKPASS_HOST); any other prompt gets nothing.
  • Proxies: http.proxy and other proxy settings from git config files are not used, since the global and system config is dropped. A proxy comes from the service environment (HTTPS_PROXY, HTTP_PROXY, NO_PROXY), which git honours; a custom CA from GIT_SSL_CAINFO. Gitoodo does not set -c http.proxy= (an empty value would switch the environment proxy off). On Windows the token calls use http.sslBackend=schannel, the system certificate store.
  • Inside a worker (GITOODO_ISSUE set) gitoodo worker push|pr, gitoodo ask and the MCP tools only work through the dispatcher's broker (the capability in GITOODO_WORKER_CAPABILITY) or, on a satellite, through the main host. Without a capability they refuse; they never read the keychain token there.
  • A headless service that gets its tokens as GITOODO_TOKEN_* takes them out of its environment at start and keeps them in memory, so no child (git, hooks, agents) inherits them. Managed workers start with a cleaned environment in any case.

Limits: a worker runs as the same operating-system user. In unattended mode it can do whatever that user can, including starting other programs; the trust boundary keeps strangers from steering it, it does not sandbox it. guarded relies on the agent's sandbox for that. The same holds for the token file gitoodo account keeps on a computer without a usable keyring (#1208, <state>/credentials/, mode 0600, docs/daemon.md "Headless setup"): that user can read it, as they could read an unlocked keyring. The account and repo commands themselves refuse to run inside a worker session (GITOODO_ISSUE set).

Not covered by the change: LFS filters and other settings from the user's global git config no longer apply to the token-carrying calls (the first clone included); a clone that needs Git LFS fetches its LFS objects on the first local checkout step.
