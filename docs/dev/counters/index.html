Counters

Every counter in Gitoodo shows a value of one Counts value, computed in Rust (crates/core/src/sync/counts.rs, SyncHub::counts in src-tauri/src/sync.rs). The webview never counts on its own; it reads get_counts once and follows the counts event.

CounterValue
Tray title, Dock badge"needs you" (as the header)
Tab "Fragen", headertotal + refused merges + status
Heading "Fragen"questions, tasks, approvals
Bundle "Freigabe"open approvals (#705)

total = questions + tasks + approvals, so the single tab shows the tray number. Approvals of foreign contributions (intake-approval-* cards) are no questions: the heading counts them apart, and the bundle above the list holds them. Tasks for the human are waiting items without a valid open question block (needs-human with a description and maybe a - [ ] acceptance list, e.g. a step in a developer portal only a person can do; crates/core/src/human_task.rs). They ask for a hands-on step, not a decision: the list shows them in their repo's group after its questions with the tag "Aufgabe" (#897), the sheet as "Aufgabe" with the checklist, "Erledigt" and "Zurück an den Orchestrator" (both with an optional note "Anmerkung (optional)"; on a hand-back the note is the person's instruction to the worker, see "Instructions" in docs/question-format.md), and the heading names every kind that waits ("6 Fragen · 3 Aufgaben · 161 Freigaben"; only questions: "6 Fragen warten auf dich"). There is no inbox of forge notifications any more (#189): Gitoodo never fetches or marks forge notifications, and only waiting items are counted. The header shows no count (#84): each number appears once, on its tab. One "needs you" (#919). The header's overall state ("3 need you"), the badge on "Fragen an mich" and what that page lists on landing are one set, and a click on the header's number always lands on that page while the number is above zero:

  • total (questions, tasks and approvals in scope, see "Autopilot scope" below),
  • issues the autopilot gave up on ("Hängt fest", label stalled) in repos with the autopilot on, except those the resolver still takes (its attempt queued, running or sure to come, decided in the core by resolver::takes; docs/orchestrator/resolver.md, "In the app"): they wait behind the page's quiet "N the resolver is taking – show" (resolverTakes) and are in no count, listed on the page with their reason and "Try again", "Put back" and "View issue" (#919, see docs/states.md). They are no approvals any more: a worker ran on them, so the issue never reads "waits for your approval" (intake::reason),
  • ready issues in repos with the autopilot on that wait for a machine only the user can provide (an unknown host:, a machine with the wrong system, an expired agent sign-in), one each, listed on the page with their ways out (repoNeeds(…).hosts, #919). The status part "workers" no longer counts these (statusWaitCount), so nothing counts twice,
  • merges a repository setting refuses and the user still has to fix (waitingBlocks, #942),
  • the parts of the status only the user can fix (countedParts: a rejected sign-in, a keychain approval, ready issues waiting for a worker machine, a service that does not answer, …), each shown as a card with its fixing action at the top of the page. A disk running low is left out (#970): it has its own entry in the status bar, its own notification and its problem on the status page.

The repo part (questions in scope that are not answered yet, plus stalled issues and machine waits only the user can resolve in scope, repoNeedsCount) comes from one place, repoNeeds over the sidebar's activity (src/views/sidebar/repoActivity.ts): the repos' marks ("3 issues need you") add up to it, and the header, the badge and the page use it, so the header always equals the sum of the repos' marks plus refused merges plus status problems, which have no repo mark. needsYouTotal in src/views/shell/overall.ts adds them up, and the header's tooltip names the parts (needsYouHint, #1043: "In den Repos: 14 · Statusprobleme: 1"), so a number above the sum of the marks always says why (the button also carries it as its accessible description, since a tooltip alone never reaches screen readers); landing in src/views/questions/landing.ts is what the page lists, and needsYouCount.test.ts pins both to each other for a mix of questions, tasks, approvals, refused merges, machine notices, stalled issues, machine waits and repos with and without the autopilot. A way out taken on the page takes its issue out of every count at once (markResolved in useRepoWorkspace.ts, for at most five minutes until the read model shows the change). Repos without the autopilot never feed the number: their questions, tasks and approvals wait behind the page's quiet "N more from repos without autopilot – show" at the end, and that N is never added anywhere.

Tray and Dock show the same number. The window reports its "needs you" number to the app (set_needs_you, from Shell.tsx) whenever it changes; the tray title, its tooltip and, on macOS, the Dock badge (visible while the window has a Dock icon) show that number (shown_total in src-tauri/src/tray.rs). Before the window reported one, right after the start, they show the core's total. The main window is only hidden, never closed, so it keeps reporting while it is not on screen. Earlier the tray showed only total, so it could read 1 while header and badge read 22 (stalled issues and machine waits are no questions). Unseen items (the red tray check) still come from the core's Counts. Tray and webview are updated from the same Counts in the same call (publish_counts), after every poll, after answering or commenting, and after removing an account.

Rule#

  • Questions: open entries of all "waiting for me" views, over all accounts, minus questions answered through the app (answer card or free comment) whose waiting_since is not newer than the posted comment. Such an answer is dropped at the next poll once the question has left the list or waits again. The popover shows the same questions teal ("handled"). These marks live in the core and count for every client (#1873): an answer from a paired phone sets the same mark as one from the window, so the counts drop at once, and every step (sending, answered, failed) reaches each window as the answered event, which the window's own marks follow (get_answer_marks for a window that opens later). A failed post takes the mark back everywhere. One answer per item runs at a time; a second one that finds the mark is refused with already_answered and the place of the first answer instead of posting again (see docs/mobile.md, "Answered once").
  • Tray switch (#1376): every "waiting for me" view is polled and counts in the window (list, header, badges). A view's switch "Zähler in der Menüleiste/Taskleiste" (counts_in_tray) only decides whether its items also count in the tray and Dock: items found only by views with the switch off (Counts::quiet, quiet_unseen) are subtracted from the tray number and never turn the check red, and they get no notification or reminder.
  • Kind (account_counts, mirrored by waitKind in src/views/questions/tasks.ts): an entry whose newest card is an intake approval is an approval; one without an open question block is a task; every other entry is a question. Each entry counts once.
  • Overview (#237, #933), the start page: statistics only. It lists no questions and shows no "needs you" number; that number lives in the header and on "Fragen an mich". Repo rows with an open question (same rule) carry a mark without a number. No sidebar filter changes that number.
  • Disabled repos (#135): items of repos switched off in the settings are in no list, no counter, no unseen mark and no system notification. They are dropped centrally (without_disabled, read by SyncHub::tally and the snapshot events), so switching a repo off updates tray and lists at once; switching it on shows its items again (after the next sync for what the poll skipped).
  • Ungated repos (#705): approvals of repos this app's orchestrator lists as observed or paused are in no counter and no list (without_ungated, from Config::ungated), since nothing works on them there; the paused intake asks no new ones. Repos it does not list keep their approvals. The other questions of those repos count as before.
  • Autopilot scope (#897): in the orchestrator mode only repos with the autopilot on (active in orchestration.json, Config::autopilot) count. What waits in paused, observed or unlisted repos is in no counter, no unseen mark, no reminder, no chat notice and no system notification (within_autopilot in SyncHub::tally and SyncHub::counted, within_scope for the toasts); the sidebar sets no "needs you" mark there either. The snapshot event names the repos (autopilot), so "Fragen an mich" lists those first, grouped by repo with the questions before the tasks, and keeps the rest behind "N weitere aus Repos ohne Autopilot – anzeigen" at the end. The direct mode and the setting asked_all_repos ("Fragen auch aus Repos ohne Autopilot", Settings → Notifications) count every repo (autopilot is null). Switching a repo's autopilot or the setting republishes counts and snapshots at once; an unreadable orchestration file hides nothing.
  • List filters (search, repo, kind, status; #61) never change any counter. They narrow what a list shows, not what waits; otherwise the tray (which knows no filters) and the popover would disagree. Under an active filter only the head of the view says "shown of total" (e.g. "3 of 12 questions need you", #109); without a filter it shows the total.
  • A failing account keeps its last good entries, so its counts stay stable until the next successful poll.
  • Paging: every list request follows the forge's Link header (collect_pages), so counts are not capped at one page of 50.

Seen and unseen#

Every counted item (open question) is either seen or unseen (crates/core/src/store/viewed.rs, unseen_keys in counts.rs).

  • Seen means the item was visible in the opened list: its row stayed at least 60 % in view for about 0.7 s while the window was focused and visible. The webview only reports the keys (mark_seen); Rust looks up the item's activity time and stores it as the mark.
  • New activity makes it unseen again: a question whose waiting_since is newer than its mark is unseen. Answered (handled) questions are never unseen.
  • Snooze (snooze_question, unsnooze_question): a snoozed question leaves the list, the counters and the unseen marks until its wake-up time (presets: 1 hour, tomorrow 09:00 local, 1 week; computed in src/state/snooze.ts). It returns by itself at that time (timer plus every poll), without restart. New activity on the issue does not wake it early. Stored per account in viewed.json (snoozed, unix seconds); expired or vanished entries are pruned on the next poll.
  • Tray: one unseen item turns the tray check red (macOS and Windows); the tooltip names how many, e.g. "Gitoodo (3, 1 unseen)". Counts.unseen carries the number.
  • Lists: unseen rows carry a small neutral ink dot (6 px) and a hidden "Neu"/"New" for screen readers, never red. A dot stays while the user looks at the list and is gone once the window loses focus, so it never vanishes under the user's eyes.
  • Persistence: marks live in viewed.json next to the settings and survive restarts. Marks of items that left the lists are dropped at the next poll; a removed account is forgotten.
  • Local only: viewed.json is not part of the settings export and is never sent anywhere.

System notifications#

A system notification appears only for a new hit of a "waiting for me" view that counts in the tray (assignment and labels as set in the criteria editor, #143). A plain new issue that no counting view matches never notifies, neither does a hit in a view that does not count, and an item in two counting views notifies exactly once (the hits are de-duplicated by repo and number in fetch_account). The first poll after a start is the baseline and notifies nothing. Covered by the tests in crates/core/src/sync/fetch.rs.

Where a click leads (#939)#

Every notification carries its target, and a click brings the app forward and opens it there:

NotificationOpens
New question (poll, dispatcher, reminder)the question's card over "Asked of me"
Several new questions (summary)"Asked of me"
Worker stalled, merge failed, merge vetoedthe issue or pull request on its repository's page
Issue waits for its worker machineSettings → Worker machines
Invalid orchestrator settingsthe status page
Low disk space (#970)Settings → Storage
Usage limit warningnothing beyond the app (no single place to open)

The target holds only kind, account id, owner/name and number, never a token. The core keeps the last clicked target until the window takes it (take_notification_target) and announces it with the event notification-open, so a window that opens only because of the click still finds it. Per platform:

  • macOS: the target travels in the request identifier of the UNNotificationRequest; a delegate of UNUserNotificationCenter reports the click (crates/scoped-folder/src/notification.rs), also when the click started the app.
  • Windows MSIX (store build or installed package): the toast's launch arguments carry the target; its Activated handler reports a click while the app runs. A click after the app ended starts it without the target (no toast activator is registered).
  • Direct Windows install and Linux: the notification plugin reports no click, so a click only brings the app forward, as the system does by itself.

Every alert of the dispatcher is worded in the app language (title and body); a question names its first line, else the issue title, never the dispatcher's log text. On a question alert the app reads that one issue again at once (fetch_issue, the same filters as the full poll) and posts the notification only once the list has the question, or after 5 s at the latest; the poll that later finds the same question does not announce it a second time. Covered by the tests in src-tauri/src/human_control.rs, src-tauri/src/notify_target.rs, src-tauri/src/sync.rs and src/state/notificationTarget.test.ts. The browser demo simulates a click with ?notification=question|item|questions|hosts|status at the start or gitoodoDemoNotificationClick("question") while it runs.
