Gitoodo cleans up its own worktrees, branches and temp files: after merges, after crashes and resets, after an uninstall, and above all in the user's own checkouts, which serve as clones since #755. Code: crates/core/src/hygiene/ (decisions, the only removing code), the dispatcher's crates/cli/src/dispatcher_hygiene.rs and the satellite's crates/cli/src/satellite_hygiene.rs.

Safety rule#

In a user checkout Gitoodo only ever runs git worktree remove on worktrees below the worktree root that are its own, git worktree prune, git branch -D <prefix>/<number>… and a fetch of the base. User branches, stashes, the index and working-tree changes of the checkout are never touched (crates/core/tests/hygiene.rs checks this). Anything that holds work that would be lost (uncommitted files, commits on no remote branch and not in the base by content) is never removed silently; it is reported as a leftover.

Ownership#

  • Every worktree Gitoodo creates (dispatcher and satellite) gets the marker file gitoodo-owner (JSON: issue key, branch, time, host) in its git folder (<checkout>/.git/worktrees/<name>/), so the working tree stays clean.
  • Its branch is <branch_prefix>/<number>-<title> (default prefix gitoodo).
  • Older worktrees without a marker count as Gitoodo's when they lie below the worktree root on such a branch. Agent sessions (agent-session/*) never match.

Reconcile round#

At dispatcher start (after the leases of the earlier run are released) and every sweep interval (5 min), the dispatcher scans the checkouts of the configured repos, every checkout a folder below worktree_root points to, and the orphan folders there. Before deciding it fetches the base.

StateAction
lease held or worker running (here or on a satellite)keep
a "Solve with an agent" session of the issue (#919)keep
issue taken: in-progress or assigned (#1813)keep
merged (own commits in the base, also after squash), cleanremove worktree and local branch
issue closed, nothing unsavedremove worktree and local branch
issue open, clean and pushed (abandoned)remove worktree, keep branch for a new start
waiting for a human (needs-human, stalled) or unknownkeep
unsaved workreport as leftover
folder deleted by handworktree prune, branch as above
orphan folder: only build output, empty, or files pushedremove the folder
orphan folder with files saved nowherereport as leftover, saved by itself (below)

Merged needs work of its own (#1813): a fresh branch, cut from the base and never committed to, is an ancestor of the base as well. It counts as merged only when it holds work of its own: commits on no remote branch, or a commit, merge, cherry-pick or revert its reflog records, or a start elsewhere than the base (taken over from the forge's branch). Without a reflog this is unknown and nothing goes as merged; a closed issue still clears it. A branch that only moved along the base stays fresh.

A "Solve with an agent" session (docs/agent-session.md) works in the issue's worktree without a lease; its record in own-sessions/ keeps the worktree in use until the person closes the tile or hands the issue back.

The lease sweep and the cleanup after a merge also delete the local branch once its work is merged or its issue closed. A lease taken between scan and removal wins (checked again right before).

Satellites take part on the main host's word: hygiene_scan returns their items, the main host decides with its leases and the forge, hygiene_apply carries the decisions out; a running worker's worktree is refused there too. A backup of a satellite's leftover (#886) runs through hygiene_bundle: the satellite commits the unsaved files and sends the branch beyond the base branch as a git bundle, the main host pushes it as the backup branch with the account's token (satellites hold none) and only then orders the removal. On its own, 30 s after start and every 5 minutes, a satellite sweeps old temp files (also inside the shared sessions folder) and removes what is merged (the scope the main host sent last, kept in satellite-hygiene.json). It never removes the worktree of an issue the main host holds (held in the scope: a lease, a run waiting for its restart) or that had a worker there since the main host's last word, and nothing while that word is unknown (#1813).

A restart whose worktree is gone (#1813): a worker never starts in a folder that is not there (PtyWorker::spawn refuses it; the pseudo terminal would fall back to the home folder). A satellite restart without prepare cuts the worktree again from the issue's last prepared start (copy, branch, base). When it cannot (the service restarted since, the copy is gone), it answers "worker worktree is unavailable"; the main host takes that as the issue's own fault, puts the issue back into the queue and its next start comes with prepare, so there is no loop.

Leftovers#

Reported items go to hygiene.json in the state folder (HygieneStatus): cleanup state, leftovers with host, issue, branch, commits and uncommitted files, disk reading and errors. Settings › Storage lists the leftovers, beside the automatic cleanup, each with:

  • Discard: removes the worktree and branch with whatever they hold.
  • Push as backup branch and remove: commits uncommitted files, pushes the branch as <prefix>-backup/<rest>-<time> with the account's token, then removes it. On a satellite the main host pushes from the satellite's bundle (#886).

The app queues the decision in hygiene-requests.json; the dispatcher handles it within 5 s and runs a round. dispatch.leftover_expiry_days (default 0 = off) discards leftovers automatically after that many days. gitoodo diagnose lists the leftovers.

Saved by itself (#873, #886): the user does not have to decide. A leftover on this host or on a reachable satellite that can be backed up and was first reported an hour ago (AUTO_BACKUP_SECS) is pushed as a backup branch and removed in the next round, exactly like "Push as backup branch and remove" (dispatch.cleanup_auto_backup). The newest 20 saves are kept in hygiene.json (saved: issue, branch, time); they need nobody, so no page lists them (#924). A failed push stays a leftover and is tried again next round, marked blocked: failed; a worktree a worker uses is never touched, and nothing is pushed while Gitoodo is halted. Orphan folders with files saved nowhere are saved the same way (see "Orphan folders"); a satellite that is offline is saved once it is back. Discarding is never automatic unless the expiry is set.

Remote branches#

Hourly, for every configured repo with the sweep rule on, remote <prefix>/* branches without an open pull/merge request, without a lease and without a local branch are deleted once the issue is known (open or closed) and the newer of last commit and first sighting is older than dispatch.remote_branch_grace_hours (default 24, 0 = off). At most 10 per round, one per second, through the forge adapters (Forgejo/Gitea, GitHub, GitLab; every deletion in the forge audit log and the dispatcher log).

Disk guard (#771, #970)#

Code: crates/core/src/hygiene/disk.rs (levels, readings), crates/cli/src/dispatcher_hygiene.rs (disk_tick), crates/cli/src/satellite_hygiene.rs (watch_disk), crates/cli/src/freeze.rs (pausing a worker's processes).

The app sets what stays free for you, the leftover expiry and the remote branch grace in Settings › Storage; the keys stay in the dispatch block of orchestration.json.

One space setting (#1809). "Für dich frei halten" (dispatch.keep_free_gb, "Keep free for you") is the only space setting: a new worker starts only if at least that much stays free after its repository's expected build. Empty is "Automatisch": 15 GiB, or 10 % of a small drive when that is less (so a 100 GiB drive keeps 10 GiB); 0 switches the guard off. Everything else follows from that one value K (DispatchConfig::disk_guard, disk::Guard):

DerivedFrom K
low level (no new worker)K
critical level (pause)the smaller of 2 GiB and 1 % of the volume, never above K
clean-up starts / frees tobelow 2 × K / up to 3 × K (disk::cleanup_bounds)
room for buildsfree space minus K (priority::room); no separate budget unless the file sets a cap

The status line under the field says it in one sentence from the dispatcher's last measurement (storage.json budget: keep_free, room, held): "Jetzt 165 GB frei, Gitoodos Arbeitskopien belegen 56 GB. Neue Worker starten: Gitoodo nutzt bis zu 150 GB für Builds, 15 GB bleiben für dich frei." While a repository's next build does not fit, it names the repository, its expected build and what is missing. The wait reasons, the status banners and gitoodo diagnose ("builds: Gitoodo may use up to … more, … stay free for you"; "new workers of o/r wait: their build needs about …, … are missing") use the same words. Sizes in GB are GiB, as in the field.

Former settings. Before #1809 three values set this: min_free_disk_mb (default 10240), min_free_disk_percent (default 5, the smaller of both counted) and build_budget_gb (0: a fifth of the drive, 20-200 GiB). They are still read, and no installation ends up less protected:

Saving the field writes keep_free_gb and drops the former keys from the file; saving any other field keeps them (and their floor). A satellite gets the resulting levels from the main host (HygieneScope.min_free_disk_mb/percent, the floor in min_free_floor_mb/percent), so an older satellite follows the new automatic value too.

Every 15 seconds the dispatcher (and every satellite for its own machine) reads the free space of the volume holding worktree_root and, when it differs, of the volume holding Gitoodo's own data (state, logs; the agents' data sits next to it). The free-space reading is cheap (statvfs, or GetDiskFreeSpaceExW on Windows); sizes of folders are never measured in this loop.

LevelBegins belowEnds at or aboveEffect
lowwhat stays free for you, dispatch.keep_free_gb (automatic: the smaller of 15 GiB and 10 % of the volume)the limit plus a marginno new worker starts on that machine
criticalthe smaller of 2 GiB and 1 % of the volume, never above the low limitthe limit plus a marginthe machine's running workers are paused as well

The margin is a fifth of the limit, at least 1 GiB and at most the limit itself, so a reading that wobbles around a limit does not flap: automatic on a big disk the warning begins below 15 GiB and ends at 18 GiB, the pause begins below 2 GiB and ends at 3 GiB. 0 switches the low limit off (and with it critical). A volume without a reading (a missing drive, an error) counts as fine and never holds work back. The worst volume sets the machine's level.

  • Low: no new local worker starts (satellites still take work; with none online the dispatch wait reason is disk_low), DispatcherStatus.disk_low is set and a reconcile round runs.
  • Critical: the running local workers are paused, not stopped: on macOS and Linux their whole process tree gets SIGSTOP (resumed bottom-up with SIGCONT), on Windows every thread of the tree is suspended (SuspendThread/ResumeThread). A paused worker is never counted as hung and its silence starts afresh when it resumes; one that ends during the pause leaves normally, and stopping a paused worker resumes it first so it can exit. They resume on their own once the level drops back to low or ok.
  • Satellites run the same loop for their own disk, refuse a new worker at critical ("the disk of this machine is almost full; free up space there") and report their level in the status reply. The main dispatcher places no new worker on a satellite whose disk is low or worse and lists it in DispatcherStatus.disk_hosts. Since #1675 a satellite also cleans up its own disk like the main host (below, "On a satellite") and reports that pass in its disk report (cleanup); the app then says "mini is cleaning up …" or what it freed there and asks for manual work on that machine only once its pass is done and the disk is still low.

DispatcherStatus.disk carries the machine's level, every volume (path, roles, free and total bytes, both limits, the bytes to free so the level ends), the number of paused workers and, on this computer, the automatic clean-up for the level (cleanup, see "Build output" below).

The app shows a warning in the status bar while a disk is low or worse (this computer first, then worker machines by name) and posts one system notification; it posts again only when the warning gets worse (low → critical) or after the disk was fine in between. On this computer it waits for Gitoodo's own clean-up first: while that is owed or runs, the status bar says Gitoodo is removing build output and nothing is posted; afterwards the notification says what the clean-up did and freed (or what it checked and found nothing to remove), what is left and who waits, that running workers clean up their own, and what the user can do: on Settings → Storage, remove the build output of their own repositories, which Gitoodo never removes without them (#1418). It never asks the user to remove Gitoodo's own build output by hand. A clean-up that frees enough ends the warning before it is posted. How loud a disk report is comes from the service, not the app: Report::assess() in crates/core/src/hygiene/disk.rs sets attention. info while the clean-up runs, is owed, or its last pass for the level freed something (it copes: no status bar entry, no notification, Settings → Storage shows a calm line, the status page counts it as idle, new workers wait); warn once the pass is done and freed nothing, or failed (cleanup.failed), so the person can or must act; critical while running workers are paused. A report without attention (an older service) is read as before: warn unless a pass is running. On a worker machine the text says how much to free there. The status bar entry and the notification open Settings → Storage.

What fills the disk#

After each reconcile round, at most every 15 minutes (at once when a warning begins and after "Remove build output"), the dispatcher measures on a background thread what lies on the worktree volume and stores it in storage.json (disk): Gitoodo's worktrees (kept leftovers counted apart), their build output (the folders "Remove build output" would remove now, so only worktrees without a running worker), the agents' data of Gitoodo's runs and Gitoodo's own data (each only when on the same volume), everything else as "other programs", and the free space. The parts add up to the volume's size. Settings → Storage shows them as one bar with a row per part and, during a warning, the warning with a button "Remove build output (size)". The user's own repositories (their checkouts and their build output, as the six-hourly survey measured them in auto.breakdown projects and build) are taken out of "other programs" into a part "Your repositories" with its own segment and rows (#1809); an older survey never shows more there than the reading calls other. The free part is an empty, outlined track, so it stands apart from every used part. On it a hatched area from a line marks what stays free for you ("Für dich frei halten"), and while a repository's build waits for room (budget.held, the one missing the least) a dashed frame from the end of the used space shows the size of that build: where it reaches past the line is what is missing. Rows under "Free" name what is kept free, what is left for builds and the waiting build with what is missing.

The free space is one measure everywhere: the space the system grants a new file (statvfs available blocks on macOS and Linux, GetDiskFreeSpaceExW for the caller on Windows; purgeable space macOS may free later does not count). The header, the bar and the "Free" row of Settings → Storage use the dispatcher's live reading of the worktree volume, the same one the warning, the notification and the worker guard use; the slower walk only splits the used space into its parts, and what changed since the walk lands in "other programs" (build output removed since then is taken off at once, and the free space is read again right after it, never the removal added to the reading before). Sizes of build output and worktrees are what the files hold on the disk (their blocks, each hard link once), so a removed target/ reports what it frees, not the lengths of Cargo's linked programs twice. Each part's row and its segment in the bar share one colour, free space included.

Stalled by machine faults (#982)#

An issue that is stalled only because its machine could not start a worker (no run reached the coding agent) is not the user's to fix. At dispatcher start and after a paused machine started a worker again, such issues in repositories the dispatcher may write to go back to ready, each with a short note marked <!-- gitoodo:auto -->. Which issues qualify is kept in start-faults.json in the state folder, filled the first time from the dispatcher's run log. Issues stalled for any other reason (hangs, failed checks, a stalled worker) are left alone. Details in dispatcher.

Agent data (#971)#

Coding agents keep data per session or per working folder in their own home folder. Gitoodo removes the part that belongs to its own runs once their worktree is gone, and only that part. Code: crates/core/src/agent/cleanup/ (one module per agent; tests with fake homes in cleanup/tests.rs).

Whose data. An entry is Gitoodo's only when the working folder the agent recorded is a Gitoodo worktree: exactly <worktree_root>/<repo>/<number>, compared component by component (case-insensitive on Windows, no ..), and either the agent also recorded the issue branch <branch_prefix>/<number>… of that worktree or Gitoodo recorded the worktree itself (agent-worktrees.json in the state folder, written when a worktree is created and on every sweep for every worktree with the gitoodo-owner marker). Folder names are never matched by prefix. The user's own sessions in the repository's checkout, in session-* folders below the root or anywhere else never match.

AgentRemoved per runProof
Claude Code (~/.claude, or CLAUDE_CONFIG_DIR)projects/<encoded folder>/, and for each of its sessions file-history/<id>/, session-env/<id>/, todos/<id>-*.json, debug/<id>.txtThe folder name is the encoded worktree path (every character other than A–Z, a–z, 0–9 becomes -). Because that encoding is ambiguous, every transcript in it must also name the same worktree as cwd, and none may name another branch than the worktree's issue branch; a folder whose transcripts lack this stays. Paths longer than 200 characters (the agent shortens those) are never matched.
Codex (~/.codex, or CODEX_HOME)sessions/YYYY/MM/DD/rollout-*-<id>.jsonl, archived_sessions/…, shell_snapshots/<id>.*The first line (session_meta) names the worktree as cwd and, without a ledger entry, its issue branch (git.branch).
Gemini CLI (~/.gemini, or GEMINI_CLI_HOME)tmp/<sha256 of the folder>/, history/<sha256 of the folder>/Only worktrees in Gitoodo's ledger; the folder name must be the hash of the exact worktree path.

When. After every reconcile round of the dispatcher (start, every sweep interval, "Clean up now", after merges and discards) and of every satellite for its own machine. Data goes only when the worktree folder no longer exists and no lease holds it: a kept leftover keeps its data, and so does a run that may resume. Each entry is checked again just before removal (inside the agent's home, not a link, worktree still gone); links are never followed. A worktree root that is missing (an unmounted drive), relative, the file system root or the home folder (or above it) removes nothing.

Never touched. The agents' shared files: history and index files, settings, databases, login data, Claude Code's ~/.claude.json (also its per-folder entries: the agent rewrites it while it runs), and the user's own sessions. Package-manager caches are never touched either.

Build output. "Remove build output" (Settings → Storage) removes the folders git ignores (git status --ignored, whole ignored folders only, no link on the way) in Gitoodo's own run worktrees under the worktree root that no worker, lease, remote worker or own session uses; the working copy and any other folder of the user are never touched. It runs on this machine, on a background task of the dispatcher, which picks the request up within a second. Before each worktree it checks again that nobody took it meanwhile. Settings → Storage shows the run while it goes ("Removing build output … 4.2 GB so far"), then the result ("19 GB removed") or what failed (storage.json, build_run); the dispatcher log has dispatch.build_output_started, one dispatch.cleanup_build_output per folder and dispatch.build_output_done.

It also runs by itself, without a notice:

  • long before the worker guard holds workers back (#1445): once the free space of the worktree volume falls below twice the low limit (at least the limit plus the guard's margin; 20 GiB by default), dispatch.auto_cleanup_due. After the build output of ended runs the same pass removes that of waiting or paused workers and the incremental caches of running ones (in the order above), then runs the automatic disk cleanup for a low disk (caches of tools and programs, old temp files; never the user's repositories; storage-cleanup.md) in stages until the volume has three times the limit free (30 GiB by default), when the home folder lies on the worktree volume (dispatch.auto_cleanup_more, autoclean.low_skipped); freed_bytes is the total of both. While the disk stays low the pass comes again (dispatch.auto_cleanup_next with next_in_secs): 30 minutes after one that reached its goal, 5 minutes after one that freed something but not enough, 1 minute after one that could not run, and after passes that found nothing 5, 10, 20, then every 30 minutes. When the level gets worse (or reaches low for the first time) it comes at once, but never twice within 5 minutes (dispatch.auto_cleanup_rate_limited). This pass comes before the app's warning: the disk report carries its state (cleanup: running, done_for, at, freed_bytes, failed), and the app posts the notification only once the pass for the level is done and the next disk reading is still low, with what it freed and without asking the user to remove build output. A pass that frees enough ends the warning before it is shown. Settings → Storage shows the pass while it runs ("Space is running low: Gitoodo is removing build output …", recorded in build_run from its start); a user's request meanwhile waits for it;
  • when ready issues wait because their build does not fit (build_budget, below; #1804), also while the disk is far from low: the same pass, with the same order, repeat gaps and rate limit (dispatch.auto_cleanup_due with why = build_waits and build_bytes, the smallest build that waits), frees up to what that build needs: low + the build + the guard's margin. A new wait owes one pass (cleanup.build_held; build_done once it ran, was rate limited, or could not help); when the disk is low as well, the one pass frees up to the larger of both goals. Freeing the disk cannot help when only the cap from the file (dispatch.build_budget_gb) holds the build or the guard is off: then no pass runs (dispatch.auto_cleanup_skipped) and the wait is announced at once. Until the pass ran, the status shows a calm note ("… Gitoodo is cleaning up for it right now") instead of the card, and the notification after 10 minutes waits as well (host_wait::hold_back); once the pass ran and the build still does not fit, the card says what it freed (or that it found nothing it may remove without you). The pass counts as under pressure: what rested a day may go (storage-cleanup.md, "Under pressure"), and with "Remove your repositories' build output automatically when space is short" switched on, the build output of the user's repositories that rested three days goes last;
  • for a worktree whose issue is closed or whose content is merged, in the reconcile round that finds it (also while the hygiene keeps the worktree itself).

Only one removal runs at a time; a request while one runs waits for it.

On a satellite (#1675). A worker machine cleans up its own disk by the same rules, with the same engine (hygiene::own_build, hygiene::low, autoclean::service::run_with; crates/cli/src/satellite_autoclean.rs):

  • its disk reading (every 15 seconds) starts the same low-disk pass below twice low, with the same goal, repeat gaps and rate limit (satellite.auto_cleanup_due, satellite.auto_cleanup_next): the build output of ended runs in its worktrees, then of waiting or paused workers, then the incremental caches of running ones, then the tier A/B cleanup for a low disk when the home folder lies on the worktree volume (on Windows: the same drive). Its disk report carries the pass (cleanup) like the main host's;
  • once an hour (first five minutes after its start) the scheduled tier A/B pass, and every 15 minutes the build output of ended runs;
  • the main host's settings reach it with each hygiene scope (HygieneScope.cleanup: disabled, exclude, off; an older main host sends none and the satellite's own autoclean-settings.json applies). disabled stops the tier passes, as on the main host;
  • which of its worktrees the main host still holds (a lease, tracked work, the person's own session) comes with the same scope (HygieneScope.held). A worktree counts as ended only when no worker of the satellite runs there, the main host's latest list does not hold it and no worker ran there since that list came. Without a list (an older main host, none since the satellite started) no worktree counts as ended; waiting workers' build output still goes;
  • its clones and worktrees are never part of the tier passes, and items that need a confirmation on the main host (the user's repositories) are never removed there.

A waiting worker on a satellite whose build output went is not told so at its next turn end (the main host's note); it builds again when it resumes.

Gitoodo's own build output by phase (#1418). Each measurement (below) sorts the build output of Gitoodo's worktrees on this machine by the phase of its run (hygiene::priority) and removes what may go, without being asked:

PhaseWhenWhat goes
endedno worker, lease, tracked work or own session holds the worktreeits whole build output, at once: a reconcile round that sees a worker gone measures right away
waitinga worker runs here but is paused for disk space, waits for a person or sits at its usage limit (silent for a minute), or has been silent for 30 minutesits whole build output (from 512 MiB); the worker is told at its next turn end
runninga worker worksonly while the disk runs low (below twice low): its target/<profile>/incremental caches

Under pressure the order is ended runs, then waiting or paused workers (largest first), then the incremental caches of running workers (largest first); the low-disk pass runs it right after the removal of ended runs' build output and before the cleanup of tool caches (storage-cleanup.md), and stops taking incremental caches once the volume has three times low free. A build that runs is never touched, in any phase: a build tool working in the worktree (autoclean::items::BUILDERS: cargo and rustc, Xcode, SwiftPM, Go, Make, Ninja, CMake, MSBuild), a worker waiting for its own background work (also when paused with it), or an incremental cache written in the last 10 minutes keeps it. Before each folder the removal checks again that the worktree is still in its phase and no build started; a worker that woke up keeps the rest. A worktree held otherwise (a lease, a worker on another machine, the person's own session) stays. Each removal logs autoclean.own_freed (issue, phase, what, bytes), each build output that stays autoclean.own_skipped with its reason (held, build-running, too-small, worker-running, enough-free, phase-changed, removal-running).

Room for builds. A new local worker starts only when its expected build fits (#1418, #1809): the median of the largest build output each working copy of the issue's own repository held in the last 7 days (storage.json expected, from expected_copies: per copy its largest build and when it was measured, at most 12 copies per repository; 4 GiB before the first; a copy's largest build older than 7 days gives way to what it holds now, and values of an older way of measuring, expected_measure below 3, are dropped once; #1804: one copy that built everything once, or output that piled up over many builds, no longer holds every worker back) must leave the volume above what stays free for you (low). Gitoodo has no separate budget for its build output any more; only a dispatch.build_budget_gb > 0 from the file still caps it (its build output as of the last measurement plus the expected build must stay within it). Each issue is judged by its own repository (#1804): an issue whose build does not fit waits with the host wait reason build_budget (not disk_low; the status names the machine and leads to Settings → Storage), while issues of repositories with a smaller build still start. When not even the smallest build fits, no new local worker starts (dispatch wait reason build_budget or build_space, dispatch.build_budget_hold; dispatch.build_budget_ok when it fits again), the next round measures and removes what may go, satellites still take work, and restarts in their own worktree still run. Settings → Storage shows the budget, what is used and why new workers wait (storage.json budget), in the status line under "Für dich frei halten". The status page's machine card for these issues reads the same figures (#1809): what the build of the repository missing the least needs, what is free, what is left after the space kept free, and what is missing (for a cap from the file, what is left under the cap). The page's rows, the status line and the card write every figure in the GB of the "Free" total (10^9 bytes, whole from 10 GB, one decimal below), rounded before they are subtracted (freeSplit), so free − kept free = left and build − left = missing as written; the setting's GiB value is shown converted. Should the live reading have moved past the dispatcher's judgement, the build is written as what is left plus the dispatcher's shortfall, never with nothing missing. Below are the ways out: "Remove build output (size)" when Gitoodo's own build output can go at once, otherwise "Review your repositories' build output (size)", which opens Settings → Storage at that list (the removal there asks first), and "Change “Keep free for you”", which opens the page at that field. The dashboard's per-issue link opens the page at the bar. The issues start by themselves once enough is free; nothing else is promised.

Build output of running workers. The removal never touches a worktree a worker uses. The measurement for the Storage page (every 15 minutes, every 10 while the disk runs low, and right after each removal) measures those too, with the same detection, and the dispatcher looks after them (hygiene::nudge):

  • Reminder. A worker whose worktree holds 5 GiB or more, a quarter of the free space or more, or any build output of 512 MiB or more while the disk runs low (below low plus the margin) gets one line: its size, its three largest folders, to remove what it no longer needs now or after its build and test cycle, never sources, tracked files or caches outside its worktree. At most every 45 minutes; while the disk runs low again after 10 minutes once it has 0.5 GiB less free than at the last reminder. The line is typed only at a turn end (its Stop 5 s ago and silent since, not a turn end from silence alone), never while its login is at the limit, a person typed in the last 10 minutes or left text, it waits for background work, or it waits for a person; it uses that turn end up. The worker's brief carries the same rule (brief::BUILD_OUTPUT_RULE), so does the skill's agents section.
  • Waiting worker. A worker in the phase waiting (above) loses its build output directly, whatever the disk says: apply::remove_build_output_while, with the guard of the removal above, checks before each folder that it still waits and no build started, and stops otherwise. The worker is told at its next turn end ("while you were waiting, Gitoodo removed X of build output …; the next build creates it again"); one whose incremental caches went while the disk ran low hears that too.
  • Storage page. storage.json lists the working copies holding build output (copies, largest first, with repository, issue, size, the largest folders and use: free, worker, held), what each worker was told (reminded_at, reminder_pending, cleared_bytes, cleared_at), and disk.busy_build_bytes (build output of busy copies, part of the working copies' size). The page lists them under "Build output per working copy", so the gap between the disk's build output and what the button removes explains itself.

Storage page. After each pass the dispatcher writes storage.json to the state folder: per agent what Gitoodo's runs still hold (measured in the pass, on the service's background thread) and the last removal. Settings → Storage only reads it.

By hand. gitoodo clean --dry-run lists what would be removed (agent, size, path, worktree); gitoodo clean removes it. Both refuse when the leases cannot be read.

Temp files and maintenance#

  • Temp artefacts live under one root, <system temp>/gitoodo, as RAII folders removed when done. At dispatcher, satellite (30 s later) and app start, leftovers older than 24 h are removed, including the older names in the system temp folder.
  • Every 6 hours: git worktree prune in every checkout; in Gitoodo's own clones (below clone_root) also git remote prune origin (with the account's token) and git gc --auto.

Logging#

Every removal, backup, remote deletion and maintenance pass is a cleanup step (logging::run::Step, see logging) plus a dispatch.cleanup_* event.

Uninstall#

scripts/uninstall.sh --keep-repos (Windows: scripts/uninstall.ps1 -KeepRepos) keeps the working copies but removes Gitoodo's worktrees and <prefix>/* branches from them (only what loses nothing; the rest is listed). --dry-run (-DryRun) lists what would be removed.

Orphan folders#

An orphan is an issue folder below the worktree root (<root>/<repo>/<n>) whose git link is broken, so git cannot say what it holds. The round sorts its files itself: well-known build output folders (target/, node_modules/, dist/, .venv/, …) and system files (.DS_Store) are no work; every other file counts as saved when its content is reachable from a remote-tracking branch of the checkout the folder belonged to (git hash-object against git rev-list --objects --remotes, read once per checkout and round). A folder that is empty, holds only build output or only saved files is removed like any other worktree nobody needs. Without a readable checkout no file counts as saved. A folder without any git link takes the checkout its siblings' working worktrees belong to (all below <root>/<repo>/, one checkout): that is what a removal leaves behind when a locked file stops it halfway on Windows, the .git link gone first and the rest still there (#1901).

The build output inside an orphan folder (the folders above) goes with the build output of ended runs, on the main host and on each satellite, also while the folder itself waits for its backup or for the person (dispatch.cleanup_orphan_build_output, satellite.cleanup_orphan_build_output).

Before a worktree or an orphan folder is removed on Windows, the programs whose command line names it are ended (hygiene.process_ended): a test app, a dev server or a type checker a worker left running there holds its files open, and the removal would stop halfway. Paths are matched with either separator, as a root from ~/… joins them mixed. The other systems remove open files, and nothing is ended there.

One with files saved nowhere is a leftover for an hour and then saved like an ended worker's worktree: its files (build output and system files left out, ignored files kept) are committed on top of the base branch as <prefix>/<n>-orphan in the checkout its broken git link names, through a scratch index, so the checkout's own index, working tree and branch stay as they are. That branch is pushed as <prefix>-backup/<n>-orphan-<stamp> with the account's token (a satellite sends it as a bundle), then the folder and the local branch are removed (dispatch.cleanup_auto_backup, dispatch.cleanup_backup). Only what cannot be saved stays, and the leftover says why (blocked): not_git (the folder has no git link and no worktree next to it names a checkout), unreadable (its contents cannot be read), repo_unknown (the checkout is gone or the repository is not one of Gitoodo's), no_branch (a worktree on no branch) or failed (the last push or commit failed; tried again every round). Settings › Storage names each by repository and issue ("whispaste #1788") with its size and its path on hover, says when it is saved or why it cannot be, with what the user can do, and hides the "Leftovers" section when the list is empty. Only a leftover that needs a decision (blocked, or one an older dispatcher does not save by itself) gets a card with its buttons; those saved by themselves share one folded line, "3 leftovers are saved automatically by 10:59" (the latest of their times), which opens to compact rows with "Back up now" and "Discard" (#1812).
