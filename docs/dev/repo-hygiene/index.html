Gitoodo cleans up its own worktrees, branches and temp files: after merges, after crashes and resets, after an uninstall, and above all in the user's own checkouts, which serve as clones since #755. Code: crates/core/src/hygiene/ (decisions, the only removing code), the dispatcher's crates/cli/src/dispatcher_hygiene.rs and the satellite's crates/cli/src/satellite_hygiene.rs.

Safety rule#

In a user checkout Gitoodo only ever runs git worktree remove on worktrees below the worktree root that are its own, git worktree prune, git branch -D <prefix>/<number>… and a fetch of the base. User branches, stashes, the index and working-tree changes of the checkout are never touched (crates/core/tests/hygiene.rs checks this). Anything that holds work that would be lost (uncommitted files, commits on no remote branch and not in the base by content) is never removed silently; it is reported as a leftover.

Ownership#

  • Every worktree Gitoodo creates (dispatcher and satellite) gets the marker file gitoodo-owner (JSON: issue key, branch, time, host) in its git folder (<checkout>/.git/worktrees/<name>/), so the working tree stays clean.
  • Its branch is <branch_prefix>/<number>-<title> (default prefix gitoodo).
  • Older worktrees without a marker count as Gitoodo's when they lie below the worktree root on such a branch. Agent sessions (agent-session/*) never match.

Reconcile round#

At dispatcher start (after the leases of the earlier run are released) and every sweep interval (5 min), the dispatcher scans the checkouts of the configured repos, every checkout a folder below worktree_root points to, and the orphan folders there. Before deciding it fetches the base.

StateAction
lease held or worker running (here or on a satellite)keep
a "Solve with an agent" session of the issue (#919)keep
merged (content in the base, also after squash), cleanremove worktree and local branch
issue closed, nothing unsavedremove worktree and local branch
issue open, clean and pushed (abandoned)remove worktree, keep branch for a new start
waiting for a human (needs-human, stalled) or unknownkeep
unsaved workreport as leftover
folder deleted by handworktree prune, branch as above
orphan folder (no worktree any more)report as leftover

A "Solve with an agent" session (docs/agent-session.md) works in the issue's worktree without a lease; its record in own-sessions/ keeps the worktree in use until the person closes the tile or hands the issue back.

The lease sweep and the cleanup after a merge also delete the local branch once its work is merged or its issue closed. A lease taken between scan and removal wins (checked again right before).

Satellites take part on the main host's word: hygiene_scan returns their items, the main host decides with its leases and the forge, hygiene_apply carries the decisions out; a running worker's worktree is refused there too. A backup of a satellite's leftover (#886) runs through hygiene_bundle: the satellite commits the unsaved files and sends the branch beyond the base branch as a git bundle, the main host pushes it as the backup branch with the account's token (satellites hold none) and only then orders the removal. On its own, 30 s after start and every 5 minutes, a satellite sweeps old temp files (also inside the shared sessions folder) and removes what is merged in content (the scope the main host sent last, kept in satellite-hygiene.json).

Leftovers#

Reported items go to hygiene.json in the state folder (HygieneStatus): cleanup state, leftovers with host, issue, branch, commits and uncommitted files, disk reading and errors. The board ("All repos") lists the leftovers, each with:

  • Discard: removes the worktree and branch with whatever they hold.
  • Push as backup branch and remove: commits uncommitted files, pushes the branch as <prefix>-backup/<rest>-<time> with the account's token, then removes it. On a satellite the main host pushes from the satellite's bundle (#886).

The app queues the decision in hygiene-requests.json; the dispatcher handles it within 5 s and runs a round. dispatch.leftover_expiry_days (default 0 = off) discards leftovers automatically after that many days. gitoodo diagnose lists the leftovers.

Saved by itself (#873, #886): the user does not have to decide. A leftover on this host or on a reachable satellite that can be backed up and was first reported an hour ago (AUTO_BACKUP_SECS) is pushed as a backup branch and removed in the next round, exactly like "Push as backup branch and remove" (dispatch.cleanup_auto_backup). The newest 20 saves are kept in hygiene.json (saved: issue, branch, time); they need nobody, so no page lists them (#924). A failed push stays a leftover and is tried again next round; a worktree a worker uses is never touched, and nothing is pushed while Gitoodo is halted. Orphan folders without a branch still wait for a decision; a satellite that is offline is saved once it is back. Discarding is never automatic unless the expiry is set.

Remote branches#

Hourly, for every configured repo with the sweep rule on, remote <prefix>/* branches without an open pull/merge request, without a lease and without a local branch are deleted once the issue is known (open or closed) and the newer of last commit and first sighting is older than dispatch.remote_branch_grace_hours (default 24, 0 = off). At most 10 per round, one per second, through the forge adapters (Forgejo/Gitea, GitHub, GitLab; every deletion in the forge audit log and the dispatcher log).

Disk guard (#771, #970)#

Code: crates/core/src/hygiene/disk.rs (levels, readings), crates/cli/src/dispatcher_hygiene.rs (disk_tick), crates/cli/src/satellite_hygiene.rs (watch_disk), crates/cli/src/freeze.rs (pausing a worker's processes).

Every 15 seconds the dispatcher (and every satellite for its own machine) reads the free space of the volume holding worktree_root and, when it differs, of the volume holding Gitoodo's own data (state, logs; the agents' data sits next to it). The free-space reading is cheap (statvfs, or GetDiskFreeSpaceExW on Windows); sizes of folders are never measured in this loop.

LevelBegins belowEnds at or aboveEffect
lowthe smaller of dispatch.min_free_disk_mb (default 10240 MiB) and dispatch.min_free_disk_percent (default 5 %)the limit plus a marginno new worker starts on that machine
criticalthe smaller of 2 GiB and 1 % of the volume, never above the low limitthe limit plus a marginthe machine's running workers are paused as well

The margin is a fifth of the limit, at least 1 GiB and at most the limit itself, so a reading that wobbles around a limit does not flap: with the defaults on a big disk the warning begins below 10 GiB and ends at 12 GiB, the pause begins below 2 GiB and ends at 3 GiB. 0 switches the low limit off (and with it critical). A volume without a reading (a missing drive, an error) counts as fine and never holds work back. The worst volume sets the machine's level.

  • Low: no new local worker starts (satellites still take work; with none online the dispatch wait reason is disk_low), DispatcherStatus.disk_low is set and a reconcile round runs.
  • Critical: the running local workers are paused, not stopped: on macOS and Linux their whole process tree gets SIGSTOP (resumed bottom-up with SIGCONT), on Windows every thread of the tree is suspended (SuspendThread/ResumeThread). A paused worker is never counted as hung and its silence starts afresh when it resumes; one that ends during the pause leaves normally, and stopping a paused worker resumes it first so it can exit. They resume on their own once the level drops back to low or ok.
  • Satellites run the same loop for their own disk, refuse a new worker at critical ("the disk of this machine is almost full; free up space there") and report their level in the status reply. The main dispatcher places no new worker on a satellite whose disk is low or worse and lists it in DispatcherStatus.disk_hosts.

DispatcherStatus.disk carries the machine's level, every volume (path, roles, free and total bytes, both limits, the bytes to free so the level ends) and the number of paused workers.

The app shows a warning in the status bar while a disk is low or worse (this computer first, then worker machines by name) and posts one system notification; it posts again only when the warning gets worse (low → critical) or after the disk was fine in between. Every text says how much to free and how: on this computer "Remove build output" under Settings → Storage, on a worker machine freeing space there. The status bar entry and the notification open Settings → Storage.

What fills the disk#

After each reconcile round, at most every 15 minutes (at once when a warning begins and after "Remove build output"), the dispatcher measures on a background thread what lies on the worktree volume and stores it in storage.json (disk): Gitoodo's worktrees (kept leftovers counted apart), their build output (the folders "Remove build output" would remove now, so only worktrees without a running worker), the agents' data of Gitoodo's runs and Gitoodo's own data (each only when on the same volume), everything else as "other programs", and the free space. The parts add up to the volume's size. Settings → Storage shows them as one bar with a row per part and, during a warning, the warning with a button "Remove build output (size)".

Stalled by machine faults (#982)#

An issue that is stalled only because its machine could not start a worker (no run reached the coding agent) is not the user's to fix. At dispatcher start and after a paused machine started a worker again, such issues in repositories the dispatcher may write to go back to ready, each with a short note marked <!-- gitoodo:auto -->. Which issues qualify is kept in start-faults.json in the state folder, filled the first time from the dispatcher's run log. Issues stalled for any other reason (hangs, failed checks, a stalled worker) are left alone. Details in dispatcher.

Agent data (#971)#

Coding agents keep data per session or per working folder in their own home folder. Gitoodo removes the part that belongs to its own runs once their worktree is gone, and only that part. Code: crates/core/src/agent/cleanup/ (one module per agent; tests with fake homes in cleanup/tests.rs).

Whose data. An entry is Gitoodo's only when the working folder the agent recorded is a Gitoodo worktree: exactly <worktree_root>/<repo>/<number>, compared component by component (case-insensitive on Windows, no ..), and either the agent also recorded the issue branch <branch_prefix>/<number>… of that worktree or Gitoodo recorded the worktree itself (agent-worktrees.json in the state folder, written when a worktree is created and on every sweep for every worktree with the gitoodo-owner marker). Folder names are never matched by prefix. The user's own sessions in the repository's checkout, in session-* folders below the root or anywhere else never match.

AgentRemoved per runProof
Claude Code (~/.claude, or CLAUDE_CONFIG_DIR)projects/<encoded folder>/, and for each of its sessions file-history/<id>/, session-env/<id>/, todos/<id>-*.json, debug/<id>.txtThe folder name is the encoded worktree path (every character other than A–Z, a–z, 0–9 becomes -). Because that encoding is ambiguous, every transcript in it must also name the same worktree as cwd, and none may name another branch than the worktree's issue branch; a folder whose transcripts lack this stays. Paths longer than 200 characters (the agent shortens those) are never matched.
Codex (~/.codex, or CODEX_HOME)sessions/YYYY/MM/DD/rollout-*-<id>.jsonl, archived_sessions/…, shell_snapshots/<id>.*The first line (session_meta) names the worktree as cwd and, without a ledger entry, its issue branch (git.branch).
Gemini CLI (~/.gemini, or GEMINI_CLI_HOME)tmp/<sha256 of the folder>/, history/<sha256 of the folder>/Only worktrees in Gitoodo's ledger; the folder name must be the hash of the exact worktree path.

When. After every reconcile round of the dispatcher (start, every sweep interval, "Clean up now", after merges and discards) and of every satellite for its own machine. Data goes only when the worktree folder no longer exists and no lease holds it: a kept leftover keeps its data, and so does a run that may resume. Each entry is checked again just before removal (inside the agent's home, not a link, worktree still gone); links are never followed. A worktree root that is missing (an unmounted drive), relative, the file system root or the home folder (or above it) removes nothing.

Never touched. The agents' shared files: history and index files, settings, databases, login data, Claude Code's ~/.claude.json (also its per-folder entries: the agent rewrites it while it runs), and the user's own sessions. Package-manager caches are never touched either.

Build output. "Remove build output" (Settings → Storage) removes, only on request, the folders git ignores (git status --ignored, whole ignored folders only, no link on the way) in Gitoodo worktrees without a running worker. It runs on this machine.

Storage page. After each pass the dispatcher writes storage.json to the state folder: per agent what Gitoodo's runs still hold (measured in the pass, on the service's background thread) and the last removal. Settings → Storage only reads it.

By hand. gitoodo clean --dry-run lists what would be removed (agent, size, path, worktree); gitoodo clean removes it. Both refuse when the leases cannot be read.

Temp files and maintenance#

  • Temp artefacts live under one root, <system temp>/gitoodo, as RAII folders removed when done. At dispatcher, satellite (30 s later) and app start, leftovers older than 24 h are removed, including the older names in the system temp folder.
  • Every 6 hours: git worktree prune in every checkout; in Gitoodo's own clones (below clone_root) also git remote prune origin (with the account's token) and git gc --auto.

Logging#

Every removal, backup, remote deletion and maintenance pass is a cleanup step (logging::run::Step, see logging) plus a dispatch.cleanup_* event.

Uninstall#

scripts/uninstall.sh --keep-repos (Windows: scripts/uninstall.ps1 -KeepRepos) keeps the working copies but removes Gitoodo's worktrees and <prefix>/* branches from them (only what loses nothing; the rest is listed). --dry-run (-DryRun) lists what would be removed.
