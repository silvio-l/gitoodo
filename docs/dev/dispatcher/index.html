gitoodo dispatcher runs in the foreground (own process, own service later) and starts one worker (Claude Code, Codex or Gemini CLI, see "Worker launch per agent") per ready issue, each in its own git worktree behind a PTY. It is a client of the classifier: it reads the read model, claims work with next, reports with done and never writes labels itself. stalled and needs-human go out as Request::Flag; only the classifier sets them.

What it does#

  • Push loop (5 s): repos in an active state, ready issues by score, host choice (choose_host, local host only for now), claim via the classifier, lease, worktree (dispatch.worktree_root, branch dispatch.branch_prefix), worker start. Limits come from dispatch.max_workers (default 2, so a first setup does not start workers in many repos at once), cores_per_worker, each machine's own "workers at once" (#967, see "Workers per machine") and min_free_memory_mb. The slots are shared fairly across repositories (see "Fair share across repositories").
  • Readiness: an issue without the ready label (or a legacy alias such as status:bereit) is only ready by a trusted author and a complete body, and never in a repo whose backlog setting is New for issues from before adoption (intake reason backlog; it waits for approval). Every new ready decision logs classifier.ready with via = label or trusted_author (issues ready when first seen at debug); classifier.ready_seen counts those per poll, split into label and trusted_author.
  • One instance (release-gate review M7): at start the dispatcher takes an OS file lock (dispatcher.lock) in its config folder and in its state folder, before it touches any lease; the OS frees it when the process dies, so a crash leaves no stale lock. A second dispatcher for the same folders (second install, a restart while the old one still runs) exits at once, or under a service manager waits until the lock is free. Only then, and after it owns the control socket, does it release leases.
  • Leases (60 s): every running worker's lease is renewed. Each local lease names its owner (machine, process id, start time). At start only the local leases whose owner is provably gone are released: an earlier process on this machine that no longer runs, or a lease from a version that did not record owners. Leases owned on another machine and satellite leases are never deleted at start; they expire by time or follow the unreachable grace. The forge-side gitoodo:lease v1 comments are never deleted. An issue whose dead local lease is released at start goes back into the queue (Flag::Release on the next push tick: in-progress removed, ready set), so a killed dispatcher leaves no orphans behind (#337).
  • Orphans (#337): an issue labelled in-progress without a running worker is orphaned (no lease, lease expired, worker ended, or a local lease of unknown origin). It takes no worker slot. The dispatcher cleans orphans up by itself (#868): once a minute it looks for them in the repos it may write to (paused or active), and one that is still orphaned after orphans::GRACE_SECS (five minutes) goes back to ready through the classifier (Flag::Requeue, the same fresh read and swap as "Reset"); a worker that starts meanwhile, here or on a satellite, ends the grace. Logged as dispatch.orphan_requeued. The board lists orphans apart on the workers page until then; "Reset" (reset_orphans, core orchestration::orphans::reset) does it at once: it reads each picked issue fresh, leaves any the dispatcher runs a worker for, and swaps in-progress for ready. The classifier marks the leases this machine's dispatcher took (LeaseHolder.ours, Lease.origin names the machine), so "runs on another machine" is shown only for a known other machine.
  • **Broken orchestration.json (M9):** the dispatcher keeps running. Running workers stay managed with the last valid configuration (lease renewal, merges, restarts, hygiene, remote polls); no new worker or automation starts until the file is valid again (wait reason config_invalid). The problem is reported once per distinct problem: the log (dispatch.config_invalid), a desktop alert (config_invalid) and config_problem in the status, each with the file path and for a parse error the line and column, never the file's content. gitoodo doctor prints the same check. A valid file clears it (dispatch.config_valid). Broken from the start, there is no fallback and nothing is dispatched.
  • Hang policy: no output and no hook ping for dispatch.hang_timeout_seconds restarts the worker in the same worktree; after dispatch.max_restarts restarts the issue is flagged stalled. A locked login (see "Usage limits") is waiting, never a hang or a restart.
  • Machine faults (#982): a start that fails before the agent runs is the machine's fault, not the issue's: the agent is missing or signed out, or the clone, the worktree or the spawn fails (here or on a satellite, also on a restart). See "Machine faults" below.
  • Exit with a pull request: merge_when_ready (the forge's auto-merge where the forge itself requires checks, else merge pinned to the head SHA once the checks pass). Pending pulls are retried every minute; failed checks restart the worker. Exit without a pull request counts as a restart. After a dispatcher restart (#565) the waiting pulls are rebuilt from the forge: an open pull on the dispatcher's own branch for the issue (<branch_prefix>/<n>-…, the pull's branch name as the forge reports it, even when the issue's title changed) whose issue is open, has a worktree here and does not wait for a person (needs-human, stalled). A person's own pull that closes the same issue from another branch is never taken up, updated or merged. Merge gate (dispatch::merge::decide, pure): the style is the configured one (default squash) when the repo settings allow it, otherwise the first allowed of squash, fast-forward-only, merge, rebase. Every merge is pinned to the checked head SHA (Forgejo head_commit_id). The style per repo is the one set in that repository's settings → Merging (repos[].merge_method, #926), else the global dispatch.merge_method; the first attempt of each pull logs the effective style and why (merge style squash (repo setting), squash (dispatcher default), or squash (dispatcher default rebase is not allowed by the forge)). Behind-base update (#383): a pull whose branch is behind its base is brought up to date locally and the checks are awaited again. Fast-forward-only and rebase rebase the branch onto the base (linear history); squash and merge commit merge the base into the branch. The push uses the credential-free askpass path of the worker push; the branch is pushed only with --force-with-lease on the pull's head SHA, so a foreign push is never overwritten. The worker's worktree is used while it has the branch checked out clean at that SHA; when it is gone (cleaned up, a restart) or holds other commits (a later run that never pushed) or uncommitted changes, the update runs in a temporary detached worktree of the repository's clone, from the head the forge reported, with hooks off, and the worker's worktree stays as it is. A real conflict is not retried: the pull gets a comment naming the files and the issue is stalled with the cause conflict. At most 3 updates per pull (a base that still moves on: base_moving); a failed update does not count as one, is tried once more, and a second failure in a row stalls the issue with update_failed and the reason in the log (dispatch.branch_stuck). A satellite run is updated on the satellite (#391): the dispatcher sends update_branch over SSH and the satellite runs the same update with its own git credentials (helper or SSH key, no token, no extra forge permission), pushing with the same lease. When the satellite has no usable credential or is unreachable, the run log states why and the issue is stalled with update_failed. The forge's own "update branch" call is not used, except on GitLab projects with fast-forward or semi-linear merges: there GitLab rebases the branch itself (its rebase call on the merge request) and the new head is awaited like a push; a branch GitLab cannot rebase (conflict) takes the local update. GitLab's 406 ("branch cannot be merged") is a refusal like 405/409, so a refused, stale branch is updated instead of failing. Which checks gate: the checks the forge requires, read from the classic branch protection and, on GitHub, the rulesets of the base branch (GET /repos/{o}/{r}/rules/branches/{branch}, rule required_status_checks); on Gitea/Forgejo the protection rule named like the base branch, else the first glob rule that matches it (release/*, {main,dev}; by priority where reported), whose required contexts may be globs too; on GitLab the head pipeline when "Pipelines must succeed" is on (pending until it exists; a pipeline of an older head counts as pending). Only then is the forge's auto-merge used, since without required checks it would merge at once. When the forge requires nothing or hides its rules, every check the head reported gates (statuses and check runs: success, neutral and skipped pass, pending waits, a failure fails), plus the repo's extra checks. A head with no check at all waits dispatch.ci_grace_seconds (default 180 s, 0-3600) from when the gate first saw it, so CI that has not started yet is not taken for "no CI"; a repo without CI merges after that. Failed merge calls: the next attempt waits 1, 2, 4 … up to 30 minutes (a back-off round does not use up a merge attempt), and the alert merge_failed names a cause category (auth 401/403, protection, conflict or behind, not_acceptable 406, server, other), never the forge's text; the same cause for the same pull is alerted once, then again only after 1 h, 2 h … up to a day; a new cause at once. The full error stays in the dispatcher log. A merge the branch protection refuses (protection) is diagnosed (#942): the dispatcher reads the rule of the base branch (repository account first, merge account second) and names the cause (merge_allowlist, check_missing, check_failing, approvals, outdated, unknown, unreadable). An outdated branch is updated and merged again, a failed required check goes back to the worker. Every other cause is kept in merge-blocks.json in the state folder, one entry per pull request, notified once per pull request and cause (the entry survives a restart, so a restart does not notify again) and shown as a card in "Asked of me". For the merge allowlist, a required check that never reports and missing approvals the dispatcher stops merging; it reads the rule again every 120 s, and at once after "Allow the merge account" on the card, and merges once the cause is gone. These waits use up no merge attempt. GitLab rules are not read (unreadable). The same causes are checked ahead of time when a repository is added or its autopilot switched on (the setup check: readiness items merge-account, worker-push, reporting-checks, approvals); the check only shows them and never holds the switch up. See Branch rules that work with the autopilot.
  • Sweeper (5 min and after each merge): removes worktrees of merged or closed issues and their local branches; a worktree with unmerged commits is reported once (needs-human) and kept. The same tick runs the reconcile round of the repo hygiene (#771): Gitoodo's worktrees and branches without lease or worker, also after a crash, in every checkout and on satellites; stale remote branches; maintenance; and the disk guard before each new local worker.
  • Shutdown: SIGTERM or ctrl-c stops the workers, removes the control socket and exits.
  • Logs go to dispatcher.jsonl in the log folder (logging) with issue keys only, never tokens; stderr only takes bootstrap output (dispatcher.stderr.log).

Agent programs (#963). Every supported coding agent (Claude Code, Codex, Gemini CLI) is found by itself; nothing has to be set. Only when an agent is not found does the dispatcher settings page offer that agent's own program path (dispatch.agent_programs with claude_code, codex and gemini, each empty by default), and only for an agent new workers start on (the workers' agent, or an agent with a share of the worker distribution); a set path stays visible to change or clear it. A set path must point to an existing file. The former single field dispatch.worker_program moves once to agent_programs.claude_code: the app does it at start under its config-write lock (the dispatcher never writes orchestration.json, it reads the old field the same way until then). claude or an empty value is dropped (found automatically); an absolute path to an existing file or a bare command name other than claude (such as a wrapper) is moved; a path to a missing file is dropped, so Claude Code is found automatically, and the log records config.worker_program_migrated with the outcome only (automatic, moved, missing, already_set), never the path. A path already set for Claude Code wins over the old field. For tests, GITOODO_WORKER_PROGRAM overrides Claude Code's program for one run; an empty value is ignored. A bare name such as claude is looked up independent of the service's own PATH (#982), because a launchd/systemd service runs with a short one: the service's PATH, then the PATH of the user's login shell ($SHELL -l, read once at dispatcher start with a 5 s limit), then the usual install folders (~/.local/bin, ~/.claude/local, /opt/homebrew/bin, /usr/local/bin, …). Only absolute folders count, so the result is always a full path. Not found, the issue is not dispatched and the reason reads "claude was not found in PATH, the login shell's PATH or the usual install folders …"; a path (with /) is used as given and must exist. The folder of the found program is put first in the worker's PATH (not for clean_env workers or remote hosts). At start the dispatcher logs where it found the orchestrator's agent (dispatch.agent_found with path and source: configured, path, login_shell, known_folder) or that it is missing (dispatch.agent_missing); missing while a repository has Autopilot on, this machine is paused at once (see "Machine faults").

Workers survive an update (#965)#

Running workers outlive every update or restart of the app and the dispatcher service. The user does nothing; the work goes on where it was.

  • Worker hosts. The dispatcher does not start the agent as its own child. It starts a small host process (gitoodo worker-host, hidden) that owns the agent's terminal (PTY) and keeps it running. The start command reaches the host on its stdin (with the worker's capability, which is never written to disk or onto a command line); the host answers with one line (its pid and the agent's) and from then on serves a private socket: <state>/runs/<id>.sock (mode 0600 in a 0700 folder) on macOS and Linux, the named pipe \\.\pipe\gitoodo-worker-<user>-<id> (current user only) on Windows. The dispatcher attaches to it with the same frames as the attach protocol: output with the backlog of the ring, size, input, resize, and the exit code. Each worker has a run file <state>/runs/<id>.json with everything needed to take it over (issue, worktree, branch, lease, run id, agent, session id, the program and arguments Gitoodo built, a SHA-256 of the capability, pids). It keeps no environment at all: a dispatcher that takes the worker over builds the environment again as for any start, from its own environment and the configuration, so no token, credential in a URL or capability is ever written there. The backlog a viewer gets on attaching (and the redraw after a re-attach) is the host's output ring in memory only and goes with the host. The only output on disk is the run's transcript in the log folder, which the host writes exactly as a dispatcher-run worker always did (#749, its own retention).
  • Detached per platform.
    • macOS: the host starts in its own process group (setpgid); the agent under it gets its own session from the PTY. The dispatcher's launchd agent has AbandonProcessGroup, so launchd does not end the workers when it stops or restarts the service, and a terminal hangup is ignored by the host.
    • Linux: the same process group; the systemd user unit has KillMode=process, so stopping or restarting the unit ends only the dispatcher. A user manager that ends at logout (no lingering) still ends everything it runs, as before.
    • Windows: the host starts with CREATE_BREAKAWAY_FROM_JOB, CREATE_NEW_PROCESS_GROUP and CREATE_NO_WINDOW; a job that does not allow breaking away refuses the first flag, then the host starts without it (it then stays in that job and ends with it; the resume below takes over). The agent runs in a ConPTY owned by the host. ConPTY starts by asking for the cursor position and holds the program's output until it is answered; the worker's own reader answers it (a fresh terminal, top left) and keeps it out of the output, so a worker nobody watches runs on and a viewer attaching later does not answer it a second time.
  • Shutdown. A dispatcher that stops (update, service restart, app quit) leaves the hosted workers running, refreshes their run files and logs dispatch.shutdown with kept. A watchdog exit or a crash leaves them running too; the run files are written at every start and restart.
  • Take-over at start. After the instance lock and the control socket and before any lease is released, the new dispatcher reads every run file and asks its host how it is (dispatch.handover sums it up):
    • Host there, worker running: it re-attaches (output, status, terminal; dispatch.worker_reattached), takes the lease over with a fresh term (also when it expired while no dispatcher renewed it) and recognises the worker's capability again by its hash. The sessions page shows the worker with its old start time.
    • Worker ended during the update: the host keeps the exit code (<id>.exit) until a dispatcher took it, at most 24 h. The new dispatcher re-attaches, gets the end and handles it as usual (finish, merge flow, restart).
    • Host gone (a reboot, a crash of the host): the agent resumes its own session in the kept worktree, with the same lease and run id (dispatch.worker_resumed): Claude Code with --resume <id> (each worker is started with a preset --session-id, its transcript must exist), Codex with resume <id> (its newest session log in that worktree), and a short note to continue where it left off. Gemini CLI and custom programs have no resume by id yet; they, and a worktree without a session, start afresh in the same worktree with the original brief.
    • Another worker holds the issue now, or the worktree is gone: the run is dropped (dispatch.handover_dropped, held, worktree_gone); a still running host is ended first. A dead owner's lease is then freed by the usual start pass and the issue goes back into the queue.
  • Never twice. One dispatcher per folders (instance lock); a run is taken over only when the lease is missing, its own (same worker) or abandoned (LeaseStore::take_over); a lease of another worker wins, and the outlived worker is ended. A host whose dispatcher stays away for 15 minutes ends its worker without an exit code, so the next dispatcher resumes instead of re-attaching late. A dispatcher that cannot be reached is waited for by a worker's own gitoodo worker … commands for up to 3 minutes (reconnect every 2 s), so an update in the middle of a merge request loses nothing.
  • Paused for disk space (#970): a worker the disk guard paused keeps its processes stopped across the update; its run file says so, the new dispatcher counts it as paused (never silent, never restarted) and its first disk reading resumes it, or keeps it paused while the disk is still full.
  • Not hosted: automation sessions (session: keys) are children of the dispatcher and end with it, as before. Satellites: see satellites.
  • App. While the dispatcher is away the work area keeps the running sessions and shows one quiet line, "Reconnecting 3 workers …"; an open terminal reconnects by itself. After 3 minutes without a dispatcher it names what to do (quit and reopen Gitoodo; the sessions continue).
  • Verified: the real gitoodo worker-host with a real agent process outliving its first dispatcher and taken over by a second (crates/cli/tests/worker_host.rs) on macOS and on Windows 11 (named pipe, ConPTY under the host). Not verified on real machines yet: an update of the installed app with workers running, the Windows breakaway inside the scheduled task's job, and a real Claude Code or Codex resume (the arguments are tested, not the agents' behaviour).

Starting right away (#965)#

Workers start as soon as the dispatcher may start them, not after the next slow round.

  • At start. The classifier keeps the model of its last poll in dispatch-model.json in its state folder and answers dispatch_model with it until its first poll of this run is done (a full poll of many repositories takes up to a minute and a half); the first round starts on it at once. Starts stay safe: the lease table, the worker limits and the disk check decide as always, and an issue that changed meanwhile is caught by the classifier's next model.
  • Leftover search off the start path. The search for pull requests of an earlier dispatcher runs in parallel per repository (90 s at most each) in the background. Putting released issues back into the queue and the orphan sweep wait for it, so nothing is started twice; new starts do not.
  • Resume. The dispatcher checks the switch every second. When it opens (a resume, the end of an emergency stop, the first repository switched on) it starts a round at once, puts the merge round back by a full interval, clears the start back-offs of every machine and asks for a fresh usage check of a limited agent (dispatch.resumed).
  • Not yet fixed. A start can still wait behind the classifier's reconcile of the same repository's writes (both take one lock; seen at 24.5 s for a large repository).

Machine faults (#982)#

A worker start that fails before the agent runs says nothing about the issue: spawn_failed, the agent missing or signed out, or a clone or worktree error on the machine. Before, every such start flagged the issue stalled, so one broken machine stalled the whole queue.

  • The issue goes back unchanged. The run ends as start_failed, the lease goes and the issue goes back into the queue (Flag::Requeue: in-progress for ready). It counts no restart and is never flagged stalled. A restart of a running issue that fails the same way does the same instead of giving up.
  • The machine pauses. After the first such failure the machine (this one or a satellite) takes no new start; other machines go on. The back-off is 1, 2, 5, 10 and then every 15 minutes; after it the next ready issue is the retry. A start that works ends the pause by itself (dispatch.machine_resumed). While this machine is paused and no satellite is online, the dispatch wait reason is machine_fault.
  • One alert per pause. The alert machine_fault names the machine and the kind (agent_missing, agent_login, no_checkout, start_failed, unreachable), never the error's raw text; the app words it ("Coding agent not found on this computer" plus the next step; for a worker machine its name and the action there) and a click opens the status page. A worker machine that did not answer (unreachable) gives no alert and no status-page problem (#965): it is retried by itself, the work goes elsewhere and Settings shows it offline. A satellite that answered with a reason is never unreachable; the fault also keeps the agent and repository of the failed start, and the status page shows the reason after the machine's name. DispatcherStatus.machine_faults lists the paused machines (kind, since, failures, next retry, readable reason); the status page and the Autopilot card show it.
  • Recovery. start-faults.json in the state folder notes per issue the machine faults of attempts that never reached the agent; a run that reaches it removes the issue, entries go after 30 days. At start and after a machine recovered (10 per push round, after its dispatch, #988), every issue that is stalled in a repository the dispatcher may write to and noted there goes back to ready (Flag::Restore: the classifier reads it fresh, posts a short note marked <!-- gitoodo:auto --> and swaps the labels). The first time the file is filled from the dispatcher's own run log (run.end with start_failed and no worker.run of the issue), so issues stalled by an older version come back too.

Worker launch per agent#

The step's agent (ai.agents.orchestrator, or the worker pool's choice) decides the command line; the permission flags follow the repo's worker mode (docs/security.md). Every worker runs in its PTY with GITOODO_ISSUE and a full-colour terminal.

  • Claude Code: the interactive session, claude <permission flags> --settings <json> [--model m] <prompt>. The settings add the status line and the Stop/StopFailure hooks, each calling gitoodo hook <event>.
  • Codex (#934): the interactive terminal UI too, so the session shows Codex's own screen and its input line (instruct, hold, a typing viewer): codex --no-daemon <permission flags> [-c notices off] --enable hooks --dangerously-bypass-hook-trust -c hooks.<Event>=… [--model m] -- <prompt>. --no-daemon keeps each session off the shared background server, which would hand it the environment and hooks of the first session. The hooks are session settings, nothing is written to ~/.codex: Stop reports stop, UserPromptSubmit and PostToolUse report activity. The host that starts the process adds the worktree's folder trust as -c projects={"<worktree>"={trust_level=…}} (as given and resolved), so Codex's trust menu never swallows the first input. The worker starts from the clean environment (no API keys).
  • Gemini CLI: headless, gemini --yolo [--sandbox …] [--model m] -p <prompt>; it exits when done.

A satellite gets the same arguments; it resolves its own codex or gemini (acp::worker_binary) and adds the folder trust for its own path.

What a worker loads#

A worker does one issue in one worktree. Everything an agent loads at its start is sent with every model call of the session, so the user's personal setup (dozens of skills and slash commands, plugins, MCP servers with their tool lists, memory) costs tokens on every turn and adds tools the issue does not need. Workers therefore start lean (agent::lean); the measured start context of a one-line task dropped by about a third for Claude Code (9,538 → 6,466 tokens, 18 → 10 tools) and a quarter for Codex (16,157 → 11,908 tokens).

The user's settings files still load: they carry the login helper, the provider environment, deny rules and the model. Hooks the user wrote there stay too, since they cannot be dropped without dropping those settings; plugin hooks go with the plugins.
  • Codex: -c features.<name>=false for plugins, apps, memories, browser_use, computer_use, in_app_browser, image_generation, tool_suggest and goals, -c skills.include_instructions=false -c skills.bundled.enabled=false, -c mcp_servers.<name>.enabled=false for each server of the user's config.toml, and -c hooks.<Event>=[] for each hook event there that Gitoodo does not set itself. Unknown keys and feature names are ignored by Codex, so older versions start the same way.
  • Gemini CLI: unchanged.

The host that starts the process completes the arguments from its own configuration: the dispatcher sends a marker (--disable-slash-commands for Claude Code, -c gitoodo_worker_mcp=[…] for Codex) and PtyWorker::spawn reads the user's plugins (CLAUDE_CONFIG_DIR or ~/.claude/settings.json) and the Codex servers and hooks (CODEX_HOME or ~/.codex/config.toml) there, so a worker machine switches off its own. Nothing is written to those folders. Automations and the user's own sessions (#991) keep the full setup: they run the user's own prompt and may rely on the user's tools.

MCP servers per repository: a repository whose workers need a server names it under Settings → repository → Workers → "MCP servers for workers" (worker_mcp_servers in orchestration.json, letters, digits, _ - ., at most 20; none by default). The name is the one in the agent's own configuration. Claude Code then loads its configured servers filtered to these (allowedMcpServers in the session settings); Codex keeps these and switches off the others of the user's config.toml. Servers a repository defines in its own .mcp.json or .codex/config.toml count like the others for Claude Code and stay untouched for Codex.

Sub-agents (#952): unless the repo setting worker_sub_agents is on (Settings → repo options "Workers may use sub-agents", default off), Claude Code gets --disallowed-tools Agent (before --settings, so the option's values end there and never swallow the prompt) and Codex -c features.multi_agent=false -c features.multi_agent_v2=false; Gemini CLI has no such switch. The prompt tells the worker not to start other agent sessions. Every 15 seconds the dispatcher (and each satellite for its own workers, told by sub_agents in the spawn request) lists the processes and looks for claude, codex or gemini below an issue worker's agent process (nested_agents::nested, pure over (pid, ppid, name) records; the worker's own agent and its same-agent helper processes do not count). A find is logged once as dispatch.nested_agent and, with the setting off, ended each round it is still there (docs/security.md).

Usage of sub-agents needs no extra counting: the usage Gitoodo shows is the login's limit windows (status line, usage endpoint, Codex limits read), and a sub-agent runs under the same login, so its consumption is already in them.

How a run ends: a turn end (Stop) and activity are signs of life for the hang policy. A run ends by gitoodo ask (parked), gitoodo worker split, gitoodo worker blocked, an exit of the agent (with or without a pull request, see above), stop/cancel, or the hang policy.

A turn end without a result. An issue worker whose turn ends (Stop, Claude Code and Codex alike) before it delivered, asked, split or recorded a dependency is not working any more, it waits. 30 seconds later, unless a tool call or a new turn came in between, the dispatcher looks at it:

  • At its usage limit (a StopFailure, a Claude lock, a Codex report that says blocked): nothing; continue follows at the reset.
  • Someone typed into the session in the last 10 minutes or left unsent text in it: the worker is theirs. It is listed idle (the tile says "Idle, waits for your reply") until it draws again.
  • Otherwise the dispatcher types one reminder (NUDGE_LINE): finish with gitoodo worker pr, gitoodo ask, gitoodo worker split or gitoodo worker blocked, or go on. A second such turn end of the same process ends it (dispatch.worker_idle); the exit without a pull request counts as a restart like any other, so an idle agent no longer sits until the hang policy. An automation session ends at its first Stop with success. A Codex issue worker also ends with the turn that opened its pull request: after a successful gitoodo worker pr its next Stop ends the process and the exit counts as success, so the merge gate starts at once, as it did when the headless run exited there. A Claude Code session stays open after delivery until the hang policy ends it (unchanged). Without the Stop hook (Codex held it back) a Codex worker falls back to that hang path too. A restart (hang, failed checks, steering) starts a fresh session with the brief; no earlier session is resumed.

Usage limits: Claude Code reports a hit limit through StopFailure and its status line. Codex has neither: each Stop of a Codex worker asks for a fresh Codex limits read on the next usage tick (at most once a minute, not while that read backs off), next to the regular poll and the read after a failed exit. A report that says blocked marks the running Codex workers limited; the first report that no longer does types continue into them, like the reset of a Claude lock.

Typing into Codex: an instruction (and continue) goes in as one bracketed paste (ESC [200~ … ESC [201~) and the Enter follows as its own write 250 ms later, because the Codex UI takes a fast burst of keys as a paste and an Enter inside it as a line break.

Settings in the app#

Settings → Dispatcher edits the dispatch block of orchestration.json (worker limit, usage threshold, agent programs, clone and worktree folders, projects folders, base branch, default merge style, trusted authors). Every field saves by itself (#935): pickers, switches and the merge style at once, text and number fields after a short pause in typing and when the field is left. Each save reads the stored form again and sends it with only that field changed, so two fields saved in a row never undo each other. The core runs the same validation as the daemon (Config::field_errors) and writes the file only when the value is valid, under the app's config write lock; a refused value is not saved, stays in its field as typed and shows its problem there. The merge style offers what the core supports; the default is squash. A repository can choose its own style in its own settings (below); the repository's forge settings win: a style it does not allow falls back as described under "Exit with a pull request".

Worker commands#

  • gitoodo ask [--issue <key>] reads a JSON spec from stdin (id, to, optional context (at most 3 lines), deadline, questions with text, kind, options, recommendation), renders it in question format v2 (docs/question-format.md) as worker block, posts it as a comment, asks the classifier for needs-human and parks the worker: it is stopped without restart or report until a human answers. The issue defaults to GITOODO_ISSUE, which the dispatcher sets (account/owner/name#n). Before posting it checks that the human can decide from the card alone (#949): a context of at least one sentence, every question ending in ?, a consequence for every option of a choice question. Otherwise it posts nothing and names every problem (question not posted: …), so the worker rewrites the spec. The skill (skill/gitoodo-questions/SKILL.md) shows the spec with a good and a bad example.
  • gitoodo worker follow-up --title <t> --body-file <path|-> [--label <kind>] proposes a follow-up issue for work outside the worker's own issue (spec 8.3, #337). See "Worker follow-up issues".
  • gitoodo worker split --plan <path|-> splits the worker's issue into parts before it writes code (#1012). See "Splitting an issue into parts".
  • gitoodo worker blocked --on <#n[,#m]> --reason <text> says the worker's issue cannot go on before other issues land. The broker checks the references (#n, repo#n, owner/repo#n, at most 10, not the issue itself, at least one still open), adds a Depends on … line for the missing ones to the issue's description, which the classifier reads as blocked, and posts a short note with the reason ("Waits for #361. …", marked as Gitoodo's own, so it declares nothing itself). Then the run ends as blocked: the lease goes, an untouched worktree goes, and the issue waits in the queue until its dependencies are closed. It is never counted as a restart or a failure. Refusals start with dependency not recorded: and name the problem; satellites refuse for now.
  • gitoodo hook status-line|stop|stop-failure|activity reports a Claude Code or Codex hook to the dispatcher; silent when none runs. It reads (and drops) the hook's JSON input, prints nothing and never fails the hook.

Attach protocol#

Unix socket dispatcher.sock in the private runtime folder (dispatcher_rpc::socket_path), mode 0600 in a 0700 folder; newline-delimited JSON (crates/core/src/dispatcher_rpc.rs). On Windows the same protocol runs over the named pipe \\.\pipe\gitoodo-dispatcher-<user> (dispatcher_rpc::pipe_name): its DACL grants access to the current user's SID only, remote clients are rejected and the first instance is created exclusively, so a second dispatcher or a foreign process cannot take the name (#354; the pipe code is the small gitoodo-pipe-security crate, the only place with unsafe). A pipe serves one client per instance, so the dispatcher creates the next instance before it hands over a connection. Named pipes have no half-close: the client detaches by shutting down its write side. A connection starts with one request:

instruct (#883) writes t into the worker's terminal as one line (line breaks become spaces, control characters go, at most 4000 characters) and Enter 250 ms later, so an agent does not read the Enter as part of a paste. Nothing goes to the forge. The dispatcher counts the keys typing viewers send per worker (characters add, Backspace takes one away, Enter, Ctrl-C and Ctrl-U empty the line, escape sequences change nothing); while that count is above zero a human left unsent text in the agent's input line, and instruct answers error starting with the input line holds unsent text instead of gluing the instruction to it. A started or restarted worker starts with an empty line. For a worker on a satellite the dispatcher opens the satellite's attach stream and sends the line as input frames.

hold (#884) pauses a worker softly: it sends the agent an instruction (the same path as instruct) to finish the step it is on, then stop and wait, and marks the worker held. The worker keeps its process, worktree and lease; while held, quiet is not a hang, so the dispatcher does not restart it. resume sends "continue where you left off" and ends the mark; both answer ok without sending anything when the worker already is in that state. A restart ends the mark. cancel ends the worker and puts the issue back into the queue: the lease is released without the needs-human flag, so the next free slot picks the issue up again with a fresh agent. Unlike stop, nobody has to decide first.

After attach the dispatcher sends output frames (hex bytes; first the 256 KiB backlog, then live output) and a final exit frame. When the worker is restarted while a viewer is attached (hang, failed checks, steering), the stream does not end: it goes on with the new process after a terminal reset (ESC c), its backlog and its size, so the exit frame always means the worker is really gone. The client may send input frames (hex bytes) at any time; they are written to the worker's terminal, and {"frame":"resize","cols":c,"rows":r} frames, which set the size of the worker's terminal (zero sizes are ignored). Bytes of the terminal are opaque, so a client can render them with any terminal emulator. Closing the connection detaches; the worker keeps running.

Human control (#568)#

The dispatcher reads control.json on every push tick (spec §5.7). While the global switch is paused it starts no worker and merges nothing, and it stops the running ones (lease released, in-progress removed, no needs-human). Workers of a repo that is no longer active are stopped the same way. A held PR keeps waiting without using a merge attempt, a vetoed PR is flagged needs-human and never merged. Questions, stalls, failed merges and vetoes are written to activity/alerts.jsonl for the app's desktop notifications; each alert names its account, repository and item, so a click opens it (#939, docs/counters.md), and a failed merge carries its cause (including checks and attempts), which the app words in the UI language.

Emergency stop#

"Alles anhalten" stops all orchestration at once. It is halted in orchestration.json (gitoodo_core::orchestration::halt), set from the stop control in the title bar, the tray menu, Cmd/Ctrl+Shift+H or gitoodo stop-all, and lifted with "Fortsetzen" or gitoodo resume. While halted:

  • the dispatcher starts no worker and no automation, merges nothing, updates no branch and skips the cleanup round; running workers are stopped like a pause above (lease released, in-progress removed so the issue is ready again, worktree kept);
  • the classifier writes nothing (labels, comments, milestones, approvals); reading and the read model go on, so the app keeps showing everything;
  • the repos keep their own states. Resuming does not switch anything on: every repo continues as it was (active, paused, observed).

The older global pause (paused in control.json) still counts as halted and is moved into halted at the next start.

Across restarts (#925): the stop keeps its state. What ran when the app ended runs again after a restart of the app, the services or the machine; what was halted stays halted until the user resumes. A start only folds the older global pause into halted and drops the former start-mode fields (on_start, start_session) from the file; files that still have them load as before. A missing orchestration.json (fresh install) is not created.

dispatch.max_workers defaults to 2 when the file does not set it; the dispatcher never runs more workers than that over all hosts.

Workers per machine (#967)#

A machine runs at most capacity = min(automatic, max_workers) workers at once: automatic is one per dispatch.cores_per_worker cores (at least one), max_workers the user's own maximum for that machine (local_host.max_workers for this one, hosts[].max_workers for a satellite; absent = automatic; set in Settings › Worker machines, docs/orchestrator/satellites.md).

  • Host choice: a machine at its capacity takes no new worker; among the others the lowest load running / capacity wins, so a capped machine counts as fuller than its cores suggest.
  • Fair share: the share splits the slots the machines offer together: the sum of the capacities of this machine and every satellite that answers, never more than max_workers (dispatch::host::slots). Capped machines therefore never promise a repository slots no machine can fill.
  • Wait reason: an issue pinned to a machine (host:) that is full because of its own maximum, not its cores, waits with reason host_limit; host-wait.json and the read model carry the machine and the number (limit: {host, max}, this machine by its own name), the log says "studio runs at most 2 at once", and the board says "Waits for “studio”: it already runs as many workers as you set for this machine (2)." with the link to the worker machines. A machine full by its cores keeps at_capacity. The wait ends by itself and is never notified.

Test desktop for desktop checks (#986, #995)#

Workers that check native apps use Agent Desktop (permissions). Every machine whose Agent Desktop is ready and whose desktop use is not off is a test desktop for its platform, so a cross-platform app is checked on each platform it targets. When a worker has at least one test desktop, its brief gets a paragraph (brief::desktop_rule): the desktops with name and platform, a check on every platform the repository or the issue targets (its own machine first), --on NAME for another machine, every Agent Desktop command as gitoodo desktop [--on NAME] <command> ... (never the agent-desktop program directly), gitoodo desktop-turn [--on NAME] "WHAT" to wait for a desktop, one desktop command at a time, gitoodo desktop-turn [--on NAME] --done before long builds or test runs, and gitoodo ask instead of guessing when a platform, a permission or the app is missing. Workers start without skills ("What a worker loads"), so the paragraph points to the guide Agent Desktop ships: gitoodo desktop skills list and gitoodo desktop skills get NAME print the version-matched skills (the same text the assistants' skill folders hold for the user's own sessions).

  • Setting, per machine: desktop on local_host and on each hosts[] entry of orchestration.json (Settings › Worker machines › "Desktop tests" on each machine's card): {"mode": "off"} (not allowed), {"mode": "when_idle", "idle_seconds": N} (30–3600, the default with 120 s, not written) or {"mode": "always"} (also while someone works there, for a dedicated test machine). The field shows on this machine's card when Agent Desktop can run here (not in the store build) and on a worker computer's card once its setup reported Agent Desktop. The former single test_desktop block (target, while_in_use, idle_seconds) is still read: on load its values move to the named machine (absent target = this machine; a name that is no longer a machine is dropped), and it is never written again.
  • Which desktops a worker gets (dispatcher::usable_desktops): for a worker on this machine, this machine when Agent Desktop is installed here, and every worker computer whose last setup (desktop-rollout.json in the config folder) found an Agent Desktop version, that answers the dispatcher (its reported system is the platform) and is not still being set up. A worker computer whose permission still waits for the person there is listed with that note, so the worker asks instead of failing. A worker on a worker computer gets only that computer's own desktop: the worker computer knows neither the other machines nor their SSH sign-in (keys and kept passwords stay on the machine running the dispatcher), so it cannot reach another desktop.
  • Worker environment: GITOODO_DESKTOP_SESSION (Gitoodo <repo>#<n>, so a waiting worker names the holder), GITOODO_DESKTOPS (JSON list of {name, platform, guard, own, needs_permission}; guard is the idle threshold in seconds, 0 = any time; own is the machine the worker runs on, used without --on) and, for a worker on this machine, GITOODO_DESKTOP_WAIT (<state>/desktop-wait/<worker key>.json).
  • Turns (crates/core/src/desktop_turn.rs): one session holds a desktop at a time, recorded in <state>/desktop-wait/local.lease under a file lock on the machine that owns the desktop. A worker there takes it directly; a worker reaching it with --on runs gitoodo desktop-turn --remote <base64 JSON> there over SSH (the same link gitoodo desktop uses), so both meet at the same lease and never act side by side. The first gitoodo desktop command of a worker takes the desktop when it is free; gitoodo desktop-turn "WHAT" polls for up to 100 s (every 2 s here, every 5 s over SSH) and prints OK, BUSY: <holder> … or PERSON: …, each naming the machine; both waiting answers (and a desktop command refused for the same reason) exit with code 75, and the worker runs it again within 90 s. A turn ends with --done or by itself 10 minutes after the last desktop command. With "when idle", a new turn also waits until nobody has used mouse or keyboard at that desktop for the set time, measured on the machine that owns it: macOS reads the HID system (works from SSH too), Windows asks GetLastInputInfo in the signed-in session (from SSH through the same interactive bridge as the desktop commands). Where the idle time is unknown (Linux, or Windows without a signed-in session, where the desktop command itself then reports that nobody is signed in) only the turns apply.
  • A person comes first, at every command: under "when idle" every gitoodo desktop command of the holder measures the idle time again, not only the first one. The lease notes when the holder's last command ended (acted); input later than that (2 s slack for late events) came from a person, so the turn ends at once: the lease is removed, the command is refused with PERSON (exit 75), and anyone waiting gets PERSON too, not BUSY. A new turn then needs the full idle time again. Only a single command already running finishes. "Always" never measures. Each grant, refusal and ended turn is appended with the measured idle seconds to <state>/desktop-wait/<target>.turns (JSON lines, no secrets, kept to about 256 KB).
  • No way around the turn: in a worker (GITOODO_ISSUE set), the agent-desktop launcher Gitoodo installs in ~/.local/bin runs gitoodo desktop <command> instead of the program, so a skill that names agent-desktop still takes the turn; without gitoodo it refuses (exit 126). On Windows the launcher always went through gitoodo desktop. A worker without any usable desktop (desktop use off everywhere it can reach) is refused by gitoodo desktop (exit 2) instead of running the program unchecked. A person's own agent-desktop commands outside a worker run directly as before.
  • Another machine's desktop: gitoodo desktop --on NAME sends the command over SSH to that computer's gitoodo desktop (arguments as base64 JSON, so no remote shell reinterprets them). On Windows it runs in the signed-in desktop session, which must be unlocked.
  • Wait reason: while a worker on this machine waits, the wait file holds desktop_wait {target, reason: busy|person, holder} with the machine's name as target; the read model carries it for issues with a lease (a file older than 60 s counts as left over), and the board shows "Waits for the desktop of “hp840” while another worker uses it." or "Waits until nobody works at “mac”." with the holder in the tooltip. It is calm: the worker goes on by itself. The file goes when the worker gets the desktop, and the dispatcher removes it when the worker ends. Workers on worker computers report no wait to the board (their wait file would lie on the other machine).
  • Moving to a free desktop elsewhere (crates/core/src/desktop_move.rs, dispatcher_desktop.rs): a worker on this machine that has waited 3 minutes for a desktop (busy or someone working there; the wait keeps its start across the worker's requests) moves once to another worker machine whose desktop of the same system is free. Each dispatch round looks at the waiting workers. A candidate is a worker machine with a usable desktop of that system (not the waited one), whose labels allow the run (os:, and the system a host: alias such as host:mac stands for), that takes a worker now (online, the run's agent ready, a free slot, not paused) and whose desktop would grant a turn right now under its own setting. The look is gitoodo desktop-turn --remote with probe: true over SSH, in the background, valid for 90 s; it takes nothing there (an older Gitoodo there takes the turn and is handed it back at once). Machines whose desktop may be used "always" come first, then by name. The move: the worker is ended, what it had not committed becomes one WIP: … commit (hooks skipped), the branch is pushed with the account from this machine, the lease moves to the target and the run starts there with the same run ID through the usual satellite start (the copy with the pushed branch comes from this machine, #965) and a brief section "Moved here for desktop tests". The local worktree and branch then go; a later run here fetches the branch from the forge first. The log says dispatch.desktop_move_started and dispatch.desktop_moved (from, to), the tile "Moved to “laptop” for desktop tests." while that run lasts.
  • When not: never for an issue pinned to a machine (host: naming a machine, or naming neither a machine nor a system), never twice in one run, never for a worker paused, stopped, held or done (a stop at the same moment wins). When the work cannot be committed or pushed (dispatch.desktop_move_refused), the worker starts again here and keeps waiting. When the start on the target fails, the issue goes back into the queue with its work on the forge and in the worktree here. When no machine fits, the worker keeps waiting, the look repeats every minute, and the board adds "No other machine can take the desktop tests right now." (desktop_wait.no_other; dispatch.desktop_no_other once per run).
  • Placement: an issue whose run waited for a desktop is remembered with that desktop's system (<state>/desktop-needs.json, 14 days, forgotten when the issue is finished). Its next start goes to a machine whose desktop of that system is free right now (this machine's is asked directly), before the usual placement; with none free, or pinned to a machine, the usual placement decides. An issue is only known to need a desktop from such a wait: there is no label for it.
  • Not done: running only the desktop commands on another machine while the worker stays here would need the app under test built and started there; moving the whole run does that. After a move the worker reaches only its new machine's desktop (worker machines do not hold the SSH sign-ins of the others), so a check on a further platform waits for a question to the user.

Fair share across repositories (#959)#

The push loop asks the pure planner dispatch::fair::plan which repository starts next; inside the repository the best ready issue (score, then the classifier's order) still goes first.

  • Share: every repository with Autopilot on that has ready issues or running workers (here and on satellites) is active and gets floor(slots / active) slots, at least one; slots is max_workers, or fewer when the machines' capacities add up to less (#967). A repository at its share starts nothing more while another one below its share has ready work.
  • Rotation: repositories below their share go first, in turns: one that never started goes first (best ready score first), then the one whose last start is the oldest; a repository that just started goes to the end. The order is kept in memory across ticks (fair::Turns); after a restart every repository starts even, and a repository switched off or removed leaves it.
  • Urgent issues: a ready priority:p0 issue (also the legacy prio:0) puts its repository at the front of its group; the classifier already starts p0 first inside a repository. Urgency neither breaks the share nor the global limit.
  • No idle slot: slots no repository below its share can use (no ready work there) go to the repositories with more ready work, in the same order, so no slot stays free while anything is ready. max_workers and every host limit (cores, memory, usage, os:/host:) still hold.
  • No weighting: every repository counts the same.
  • Several starts per tick: the loop plans again after each start; a repository whose ready issues no host takes or the classifier does not hand out sits out the rest of the tick, so its slot goes to the next one. A repository whose issues are all pinned to a full or missing machine is below its share but never holds a free slot back.
  • Wait reason: a ready issue held back by the share is written to host-wait.json with reason repo_share and shows on the board as "Waits for a free slot of this repository." (no link to the hosts, nothing to set up); a reason a host gives for a pinned issue wins. While slots are free but no machine takes an issue without labels, the share is not what holds it: the issue shows that machine reason instead. It ends by itself and is never notified.
  • Why a machine takes nothing: a machine with free slots that takes no worker while work is ready logs dispatch.host_rejected with the reason per agent, once per change (logging); gitoodo diagnose lists it per machine.

stop_worker(issue)stop: the worker ends for good; the lease is released and the issue gets the needs-human flag, so it is not dispatched again by itself
hold_worker(issue)hold: soft pause, the agent finishes its step and waits
unhold_worker(issue)resume: the held agent carries on
cancel_worker(issue)cancel: the worker ends, the lease is released and the issue goes back into the queue
restart_worker(issue)restart: kills the process and starts it again in the same worktree; counts as a restart
instruct_worker(issue, text)instruct: one line into the agent's terminal, then Enter; half_typed while a human left unsent text there, invalid_instruction for an empty or too long text
boost_issue / unboost_issueadds / removes the manual boost label (score.boost_label) the queue score already reads
pause_repo / resume_reporepo state active to paused and back in orchestration.json; other states are invalid_state

issue is the worker key (<account>/<owner>/<repo>#<n>) from dispatcher_workers. Steering reaches workers on the local host only; workers on a satellite are not in the dispatcher's local list and answer refused. instruct_worker is the exception: it reaches satellite workers through their attach stream, like the terminal.

In the overview, the sessions page and an enlarged tile of the repository view, each worker that runs on this host offers pause (or continue while held), restart and cancel (#884). Cancel and restart ask once before they run; a held worker's tile says "Paused". Park and stop stay in the protocol and the commands for scripts. Issues that wait in the queue offer a boost toggle, and a boosted issue keeps the toggle so it can be unboosted. Active and paused repos offer pause or resume in their header. Every action shows a pending, done or failed line under its row, and a steering error is shown in plain words. When the app turns out to be in direct mode, the controls disappear and one line says why. The read model marks a boosted issue with boosted: true.

Live terminal in the app#

In orchestrator mode the agent dashboard asks the dispatcher every five seconds for its workers (dispatcher_workers; quiet, "no dispatcher running" is a normal state). An issue with a running worker gets a "Terminal" button; it attaches (dispatcher_attach), shows the backlog and live output in xterm.js, sends keystrokes (dispatcher_input) and the terminal size (dispatcher_resize), and "Detach" closes the connection (dispatcher_detach). The client lives in crates/core/src/dispatcher_client.rs: Unix sockets on macOS/Linux, the current user’s named pipe on Windows. Worker lists, status, attach, input, resize and detach use the same app commands on every platform. Without a listening dispatcher the app reports offline. Named pipes have no half-close; detaching drops both connection halves so the server releases that viewer.

Run cargo test -p gitoodo-core --lib dispatcher_client::tests on Windows to check the real named-pipe transport: attach with backlog, input, resize and exit, plus worker/status polling while a read-only sizing view stays attached, live output and detach. The polling test uses separate pipe instances as the dispatcher does; the client and server must both close in time.

Device check (2026-11-19, Windows 11 x64): the test-access app against an isolated protocol fixture using create_private_pipe showed one worker, backlog and live output, and 37% usage. Opening the full terminal sent Attach { interactive: false, sizing: true }; resizing the app changed the received terminal size from 84×27 to 86×18. Detaching returned to the live worker list. This checks the app commands over a real named pipe, without starting a coding agent or using the showcase’s in-memory transport. The same app flow was also checked on macOS with an isolated Unix-socket fixture (resize to 85×29 cells, then detach).

Workers run with TERM=xterm-256color, COLORTERM=truecolor and TERM_PROGRAM=gitoodo on every host (crates/cli/src/pty_host.rs). Agents that support synchronized output (CSI ? 2026 h/l) wrap each redraw in it, and xterm.js then shows only finished frames, without the cursor jumping through a half-drawn one (#928). Claude Code sends these frames only for terminals it recognises, so the PTY also sets CLAUDE_CODE_FORCE_SYNC_OUTPUT=1. A backlog sent again starts with a terminal reset, so a frame left open never holds the view.

Reconnecting. A stream that closes without the worker's exit (the dispatcher is updated or restarted) is attached again, first after 2 seconds, then after twice as long each time, at most every 30 seconds, for up to 3 minutes. For a worker the dispatcher still lists, a refused or broken attach is tried again too. A worker tile and the opened session attach anew when the worker's restart count changes (a new process after an exit without a pull request). Only then does a tile say what happened: "This worker has ended. Gitoodo takes the next step for the issue." when the worker is gone, "The dispatcher cannot be reached. Once it runs again, it carries on with the issue and the worker shows up here again." when the dispatcher did not come back.

Tile states. Working; waiting for an answer; checks running; paused (soft pause or disk); paused at the usage limit ("Paused until 14:20", the reset from the agent's lock, with the line "Usage limit reached. The worker carries on by itself afterwards."); idle ("The agent ended its turn and waits for your reply in the session.").

Usage limits#

Worker distribution. With dispatch.worker_pool set, new workers are spread over the agents by share of starts (not tokens or cost): codex_percent (default 50) and gemini_percent (default 0, #963) with Claude Code taking the rest; the two shares together are at most 100. With redistribute an agent at its limit or not ready hands its starts to the others, and the chosen shares resume afterwards; pause_unknown_usage holds back an agent whose usage is not known yet. On a worker machine that holds only while a worker of that agent runs there: an idle worker machine often cannot read its usage (the agent's access token there runs out between runs, or its credential store is closed to a session without a desktop) and only a run renews it, so one worker of each agent may start there to find out; a further one waits for the report that run brings. A known limit and a not-ready agent still keep it off the machine. Each agent runs its own model choice (ai.models.workers in the settings, one per agent; empty = the workers' step choice when it belongs to that agent, else its recommended model). Worker machines report every agent they find, Gemini CLI included (#957).

The usage limits below apply to Claude Code and Codex. Gemini CLI reports no usage: it is never held back by the threshold or by "pause on unknown usage", only by not being ready.

The dispatcher tracks the Claude Code login of this host: the 5-hour window, the weekly window and the weekly window per model, each with percent used and reset time, plus the time of the report and a stale flag (no report for 10 minutes). Sources, newest report wins:

  1. Status line: workers start with --settings that sets statusLine to gitoodo hook status-line; its rate_limits JSON from stdin is forwarded as usage in the hook request.
  2. OAuth usage endpoint (https://api.anthropic.com/api/oauth/usage), for times when no session runs. Polled every 15 minutes after a good answer and only while workers are wanted; failures back off exponentially from 5 minutes up to 1 hour and Retry-After is honoured. The token is read-only from Claude's own login (macOS keychain, else ~/.claude/.credentials.json), kept in memory, never refreshed, never logged or sent to the app.
  3. StopFailure hook: a usage-limit failure marks the limit as reached.

Gating: at or above dispatch.usage_threshold_percent (default 90, 1..=100) no new worker starts; running ones continue. When the limit is reached the login is locked until the reset (5 minutes when the reset is unknown): the lock is not a hang and no restart is counted. At the reset the dispatcher types continue and Enter into the terminals of the workers that hit the limit. Such a worker keeps its run; list marks it limited with limited_until (the lock's end, when known), and its tile says "Paused until …" instead of "Working". The lock holds back new workers of that agent.

At the limit. While an agent is locked or a window of it is full, its usage source (OAuth endpoint, Codex app server) is asked every 5 minutes instead of every 15, or just after a known reset when that comes sooner, never more than once a minute; a back-off after failures and Retry-After stay. When the source reports room in every window again, the lock ends at once (also a lock with a known reset), the stopped workers get continue and new workers start with the next push round. Free again, the agent goes back to the normal interval.

Check at the reset. No timer of its own is needed: the usage round runs every 30 seconds and asks a locked agent's source at its known reset plus 15 seconds (RESET_GRACE_SECS), or every 5 minutes while the reset is unknown (a lock from the StopFailure hook lasts 5 minutes and is then checked again). A known lock also ends by its time; the push round every 5 seconds sees that (poll_unlock), types continue into the stopped workers and starts new ones in the same round. Each window (5-hour, weekly, weekly per model) is tracked with its own reset; the lock lasts until the last full window resets. Worker machines pace their own logins the same way (#1036): at the limit each machine asks its source at the reset instead of the normal interval and reports the fresh values with the next poll of the main host (at most 20 seconds).

Locks survive a restart. usage-cache.json keeps each agent's lock (until, and whether the reset was known) beside its last values. A new dispatcher re-arms a kept lock that has not ended yet (at most 8 days ahead; a lock of this run is never replaced), marks the workers it takes over as stopped by the limit and wakes them at the reset as before. A lock that ended while nothing ran is dropped.

Resume now and Check limits now. {"cmd":"recheck","agent":"claude_code"} (or "codex") wakes the usage round at once: the agent's source is asked right away unless it was asked less than 30 seconds ago (MIN_CHECK_SECS) or still asks to wait (Retry-After), and the reply is the status after that round (at most 30 seconds later). The same request reaches every connected worker machine, which asks its own logins at once and answers when its report is fresh (at most 20 seconds). Free again, the lock ends at once and workers start with the next push round; still at the limit, the lock stays and the fresh values show. The app sends it from "Resume now" (one agent) and from "Check limits now" at the top of "Agent usage" (every agent with usage, at most once per 30 seconds, with "Checked just now" afterwards); the command line has gitoodo usage --refresh [--json] (without --refresh it prints the last values). The dispatcher never writes orchestration.json for it.

After a restart (#988). The last good values of each agent are kept in usage-cache.json in the state folder. At start they show at once (marked stale by their age, seeded in the status), and for the start of new workers a kept report counts as current for at most 3 hours, until this run's first own report replaces it, also with "pause on unknown usage" on: an agent that was open keeps starting workers, one that was at its limit stays held. Each agent without current values (no report in the last 10 minutes) is asked at once (OAuth endpoint, Codex app server), beside the recovery of pull requests and before the first placement; a back-off after failed queries (a rate limit) is kept. The start-up order is: free dead leases, check the agent, recover pull requests and ask for usage (together), first push round; the cleanup of leftovers a minute later. Stalled issues of machine faults (#982) go back into the queue 10 per push round, after that round's dispatch, so a long list never holds up the first workers.

Why nothing starts. Every entry of providers carries wait while that agent takes no new worker: not_ready (not installed or not signed in, see usage.problem), limit (window five_hour or week, until the reset in unix seconds when known) or checking (no current values yet and unknown usage counts as no capacity). While every agent waits this way and ready issues are queued, the work area (repository sessions and "All repositories") says why in one line, e.g. "No new session starts: Claude Code: weekly limit until Fri 15:00 · Codex: checking usage …" (repo-usage-gate).

{"cmd":"status"} replies {"reply":"status","status":{...}} with usage (windows, stale, updated_at), threshold_percent, throttled, locked_until (unix seconds or null), workers, max_workers and queued (ready issues without a slot, as of the last push round), plus config_problem while orchestration.json cannot be used.

In orchestrator mode the app's status bar asks for it every 15 seconds (dispatcher_status) and shows the 5-hour and weekly percentages; an agent paused at its limit shows "paused until 14:20" instead (or "paused until reset" when the end is unknown). A click opens the details: reset times, throttled or paused (with the time work resumes and a "Resume now" button that has the dispatcher check that agent again; still at the limit, it says "Still at the limit, resets 14:20"), how old the values are (stale marked), running workers and queue length. A window whose reset time has passed counts as 0 %. Without a dispatcher the bar only says "Dispatcher off"; in direct mode it shows nothing.

Worker delivery#

gitoodo worker pr [--title T] [--body TEXT] pushes the worker's branch and opens the pull request with Closes #N (default title: issue title plus (#N)); gitoodo worker push only pushes. Both run in the worker's worktree, read GITOODO_ISSUE, and hand the delivery to the dispatcher's broker (capability in GITOODO_WORKER_CAPABILITY), which holds the account's token. Inside a worker without a capability they refuse and never fall back to the keychain (release-gate review H2, docs/security.md). The token never reaches the worker's environment, files, git config, remote URL or logs.

How the push gets its credential: git push runs as a child in a scratch git directory Gitoodo configures itself (token_git.rs; objects from the checkout, never its config or hooks) with an explicit https URL built from the account origin (not the worktree's origin), system and global config off, hooks and fsmonitor off, credential.helper and core.askPass cleared, GIT_TERMINAL_PROMPT=0, and GIT_ASKPASS pointing at the gitoodo binary itself (gitoodo askpass). Only that child gets GITOODO_ASKPASS_USER/GITOODO_ASKPASS_TOKEN/ GITOODO_ASKPASS_HOST; the askpass call answers git's username and password prompts from them, and only for prompts that name the forge host. Details and the proxy rule: docs/security.md. Alternatives rejected: a token in the remote URL or git config (persists on disk and in ps), a credential helper script (a file with the secret path or token), a setup-assistant check only (needs credentials in the worker's reach). The same route serves the dispatcher's fetch of the base branch before it cuts a worktree (worker_pr::fetch_base) and the branch updates (#385). Git output is scrubbed of the token, and a refused login (missing, expired or unauthorized token) is turned into a readable reason. Satellites hold no token and still fetch with their own git credentials. Branch guard: never main, master, dev, HEAD or the base branch; the refspec is HEAD:refs/heads/<branch>, so there is no force push.

Residual risk: for the few seconds of the push the token is in the environment of the git child (same user, readable by processes of that user, as for any askpass flow). Limits: a worker on a satellite has no token, so these commands refuse there; a satellite sends the branch back and this computer pushes it and opens the pull request (#582; the behind-base update runs there with the satellite's own git credentials). The path of the gitoodo binary must not contain spaces.

Worker follow-up issues#

A worker that finds work outside its issue (a bug elsewhere, a missing test, outdated docs) proposes it with gitoodo worker follow-up; the worker brief says when to use it and that it is never a way to hand off parts of the worker's own task (that is a split, below). The command reads the body from the file (- is stdin, at most 16 KiB) and sends a follow_up action to the broker with the worker's capability, like worker pr; there is no direct path, so a worker without a capability or on a satellite is refused.

The broker checks, in order: capability and issue path, title and body (follow_up::validate), the repo setting worker_follow_ups in orchestration.json (default on; Settings → repo options "Workers may propose follow-up issues"), a live lease of this worker on its issue (the lease file in the state folder), and the budgets: dispatch.max_follow_ups_per_run per run (default 3, 0–20, no field in the form; 0 switches the brief line off and refuses every proposal) and 10 per repo and hour. A proposal that creates nothing (duplicate, unknown label, too deep, forge error) gives its slot back. Chains stop at follow_up::MAX_DEPTH (3): the marker carries depth=D, the parent's depth is read from its body, and a proposal from an issue at depth 3 is refused ("too deep"). Then follow_up::open creates the issue with the account's token: dedupe by normalised title against the open issues, body with the worker's text (<!-- defused) plus the footer "Follow-up from #N (worker W)" and the gitoodo:follow-up marker, label gitoodo when the repo has it and the optional kind label (only existing labels that are no workflow, priority, host or release label), and a note on the parent issue. The broker never labels it ready itself; the classifier's intake does on its next run, or, where the repo has "Approve each follow-up before it is worked on" on (follow_up_approval, default dispatch.follow_up_approval, off; Settings → Dispatcher), asks the repo's human for approval first (docs/security.md, "Worker follow-up issues"). The note on the parent and the reply to the worker say which of the two happens.

Replies are one line for the worker: the new issue number on success, otherwise follow-up issue not created: <reason>. Forge and transport errors are logged (dispatch.follow_up_refused, dispatch.follow_up_created, without tokens or texts) and reach the worker only as the broker's generic refusal.

Splitting an issue into parts#

The brief starts with the scope of the issue (split::brief_section, #1012): where splitting is offered (setting worker_follow_ups, local workers), the worker first sizes up the issue and either does all of it in this run (preferred) or, before writing code, writes a plan and runs gitoodo worker split --plan <file> (file or - for stdin, at most 32 KiB). Without the offer the brief says to do the whole issue in one run; a part's brief says it is never split again; a parent whose parts are all closed gets the list of its parts and the task to integrate and verify the whole.

The command sends a split action to the broker with the worker's capability. The broker checks, in order: capability and issue path, the plan (split::parse and split::validate: 2–8 parts, a reason, each part by follow_up::validate, after only naming earlier parts, no two equal titles), the repo setting, a live lease of this worker and at most 5 splits per repo and hour (apart from the follow-up budget; a split that creates nothing gives its slot back). Then split::open reads the repository's issues (open and closed), refuses a parent that is itself a part, a parent whose parts are all closed and a part that depends on the parent, reuses the parts that exist by index, checks titles and labels of the missing ones, and creates them in order (body, Depends on line for the after parts, footer with the gitoodo:part marker, label gitoodo and the optional kind). A note on the parent lists the parts.

On success the worker reads the part numbers and that it must stop without a pull request; the broker marks the run as split and stops the worker once the reply is out. Its end is reported as Event::Split: run result split (a good end), trace dispatch.split, lease released, worktree and branch removed when the worktree holds no work of its own (no changed file, no commit that no remote has; otherwise it stays for the integrating run, dispatch.split_kept_worktree), and the parent back to ready (Flag::Requeue), where it waits for its open parts like for a dependency. Parts count as Gitoodo's own when the login it writes with now or an earlier one (orchestrator_writers) opened them, so a switched forge account keeps the parent waiting. A refusal reaches the worker as issue not split: <reason> (dispatch.split_refused); it changes nothing on the parent, and the worker goes on (fix the plan or do the issue in this run).

Deviations from the spec#

  • Only the local host is used; the host abstraction is in place for SSH satellites (step 8).
  • The hang policy counts in one-second ticks; the git-change signal is not fed yet, so output and hook pings are the only proof of life.
