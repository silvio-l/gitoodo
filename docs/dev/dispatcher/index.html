gitoodo dispatcher runs in the foreground (own process, own service later) and starts one worker (Claude Code, Codex or Gemini CLI, see "Worker launch per agent") per ready issue, each in its own git worktree behind a PTY. It is a client of the classifier: it reads the read model, claims work with next, reports with done and never writes labels itself. stalled and needs-human go out as Request::Flag; only the classifier sets them.

What it does#

  • Push loop (5 s): repos in an active state, ready issues by score inside the repository's release focus (only the next or a chosen release and what it waits for, or all; never an issue of another release; a chosen release without the idle fallback; see release.md, "Release focus"), host choice (choose_host, local host only for now), claim via the classifier, lease, worktree (dispatch.worktree_root, branch dispatch.branch_prefix), worker start. Limits come from dispatch.max_workers (default 2, so a first setup does not start workers in many repos at once), cores_per_worker, each machine's own "workers at once" (#967, see "Workers per machine") and min_free_memory_mb. The slots are shared fairly across repositories (see "Fair share across repositories").
  • Readiness: an issue without the ready label (or a legacy alias such as status:bereit) is only ready by a trusted author and a complete body, and never in a repo whose backlog setting is New for issues from before adoption (intake reason backlog; it waits for approval). Every new ready decision logs classifier.ready with via = label or trusted_author (issues ready when first seen at debug); classifier.ready_seen counts those per poll, split into label and trusted_author.
  • One instance (release-gate review M7): at start the dispatcher takes an OS file lock (dispatcher.lock) in its config folder and in its state folder, before it touches any lease; the OS frees it when the process dies, so a crash leaves no stale lock. A second dispatcher for the same folders (second install, a restart while the old one still runs) exits at once, or under a service manager waits until the lock is free. Only then, and after it owns the control socket, does it release leases.
  • Leases (60 s): every running worker's lease is renewed. Each local lease names its owner (machine, process id, start time). At start only the local leases whose owner is provably gone are released: an earlier process on this machine that no longer runs, or a lease from a version that did not record owners. Leases owned on another machine and satellite leases are never deleted at start; they expire by time or follow the unreachable grace. The forge-side gitoodo:lease v1 comments are never deleted. An issue whose dead local lease is released at start goes back into the queue (Flag::Release on the next push tick: in-progress removed, ready set), so a killed dispatcher leaves no orphans behind (#337).
  • Orphans (#337): an issue labelled in-progress without a running worker is orphaned (no lease, lease expired, worker ended, or a local lease of unknown origin). It takes no worker slot. The dispatcher cleans orphans up by itself (#868): once a minute it looks for them in the repos it may write to (paused or active), and one that is still orphaned after orphans::GRACE_SECS (five minutes) goes back to ready through the classifier (Flag::Requeue, the same fresh read and swap as "Reset"); a worker that starts meanwhile, here or on a satellite, ends the grace. An issue whose lease in this dispatcher's lease file is still in force or expired inside dispatch.lease_grace_seconds waits on: its next claim would be refused and the issue stall at once. Logged as dispatch.orphan_requeued. The board lists orphans apart on the workers page until then; "Reset" (reset_orphans, core orchestration::orphans::reset) does it at once: it reads each picked issue fresh, leaves any the dispatcher runs a worker for, and swaps in-progress for ready. The classifier marks the leases this machine's dispatcher took (LeaseHolder.ours, Lease.origin names the machine), so "runs on another machine" is shown only for a known other machine. That covers workers on this machine's satellites too: their leases carry the origin as well (since 2026-11-19), so an ended satellite run is an orphan of this install, not "+N by other installs" on the worker-slots tile. An older satellite lease without an origin counts as foreign until it expires.
  • **Broken orchestration.json (M9):** the dispatcher keeps running. Running workers stay managed with the last valid configuration (lease renewal, merges, restarts, hygiene, remote polls); no new worker or automation starts until the file is valid again (wait reason config_invalid). The problem is reported once per distinct problem: the log (dispatch.config_invalid), a desktop alert (config_invalid) and config_problem in the status, each with the file path and for a parse error the line and column, never the file's content. gitoodo doctor prints the same check. A valid file clears it (dispatch.config_valid). Broken from the start, there is no fallback and nothing is dispatched.
  • Hang policy: no output and no hook ping for dispatch.hang_timeout_seconds restarts the worker in the same worktree; after dispatch.max_restarts restarts the issue is flagged stalled. A locked login (see "Usage limits") is waiting, never a hang or a restart. A restart waits (dispatch.capacity_wait) while the disk of the worker's machine is low, here or on a satellite: a worker started on a full disk fails within seconds and would use up the restarts.
  • Machine faults (#982): a start that fails before the agent runs is the machine's fault, not the issue's: the agent is missing or signed out, or the clone, the worktree or the spawn fails (here or on a satellite, also on a restart). See "Machine faults" below.
  • Exit with a pull request: merge_when_ready (the forge's auto-merge where the forge itself requires checks, else merge pinned to the head SHA once the checks pass). Pending pulls are retried every minute; failed checks restart the worker. Exit without a pull request counts as a restart. After a dispatcher restart (#565) the waiting pulls are rebuilt from the forge: an open pull on the dispatcher's own branch for the issue (<branch_prefix>/<n>-…, the pull's branch name as the forge reports it, even when the issue's title changed) whose issue is open, has a worktree here and does not wait for a person (needs-human, stalled). A person's own pull that closes the same issue from another branch is never taken up, updated or merged. Merge gate (dispatch::merge::decide, pure): the style is the configured one (default squash) when the repo settings allow it, otherwise the first allowed of squash, fast-forward-only, merge, rebase. Every merge is pinned to the checked head SHA (Forgejo head_commit_id). The style per repo is the one set in that repository's settings → Merging (repos[].merge_method, #926), else the global dispatch.merge_method; the first attempt of each pull logs the effective style and why (merge style squash (repo setting), squash (dispatcher default), or squash (dispatcher default rebase is not allowed by the forge)). Behind-base update (#383): a pull whose branch is behind its base is brought up to date locally and the checks are awaited again. Fast-forward-only and rebase rebase the branch onto the base (linear history); squash and merge commit merge the base into the branch. The push uses the credential-free askpass path of the worker push; the branch is pushed only with --force-with-lease on the pull's head SHA, so a foreign push is never overwritten. The worker's worktree is used while it has the branch checked out clean at that SHA; when it is gone (cleaned up, a restart) or holds other commits (a later run that never pushed) or uncommitted changes, the update runs in a temporary detached worktree of the repository's clone, from the head the forge reported, with hooks off, and the worker's worktree stays as it is. A conflict only in changelogs (CHANGELOG*, CHANGES.*: both sides added entries at the same place) is no conflict: both entries are kept where they were added, step by step of the rebase, and the update goes on (#1493, update::union_conflicts), on the main host and on a satellite alike, whatever the repository's git settings. A real conflict is not retried: the pull gets a comment naming the files and the issue is stalled with the cause conflict. At most 3 updates per pull (a base that still moves on: base_moving); a failed update does not count as one, is tried once more, and a second failure in a row stalls the issue with update_failed and the reason in the log (dispatch.branch_stuck). A satellite run is updated on the satellite (#391): the dispatcher sends update_branch over SSH and the satellite runs the same update with its own git credentials (helper or SSH key, no token, no extra forge permission), pushing with the same lease. When the satellite has no usable credential or is unreachable, the run log states why and the issue is stalled with update_failed. The forge's own "update branch" call is not used, except on GitLab projects with fast-forward or semi-linear merges: there GitLab rebases the branch itself (its rebase call on the merge request) and the new head is awaited like a push; a branch GitLab cannot rebase (conflict) takes the local update. GitLab's 406 ("branch cannot be merged") is a refusal like 405/409, so a refused, stale branch is updated instead of failing. Which checks gate: the checks the forge requires, read from the classic branch protection and, on GitHub, the rulesets of the base branch (GET /repos/{o}/{r}/rules/branches/{branch}, rule required_status_checks); on Gitea/Forgejo the protection rule named like the base branch, else the first glob rule that matches it (release/*, {main,dev}; by priority where reported), whose required contexts may be globs too; on GitLab the head pipeline when "Pipelines must succeed" is on (pending until it exists; a pipeline of an older head counts as pending). Only then is the forge's auto-merge used, since without required checks it would merge at once. When the forge requires nothing or hides its rules, every check the head reported gates (statuses and check runs: success, neutral and skipped pass, pending waits, a failure fails), plus the repo's extra checks. A head with no check at all waits dispatch.ci_grace_seconds (default 180 s, 0-3600) from when the gate first saw it, so CI that has not started yet is not taken for "no CI"; a repo without CI merges after that. A check the forge requires that has no status at all for the head, while no reported check is pending, stops the wait once the gate has seen that head for 30 minutes (or the CI grace period when that is longer; #2064): CI skipped it (a job whose if: was false) or never ran it for that push, and a status nobody creates never comes. The run log gets dispatch.checks_missing with the missing contexts and the checks wait ends as a timeout. A branch behind its base is updated first (the push starts CI again, and the new head starts the wait anew); a current one stalls the issue with checks_missing, whose record names the missing checks (checks, shown in "Asked of me" and in the resolver's brief), and the resolver's attempt pushes the branch anew. A required check that reported and runs keeps waiting as before. Failed merge calls: the next attempt waits 1, 2, 4 … up to 30 minutes (a back-off round does not use up a merge attempt), and the alert merge_failed names a cause category (auth 401/403, protection, conflict or behind, not_acceptable 406, server, other), never the forge's text; the same cause for the same pull is alerted once, then again only after 1 h, 2 h … up to a day; a new cause at once. The full error stays in the dispatcher log. Busy and server answers are not a refusal (#1880): a 405, 409 or 423 whose text says the forge is busy ("Please try again later", "is being merged", "merge is in progress", "is still being checked") waits the same back-off and tries again, with no alert and no card. A 5xx answer does the same, and after 3 in a row (SERVER_CARD_AFTER) the pull gets the card server ("The forge answers the merge with a server error, several times in a row") quoting the forge's message (scrubbed of tokens, at most 300 characters) with Open PR and Try again; the dispatcher keeps trying at the back-off, and the first call that goes through (merged or refused for another reason) removes the card. Try again (merge_block_retry) marks the entry; the dispatcher's next round takes the mark (dispatch.merge_retry_requested), drops the back-off and merges at once. A pull request that changes nothing is never merged (#1880): before the merge call the dispatcher reads the pull's size (ForgeAdapter::pull_changed_files: changed_files, additions, deletions on Forgejo, Gitea and GitHub; GitLab says nothing and merges as before). A pull with 0 changed files and 0 changed lines is closed with a note ("Nothing to merge"), and its issue is closed with the pull's description as summary, marked as Gitoodo's (<!-- gitoodo:auto -->). Both notes, like the note of gitoodo worker close, are in the issue's forge language (#1889). The run ends as closed (dispatch.empty_pull_closed), the worktree and branch go as after a merge, and no card or alert is shown. A failed close waits the back-off and tries again. A merge the branch protection refuses (protection) is diagnosed (#942): the dispatcher reads the rule of the base branch (repository account first, merge account second) and names the cause (merge_allowlist, check_missing, check_not_run, check_failing, approvals, outdated, unknown, unreadable). A required check without a result on the head is looked for on the newest commit of the base branch and on up to five other open pull requests into it (the same look as the setup check): where it reports there, it only did not run for this one commit (check_not_run, for example a CI trigger that skipped a force-push), otherwise it reports nowhere (check_missing). The unknown card (#1880) says what was checked and found fine (the merge account may merge, the required checks are green, the approvals are there, the branch is up to date), quotes the forge's message and gives the step "Open the pull request on the forge and merge it there once by hand – the message there names the reason", with Open PR and Try again. An outdated branch is updated and merged again, a failed required check goes back to the worker. Every other cause is kept in merge-blocks.json in the state folder, one entry per pull request, notified once per pull request and cause (the entry survives a restart, so a restart does not notify again) and shown as a card in "Asked of me". For the merge allowlist, a required check that reports nowhere and missing approvals the dispatcher stops merging; it reads the rule again every 120 s, and at once after "Allow the merge account" on the card, and merges once the cause is gone. These waits use up no merge attempt. A check_not_run is no setting: the dispatcher starts CI for the head again (Forgejo, Gitea and GitHub: close and reopen the pull request, which replays the reopened event; GitLab: a new merge request pipeline), waits RERUN_WAIT (5 min), reads again and merges once the check is green. It does so at most RERUNS_PER_HEAD (2) times per head commit, a new head starts from zero; the count lives in the dispatcher and starts anew after a restart. Only then, or when the forge refuses the start, the card "did not run for this commit" asks the person, says how often Gitoodo tried and offers Start the check again (one more start per click) and Open PR; it never advises removing the check. GitLab rules are not read (unreadable). The same causes are checked ahead of time when a repository is added or its autopilot switched on (the setup check: readiness items merge-account, worker-push, reporting-checks, approvals); the check only shows them and never holds the switch up. See Branch rules that work with the autopilot.
  • Sweeper (5 min and after each merge): removes worktrees of merged or closed issues and their local branches; a worktree with unmerged commits is reported once (needs-human) and kept. The same tick runs the reconcile round of the repo hygiene (#771): Gitoodo's worktrees and branches without lease or worker, also after a crash, in every checkout and on satellites; stale remote branches; maintenance; and the disk guard before each new local worker.
  • Shutdown: SIGTERM or ctrl-c stops the workers, removes the control socket and exits.
  • Logs go to dispatcher.jsonl in the log folder (logging) with issue keys only, never tokens; stderr only takes bootstrap output (dispatcher.stderr.log).

Agent programs (#963). Every supported coding agent (Claude Code, Codex, Gemini CLI) is found by itself; nothing has to be set. Only when an agent is not found does the dispatcher settings page offer that agent's own program path (dispatch.agent_programs with claude_code, codex and gemini, each empty by default), and only for an agent new workers start on (the workers' agent, or an agent with a share of the worker distribution); a set path stays visible to change or clear it. A set path must point to an existing file. The former single field dispatch.worker_program moves once to agent_programs.claude_code: the app does it at start under its config-write lock (the dispatcher never writes orchestration.json, it reads the old field the same way until then). claude or an empty value is dropped (found automatically); an absolute path to an existing file or a bare command name other than claude (such as a wrapper) is moved; a path to a missing file is dropped, so Claude Code is found automatically, and the log records config.worker_program_migrated with the outcome only (automatic, moved, missing, already_set), never the path. A path already set for Claude Code wins over the old field. For tests, GITOODO_WORKER_PROGRAM overrides Claude Code's program for one run; an empty value is ignored. A bare name such as claude is looked up independent of the service's own PATH (#982), because a launchd/systemd service runs with a short one: the service's PATH, then the PATH of the user's login shell ($SHELL -l, read once at dispatcher start with a 5 s limit), then the usual install folders (~/.local/bin, ~/.claude/local, /opt/homebrew/bin, /usr/local/bin, …). Only absolute folders count, so the result is always a full path. Not found, the issue is not dispatched and the reason reads "claude was not found in PATH, the login shell's PATH or the usual install folders …"; a path (with /) is used as given and must exist. The folder of the found program is put first in the worker's PATH (not for clean_env workers or remote hosts). At start the dispatcher logs where it found the orchestrator's agent (dispatch.agent_found with path and source: configured, path, login_shell, known_folder) or that it is missing (dispatch.agent_missing); missing while a repository has Autopilot on, this machine is paused at once (see "Machine faults").

Workers survive an update (#965)#

Running workers outlive every update or restart of the app and the dispatcher service. The user does nothing; the work goes on where it was.

  • Worker hosts. The dispatcher does not start the agent as its own child. It starts a small host process (gitoodo worker-host, hidden) that owns the agent's terminal (PTY) and keeps it running. The start command reaches the host on its stdin (with the worker's capability, which is never written to disk or onto a command line); the host answers with one line (its pid and the agent's) and from then on serves a private socket: <state>/runs/<id>.sock (mode 0600 in a 0700 folder) on macOS and Linux, the named pipe \\.\pipe\gitoodo-worker-<user>-<id> (current user only) on Windows. The dispatcher attaches to it with the same frames as the attach protocol: size, the current screen, live output, input, resize, and the exit code. On macOS a launchd job stands in front of every host (#1933, worker_host_client::launch_job): launchctl submit runs the service helper as gitoodo worker-host --io <state>/runs/<id>.io, which reads the start command and its starter's environment from a pipe there, starts the host as its child with that environment, passes its line back through a second pipe, waits for it and removes its job afterwards. macOS judges local-network access by the process leading the coalition a program was born into; a host that were the starter's child would stay in the app's or the service's coalition and lose every connection into the local network ("No route to host" for git, python, builds) once an update ended its starter. Without launchd (a sandboxed build) the host starts as a child.
  • Host program per build (macOS). macOS grants local-network access per executable build (the Mach-O UUID of the program at its path). Once an update puts another build where a running host's program lies, that host's new children get "No route to host" for every address in the local network within seconds; Apple's own tools and connections already open keep working. So a host never runs from the app bundle: host_program::stable copies the whole signed helper bundle once per build to <bin>/hosts/<build>/GitoodoService.app (<bin> is the folder of the stable CLI copy, paths::hosts_dir; <build> the first 16 hex digits of the helper's SHA-256) and every new host starts from there. A copy is made in a folder of its own, checked (signature with codesign --verify --strict, the hash once more) and renamed into place; one that is there is never written again. An update makes a new folder beside it, and the hosts of the old build keep their unchanged file and their network. The copy keeps signature, bundle id and team, so the permission the person gave the helper covers it, with no new prompt. When the copy cannot be made, the host runs from the bundle as before (worker_host.program_copy_failed). At dispatcher and app start and in the dispatcher's six-hourly maintenance round, host_program::sweep removes the copies no running process uses and that were neither made nor used in the last 10 minutes, never the current build's; it removes nothing when the process list cannot be read. Checked on macOS 27 with the signed helper: hosts started from two copies reached the local network at once; replacing a copy with a re-signed bundle of the same build cut nothing; replacing the bundle a host ran from with another build cut that host's new children within about 30 seconds ("No route to host"), while hosts of the same builds at untouched paths kept their network. A build the system has not seen yet may wait a few seconds for its first connection; the service runs the same build, so this is rare. Linux and Windows keep starting hosts from the program as it is: Linux has no such permission, a process keeps its image when the file is replaced, and Windows cannot replace a running .exe (the update waits for it).
  • Cut off by an update. A host started before the copies (from the bundle) loses the network with the update. The dispatcher that takes such a worker over sees that its host's program was made after the host started (host_program::replaced, dispatch.worker_cut_off) and starts it again under a new host at a safe point: its turn ended, or it has been silent for PROMPT_SILENCE_TICKS, at the latest after 5 minutes. The new process resumes the agent's session in the same worktree (Claude Code --resume, Codex resume), else starts with its brief; it does not count as a restart (dispatch.worker_network_restart). Each worker has a run file <state>/runs/<id>.json with everything needed to take it over (issue, worktree, branch, lease, run id, agent, session id, the program and arguments Gitoodo built, a SHA-256 of the capability, pids). It keeps no environment at all: a dispatcher that takes the worker over builds the environment again as for any start, from its own environment and the configuration, so no token, credential in a URL or capability is ever written there. The screen a viewer gets on attaching (and the redraw after a re-attach) is the host's terminal state in memory only and goes with the host. The only output on disk is the run's transcript in the log folder, which the host writes exactly as a dispatcher-run worker always did (#749, its own retention).
  • Detached per platform.
    • macOS: the host starts in its own process group (setpgid); the agent under it gets its own session from the PTY. The dispatcher's launchd agent has AbandonProcessGroup, so launchd does not end the workers when it stops or restarts the service, and a terminal hangup is ignored by the host.
    • Linux: the same process group; the systemd user unit has KillMode=process, so stopping or restarting the unit ends only the dispatcher. A user manager that ends at logout (no lingering) still ends everything it runs, as before.
    • Windows: the host starts with CREATE_BREAKAWAY_FROM_JOB, CREATE_NEW_PROCESS_GROUP and CREATE_NO_WINDOW; a job that does not allow breaking away refuses the first flag, then the host starts without it (it then stays in that job and ends with it; the resume below takes over). The agent runs in a ConPTY owned by the host. ConPTY starts by asking for the cursor position and holds the program's output until it is answered; the worker's own reader answers it (a fresh terminal, top left) and keeps it out of the output, so a worker nobody watches runs on and a viewer attaching later does not answer it a second time.
  • Shutdown. A dispatcher that stops (update, service restart, app quit) leaves the hosted workers running, refreshes their run files and logs dispatch.shutdown with kept. A watchdog exit or a crash leaves them running too; the run files are written at every start and restart.
  • Replaced program (#2068, macOS). An app reinstall or update can replace the bundle while the services keep running the old file (the app still quitting, so its start never refreshed them). macOS then refuses local-network access to the git processes of such a program ("No route to host" after 0 ms), while its already open connections go on. So the dispatcher and the classifier under launchd measure their own program at the start (build_id::running), look at its size and modification time every 5 s, and once the file changed and then stayed unchanged for 10 s (build_id::Settle; a file that keeps changing is never measured) compare its hash. Another build ends the service like a stop: the dispatcher between two rounds of its main loop (no start or round is cut off), its hosted workers handed over as above, satellite workers through their run records; KeepAlive starts the new file, which measures itself anew, so there is no loop. Logged as service.binary_replaced (component, installed, running). Only on macOS: Linux keeps running the old image with full network access, and the Windows scheduled task restarts a service only after a failure (a running .exe cannot be replaced there anyway). A process the app or a terminal started is never ended for it. Satellites watch their binary themselves and wait for their workers (satellite::watch_binary).
  • Take-over at start. After the instance lock and the control socket and before any lease is released, the new dispatcher reads every run file and asks its host how it is (dispatch.handover sums it up):
    • Host there, worker running: it re-attaches (output, status, terminal; dispatch.worker_reattached), takes the lease over with a fresh term (also when it expired while no dispatcher renewed it) and recognises the worker's capability again by its hash. The sessions page shows the worker with its old start time.
    • Worker ended during the update: the host keeps the exit code (<id>.exit) until a dispatcher took it, at most 24 h. The new dispatcher re-attaches, gets the end and handles it as usual (finish, merge flow, restart).
    • Host gone (a reboot, a crash of the host): the agent resumes its own session in the kept worktree, with the same lease and run id (dispatch.worker_resumed): Claude Code with --resume <id> (each worker is started with a preset --session-id, its transcript must exist), Codex with resume <id> (its newest session log in that worktree), and a short note to continue where it left off. Gemini CLI and custom programs have no resume by id yet; they, and a worktree without a session, start afresh in the same worktree with the original brief.
  • Host lost while the dispatcher runs (#1566). A host that goes away without the worker's exit (it crashed or was killed, the agent with it) is told apart from a worker that ended: when the run left no pull request, it starts again in its worktree resuming the agent's session as above (dispatch.host_lost, session), else with its brief. It counts as a restart, so a host that keeps dying runs into the usual restart limit.
  • Last screen after a lost host (#1566). A run started again after its host was lost (at the take-over or while the dispatcher runs) does not show an empty tile: its viewers get the run's last screen from its transcript (the plain text of #749, gitoodo_core::logging::transcript, the newest 1000 lines of the newest attempt that wrote any, also the parts a crashed host left unfinished), one dim line "Session resumed" ("Started again" without a session; in the app's language) and the new output below it. Only viewers see it: what the dispatcher reads off the worker's screen (its prompt, a usage-limit notice, a named blocker) comes from the new output alone, so an old notice in the transcript never counts again. A restart that waits for a free slot starts later without it.
    • Another worker holds the issue now, or the worktree is gone: the run is dropped (dispatch.handover_dropped, held, worktree_gone); a still running host is ended first. A dead owner's lease is then freed by the usual start pass and the issue goes back into the queue.
  • Never twice. One dispatcher per folders (instance lock); a run is taken over only when the lease is missing, its own (same worker) or abandoned (LeaseStore::take_over); a lease of another worker wins, and the outlived worker is ended. A host whose dispatcher stays away for 15 minutes ends its worker without an exit code, so the next dispatcher resumes instead of re-attaching late. A dispatcher that cannot be reached is waited for by a worker's own gitoodo worker … commands for up to 3 minutes (reconnect every 2 s), so an update in the middle of a merge request loses nothing.
  • Paused for disk space (#970): a worker the disk guard paused keeps its processes stopped across the update; its run file says so, the new dispatcher counts it as paused (never silent, never restarted) and its first disk reading resumes it, or keeps it paused while the disk is still full.
  • Not hosted: automation sessions (session: keys) are children of the dispatcher and end with it, as before.
  • Workers on worker machines run under that machine's service and outlive the dispatcher anyway. What it needs to supervise them (issue, run, lease id, start time, the start command without its environment, the worktree there, restarts, whether the worker had ended) is kept in <state>/remote-runs.json, written right after each start and restart and after every remote poll when it changed. A file of a newer version (a newer build ran before) is neither read nor overwritten. The new dispatcher takes the workers over right after the local ones (dispatch.remote_reattached): only while the same worker's lease on that machine still holds the issue and no live dispatcher owns it (not another machine's, not another process here; else dispatch.remote_dropped with the reason), with the lease taken over, the start time kept and polls from before the takeover ignored, so exits, hangs, idle and limit ends, delivery, the overview and cleanup go on as before the restart. A run whose worker had already ended is not taken over; its open pull request or expired lease is recovered the usual way, as after the end of a local worker. A satellite lease of a gone dispatcher process of this machine without a record (started by a build before this file existed) is taken over once its satellite lists the worker (the scan only reads the lease file), without a start command: when it ends or hangs it is not restarted, its issue goes back into the queue (dispatch.remote_requeued). Its lease id at the classifier is not in the local lease; the dispatcher reads it from the classifier's read model (at most once a minute while one is missing, and again when the run is reported done, dispatch.remote_lease_found), so the completion is accepted. See satellites.
  • App. While the dispatcher is away the work area keeps the running sessions and shows one quiet line, "Reconnecting 3 workers …"; an open terminal reconnects by itself. After 3 minutes without a dispatcher it names what to do (quit and reopen Gitoodo; the sessions continue).
  • Verified: the real gitoodo worker-host with a real agent process outliving its first dispatcher and taken over by a second (crates/cli/tests/worker_host.rs) on macOS and on Windows 11 (named pipe, ConPTY under the host). Automated since #1566: a host that goes away without an exit counts as lost (worker_host::tests), the take-over shows the note above the resumed session and keeps it off the screen the dispatcher reads (dispatcher::tests), and the last screen comes from a finished transcript as well as from a crashed host's parts (transcript::tests, pty_host::tests). Not verified on real machines yet: an update of the installed app with workers running (macOS install.sh, Windows MSIX and Setup), the Windows breakaway inside the scheduled task's job, and a real Claude Code or Codex resume after the host was killed (the arguments are tested, not the agents' behaviour). The check for each: two workers (Claude Code and Codex, the versions installed at the time) running on issues of a test repository; install the build of the branch over the installed release (macOS install.sh, Windows the MSIX and the Setup package); both tiles come back without a click and both workers deliver their pull request. For the resume: kill one worker's gitoodo worker-host process; the tile shows the last screen and "Session resumed", and the agent goes on in the same conversation (its session id in the transcript of the new attempt).

Starting right away (#965)#

Workers start as soon as the dispatcher may start them, not after the next slow round.

  • At start. The classifier keeps the model of its last poll in dispatch-model.json in its state folder and answers dispatch_model with it until its first poll of this run is done (a full poll of many repositories takes up to a minute and a half); the first round starts on it at once. Starts stay safe: the lease table, the worker limits and the disk check decide as always, and an issue that changed meanwhile is caught by the classifier's next model.
  • Leftover search off the start path. The search for pull requests of an earlier dispatcher runs in parallel per repository (90 s at most each) in the background. Putting released issues back into the queue and the orphan sweep wait for it, so nothing is started twice; new starts do not.
  • Resume. The dispatcher checks the switch every second. When it opens (a resume, the end of an emergency stop, the first repository switched on) it starts a round at once, puts the merge round back by a full interval, clears the start back-offs of every machine and asks for a fresh usage check of a limited agent (dispatch.resumed).
  • Repository by repository (#1422). The classifier polls up to four repositories at a time (one at a time again for the rest of a poll once the forge asks to slow down; triage stays one call at a time) and hands each one to the dispatcher as soon as it is read, instead of at the end of the whole poll. It reads first the repositories with a waiting resolver attempt, then those with the autopilot on, then those with ready issues or waiting triage. Before its first poll is done a repository not read yet keeps its stored model, so none goes empty meanwhile. Measured read-only against a Forgejo with 36 repositories (classifier::tests::measure_one_poll, three cold processes each, median): one at a time 67.7 s, four at a time 35.3 s, the same 2,352 requests and no rate limit. The first repository reaches the dispatcher after 6.6 s instead of 3.3 s, since four share the forge from the start; the order above puts the repositories that matter at the front, so this is accepted.
  • Writes lock one repository. The classifier's writes and the dispatcher's take a lock per repository (orchestration::gate); only steps over every repository take them all. A start no longer waits behind another repository's reconcile. Cleanup at the start (orphan sweep, stalled runs, resolved attempts) asks the model the classifier has now and does not wait for its first poll.

Machine faults (#982)#

A worker start that fails before the agent runs says nothing about the issue: spawn_failed, the agent missing or signed out, or a clone or worktree error on the machine. Before, every such start flagged the issue stalled, so one broken machine stalled the whole queue.

  • The issue goes back unchanged. The run ends as start_failed, the lease goes and the issue goes back into the queue (Flag::Requeue: in-progress for ready). It counts no restart and is never flagged stalled. A restart of a running issue that fails the same way does the same instead of giving up.
  • The machine pauses. After the first such failure the machine (this one or a satellite) takes no new start; other machines go on. The back-off is 1, 2, 5, 10 and then every 15 minutes; after it the next ready issue is the retry. A start that works ends the pause by itself (dispatch.machine_resumed). While this machine is paused and no satellite is online, the dispatch wait reason is machine_fault.
  • Only machine faults pause. A worktree that is gone or belongs to another issue (worker worktree is unavailable, … does not match its assignment) concerns that issue only (fault::issue_level, #1491): the issue goes back into the queue, dispatch.issue_fault is logged and the machine keeps starting. A restart of a running issue whose worktree is gone makes it anew from the branch on the forge first (dispatch.worktree_recreate_failed when that fails). The cleanup never removes the worktree of a pull request that waits for its checks or is being looked at (has_active_work), even without a lease after a dispatcher restart.
  • Self-healing first (#1491). A pause is no notice while its first retries may still end it. It is alerted, and shown on the status page, overview, repository page and in the tray, only once it lasts (fault::lasting, src/views/status/persistence.ts): three failed starts or 10 minutes; a missing or signed-out agent after two or 2 minutes. The same rule hides every other fault Gitoodo retries by itself (the server unreachable, a forge error, a delivery that timed out) until it lasts, and a success ends it at once; only faults the person must fix (a token, an approval, a full disk) show at once.
  • One alert per pause. The alert machine_fault names the machine and the kind (agent_missing, agent_login, no_checkout, start_failed, unreachable), never the error's raw text; the app words it ("Coding agent not found on this computer" plus the next step; for a worker machine its name and the action there) and a click opens the status page. A worker machine that did not answer (unreachable) gives no alert and no status-page problem (#965): it is retried by itself, the work goes elsewhere and Settings shows it offline. A satellite that answered with a reason is never unreachable; the fault also keeps the agent and repository of the failed start, and the status page shows the reason after the machine's name. DispatcherStatus.machine_faults lists the paused machines (kind, since, failures, next retry, readable reason); the status page and the Autopilot card show it.
  • Recovery. start-faults.json in the state folder notes per issue the machine faults of attempts that never reached the agent; a run that reaches it removes the issue, entries go after 30 days. At start and after a machine recovered (10 per push round, after its dispatch, #988), every issue that is stalled in a repository the dispatcher may write to and noted there goes back to ready (Flag::Restore: the classifier reads it fresh, posts a short note marked <!-- gitoodo:auto --> and swaps the labels). The first time the file is filled from the dispatcher's own run log (run.end with start_failed and no worker.run of the issue), so issues stalled by an older version come back too.
  • Stalls that no longer hold. Once a minute (10 per look, after the push round) every stalled issue of a writable repository whose recorded or inferred cause no longer holds (core stall::resolved) goes back to ready the same way, with its own note (Flag::Resolved, recovery::Note::Resolved): a stall at a start dialog (folder trust, the permission-mode confirmation, a sign-in) from before stall::START_DIALOGS_FIXED, since when such a run pauses its machine instead, and a refused lease (lease_refused) once this dispatcher's lease file no longer holds the issue. Logged as dispatch.stall_resolved. A claim never takes an issue whose working copy a lease still holds, and a lease of a run of this dispatcher that refuses a claim anyway is a wait (dispatch.lease_wait, the issue goes back into the queue), never a stall (#1493). Every other cause would repeat or needs a person and stays.
  • Failed checks. When the checks of a delivered pull request fail and the worker is restarted for it, the dispatcher notes the failed checks (names, the forge's short text, run pages) in failed-checks.json in the state folder; the new worker's brief lists them under "Failed checks of pull request #n" with what to do (and gitoodo worker context repeats them as failed_checks), so it fixes them or asks instead of delivering the same commit again. For up to 5 failed checks, required ones first, the dispatcher also reads the end of the job's log through the forge API (Forgejo/Gitea, GitHub, GitLab); the context carries it redacted and fenced as untrusted data in failed_checks.logs (see docs/security.md), and Gitoodo's own log never gets its text. Without read access or a log, the note stays as before. A merge drops the note.
  • Review feedback. See "Review feedback" below: changes a trusted reviewer asks for restart the worker on its branch like failed checks do, without using up its restarts.

Worker launch per agent#

The agent the worker distribution picks for the start (see "Usage limits") decides the command line; the permission flags follow the repo's worker mode (docs/security.md). Every worker runs in its PTY with GITOODO_ISSUE and a full-colour terminal.

  • Claude Code: the interactive session, claude <permission flags> --settings <json> [--model m] <prompt>. The settings add the status line and the Stop/StopFailure hooks, each calling gitoodo hook <event>.
  • Codex (#934): the interactive terminal UI too, so the session shows Codex's own screen and its input line (instruct, hold, a typing viewer): codex --no-daemon <permission flags> [-c notices off] --enable hooks --dangerously-bypass-hook-trust -c hooks.<Event>=… [--model m] -- <prompt>. --no-daemon keeps each session off the shared background server, which would hand it the environment and hooks of the first session. The hooks are session settings, nothing is written to ~/.codex: Stop reports stop, UserPromptSubmit and PostToolUse report activity. The host that starts the process adds the worktree's folder trust as -c projects={"<worktree>"={trust_level=…}} (as given and resolved), so Codex's trust menu never swallows the first input. The worker starts from the clean environment (no API keys). Codex on Windows runs hook commands through PowerShell, so there the program is a bare path when it holds only letters, digits and path characters, and & '<path>' otherwise (hook_cli::codex_word); a quoted path alone is only a string to PowerShell, and every hook exited with 1. Claude Code's hooks keep the POSIX quoting.
  • Gemini CLI: headless, gemini --yolo [--sandbox …] [--policy …] [-e none --allowed-mcp-server-names …] [--model m] -p <prompt>; it exits when done. The prompt comes last, after every option that takes several values ("What a worker loads").

A satellite gets the same arguments; it resolves its own codex or gemini (acp::worker_binary) and adds the folder trust for its own path.

What a worker loads#

A worker does one issue in one worktree. Everything an agent loads at its start is sent with every model call of the session, so the user's personal setup (dozens of skills and slash commands, plugins, MCP servers with their tool lists, memory) costs tokens on every turn and adds tools the issue does not need. Workers therefore start lean (agent::lean); the measured start context of a one-line task dropped by about a third for Claude Code (9,538 → 6,466 tokens, 18 → 10 tools) and a quarter for Codex (16,157 → 11,908 tokens).

The name is the one in the agent's own configuration. Servers a repository defines in its own .mcp.json or .codex/config.toml count like the others for Claude Code and stay untouched for Codex.

Sub-agents (#952): unless the repo setting worker_sub_agents is on (Settings → repo options "Workers may use sub-agents", default off), Claude Code gets --disallowed-tools Agent (before --settings, so the option's values end there and never swallow the prompt) and Codex -c features.multi_agent=false -c features.multi_agent_v2=false -c agents.enabled=false (the last one also drops Codex's multi-agent role text from the instructions, #1554) and Gemini CLI --policy ~/.gemini/policies --policy <state>/gemini-worker-policy.toml (#1555). The policy denies invoke_agent and the built-in agents' names in every mode at the user tier, above the yolo allow-all of the default tier; a denied tool leaves the model's tool list, and the system prompt's sub-agent section goes with it. A --policy replaces Gemini CLI's own user policy folder instead of adding to it, so the dispatcher sends that folder (~/.gemini/policies, the marker) and the host that starts the worker adds the file it writes into its state folder after it; an older host passes the folder alone, so the user's own policy folder loads as before (only policyPaths in its Gemini settings stay unread there until it is updated). Where the user's or the system's Gemini settings name their own policyPaths (which a --policy would replace too), or the file cannot be written, the host drops the pair and the worker starts as before. The prompt tells the worker not to start other agent sessions. Every 15 seconds the dispatcher (and each satellite for its own workers, told by sub_agents in the spawn request) lists the processes and looks for claude, codex or gemini below an issue worker's agent process (nested_agents::nested, pure over (pid, ppid, name) records; the worker's own agent and its same-agent helper processes do not count). A find is logged once as dispatch.nested_agent and, with the setting off, ended each round it is still there (docs/security.md).

Usage of sub-agents needs no extra counting: the usage Gitoodo shows is the login's limit windows (status line, usage endpoint, Codex limits read), and a sub-agent runs under the same login, so its consumption is already in them.

How a run ends: a turn end (Stop) and activity are signs of life for the hang policy. A run ends by gitoodo ask (parked), gitoodo worker split, gitoodo worker blocked, an exit of the agent (with or without a pull request, see above), stop/cancel, or the hang policy.

A turn end without a result. An issue worker whose turn ends (Stop, Claude Code and Codex alike) before it delivered, asked, split or recorded a dependency is not working any more, it waits. 30 seconds later, unless a tool call or a new turn came in between, the dispatcher looks at it:

  • Stopped at its usage limit (a StopFailure, a lock of its login, a Codex report that says blocked) with the reset at most 30 minutes away (LIMIT_HOLD_SECS) or not known: it keeps its slot, the login is locked until the reset (a guessed lock lasts 5 minutes) and continue follows then. Freeing the slot without a known reset would only start the same agent on the issue again at the same limit.
  • Someone typed into the session in the last 10 minutes or left unsent text in it: the worker is theirs. It is listed idle (the tile says "Idle, waits for your reply") until it draws again.
  • Its screen shows its own background work still running (a count in the agent's turn-end line or footer: "2 shells, 1 monitor still running", "1 shell still running", "⏵⏵ bypass permissions on · 2 shells", "1 background terminal running"; core stall::background_work). The footer counts also while the agent is busy again after one of its shells finished, when the turn-end line is gone: it ended its turn to wait for it and goes on by itself once it finishes. Nothing happens (dispatch.worker_background), no reminder, no end. While the screen shows it, the silence counts as a sign of life for the hang policy and the silence look below, for at most an hour from the first sighting (BACKGROUND_HOLD_MS); a background command that never ends does not hold the slot longer. Satellites do the same for their workers.
  • Stopped at its usage limit with the reset further off (a used-up week): the run ends to free its slot (dispatch.worker_limit_idle, then dispatch.worker_limit_released with the reset). Once the process is gone its work is saved (below), the lease goes and the issue goes back into the queue (Requeue, the run's result is limited). That agent is held off the issue until the reset, on every machine (a hold of this dispatcher by issue and agent, kept in memory; without a known reset 30 minutes, doubling per release up to 8 hours); another agent of the pool may take it up from the branch.
  • Otherwise the dispatcher types one reminder (NUDGE_LINE): finish with gitoodo worker pr, gitoodo ask, gitoodo worker split or gitoodo worker blocked, or go on. A second such turn end of the same process ends it (dispatch.worker_idle): once the process is gone its work is saved and the issue stalls with no_result ("3 runs without a result" or "Runs without a result", which "Solve" shows), so an idle agent neither sits until the hang policy nor is restarted into the same idle prompt.
  • A turn that ends naming exactly one other issue of the repository as blocking ("Blocked by #1789, no PR", "wartet auf #12") without recording it gets a reminder with the exact command instead (gitoodo worker blocked --on #1789 …). If the second turn end still names it, the dispatcher records it itself (the shared record_dependency, below) and the run ends as blocked, not as a stall. Several named issues, or only closed ones, record nothing.

Silence without a turn end. An interactive agent (Claude Code, Codex) that draws nothing and sends no hook for 5 minutes (Timing::idle_silence_ticks) may sit at its prompt without its Stop having arrived (the hook did not run, or went to a dispatcher that is gone), or may wait for a long silent command. It gets the same look (dispatch.worker_quiet), but at most the reminder, once per process: silence never ends a run or frees its slot. After the reminder only a real turn end ends it as above; otherwise the hang policy decides with its own timeout (dispatch.hang_timeout_seconds), as before.

Every step counts as a sign of life, so a worker still idle afterwards is looked at again after the next silence. Saving the work: what the worker had not committed becomes one WIP: commit (hooks and signing skipped) on the assigned branch, and the branch is pushed with the account; the worktree stays. Changed tracked files go in; new files up to 1 MiB too, each logged (dispatch.wip_new_files), larger ones (builds, dumps) stay in the worktree. New files named like a secret never go in: .env*, SSH keys, .netrc and similar, credentials.json, key and store formats (.pem, .key, .p12, .jks, .tfstate and so on), and configuration or data files (.json, .yaml, .txt, no extension and so on) whose name holds "secret", "token", "password", "credential" or "private"; source such as tokenizer.rs goes in. Such a file makes the save partial (dispatch.wip_withheld): the rest is pushed, but the issue stalls with no_result and the stall says how many files stayed in the worktree, since a run elsewhere would lack them. No commit is made when the worktree is not on the assigned branch or in the middle of a rebase, merge, cherry-pick or revert. A failure is logged (dispatch.idle_save_failed, dispatch.idle_push_failed) and the work stays in the worktree; the issue then stalls with no_result even at the limit, so no run elsewhere starts without the work. A worker that changed nothing beyond the base has nothing to save. A move for a test desktop is refused for the same files, since the worktree goes after the move. On a satellite the service saves and delivers the work itself (see docs/orchestrator/satellites.md).

The run file keeps what an idle agent will not send again: a pending turn end from a Stop (turn_ended), the reminder (nudged), the stop at the limit (limited) and when a person last typed into the session (typed_at). A dispatcher that takes the worker over (#965) gives a pending turn end a full grace from its own start, never reminds twice, keeps a limited worker waiting for its continue and leaves a session someone talks to theirs.

While its login is stopped at the limit (a lock or a blocked Codex report) a worker shows as paused at the limit with the reset, never as working, whether or not a hook said so. Figures alone, a window that reads 100 %, neither pause nor release a worker: they may be stale or estimated, or extra usage goes on past them. The hang policy excuses an issue worker's silence only while it waits for the reset that stopped it (continue follows); a threshold, a full window or stale figures no longer excuse it, so an idle worker cannot hold its slot unseen.

An automation session ends at its first Stop with success. A Codex issue worker also ends with the turn that opened its pull request: after a successful gitoodo worker pr its next Stop ends the process and the exit counts as success, so the merge gate starts at once, as it did when the headless run exited there. A Claude Code session stays open after delivery until the hang policy ends it (unchanged). Without the Stop hook (Codex held it back) a Codex worker gets the reminder after the 5-minute silence above and is otherwise left to the hang policy. A restart (hang, failed checks, steering) starts a fresh session with the brief; no earlier session is resumed.

Usage limits: Claude Code reports a hit limit through StopFailure and its status line. Codex has neither: each Stop of a Codex worker asks for a fresh Codex limits read on the next usage tick (at most once a minute, not while that read backs off), next to the regular poll and the read after a failed exit. A report that says blocked marks the running Codex workers limited; the first report that no longer does types continue into them, like the reset of a Claude lock. A worker that is idle at a limit whose reset is known to be far off does not wait for it: it frees its slot (see "A turn end without a result").

The agent's own limit notice (all three agents). An interactive agent at its limit says so in its terminal and then sits at its prompt; Codex sends no hook for it and keeps redrawing its background-terminal line, so neither a hook nor a silence ever came, and a run read "working" for as long as nobody looked. Every 10 ticks (LIMIT_LOOK_TICKS, about 10 s) the dispatcher, and the satellite for its own workers, reads the visible rows of each worker's screen, row by row also where the agent (or the Windows console) pads them to the full width, for the agent's own notice at the start of a line (agent::limit_notice, real screens as test fixtures): Codex "You've hit your usage limit … try again at Nov 24th, 2026 2:39 PM", Claude Code "You've hit your 5-hour limit · resets 11:50am (Europe/Berlin)" or "Usage limit reached · … resets …", Gemini CLI "Usage limit reached for all Pro models. Access resets at 3:05 PM PST." or its quota API Error. The same row-by-row reading serves the look for a start dialog the agent cannot pass alone and for its own background work, and blanks at the ends of padded rows never push a dialog out of the part of the screen that is read. The reset is read as the agent wrote it, in the named zone or the machine's own; a duration ("try again in 2 hours") counts from now. A new notice locks that login until the reset (never past 8 days, cached across restarts like any lock), so no worker or resolver starts into it on any machine with that login, marks the run limited (its tile reads "Paused until Tue 14:39", without a running time) and counts as its turn's end: a near reset keeps it for continue, a far one ends the run, saves its work on the branch and sends the issue back into the queue for an agent with usage left. The same notice counts once; a continue after the reset is not undone by the line still on screen. Gemini CLI may retry or switch to a smaller model after a quota error, so its notice stops a run only once it is silent for 20 ticks; the login is held at once. A resolver run ends at its notice at once (it holds no slot until a reset) and waits in the resolver's queue for usage.

Never "hung" at the limit. Before the watchdog ends a silent run as hung, it reads that run's last screen, on a worker machine through a watch-only attach (it never types and never sizes the terminal): a run that sits at its agent's limit notice, or at a limit its hook reported, ends as limited instead (dispatch.hung_at_limit), which catches a notice the live look missed or a worker machine that does not look for it itself yet. Its login is locked until the reset the notice names (an hour when it names none; a time without a zone is the worker machine's, which its status reports): by the login, so on every machine with it, this computer's own tracker included; without a known login only on that machine. An issue goes back into the queue, a resolver attempt waits for usage; neither counts as a failed attempt.

Typing into a worker: every line Gitoodo types into an agent (the reminders, continue, the build-output reminders, instructions from the overview and to all sessions at once, pause and resume) goes one way (submit::type_line): the text first (for Codex as one bracketed paste, ESC [200~ … ESC [201~), the Enter as its own write 250 ms later, because the agents take a long, fast burst of keys as a paste and an Enter inside it as part of the paste; the line then stayed unsent in the input box. After the Enter the dispatcher reads the worker's screen: while its input box (the rows from the last prompt mark down to the box's border) still holds the line, it presses Enter again, after 1 s and 2 s (dispatch.submit_retry); still there after 4 s more, it logs dispatch.submit_failed (warn). An instruction for a worker on a satellite goes over the bridge as text and a separate Enter, without the check.

A Gitoodo line that still sits unsent in the input box from earlier (an older build pressed its Enter inside the paste, or every retry failed) is sent off on its own (submit::own_line, dispatch.stale_line_submitted). It is recognised only by the known starts of Gitoodo's own lines: the reminders after a turn without a result (local and satellite), the one about a named but unrecorded dependency, the build-output reminders, and a box holding nothing but continue. Pause and resume are left out: whether they still apply depends on the pause set since. The dispatcher (and a satellite for its own workers) looks at the input box once after it took the worker over or started it, and at every turn end due for its step, and presses Enter through the same path with its screen check, only while the agent sits idle at its prompt (silent for 5 ticks; a busy agent redraws its spinner every second). A busy agent is left alone and looked at again at its next turn end: an Enter mid-turn would hand a working agent "your turn ended without a result", and its effect can only be checked on the screen once the agent is back at its prompt. Never while a person talks to it or left text in the input line (typed_line, which counts only a viewer's keys, so a stale Gitoodo line never counts as a person typing), while its login is at the usage limit or while it waits for a person; its own background work does not hold the Enter back. The Enter uses up the turn end, as the agent starts a new turn. A new line typed on top of such a stale line (type_line) presses its Enter first and types the new text a second later, so the two are never glued together and a later instruction is never held back.

Build output (#970): the brief tells every worker to remove regenerable, git-ignored build output it no longer needs and never sources, tracked files or caches outside its worktree. The storage measurement also measures the running workers' worktrees; a worker with 5 GiB or more, a quarter of the free space, or (while the disk runs low) 512 MiB or more gets one reminder line with the size and its largest folders. It goes through the same channel as the other reminders, only at a real turn end (its Stop 5 ticks ago and silent since) and never while its login is at the limit, a person typed or left text, it waits for background work or for a person; the turn end is used up. At most every 45 minutes, every 10 while the disk runs low and keeps filling. Below the warning level itself, an idle worker (at its usage limit or waiting for a person, silent a minute, no background work) loses its build output directly and is told at its next turn end. When the disk reaches the level that holds new workers back, the automatic removal of idle and merged worktrees' build output runs first and the warning in the app waits for it (see docs/orchestrator/hygiene.md, "Build output" and "Build output of running workers"). Satellite workers are not measured yet.

Live state of a session (#1427)#

A tile says what the agent in its session does right now, not what the issue's labels said when the classifier last looked (they lag behind: a worker answering a question still showed "Waiting for an answer"). WorkerInfo.live (crates/core/src/agent/live.rs, in list and in a worker machine's fleet facts) holds the state, the time of its last signal (unix s on the worker's machine), the time of the last hook and, while a tool runs, since when:

  • Hooks decide. Claude Code workers get UserPromptSubmit → activity, PreToolUse → tool-start, PostToolUse → tool-end, Notification (permission prompt or question dialog) → needs-you, besides Stop/StopFailure; Codex workers get UserPromptSubmit and PostToolUse → activity and, where the machine's Codex is at least 0.117.0 (the first with PreToolUse; codex --version, read once per machine and program when a worker starts, worker.codex_version), PreToolUse → tool-start (#1441). An older Codex or one whose version cannot be read starts with the other hooks only. A PreToolUse of the agent's question tool means it needs a person.
  • working from a prompt or a tool until the turn ends; between a tool's start and its end it stays working however long the command takes (the tooltip says "A command has been running for …"). A permission request and a question are one state, needs_you ("Needs you"). stop/stop-failure give done, shown once it stood 1.5 s (DONE_SETTLE_MS, #1440): an agent that goes on at once (a continue, a queued prompt) never flickers to "Turn ended" and back. The status line only refreshes the signal time.
  • Without hooks the terminal stands in: the agent's status sequence (OSC 7501, state=working, blocked with kind=permission|question, idle|done|error) and its window title (a braille spinner or ✦ → working, ✋ or "action required/permission/waiting" → needs you, ✳/◇ → done), read from the PTY by the dispatcher and the worker machine when they list their workers. It counts only while no tool is open and no hook came for 2 minutes (HOOK_TRUST_SECS); the status sequence wins over the title. The tooltip says when the terminal decided.
  • Silence is no signal: a working session with nothing for 30 minutes (SILENT_SECS, SILENT_MS in the app) shows "No signal for …" with a hint to look into the session, never "Waiting".

Order on a tile: paused, usage limit, then the live state (needs_you → asks, working → working or silent), then an idle turn end, then the issue's readiness (a done session whose issue says nothing else shows "Turn ended"). The state is one small mark and a short label (the working mark breathes slowly, still with reduced motion); details are in the tooltip only.

Settings in the app#

Settings → Dispatcher edits the dispatch block of orchestration.json (worker limit, usage threshold, agent programs, clone and worktree folders, projects folders, base branch, default merge style, trusted authors). Every field saves by itself (#935): pickers, switches and the merge style at once, text and number fields after a short pause in typing and when the field is left. Each save reads the stored form again and sends it with only that field changed, so two fields saved in a row never undo each other. The core runs the same validation as the daemon (Config::field_errors) and writes the file only when the value is valid, under the app's config write lock; a refused value is not saved, stays in its field as typed and shows its problem there. Settings without a field in the app (branch prefix, restarts, timeouts) are kept as they are, and their errors are shown at the top.

Leaving the page never drops a typed value (#1321). A value still waiting for its pause saves when the page goes, whichever way it goes, also when the click on the way back leaves the focus in the field. The back link and, side by side, the section list wait for those saves; if a value was refused or a save failed, the page asks inline instead of going: "Stay" keeps every edit and is focused, "Try again" repeats a failed save, "Discard and go back" leaves the file as it is.

A running dispatcher reads the file every round, so changes apply on its next round; without a running dispatcher they apply at its next start. The dispatcher itself never writes orchestration.json. The merge style offers what the core supports; the default is squash. A repository can choose its own style in its own settings (below); the repository's forge settings win: a style it does not allow falls back as described under "Exit with a pull request".

Worker commands#

  • gitoodo ask [--issue <key>] reads a JSON spec from stdin (context (at most 3 lines), questions with text, kind, options, recommendation; optional id, made up when missing, to, name, deadline), renders it in question format v2 (docs/question-format.md) as worker block, posts it as a comment, asks the classifier for needs-human and parks the worker: it is stopped without restart or report until a human answers. The issue defaults to GITOODO_ISSUE, which the dispatcher sets (account/owner/name#n). Before posting it checks that the human can decide from the card alone (#949): a context of at least one sentence, every question ending in ?, a consequence for every option of a choice question. Otherwise it posts nothing and names every problem (question not posted: …), so the worker rewrites the spec. The skill (skill/gitoodo-questions/SKILL.md) shows the spec with a good and a bad example. A spec without to goes where the routing rules say, else to the repo's human, else to the issue's author. Workers never have to guess the shape: the worker prompt (question_render::ask_rule), gitoodo ask --help and every refusal (invalid JSON, an unknown field such as question instead of questions, a vague question) show the fields and the same minimal valid spec (question_render::ASK_EXAMPLE), which a test renders.
  • gitoodo worker follow-up --title <t> --body-file <path|-> [--label <kind>] proposes a follow-up issue for work outside the worker's own issue (spec 8.3, #337). See "Worker follow-up issues".
  • gitoodo worker split --plan <path|-> splits the worker's issue into parts before it writes code (#1012). See "Splitting an issue into parts".
  • gitoodo worker blocked --on <#n[,#m]> --reason <text> says the worker's issue cannot go on before other issues land, whether the issue says so or a human's answer does (the brief tells the worker to record it, never to wait at its prompt: an idle worker is reminded once and then ended). The broker checks the references (#n, repo#n, owner/repo#n, at most 10, not the issue itself, at least one still open), adds a Depends on … line for the missing ones to the issue's description, which the classifier reads as blocked, and posts a short note with the reason ("Waits for #361. …", marked as Gitoodo's own, so it declares nothing itself). Then the run ends as blocked: the lease goes, an untouched worktree goes, and the issue waits in the queue until its dependencies are closed. It is never counted as a restart or a failure. Refusals start with dependency not recorded: and name the problem; satellites refuse for now.
  • gitoodo worker close --summary <text> closes the worker's issue without a pull request: an umbrella once its children delivered what it asks (#1816), and since #1880 any issue whose work needs no change (already done on the base branch, nothing to change). It is refused when the run changed files: the worker's branch on the forge differs from the base branch, or, while the forge cannot say, the worktree has uncommitted changes or commits that change files against origin/<base> (worktree::changes_against). Refusal: issue not closed: your branch or worktree changes files against the base branch; deliver them with gitoodo worker pr, or undo them …. When neither the forge nor the worktree can be read, it is refused as unverified. From this computer through the broker, from a worker machine through its satellite and the main host (the satellite sends its worktree answer as changed in Reply::CloseForward). The brief and the end-of-turn reminder name it, so a worker no longer opens an empty pull request. See "Umbrella issues".
  • gitoodo worker needs --tool <name[,name]> --reason <text> hands the issue back because the machine lacks a command the issue cannot be done without (from this computer through the broker, from a worker machine through its satellite). The run ends as needs_tools without counting as a failure, the issue gets tool:<name> labels and goes to a machine that has the command. Refused for the resolver. See docs/orchestrator/satellites.md, "Commands a worker machine lacks".
  • gitoodo worker needs --desktop <name[,name]> --reason <text> hands the issue over because it needs a test desktop of this Gitoodo that the worker computer it runs on cannot reach (it reaches only its own desktop). The worker commits and runs gitoodo worker push first; the satellite ends it and reports the need with its exit (ExitInfo.needs.desktops). The run ends as needs_desktop without counting as a failure, the issue gets the main host's host: label (replacing any other host: label, so it does not go back to a worker computer) and is queued again; the next run there goes on from the pushed branch and reaches every test desktop over SSH. A worker on the main host is not handed over: the broker refuses and says for each named desktop how to reach it (gitoodo desktop --on NAME) or why it cannot be used now. An older main host ignores desktops, finds neither commands nor data and sends the issue to itself as well (needs_here). See "Test desktop for desktop checks".
  • gitoodo worker resolved [--requeue | --obsolete <sha>] --reason <text> is the resolver's outcome for a stuck issue (docs/orchestrator/resolver.md): accepted only from the resolver run itself, through the broker or, on a worker machine, through its satellite, which hands it over with the run's end. It records the outcome and ends the run; the dispatcher then puts the issue back to ready with a note (--requeue: the blocker passed and a normal worker goes on).

Dependencies#

One dependency syntax, several sources. An issue waits (the dispatcher passes it over, the classifier marks it blocked until every dependency is closed, then ready) for:

  • Depends on #N lines (and their synonyms) in its description and in comments people wrote;
  • the forge's own dependency feature: Forgejo and Gitea issue dependencies (GET /repos/{owner}/{repo}/issues/{n}/dependencies), GitHub "blocked by" (…/issues/{n}/dependencies/blocked_by) and GitLab links of type "is blocked by" (/projects/:id/issues/:iid/links). A forge or repository without the feature (404, 403) has none. Inside a classifier poll the answer is reused while the issue is unchanged, for at most 30 minutes (adding a dependency changes the issue); the dispatcher's pick always reads it fresh.

Whoever finds a new dependency records it through one core function, orchestration::blocked::record_dependency(adapter, repo, number, refs, reason, source): it refuses when every named issue is closed or the issue names itself, adds a Depends on line for the missing ones to the description, with the reason after them (Depends on #12 (reason: …)), and posts a note saying who found it (Source::Worker for gitoodo worker blocked, WorkerText for a worker that only named it, Answer for a person's answer, Diagnosis for the diagnosis of a stuck issue, Triage for triage, triage.md). It touches no labels.

A worker's gitoodo worker context lists every dependency of its issue under dependencies, each with whether it is still open and why (#1605, dependencies::explain): the text after the reference on a dependency line (Wartet auf: #205 (Leit-Issue, Entscheid 5a), (reason: …), Grund: …), else the reason Gitoodo's note quoted, else the paragraph of the newest comment of a trusted person that names it, else "set on the forge without a reason on the issue". The rule beside it says that a closed dependency no longer holds the issue back and that a worker never asks a person about one.

  • Answers that defer. When a question's answer ends the wait and the chosen option, a yes to a question, a text answer or the reply itself says "defer until #N" in one sentence ("Zurückstellen, bis #1512 in dev ist", "erst nach #12", "postpone until #12", the app's languages), #N is recorded (Source::Answer) and the issue goes to blocked instead of ready (orchestrator.answer_deferred).
  • Merged, the issue kept open. Forgejo and Gitea refuse to close an issue with open dependencies (412 cannot close this issue because it still has open dependencies), also right after its pull request was merged. That is no failed merge: the outcome is MergedWaiting (also when watching an auto-merge), the worktree is cleaned up as after any merge, a note "Merged, waits for #N" goes on the issue (dispatch.merged_waiting), and the run completes with the result merged-waiting, which moves the issue to blocked instead of review. Once its dependencies are closed the classifier closes it (orchestrator.merged_closed) instead of making it ready; a later lease (a person reopened and readied it) ends that.
  • Older pull requests for the same issue. After every merge (also MergedWaiting and an auto-merge seen as merged) the dispatcher closes the other open pull requests of the repo that name the issue (Closes #N), each with a note "Superseded" pointing at the merged one, so stale attempts with red checks or conflicts no longer wait for review (#1702, dispatch.superseded_closed). A pull request that also names another issue that is still open (or cannot be read) stays; branches are never deleted. The note, like the dispatcher's other notes on the forge (conflict, merged and waiting, an issue that waits, split and follow-up), is written in the language on the forge for the issue (#1890, note_texts.rs).
  • gitoodo hook status-line|stop|stop-failure|activity|tool-start|tool-end|needs-you reports a Claude Code or Codex hook to the dispatcher; silent when none runs. It reads (and drops) the hook's JSON input (tool-start only looks at the tool's name), prints nothing and never fails the hook. The live-state events (activity, tool-*, needs-you) give up after 2 s and are limited to 5 s in the settings, so a busy host never holds up the agent.

Attach protocol#

Unix socket dispatcher.sock in the private runtime folder (dispatcher_rpc::socket_path), mode 0600 in a 0700 folder; newline-delimited JSON (crates/core/src/dispatcher_rpc.rs). On Windows the same protocol runs over the named pipe \\.\pipe\gitoodo-dispatcher-<user> (dispatcher_rpc::pipe_name): its DACL grants access to the current user's SID only, remote clients are rejected and the first instance is created exclusively, so a second dispatcher or a foreign process cannot take the name (#354; the pipe code is the small gitoodo-pipe-security crate, the only place with unsafe). A pipe serves one client per instance, so the dispatcher creates the next instance before it hands over a connection. Named pipes have no half-close: the client detaches by shutting down its write side. A connection starts with one request:

instruct (#883) writes t into the worker's terminal as one line (line breaks become spaces, control characters go, at most 4000 characters) and Enter 250 ms later, so an agent does not read the Enter as part of a paste, checked on the screen like every typed line ("Typing into a worker"). Nothing goes to the forge. The dispatcher counts the keys typing viewers send per worker (characters add, Backspace takes one away, Enter, Ctrl-C and Ctrl-U empty the line, escape sequences change nothing); while that count is above zero a human left unsent text in the agent's input line, and instruct answers error starting with the input line holds unsent text instead of gluing the instruction to it. A started or restarted worker starts with an empty line. For a worker on a satellite the dispatcher opens the satellite's attach stream and sends the line as input frames.

hold (#884) pauses a worker softly: it sends the agent an instruction (the same path as instruct) to finish the step it is on, then stop and wait, and marks the worker held. The worker keeps its process, worktree and lease; while held, quiet is not a hang, so the dispatcher does not restart it. resume sends "continue where you left off" and ends the mark; both answer ok without sending anything when the worker already is in that state. A restart ends the mark. cancel ends the worker and puts the issue back into the queue: the lease is released without the needs-human flag, so the next free slot picks the issue up again with a fresh agent. Unlike stop, nobody has to decide first.

After attach the dispatcher sends a size frame, then output frames (hex bytes; first the worker's current screen, then live output) and a final exit frame. The current screen comes from a terminal emulator that every output byte of the worker goes through (crates/cli/src/screen.rs): the bytes that draw the screen at that size, with its cursor and input modes, preceded by up to 1000 lines that scrolled off above it. A raw output tail would not do: agents redraw only the cells that change (spinner, timer, token count) by moving the cursor, so after a long run the tail holds nothing but such partial redraws, and a viewer that attaches then (a tile, a dispatcher back from an update) would show a few fragments at scattered places. When the worker is restarted while a viewer is attached (hang, failed checks, steering), or a viewer falls behind, the stream does not end: it goes on after the size and a terminal reset (ESC c) with the current screen, so the exit frame always means the worker is really gone. The worker host speaks the same protocol to the dispatcher, so a dispatcher that attaches again after an update builds the same screen. A size frame also comes whenever the worker's terminal changes size, at exactly its place in the output (#905): output and size changes go through one ordered stream of the host (crates/cli/src/pty_host.rs, Chunk): the new size is recorded under the lock that orders the output, before the local terminal is resized (outside that lock, so a console that waits until its output is read cannot deadlock the reader), so the agent's repaint for the new size always follows the size frame; a resize the terminal refuses puts the old size back. Ahead of a size change the app sends the output the redaction holds back but its last two words, which may begin a secret and wait for the rest. A viewer draws at the size of the last size frame it got; output after it is drawn for that size. The client may send input frames (hex bytes) at any time; they are written to the worker's terminal, and {"frame":"resize","cols":c,"rows":r} frames, which set the size of the worker's terminal (zero sizes are ignored). Bytes of the terminal are opaque, so a client can render them with any terminal emulator. Closing the connection detaches; the worker keeps running.

Human control (#568)#

The dispatcher reads control.json on every push tick (spec §5.7). While the global switch is paused it starts no worker and merges nothing, and it stops the running ones (lease released, in-progress removed, no needs-human). Workers of a repo that is no longer active are stopped the same way. A held PR keeps waiting without using a merge attempt, a vetoed PR is flagged needs-human and never merged. Questions, stalls, failed merges and vetoes are written to activity/alerts.jsonl for the app's desktop notifications; each alert names its account, repository and item, so a click opens it (#939, docs/counters.md), and a failed merge carries its cause (including checks and attempts), which the app words in the UI language.

Emergency stop#

"Alles anhalten" stops all orchestration at once. It is halted in orchestration.json (gitoodo_core::orchestration::halt), set from the stop control in the title bar, the tray menu, Cmd/Ctrl+Shift+H or gitoodo stop-all, and lifted with "Fortsetzen" or gitoodo resume. While halted:

  • the dispatcher starts no worker and no automation, merges nothing, updates no branch and skips the cleanup round; running workers are stopped like a pause above (lease released, in-progress removed so the issue is ready again, worktree kept);
  • the classifier writes nothing (labels, comments, milestones, approvals); reading and the read model go on, so the app keeps showing everything;
  • the repos keep their own states. Resuming does not switch anything on: every repo continues as it was (active, paused, observed).

The older global pause (paused in control.json) still counts as halted and is moved into halted at the next start.

Across restarts (#925): the stop keeps its state. What ran when the app ended runs again after a restart of the app, the services or the machine; what was halted stays halted until the user resumes. A start only folds the older global pause into halted and drops the former start-mode fields (on_start, start_session) from the file; files that still have them load as before. A missing orchestration.json (fresh install) is not created.

Parallel writers (#1382): the app, the services and the command line change orchestration.json under one exclusive advisory lock on orchestration.json.lock (orchestration::config_write): a stop, a resume or a repo switch loads, changes and saves the file while holding it (Config::update; the app's write guard takes it too), and every write goes through a temp file of its own, so parallel gitoodo stop-all/resume calls neither lose a change nor leave broken JSON. A writer that waited 10 s for another process writes nothing and says to try again. Each save keeps what it wrote as orchestration.json.bak; when the file was broken by hand, gitoodo doctor and a failing stop-all/resume name gitoodo restore-config, which puts that last valid copy back and keeps the broken file as orchestration.json.corrupt.

dispatch.max_workers defaults to 2 when the file does not set it; the dispatcher never runs more agents than that over all hosts. It is a hard upper bound for everything that runs an agent for the orchestrator (#1531): workers, resolver runs, automations, restarts and resumes, here and on every worker machine together. Resolver runs count in it like any run: of these slots the two system slots go first to them while they wait, never on top; triage calls take none (docs/orchestrator/resolver.md, "System slots"), and to the workers otherwise.

One gate (dispatch::slots::Ledger, Dispatcher::reserve_slot): every start reserves its slot before anything else happens (before the classifier's claim for a new issue, before the lease of a resolver run, before a restart, a resume after a machine's update or a move to another desktop) and holds it until the run shows in the running set or the start failed; dropping the reservation frees the slot, exactly once. The count is per issue key over the runs here, the runs on the worker machines (their last report and the starts they accepted since), the runs taken over after a restart of the dispatcher, the workers ended for their machine's update that resume after it (at most an hour), and the reservations under way; the check and the reservation happen under one lock. A start for a key that already runs (a restart in place) takes no second slot. A refused start logs dispatch.slot_refused and waits: a new issue stays in the queue, a restart waits among the deferred restarts (dispatch.capacity_wait, reason global_limit), a resume waits for the next round.

A lowered limit stops nothing: the runs going on finish (a restart in place keeps its slot) and no new one starts until the count is below the limit. The overview's "Worker slots" tile then shows the count without "of m" and says so ("limit 8: no new ones until some finish").

Placing and starting (#1423, dispatcher_launch.rs): a push round places its starts one after the other (slot reserved, host chosen, issue claimed), but runs the starts themselves (copy, worktree, worker) side by side, so a second ready issue no longer waits in queue.wait for the first one's clone.ensure and worker.spawn on a slow machine. A start under way counts on its machine from its reservation on, so the next placement of the round sees that machine as fuller. At most three starts run on one machine at a time; a further one waits for its turn there (its queue.wait includes that turn). Starts on the same copy of a repository take turns: on this machine per copy folder (fetch and worktree cut), on a worker machine per machine and repository (the copy sent from here through the worktree cut in its spawn). Each start handles its own failure; a failed start never stops the others.

Workers per machine (#967)#

A machine runs at most capacity = min(automatic, max_workers) workers at once: automatic is one per dispatch.cores_per_worker cores (at least one), max_workers the user's own maximum for that machine (local_host.max_workers for this one, hosts[].max_workers for a satellite; absent = automatic; set in Settings › Worker machines, docs/orchestrator/satellites.md).

  • Host choice: a machine at its capacity takes no new worker; among the others the lowest load running / capacity wins, so a capped machine counts as fuller than its cores suggest.
  • Fair share: the share splits the slots the machines offer together: the sum of the capacities of this machine and every satellite that answers, never more than max_workers (dispatch::host::slots). Capped machines therefore never promise a repository slots no machine can fill.
  • Wait reason: an issue pinned to a machine (host:) that is full because of its own maximum, not its cores, waits with reason host_limit; host-wait.json and the read model carry the machine and the number (limit: {host, max}, this machine by its own name), the log says "studio runs at most 2 at once", and the board says "Waits for “studio”: it already runs as many workers as you set for this machine (2)." with the link to the worker machines. A machine full by its cores keeps at_capacity. The wait ends by itself and is never notified.

Worker model per machine#

The model list and recommendation in the settings come from this computer's agent CLI. A worker machine may run an older CLI, or a login whose plan lacks a model; Codex there then refuses the model at the first request ("The model is not supported when using Codex with a ChatGPT account", model_not_found) and the worker would sit at its input line. Each start therefore takes the model that machine offers (agent::machine_model, dispatcher_models.rs).

  • What a machine offers. A satellite reads its own Codex list with the same reader as this computer (version, model ids, recommendation) once the main host first asks it for usage and every 10 minutes after, and reports it in report.agents (docs/orchestrator/satellites.md). This computer uses its own list.
  • **Before the start (machine_model::pick).** Codex keeps the chosen model where the machine lists it; otherwise it takes that machine's recommendation, and without one the agent's own default (no --model). Claude Code and Gemini CLI take aliases every version knows, so they keep the chosen one.
  • Older satellites. A satellite that reports no list (an older build, or its CLI could not be asked) keeps the chosen id only when its Codex is at least as new as the version this computer's list came from (older_version otherwise); with no version at all it runs the agent's default (unknown). The default never names a model the machine lacks.
  • During the run (safety net). A Codex or Claude Code worker whose screen shows its agent refusing the model (the error line run through the triage classifier, screen_refusal) is read once per silence: on this computer after three quiet ticks, on a satellite with its silence check. The worker ends, the run closes as model_refused, and it starts once more on the same machine with the fallback; the restart count stays. Nobody is asked. The refused model is passed over for that machine and agent for 6 hours, so new starts there skip it at once. Gemini CLI runs headless and is not read this way.
  • Refused again. A second refusal for the same issue (or a refusal of the agent's default) starts nothing more: the machine gets a visible start_failed fault naming the model problem and is paused until resumed, like any failed start.
  • Shown and logged. The dispatcher status carries machine_models (machine, agent, chosen, what it runs instead, why, version); Settings › Dispatcher › Worker agents shows one line per machine under the agent ("Codex on winpc doesn't offer this model. Its workers there run GPT-6-Astra."). Every changed choice is logged as dispatch.model_adjusted, the safety net as dispatch.model_refused, dispatch.model_fallback and dispatch.model_fallback_failed (docs/logging.md).

Test desktop for desktop checks (#986, #995)#

Workers that check native apps use Agent Desktop (permissions). Every machine whose Agent Desktop is ready and whose desktop use is not off is a test desktop for its platform, so a cross-platform app is checked on each platform it targets. When a worker has at least one test desktop, its brief gets a paragraph (brief::desktop_rule): the desktops with name and platform, a check on every platform the repository or the issue targets (its own machine first), --on NAME for another machine, every Agent Desktop command as gitoodo desktop [--on NAME] <command> ... (never the agent-desktop program directly), gitoodo desktop-turn [--on NAME] "WHAT" to wait for a desktop, one desktop command at a time, gitoodo desktop-turn [--on NAME] --done before long builds or test runs, and gitoodo ask instead of guessing when a platform, a permission or the app is missing. The paragraph also says what to do when the browser automation a worker would use does not work on its machine (#2045: the browser, its automation extension, a sign-in or a token is missing there): that is no reason to stop and no missing command for gitoodo worker needs --tool; the worker drives the browser through Agent Desktop instead and never copies browser profiles, cookies or tokens from another computer. Workers start without skills ("What a worker loads"), so the paragraph points to the guide Agent Desktop ships: gitoodo desktop skills list and gitoodo desktop skills get NAME print the version-matched skills (the same text the assistants' skill folders hold for the user's own sessions).

  • Setting, per machine: desktop on local_host and on each hosts[] entry of orchestration.json (Settings › Worker machines › "Desktop tests" on each machine's card): {"mode": "off"} (not allowed), {"mode": "when_idle", "idle_seconds": N} (30–3600, the default with 120 s, not written) or {"mode": "always"} (also while someone works there, for a dedicated test machine). The field shows on this machine's card when Agent Desktop can run here (not in the store build) and on a worker computer's card once its setup reported Agent Desktop. The former single test_desktop block (target, while_in_use, idle_seconds) is still read: on load its values move to the named machine (absent target = this machine; a name that is no longer a machine is dropped), and it is never written again.
  • Which desktops a worker gets (dispatcher::usable_desktops): for a worker on this machine, this machine when Agent Desktop is installed here, and every worker computer whose last setup (desktop-rollout.json in the config folder) found an Agent Desktop version, that answers the dispatcher (its reported system is the platform) and is not still being set up. A worker computer whose permission still waits for the person there is listed with that note, so the worker asks instead of failing. A worker on a worker computer gets only that computer's own desktop: the worker computer knows neither the other machines nor their SSH sign-in (keys and kept passwords stay on the machine running the dispatcher), so it cannot reach another desktop. The other test desktops of this Gitoodo (this machine's when allowed and installed, every other ready worker computer, also one that does not answer right now, with the system its last check noted) are named to it apart as unreachable (dispatcher::unreachable_desktops): its brief lists them, says they are registered and set up, that it never asks a person to register one, and that it hands the issue over with gitoodo worker needs --desktop NAME (see "Worker commands"). gitoodo desktop --on NAME and gitoodo desktop-turn --on NAME for such a desktop never use it and refuse with that hand-over instead of "not a test desktop for this worker"; on a worker computer whose dispatcher is older (no such list) an unknown name gets the same hint. The list is fixed when the worker starts; gitoodo desktop --on NAME and gitoodo desktop-turn --on NAME in a worker on this machine look a name missing from it up in the current settings (#1159): a worker computer that did not answer at the start, or whose desktop tests were allowed or set up later, is then used with the system its last check noted (desktop use not off, Agent Desktop found by its last setup, not being set up); otherwise the refusal says why.
  • Worker environment: GITOODO_DESKTOP_SESSION (Gitoodo <repo>#<n>, so a waiting worker names the holder), GITOODO_DESKTOPS (JSON list of {name, platform, guard, own, needs_permission}; guard is the idle threshold in seconds, 0 = any time; own is the machine the worker runs on, used without --on), for a worker on a worker computer GITOODO_DESKTOPS_ELSEWHERE ({here, desktops}: the machine it runs on and the test desktops it cannot reach, in the same form; a separate variable, so an older gitoodo there never takes one for usable) and, for a worker on this machine, GITOODO_DESKTOP_WAIT (<state>/desktop-wait/<worker key>.json).
  • Turns (crates/core/src/desktop_turn.rs): one session holds a desktop at a time, recorded in <state>/desktop-wait/local.lease under a file lock on the machine that owns the desktop. A worker there takes it directly; a worker reaching it with --on runs gitoodo desktop-turn --remote <base64 JSON> there over SSH (the same link gitoodo desktop uses), so both meet at the same lease and never act side by side. The first gitoodo desktop command of a worker takes the desktop when it is free; gitoodo desktop-turn "WHAT" polls for up to 100 s (every 2 s here, every 5 s over SSH) and prints OK, BUSY: <holder> … or PERSON: …, each naming the machine; both waiting answers (and a desktop command refused for the same reason) exit with code 75, and the worker runs it again within 90 s. A turn ends with --done or by itself 10 minutes after the last desktop command. With "when idle", a new turn also waits until nobody has used mouse or keyboard at that desktop for the set time, measured on the machine that owns it: macOS reads the HID system (works from SSH too), Windows asks GetLastInputInfo in the signed-in session (from SSH through the same interactive bridge as the desktop commands). Where the idle time is unknown (Linux, or Windows without a signed-in session, where the desktop command itself then reports that nobody is signed in) only the turns apply.
  • A person comes first, at every command: under "when idle" every gitoodo desktop command of the holder measures the idle time again, not only the first one. The lease notes when the holder's last command ended (acted); input later than that (2 s slack for late events) came from a person, so the turn ends at once: the lease is removed, the command is refused with PERSON (exit 75), and anyone waiting gets PERSON too, not BUSY. A new turn then needs the full idle time again. Only a single command already running finishes. "Always" never measures. Each grant, refusal and ended turn is appended with the measured idle seconds to <state>/desktop-wait/<target>.turns (JSON lines, no secrets, kept to about 256 KB).
  • No way around the turn: in a worker (GITOODO_ISSUE set), the agent-desktop launcher Gitoodo installs in ~/.local/bin runs gitoodo desktop <command> instead of the program, so a skill that names agent-desktop still takes the turn; without gitoodo it refuses (exit 126). On Windows the launcher always went through gitoodo desktop. A worker without any usable desktop (desktop use off everywhere it can reach) is refused by gitoodo desktop (exit 2) instead of running the program unchecked. A person's own agent-desktop commands outside a worker run directly as before.
  • Another machine's desktop: gitoodo desktop --on NAME sends the command over SSH to that computer's gitoodo desktop (arguments as base64 JSON, so no remote shell reinterprets them). On Windows it runs in the signed-in desktop session, which must be unlocked.
  • Wait reason: while a worker on this machine waits, the wait file holds desktop_wait {target, reason: busy|person, holder} with the machine's name as target; the read model carries it for issues with a lease (a file older than 60 s counts as left over), and the board shows "Waits for the desktop of “winpc” while another worker uses it." or "Waits until nobody works at “mac”." with the holder in the tooltip. It is calm: the worker goes on by itself. The file goes when the worker gets the desktop, and the dispatcher removes it when the worker ends. Workers on worker computers report no wait to the board (their wait file would lie on the other machine).
  • Moving to a free desktop elsewhere (crates/core/src/desktop_move.rs, dispatcher_desktop.rs): a worker on this machine that has waited 3 minutes for a desktop (busy or someone working there; the wait keeps its start across the worker's requests) moves once to another worker machine whose desktop of the same system is free. Each dispatch round looks at the waiting workers. A candidate is a worker machine with a usable desktop of that system (not the waited one), whose labels allow the run (os:, and the system a host: alias such as host:mac stands for), that takes a worker now (online, the run's agent ready, a free slot, not paused) and whose desktop would grant a turn right now under its own setting. The look is gitoodo desktop-turn --remote with probe: true over SSH, in the background, valid for 90 s; it takes nothing there (an older Gitoodo there takes the turn and is handed it back at once). Machines whose desktop may be used "always" come first, then by name. The move: the worker is ended, what it had not committed becomes one WIP: … commit (hooks skipped), the branch is pushed with the account from this machine, the lease moves to the target and the run starts there with the same run ID through the usual satellite start (the copy with the pushed branch comes from this machine, #965) and a brief section "Moved here for desktop tests". The local worktree and branch then go; a later run here fetches the branch from the forge first. The log says dispatch.desktop_move_started and dispatch.desktop_moved (from, to), the tile "Moved to “laptop” for desktop tests." while that run lasts.
  • When not: never for an issue pinned to a machine (host: naming a machine, or naming neither a machine nor a system), never twice in one run, never for a worker paused, stopped, held or done (a stop at the same moment wins). When the work cannot be committed or pushed (dispatch.desktop_move_refused), the worker starts again here and keeps waiting. When the start on the target fails, the issue goes back into the queue with its work on the forge and in the worktree here. When no machine fits, the worker keeps waiting, the look repeats every minute, and the board adds "No other machine can take the desktop tests right now." (desktop_wait.no_other; dispatch.desktop_no_other once per run).
  • Placement: an issue whose run waited for a desktop is remembered with that desktop's system (<state>/desktop-needs.json, 14 days, forgotten when the issue is finished). Its next start goes to a machine whose desktop of that system is free right now (this machine's is asked directly), before the usual placement; with none free, or pinned to a machine, the usual placement decides. An issue is only known to need a desktop from such a wait: there is no label for it.
  • Not done: running only the desktop commands on another machine while the worker stays here would need the app under test built and started there; moving the whole run does that. After a move the worker reaches only its new machine's desktop (worker machines do not hold the SSH sign-ins of the others), so a check on a further platform waits for a question to the user.

Fair share across repositories (#959)#

The push loop asks the pure planner dispatch::fair::plan which repository starts next; inside the repository the best ready issue (score, then the classifier's order) still goes first. Queue order and slot share explains the score and the share end to end with worked examples.

  • Share: every repository with Autopilot on that has ready issues or running workers (here and on satellites) is active and gets floor(slots / active) slots, at least one; slots is max_workers, or fewer when the machines' capacities add up to less (#967). A repository at its share starts nothing more while another one below its share has ready work.
  • Rotation: repositories below their share go first, in turns: one that never started goes first (best ready score first), then the one whose last start is the oldest; a repository that just started goes to the end. The order is kept in memory across ticks (fair::Turns); after a restart every repository starts even, and a repository switched off or removed leaves it.
  • Urgent issues: a ready priority:p0 issue (also the legacy prio:0) puts its repository at the front of its group; the classifier already starts p0 first inside a repository. Urgency neither breaks the share nor the global limit.
  • Releases due soon (#1850): a repository whose next release is due within score.release_due_days (default 14) days, or overdue, and has ready release issues goes right after the urgent ones, before the rotation: the highest pressure (open release issues per day left, overdue highest) first, then the earliest date; it also takes leftover slots first. When the release cannot make its date at the equal share (open issues over the days left at one issue per slot and day, fair::Deadline::need, is above the share), the repository may hold up to that need, at most slots - (active - 1): every other repository with work first gets its first slot, then the release fills up, then the others fill up to their share. The extra slots only go to release issues. Without a due date within the window nothing changes.
  • No idle slot: slots no repository below its share can use (no ready work there) go to the repositories with more ready work, in the same order, so no slot stays free while anything is ready. max_workers and every host limit (cores, memory, usage, os:/host:) still hold.
  • System work first: before the share is planned, waiting resolver attempts take free slots, up to the system slots (triage calls take none); the planner splits what is left. Running workers are never stopped for them.
  • No other weighting: apart from urgent issues and releases due soon, every repository counts the same.
  • Waiting for answers is not starving: a repository whose open issues all wait for a person (needs-human) has nothing ready and takes no slot; the share gives its turn to the others. The board and the sidebar say so calmly ("Active · waiting for 3 answers from you", with a way to "Asked of me") instead of "waiting for ready issues" (#1511). The test round_robin_keeps_every_repository_with_work_within_one_start_of_the_others holds the rotation to at most one start apart under load.
  • Several starts per tick: the loop plans again after each start; a repository whose ready issues no host takes or the classifier does not hand out sits out the rest of the tick, so its slot goes to the next one. A repository whose issues are all pinned to a full or missing machine is below its share but never holds a free slot back.
  • Wait reason: a ready issue held back by the share is written to host-wait.json with reason repo_share and shows on the board as "Waits for a free slot of this repository." (no link to the hosts, nothing to set up); when a release due soon takes the slot (#1850), the entry names it (release: repository, version, due date) and the board says "Waits for a free slot: release v2.0 of owner/app is due on {date} and gets more slots."; a reason a host gives for a pinned issue wins. While slots are free but no machine takes an issue without labels, the share is not what holds it: the issue shows that machine reason instead. It ends by itself and is never notified.
  • Why a machine takes nothing: a machine with free slots that takes no worker while work is ready logs dispatch.host_rejected with the reason per agent, once per change (logging); gitoodo diagnose lists it per machine.

Same files one after the other (#1576)#

Two issues worked at the same time on the same file conflict as soon as the first branch lands. So the classifier holds back a ready issue whose files a running branch of its repository already changes, for a bounded time, and starts the next ready issue instead. The rule is the pure function dispatch::overlap::verdict.

  • Expected files of an issue: the repository paths its body names in backticks (an inline code span with a / or a file extension, without URLs, flags, :line or ::item suffixes; fenced blocks are left out), and what its earlier branch changed, if it has one. An issue with neither is unknown and never waits.
  • Files of a running branch: an issue is running while it is in-progress or in-review (its branch has not landed). Its files are what its branch changes, plus the paths its issue names. The dispatcher records them in overlap-branches.json in its state folder before each start, for the running issues and for the earlier branches of the first eight ready issues:
    • Working copy here: git diff --name-only <merge-base with origin/<base>>, committed and not yet committed, no fetch.
    • No working copy here (a run on a worker machine, an earlier branch pushed elsewhere): once the branch exists on the forge, the forge's compare of the base with the branch (changed_files; Forgejo/Gitea and GitHub compare/{base}...{head}, GitLab repository/compare). The branch is found by its number in one listing of <prefix>/… (<prefix>/<number> or <prefix>/<number>-…, the newest if several), so a branch made under an older title still counts; only a forge that lists none is asked for the name the current title gives. Bounded: per repository at most every 5 minutes and for at most 12 branches, in the background (a start never waits for it), and a branch whose head did not move is not compared again.
    • Every write is a read-modify-write under a file lock (overlap-branches.lock; the waits under overlap-waits.lock), so starts and forge reads at the same time keep each other's records.
  • Union files never count: changelogs (update::is_changelog) merge by union and are left out on both sides. A folder named without an extension (src/ui) covers the files below it.
  • Bounded wait: the issue waits until the other branch landed (its issue is closed or no longer running), at most 30 minutes from its first wait; then it starts anyway. When it began waiting is kept in overlap-waits.json, so the bound holds across rounds and restarts. Nobody is asked.
  • Logged: dispatch.overlap_wait once per wait, with the issue, the other issue and the files; dispatch.overlap_wait_end with the seconds waited when it may start. Set against the resolver's conflict count they show the effect.
  • In the app: hovering the queue row says "waits for #N, same files: …"; nothing shows otherwise.
  • Off switch: per repository under the repository's rules ("Same files one after the other", rule overlap_wait), on by default.

The overview steers through the dispatcher and the existing mechanisms; every Tauri command needs orchestrator mode and returns {action, target} or a steering error (kind: "steering" with a reason: direct_mode, dispatcher_offline, refused (the dispatcher's message names the cause), invalid_state, half_typed, invalid_instruction). Live terminal in the app#

In orchestrator mode the agent dashboard asks the dispatcher every five seconds for its workers (dispatcher_workers; quiet, "no dispatcher running" is a normal state). An issue with a running worker gets a "Terminal" button; it attaches (dispatcher_attach), shows the current screen and live output in xterm.js, sends keystrokes (dispatcher_input) and the terminal size (dispatcher_resize), and "Detach" closes the connection (dispatcher_detach). The client lives in crates/core/src/dispatcher_client.rs: Unix sockets on macOS/Linux, the current user’s named pipe on Windows. Worker lists, status, attach, input, resize and detach use the same app commands on every platform. Without a listening dispatcher the app reports offline. Named pipes have no half-close; detaching drops both connection halves so the server releases that viewer.

Run cargo test -p gitoodo-core --lib dispatcher_client::tests on Windows to check the real named-pipe transport: attach with backlog, input, resize and exit, plus worker/status polling while a read-only sizing view stays attached, live output and detach. The polling test uses separate pipe instances as the dispatcher does; the client and server must both close in time.

Device check (2026-11-19, Windows 11 x64): the test-access app against an isolated protocol fixture using create_private_pipe showed one worker, backlog and live output, and 37% usage. Opening the full terminal sent Attach { interactive: false, sizing: true }; resizing the app changed the received terminal size from 84×27 to 86×18. Detaching returned to the live worker list. This checks the app commands over a real named pipe, without starting a coding agent or using the showcase’s in-memory transport. The same app flow was also checked on macOS with an isolated Unix-socket fixture (resize to 85×29 cells, then detach).

Workers run with TERM=xterm-256color, COLORTERM=truecolor and TERM_PROGRAM=gitoodo on every host (crates/cli/src/pty_host.rs). Agents that support synchronized output (CSI ? 2026 h/l) wrap each redraw in it, and xterm.js then shows only finished frames, without the cursor jumping through a half-drawn one (#928). Claude Code sends these frames only for terminals it recognises, so the PTY also sets CLAUDE_CODE_FORCE_SYNC_OUTPUT=1. DISABLE_AUTOUPDATER=1 keeps Claude Code from updating itself inside a running worker (it replaced its program under the session and then asked for a restart); agents are updated with the machine, not by a worker. A screen sent again starts with a terminal reset, so a frame left open never holds the view. The tiles' previews get their output in batches (one message per 100 ms) and keep every byte of a batch: cut to its newest part, the screen a tile attaches with would draw only fragments. A size change ends a batch, so it keeps its place. Tiles and the session view count character widths alike (Unicode 11), as the agents do.

Drawing (#905). The session view and the tiles draw at the worker's size, never at a size they measured themselves: a viewer narrower than the agent's grid wraps the agent's full-width rules into the next row, so the prompt box shows twice and the status line runs into its rule. The session view measures the cells that fit its box (whole cells, the scroll bar's room kept, after the fonts have loaded and the box stayed the same for one frame) and only asks the worker's terminal for that size (dispatcher_resize); it takes the new size when the size frame arrives, after the output drawn for the old one is parsed (src/views/dashboard/terminalStream.ts). A focused view whose size another viewer changed asks again. Output is written once per animation frame; while more than 512 KiB wait to be parsed no more is handed over until it drops below 64 KiB, so the view keeps taking keys during a flood, and with more than 8 MiB behind it (session view and tiles) it attaches again and starts with the current screen. A hidden or minimized window draws no frames; output then still goes to the terminal every 100 ms instead of piling up. Attaching again clears the terminal in the stream's order: after the output it is still parsing, before the worker's size and screen. The view uses the GPU renderer and falls back to the DOM renderer when WebGL is missing or its context is lost; the font stack has symbol and emoji fallbacks. Output passes the redaction in UTF-8-safe pieces: a pause inside a character read in two parts (the terminal is read in 1 KiB pieces) keeps the started character back instead of showing it as replacement characters. With the test build, window.__gitoodoTerminalProbe.report() gives the time from output arriving in the view to the frame that shows it (p50/p95/max) and the frames that came late while output was drawn.

Terminal questions. Agents ask their terminal at startup who it is and what it can do: device attributes, the version, the cursor position, the state of a mode, the window size, the colours. Codex waits for the answers (about 250 ms without them) and blends its panels against the reported background; Claude Code checks synchronized output and other modes with them. A worker usually starts without a focused viewer, so nobody answered. The worker's host now answers the questions it owns itself, from its own screen as drawn up to the question (crates/cli/src/terminal_queries.rs), and takes them out of the stream, so neither the session view nor a terminal behind gitoodo attach sees them and each question gets exactly one answer: primary and secondary device attributes (the same identity the view's terminal reports), the version (gitoodo and the host's version), status and cursor position, DEC and ANSI mode states, the text area in cells, the colour scheme (dark), and the foreground, background, cursor and palette colours (the app's terminal theme; a test keeps both equal). Questions the host does not own pass on unchanged: the progressive keyboard protocol (not supported, so no viewer answers it either), pixel sizes, capability and setting requests. A question split between two reads is answered once it is complete; an unfinished sequence longer than 256 bytes passes on as output. The transcript keeps the raw stream. On Windows the console host answers its own start request first (see above), the rest as on the other systems.

Keys (#905, #944). The session view opens with the focus in the terminal; while it has the focus every key goes to the agent, Esc (twice to clear the prompt), Shift-Tab, Tab, Ctrl-C/D/R/L/T/O/J, arrows, Home/End and PageUp/Down included, and no app shortcut takes one: keys stop at the terminal before any page or window handler sees them (holdKeysInTerminal). Only the clipboard chords (⌘C/⌘V on macOS; Ctrl+V and Ctrl+C with a selection or Ctrl+Shift+C on Windows/Linux; a copy chord without a selection leaves the clipboard as it is), maximize (⌘⇧M / Ctrl+Shift+M) and Shift+Esc stay with the app. On macOS the app's ⌘ chords keep working inside the terminal (⌘⇧D, ⌘⇧A, ⌘⇧H, ⌘,, ⌘[ and ⌘]), since the agents never get ⌘; on Windows and Linux the app's Ctrl chords (Ctrl+Shift+D/A/H, Ctrl+,) work after Shift+Esc. The system's own chords (⌘Q, ⌘W, Alt+F4) always work. Keys an input method is composing stay with it; Shift+Esc leaves the terminal (no keyboard trap), and a line beside the state says so while the terminal has the focus. Shift+Enter and Option/Alt+Enter give a new line in the prompt (ESC CR). On macOS ⌘Backspace and ⌘Delete delete to the start and end of the line (Ctrl-U, Ctrl-K), ⌘←/⌘→ jump there (Ctrl-A, Ctrl-E), Option+←/→ move by word (ESC b, ESC f), Option+Backspace and Option+Delete delete a word. Option with a letter, digit or punctuation key is Meta for the agents (ESC and the key's own character on the current layout, upper case with Shift: Option+P picks Claude Code's model, Option+T switches thinking), but types the layout's character when that is ASCII punctuation the layout offers only with Option (on a German layout Option+L is @, Option+5/6 are [ ], Option+7 is |, Option+8/9 are { }, Option+Shift+7 is \, Option+N is the dead key for ~). The right Option key always types the layout's character (π, ©, “), as in any text field; dead keys (accents) and input methods are never touched. Option+[ keeps its character (ESC [ would start a control sequence). The layout is learnt from the keys typed in the terminal (and read from the browser's layout map where there is one); before that the US positions stand in (optionKeyBytes in src/views/dashboard/terminal.ts). On Windows and Linux Ctrl+Backspace deletes the word before the cursor.

Paste, drop and copy. Pasted text keeps every character (umlauts, emoji, box drawing) and goes bracketed when the agent asked for it, without control characters, so a paste cannot end its own brackets (pasteText in src/views/dashboard/terminalPaste.ts). Input travels in frames of at most 8 KiB (INPUT_CHUNK): a larger paste used to go out as one line over the dispatcher's line limit, and the dispatcher closed the view's stream instead of typing it. An image on the clipboard (with no text) is sent as a file (Frame::File, PNG, JPEG, GIF and WebP as they are, other image types drawn again as PNG, at most 32 MiB); the machine the worker runs on keeps it in gitoodo-paste in its temporary folder (private to the user, removed after a week) and pastes its path into the prompt as one bracketed paste. Claude Code, Codex and Gemini CLI attach an image whose path arrives that way, also where they cannot read this computer's clipboard (a worker on a satellite, a service). Files dropped on the terminal (tauri://drag-drop over the terminal) reach a worker on this computer as their paths (Frame::Paths), each its own bracketed paste followed by a space, special characters escaped with a backslash (on Windows in double quotes); for a worker on a satellite the dispatcher sends copies of the files instead (folders are left out). Workers always run with a UTF-8 character type (LC_CTYPE, utf8_ctype in crates/core/src/agent/env.rs) when their environment names no UTF-8 locale: an app started from the Dock, a login item or the service manager has no LANG, and an agent's copy of its selection through pbcopy then put UTF-8 on the clipboard as Mac Roman (─ pasted as ‚îÄ). An agent's copy through the terminal itself (OSC 52) reaches this computer's clipboard while the terminal has the focus, as UTF-8 and at most 128 KiB of base64; a request to read the clipboard is never answered. Text selected in the terminal is copied by the view itself. Checked on macOS with Claude Code and Codex; Windows, Linux and Gemini CLI are not verified yet.

Reconnecting. A stream that closes without the worker's exit (the dispatcher is updated or restarted) is attached again, first after 2 seconds, then after twice as long each time, at most every 30 seconds, for up to 3 minutes. For a worker the dispatcher still lists, a refused or broken attach is tried again too. A worker tile and the opened session attach anew when the worker's restart count changes (a new process after an exit without a pull request). Only then does a tile say what happened: "This worker has ended. Gitoodo takes the next step for the issue." when the worker is gone, "The dispatcher cannot be reached. Once it runs again, it carries on with the issue and the worker shows up here again." when the dispatcher did not come back.

Tile states. Working; waiting for an answer; checks running; paused (soft pause or disk); paused at the usage limit ("Paused until 14:20", the reset from the agent's lock, with the line "Usage limit reached. The worker carries on by itself afterwards."); idle ("The agent ended its turn and waits for your reply in the session.").

Usage limits#

Worker distribution. New workers are spread over the three agents by share of starts (not tokens or cost). There is one setting for it, Settings → Dispatcher → Worker agents (#963): Claude Code, Codex and Gemini CLI side by side, each with its share in percent, its model and its state. The shares always add up to 100; changing one moves the other two in their ratio (when both were 0, the rest goes to the first other agent that is ready). An agent that is not installed or not signed in shows why and the command that fixes it, and cannot be given a share until it is ready (a share it already has can still go down). In config.toml this is dispatch.worker_pool: codex_percent and gemini_percent, with Claude Code taking the rest.

  • With redistribute (the default) an agent at its limit or not ready hands its starts to the others, and the chosen shares resume afterwards; without it, its starts wait.
  • pause_unknown_usage holds back an agent whose usage is not known yet.
  • Gemini CLI's quota is asked before a start (#1516, "Gemini CLI quota" below): with current figures the threshold holds it back like the others, and a model with nothing left locks it until that model's reset. Without figures neither the threshold nor "pause on unknown usage" holds it back; its card says so. Its own quota notice always does (see "The agent's own limit notice"): until the reset it names, or for a conservative hour (GEMINI_COOLDOWN_SECS) when it names none.

The former single choice (ai.agents.orchestrator, "Workers" in AI assist) is no longer a setting of its own. A configuration without dispatch.worker_pool behaves exactly like the distribution that gives that agent 100 % (WorkerPool::single: redistribution on, unknown usage held back for Codex only), and the settings show it as that distribution; the first save writes it. The core keeps ai.agents.orchestrator equal to the agent with the largest share (WorkerPool::lead, the first in the order above on a tie), on every save and at app start, so the setup checks, the doctor and the skill target name an agent the dispatcher actually starts. AI assist shows the distribution and opens the worker agents. On a worker machine unknown usage never holds it back for good:

  • Limits belong to the login, not to the machine. Each machine reports a fingerprint of its agent login: the first 12 hex digits of the SHA-256 of the ids that together name whose limits apply, as the agent keeps them in its own config. For Claude Code that is account and organization (oauthAccount.accountUuid and organizationUuid in .claude.json). For Codex it is workspace and user (tokens.account_id in auth.json, shared by every seat of a team, and the user id from the payload of tokens.id_token, read in memory only; without a user id there is no fingerprint). No id, address or token leaves the machine, and the fingerprint goes only from a worker machine to the dispatcher, never into the status the app reads. While a worker machine cannot read its figures, the current figures of the same login on this computer or on another worker machine decide for it (agent::login, dispatcher_hosts.rs).
  • Without such figures it holds only while a worker of that agent this dispatcher started there less than 10 minutes ago runs (PROBE_SECS): an idle worker machine often cannot read its usage (the agent's access token there runs out between runs, or its credential store is closed to a session without a desktop) and only a run renews it, so one worker of each agent may start there to find out, and a further one waits for the report that run brings. A worker that brought no figures in that time (stuck at a prompt, signed out) holds nothing back any more; the next start learns from the first limit it hits. A worker the satellite lists that this dispatcher does not supervise no longer counts at all (it used to count for every agent, so a single leftover held the machine back forever).
  • A known limit and a not-ready agent still keep it off the machine. A limit the machine reported stays until its end while its usage turns unknown (a restart of its service, a failed query): the dispatcher keeps the last limit per machine and agent for the same login until its end or until figures with room come in. The same login's known limit elsewhere holds there also where unknown usage may start. Each agent runs its own model choice (ai.models.workers in the settings, one per agent; empty = the workers' step choice when it belongs to that agent, else its recommended model). Worker machines report every agent they find, Gemini CLI included (#957).

The usage limits below apply to Claude Code and Codex, and to Gemini CLI while its quota figures are current. Without them Gemini CLI is never held back by the threshold or by "pause on unknown usage", only by not being ready and by the lock of its own quota notice or a spent model.

Gemini CLI quota (#1516). Gemini CLI's code-assist backend names, per model, the share left and its reset. Where Gemini CLI takes workers or orchestrates and is installed, the dispatcher (and each worker machine for its own login) asks it before the first placement and then every 5 minutes, more often near a known reset, backing off to an hour while it fails (crates/core/src/gemini_quota.rs): loadCodeAssist for the login's project (else GOOGLE_CLOUD_PROJECT), then retrieveUserQuota. Each model is one window (percent used = 1 − the fraction left); a model at 100 % locks Gemini CLI until its reset, and the wait names no five-hour or weekly window. The access token is Gemini CLI's own (~/.gemini/oauth_creds.json), read-only, in memory only and registered with the log redaction; it is never renewed, so with an ended token (Gemini CLI renews it when it runs), a login in the system keyring, an API key or a failed query there are no figures, and figures older than 10 minutes count as none: then Gemini CLI is "no limits reported" as before and the last lock stays.

The status lists all three agents in the order above, each with its share of new workers (0 where it takes none; without dispatch.worker_pool the AI settings' agent has 100) and Gemini CLI with problem: unsupported. Without current quota figures the app shows Gemini CLI as "No limits reported" wherever usage shows (the status bar's agent usage, the overview's agent limit, the limit warnings, which name it as an agent without warnings) and leaves out an agent with share 0 that is not installed here. The dispatcher log names the distribution at its start and on every change (dispatch.worker_shares, all three agents).

The dispatcher tracks the Claude Code login of this host: the 5-hour window, the weekly window and the weekly window per model, each with percent used and reset time, plus the time of the report and a stale flag (no report for 10 minutes). Sources, newest report wins:

  1. Status line: workers start with --settings that sets statusLine to gitoodo hook status-line; its rate_limits JSON from stdin is forwarded as usage in the hook request.
  2. OAuth usage endpoint (https://api.anthropic.com/api/oauth/usage), for times when no session runs. Polled every 15 minutes after a good answer and only while workers are wanted; failures back off exponentially from 5 minutes up to 1 hour and Retry-After is honoured. The token is read-only from Claude's own login (macOS keychain, else ~/.claude/.credentials.json), kept in memory, never refreshed, never logged or sent to the app.
  3. StopFailure hook: a usage-limit failure marks the limit as reached.

Gating: at or above dispatch.usage_threshold_percent (default 90, 1..=100) no new worker starts; running ones continue. When the limit is reached the login is locked until the reset (5 minutes when the reset is unknown): the lock is not a hang and no restart is counted. At the reset the dispatcher types continue and Enter into the terminals of the workers that hit the limit. Such a worker keeps its run; list marks it limited with limited_until (the lock's end, when known), and its tile says "Paused until …" instead of "Working". The lock holds back new workers of that agent. "Paused until" is the reset of the full window in the user's own time zone (the weekday within six days): with the weekly window full it is the weekly reset Claude Code names ("resets Nov 22, 7am" is "Sun 07:00" on the tile), not the earlier five-hour reset. Gitoodo sees the windows, not why Claude Code stopped (a spending cap of the account looks the same), so the tile names no window; the repository's gate line does ("Weekly limit until …").

Claude Code's limit menu. At a usage limit Claude Code submits /rate-limit-options by itself (the menu to wait, buy more usage or change plans). A worker runs with --disable-slash-commands, so its terminal shows Unknown command: /rate-limit-options once; nothing is wrong. The menu stays shut on purpose: it would swallow the continue typed at the reset, and buying usage is the user's own decision in Claude Code. Gitoodo never types a slash command into a worker (a test holds it).

At the limit. While an agent is locked or a window of it is full, its usage source (OAuth endpoint, Codex app server) is asked every 5 minutes instead of every 15, or just after a known reset when that comes sooner, never more than once a minute; a back-off after failures and Retry-After stay. When the source reports room in every window again, the lock ends at once (also a lock with a known reset), the stopped workers get continue and new workers start with the next push round. Free again, the agent goes back to the normal interval.

Check at the reset. No timer of its own is needed: the usage round runs every 30 seconds and asks a locked agent's source at its known reset plus 15 seconds (RESET_GRACE_SECS), or every 5 minutes while the reset is unknown (a lock from the StopFailure hook lasts 5 minutes and is then checked again). A known lock also ends by its time; the push round every 5 seconds sees that (poll_unlock), types continue into the stopped workers and starts new ones in the same round. Each window (5-hour, weekly, weekly per model) is tracked with its own reset; the lock lasts until the last full window resets. Worker machines pace their own logins the same way (#1036): at the limit each machine asks its source at the reset instead of the normal interval and reports the fresh values with the next poll of the main host (at most 20 seconds).

Locks survive a restart. usage-cache.json keeps each agent's lock (until, and whether the reset was known) beside its last values. A new dispatcher re-arms a kept lock that has not ended yet (at most 8 days ahead; a lock of this run is never replaced), marks the workers it takes over as stopped by the limit and wakes them at the reset as before. A lock that ended while nothing ran is dropped.

Resume now and Check limits now. {"cmd":"recheck","agent":"claude_code"} (or "codex") wakes the usage round at once: the agent's source is asked right away unless it was asked less than 30 seconds ago (MIN_CHECK_SECS) or still asks to wait (Retry-After), and the reply is the status after that round (at most 30 seconds later). The same request reaches every connected worker machine, which asks its own logins at once and answers when its report is fresh (at most 20 seconds). Free again, the lock ends at once and workers start with the next push round; still at the limit, the lock stays and the fresh values show. The app sends it from "Resume now" (one agent) and from "Check limits now" at the top of "Agent usage" (every agent with usage, at most once per 30 seconds, with "Checked just now" afterwards); the command line has gitoodo usage --refresh [--json] (without --refresh it prints the last values; one line per agent with its windows and share, Gemini CLI as "no limits reported"). The dispatcher never writes orchestration.json for it.

After a restart (#988). The last good values of each agent are kept in usage-cache.json in the state folder. At start they show at once (marked stale by their age, seeded in the status), and for the start of new workers a kept report counts as current for at most 3 hours, until this run's first own report replaces it, also with "pause on unknown usage" on: an agent that was open keeps starting workers, one that was at its limit stays held. Each agent without current values (no report in the last 10 minutes) is asked at once (OAuth endpoint, Codex app server), beside the recovery of pull requests and before the first placement; a back-off after failed queries (a rate limit) is kept. The start-up order is: free dead leases, check the agent, recover pull requests and ask for usage (together), first push round; the cleanup of leftovers a minute later. Stalled issues of machine faults (#982) go back into the queue 10 per push round, after that round's dispatch, so a long list never holds up the first workers.

Why nothing starts. Every entry of providers carries wait while that agent takes no new worker: not_ready (not installed or not signed in, see usage.problem), limit (window five_hour or week, until the reset in unix seconds when known) or checking (no current values yet and unknown usage counts as no capacity). While every agent waits this way and ready issues are queued, the work area (repository sessions and "All repositories") says why in one line, e.g. "No new session starts: Claude Code: weekly limit until Fri 15:00 · Codex: checking usage …" (repo-usage-gate).

{"cmd":"status"} replies {"reply":"status","status":{...}} with usage (windows, stale, updated_at), threshold_percent, throttled, locked_until (unix seconds or null), workers, max_workers and queued (ready issues without a slot, as of the last push round), plus config_problem while orchestration.json cannot be used, places (each machine's running workers and places) and stopped (why the autopilot starts nothing).

In orchestrator mode the app's status bar asks for it every 15 seconds (dispatcher_status) and shows the 5-hour and weekly percentages; an agent paused at its limit shows "paused until 14:20" instead (or "paused until reset" when the end is unknown). A click opens the details: reset times, throttled or paused (with the time work resumes and a "Resume now" button that has the dispatcher check that agent again; still at the limit, it says "Still at the limit, resets 14:20"), how old the values are (stale marked), running workers and queue length. A window whose reset time has passed counts as 0 %. Without a dispatcher the bar only says "Dispatcher off"; in direct mode it shows nothing.

Worker count in the status bar. Before the limits the bar says how many workers of the autopilot run over all machines and how many places are free, e.g. "Workers: 3 of 5 · 2 free" ("Workers: none active · 5 free" while none runs, "Workers: 2 of 2 · all taken" while every place is taken, "Workers: no free place" while no machine takes work). It reads places from the same status: per machine (this computer first, by its own name) the running workers with the starts under way, its places (its cores over dispatch.cores_per_worker, lowered to the user's maximum for it), whether it answers and whether it is paused (after a failed start or for a low disk). The places count only for machines that answer and are not paused, at most dispatch.max_workers; workers on the others still count as running. stopped says why the autopilot starts nothing at all: halted (everything stopped; the app's own switch shows it at once) gives "Workers: stopped", no_autopilot (no repository has its autopilot on) gives "Workers: paused", with "2 finishing" while running ones finish. Without a dispatcher it says "Workers: –". The tooltip lists every machine ("macstudio 2/3 · winpc 1/1 · nas unreachable"), the total limit when it is below what the machines offer, and while places are free why nothing starts: every agent waiting for its usage (the sessions' line) and the issues waiting for a matching machine. A click opens the sessions of all repositories. In a narrow bar only the first part stays visible; the rest stays in the button's name. Older dispatchers without places show their own count of max_workers.

Worker delivery#

gitoodo worker pr [--title T] [--body TEXT] [--replace] [--replies FILE] pushes the worker's branch and opens the pull request with Closes #N (default title: issue title plus (#N)); gitoodo worker push only pushes. Both run in the worker's worktree, read GITOODO_ISSUE, and hand the delivery to the dispatcher's broker (capability in GITOODO_WORKER_CAPABILITY), which holds the account's token. Inside a worker without a capability they refuse and never fall back to the keychain (release-gate review H2, docs/security.md). The token never reaches the worker's environment, files, git config, remote URL or logs.

How the push gets its credential: git push runs as a child in a scratch git directory Gitoodo configures itself (token_git.rs; objects from the checkout, never its config or hooks) with an explicit https URL built from the account origin (not the worktree's origin), system and global config off, hooks and fsmonitor off, credential.helper and core.askPass cleared, GIT_TERMINAL_PROMPT=0, and GIT_ASKPASS pointing at the gitoodo binary itself (gitoodo askpass). Only that child gets GITOODO_ASKPASS_USER/GITOODO_ASKPASS_TOKEN/ GITOODO_ASKPASS_HOST; the askpass call answers git's username and password prompts from them, and only for prompts that name the forge host. Details and the proxy rule: docs/security.md. Alternatives rejected: a token in the remote URL or git config (persists on disk and in ps), a credential helper script (a file with the secret path or token), a setup-assistant check only (needs credentials in the worker's reach). The same route serves the dispatcher's fetch of the base branch before it cuts a worktree (worker_pr::fetch_base) and the branch updates (#385). Git output is scrubbed of the token, and a refused login (missing, expired or unauthorized token) is turned into a readable reason. Satellites hold no token and still fetch with their own git credentials. Branch guard: never main, master, dev, HEAD or the base branch; the refspec is HEAD:refs/heads/<branch>, so there is no force push.

Replacing the branch on the forge (#1644): a delivery that does not contain the forge's branch is refused, except for the worker's own rebase onto the current base (#1565) and a replace a person approved. Since the base moves on all the time while workers run side by side, a rebase onto a base that moved on again before the delivery counts as the worker's own rebase too (#2044, Settings → Dispatcher → "Replace rebased branches without asking", dispatch.replace_rebased, on by default): the forge's head must be the one the worker last saw, and every commit the forge's branch has beyond the delivery and the base must be in the delivery as the same change (patch id, worker_pr::keeps_forge_changes); a merge commit or a changed or foreign commit on the forge still needs a person's approval. Switched off, every such replace waits for that approval as before. The approval is a question on the issue with the id replace-branch (or replace-branch-…, a later ask or a forward), answered by a trusted person with yes to question 1, which must be a yes/no question (#1651): a choice never approves, since its letter cannot tell which option is the replace when the options come in another order, and an answer to one refuses; the newest such answer counts, so a later no withdraws it (core::branch_replace). The approval covers only the state the person saw: the approved block names the forge's head commit (7 to 64 hex characters in its context or question 1), and a forge head the block does not name is refused, even after the worker fetched it, so commits pushed after the answer need a new approval. With it, gitoodo worker pr --replace pushes once with --force-with-lease=refs/heads/<branch>:<head>, where <head> is the forge's head the worker last fetched (origin/<branch>, the satellite's replaces); when the forge has moved on since, nothing is pushed and the worker gets the new commits. Without an approval --replace is refused with how to ask for it; without --replace everything stays as before. The worker never asks the person to type the push in a terminal (worker prompt REPLACE_RULE, skill).

A pull request already open from the worker's branch is taken over instead of refused (#1605): when the forge refuses a second one, the open pull request whose head is the branch is the delivery, even when another pull request (an older one from another branch) closes the issue too. Gitoodo adds the Closes #N line when its description lacks it and takes over a title or body the worker passed with --title/--body; a title made from the issue never replaces the pull request's own. The push of the run updates its head, so it counts as delivered in this run. After the run the delivery is the pull request from the run's branch first, then any that closes the issue. Once a pull request is delivered, Gitoodo's own open worker questions on the issue that no person has answered are withdrawn (edited to "A question here was withdrawn because its cause is gone: …"; question_retract.rs), so nobody answers a question the delivery made pointless.

A refused worker push or worker pr always tells the worker why, starting with not delivered: (worker_cmd::worker_reason): a fixed text per cause (no commits, invalid request, refused account, paused or read-only repository, branch moved on the forge, unknown branch, network or server error, timeout) with what to do, and for a push git refused, git's first line, clipped. Forge response bodies never reach the worker.

Residual risk: for the few seconds of the push the token is in the environment of the git child (same user, readable by processes of that user, as for any askpass flow). Limits: a worker on a satellite has no token, so these commands refuse there; a satellite sends the branch back and this computer pushes it and opens the pull request (#582; the behind-base update runs there with the satellite's own git credentials). The path of the gitoodo binary must not contain spaces.

Review feedback#

When a trusted reviewer asks for changes on a worker's pull request, comments on its lines or on its conversation, the worker gets the points and answers them (#1567). Repositories with a required review no longer stand still after a request for changes until a person steps in.

  1. Reading. While the dispatcher waits for a delivered pull request to merge (also while a setting such as a missing approval refuses the merge), it reads the feedback about once a minute (ForgeAdapter::review_feedback, core forge/review.rs): reviews that ask for changes, comment-only reviews with text, line comments (file, line or line range, text, author, link) and conversation comments. GitHub: pulls/{n}/reviews, pulls/{n}/comments, the issue comments. Forgejo/Gitea: pulls/{n}/reviews, the comments of each review, the issue comments. GitLab: the merge request's discussions and, from GitLab 17 on, the reviewers' state requested_changes. A forge that does not answer skips the look; nothing else changes.
  2. Sorting (review_feedback::sort). An item counts once: every item seen goes into the note's seen. Only items of trusted people start a round, the same people whose comments reach a worker's brief (intake::trusted_people, write access or more, organisation members, the repository's trusted authors; release-gate review H1, docs/security.md). Items of anyone else are marked seen and only counted ("N review comment(s) by people without write access left out"); their text never reaches the worker, neither in the brief nor in gitoodo worker context, whatever the worker mode. Gitoodo's own comments (its answers carry the machine marker), resolved threads and empty comments never count. On the first look at a pull request without a note, items from before the wait began count as handled, so pull requests already open when the feature arrived start no round for old feedback.
  3. Round. New trusted items go into the note's open list, the round count goes up and the worker is restarted on the same branch, with a fresh brief: its section "Review feedback on pull request #n (round r of 3)" lists every point with its id, author, place and link and the reviewer's text in a fence (quoted, never an instruction above the rules). gitoodo worker context repeats them as review (pull, round, max_rounds, items with id, kind, author, path, line, start_line, text, url, reply, omitted_untrusted, rule). A round is no failed attempt and does not use up the restarts. Logged as dispatch.review_round.
  4. Answers. The worker works through the points and delivers with gitoodo worker pr --replies FILE, a JSON list with one short answer per point ([{"id": "line:12", "text": "Renamed as asked.", "done": true}], at most 64 KiB). The worker has no token: the answers travel with the delivery (broker, or the satellite's forwarded delivery) and the main host posts them after the push (review_feedback::post, logged as review.answered, each write in the forge-write log as review_reply/review_resolve). Only open points of that pull request are answered; other ids are named back and ignored, so a worker cannot write on other threads. Every answer carries Gitoodo's marker. Where they go:
    • GitHub: a line comment in its thread (pulls/{n}/comments/{id}/replies); a thread marked done is resolved (GraphQL resolveReviewThread). Review summaries and conversation comments get an answer on the conversation that names the person and links the point.
    • GitLab: in the note's discussion; a resolvable discussion marked done is resolved (PUT …/discussions/:id?resolved=true).
    • Forgejo/Gitea: their API cannot answer or resolve a line thread, so every answer goes on the conversation, naming the person and linking the thread; threads stay for the reviewer to resolve. Answered points leave open; the worker's delivery message names unanswered ones.
  5. Limit. After three rounds (review_feedback::MAX_ROUNDS) new trusted feedback starts no worker. The dispatcher asks the person on the issue (question review-rounds-<pull>-<n>, in the language on the forge, needs-human): "Should the worker go on with the new feedback?" with a) let it go on (the open points and up to three more rounds) and b) I take over (no worker for review feedback any more; the pull request stays open until the person finishes it and it is merged). The worker started after the answer reads it in its brief; the dispatcher reads it at the next look (review_feedback::answer_of): a) counts the rounds anew, b) marks the note manual. Logged as dispatch.review_rounds_out and dispatch.review_answered.

The note lives in review-feedback.json in the state folder, keyed like the leases (<account>/<owner/repo>#n): pull, seen, open, rounds, asked, manual, omitted, at. A merge drops it; notes untouched for 30 days go with the next write. Limits: pull requests the dispatcher does not wait for (merge gate off, forge auto-merge enabled) are watched for their merge only, so their review feedback starts no round; a request for changes on GitLab before version 17 shows only through the discussions.

Triage labels#

Triage (triage.md) sets type, priority and size labels on new issues where no person set them. The dispatcher uses them when they are there and never depends on them:

  • priority:p0 … p3 orders the queue as any priority label does;
  • size:s starts the worker one model tier below the chosen worker model (Opus → Sonnet, Gemini Pro → Flash, Codex astra → sol → terra of the same version, …), logged as dispatch.small_task_model; the setting "Small tasks on a smaller model" (ai.triage.small_task_model, on by default) switches it off, and a resumed run keeps its model;
  • an open triage question sets needs-human, which holds the issue like any question;
  • the type label routes nothing.

Worker follow-up issues#

A worker that finds work outside its issue (a bug elsewhere, a missing test, outdated docs) proposes it with gitoodo worker follow-up; the worker brief says when to use it and that it is never a way to hand off parts of the worker's own task (that is a split, below). The command reads the body from the file (- is stdin, at most 16 KiB) and sends a follow_up action to the broker with the worker's capability, like worker pr; there is no direct path, so a worker without a capability or on a satellite is refused.

The broker checks, in order: capability and issue path, title and body (follow_up::validate), the repo setting worker_follow_ups in orchestration.json (default on; Settings → repo options "Workers may propose follow-up issues"), a live lease of this worker on its issue (the lease file in the state folder), and the budgets: dispatch.max_follow_ups_per_run per run (default 3, 0–20, no field in the form; 0 switches the brief line off and refuses every proposal) and 10 per repo and hour. A proposal that creates nothing (duplicate, unknown label, too deep, forge error) gives its slot back. Chains stop at follow_up::MAX_DEPTH (3): the marker carries depth=D, the parent's depth is read from its body, and a proposal from an issue at depth 3 is refused ("too deep"). Then follow_up::open creates the issue with the account's token: dedupe by normalised title against the open issues, body with the worker's text (<!-- defused) plus the footer "Follow-up from #N (worker W)" and the gitoodo:follow-up marker, label gitoodo when the repo has it and the optional kind label (only existing labels that are no workflow, priority, host or release label), and a note on the parent issue. The broker never labels it ready itself; the classifier's intake does on its next run, or, where the repo has "Approve each follow-up before it is worked on" on (follow_up_approval, default dispatch.follow_up_approval, off; Settings → Dispatcher), asks the repo's human for approval first (docs/security.md, "Worker follow-up issues"). The note on the parent and the reply to the worker say which of the two happens.

Replies are one line for the worker: the new issue number on success, otherwise follow-up issue not created: <reason>. Forge and transport errors are logged (dispatch.follow_up_refused, dispatch.follow_up_created, without tokens or texts) and reach the worker only as the broker's generic refusal.

Splitting an issue into parts#

The brief starts with the scope of the issue (split::brief_section, #1012): where splitting is offered (setting worker_follow_ups, local workers), the worker first sizes up the issue and either does all of it in this run (preferred) or, before writing code, writes a plan and runs gitoodo worker split --plan <file> (file or - for stdin, at most 32 KiB). Without the offer the brief says to do the whole issue in one run; a part's brief says it is never split again; a parent whose parts are all closed is an umbrella issue and gets the list of its parts and the task to check and close it (see "Umbrella issues").

The command sends a split action to the broker with the worker's capability. The broker checks, in order: capability and issue path, the plan (split::parse and split::validate: 2–8 parts, a reason, each part by follow_up::validate, after only naming earlier parts, no two equal titles), the repo setting, a live lease of this worker and at most 5 splits per repo and hour (apart from the follow-up budget; a split that creates nothing gives its slot back). Then split::open reads the repository's issues (open and closed), refuses a parent that is itself a part, a parent whose parts are all closed and a part that depends on the parent, reuses the parts that exist by index, checks titles and labels of the missing ones, and creates them in order (body, Depends on line for the after parts, footer with the gitoodo:part marker, label gitoodo and the optional kind). Each new part goes into the parent's release (#2061): the parent's milestone and its release:next label, so a release never waits for a part outside it. A milestone that cannot be written is logged (split.milestone_failed); the hygiene's release pass puts the part there later (see "Dependencies join the release" in release.md). A note on the parent lists the parts.

On success the worker reads the part numbers and that it must stop without a pull request; the broker marks the run as split and stops the worker once the reply is out. Its end is reported as Event::Split: run result split (a good end), trace dispatch.split, lease released, worktree and branch removed when the worktree holds no work of its own (no changed file, no commit that no remote has; otherwise it stays for the integrating run, dispatch.split_kept_worktree), and the parent back to ready (Flag::Requeue), where it waits for its open parts like for a dependency. Parts count as Gitoodo's own when the login it writes with now or an earlier one (orchestrator_writers) opened them, so a switched forge account keeps the parent waiting. A refusal reaches the worker as issue not split: <reason> (dispatch.split_refused); it changes nothing on the parent, and the worker goes on (fix the plan or do the issue in this run).

Umbrella issues#

An umbrella issue (Sammel-Issue, #1816) collects child issues instead of being implemented itself. It waits for them through the one dependency mechanism ("Dependencies"): while a child is open it is blocked and shows as "needs #…" like any issue that waits; once every child is closed it becomes ready and a worker takes it. Code: orchestration::umbrella.

An issue is an umbrella when it was split into parts (gitoodo worker split, parts opened by Gitoodo's account), or when it says so and has at least one dependency, which are then its children. It says so with the body marker <!-- gitoodo:umbrella --> or the legacy label prd. Whoever plans an umbrella outside a split (a planning session, a person) writes the marker and a Depends on #a, #b, … line naming every child; children that only point back at the umbrella are not enough.

The worker's brief (umbrella::brief_section) lists the children and says not to implement the issue again but to check its goals and acceptance criteria against what the children delivered (their merged pull requests, the code on the base branch):

  • everything met: gitoodo worker close --summary <text>. The broker checks the worker's live lease, reads the issue afresh, checks that it is an umbrella and that every child is closed (umbrella::close), posts a note with the children and the summary (marked as Gitoodo's) and closes the issue. The run ends as closed (a good end, dispatch.closed): lease released, an untouched worktree removed, nothing requeued. Refusals start with issue not closed: (no lease, a child still open, changed files, an empty or too long summary of more than 2000 characters). An issue that is no umbrella (and a split part) takes the same command without the children's check, as long as the run changed no file (umbrella::Closed::NothingToChange, dispatch.closed_unchanged). On a worker machine the satellite holds no forge token, so it works like gitoodo worker pr there: the satellite service forwards the summary on the main host's subscription (Request::Close, Reply::CloseForward), and the main host closes only while a live lease says the issue's worker runs on that very machine (satellite::authorize_close), with the same checks and the same refusals. Once closed, the satellite ends the worker without an exit record and the main host ends the run as closed itself (settle_remote_closes): lease released, nothing requeued, the worktree left to the satellite's cleanup. A refusal keeps the worker running.
  • a small remainder missing: the worker does it and delivers a pull request that closes the issue.
  • larger work missing: where worker follow-ups are allowed, the worker proposes each piece with gitoodo worker follow-up and records that the umbrella waits for them with gitoodo worker blocked; it comes back to a worker once they are closed. Elsewhere it asks with gitoodo ask.

prd was a hold like extern until #1816; it holds nothing any more. A prd issue without dependencies is a normal issue: it goes through the intake and triage, and its worker splits it if it is too big for one run. Gitoodo no longer creates the label on new repositories and never deletes it; the activation preview lists it among the labels the catalog does not know.

Deviations from the spec#

  • Only the local host is used; the host abstraction is in place for SSH satellites (step 8).
  • The hang policy counts in one-second ticks; the git-change signal is not fed yet, so output and hook pings are the only proof of life.
