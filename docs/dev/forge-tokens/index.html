Token permissions per forge

Gitoodo needs a personal access token per account. The token wizard (Settings > Accounts > add) and the Replace token … dialog of a stored account name the permissions in the words of the forge's own token page, with the reason for each. This page is the same list for later. The wizard texts live in src/views/settings/permissionGuide.ts; tests/token-permissions.test.ts fails when this page, the wizard and the checks in crates/core/src/forge drift apart.

GitHub#

Classic token (Settings > Developer settings > Personal access tokens (classic)); the wizard opens the page with both boxes ticked:

PermissionWhy
repoRead repositories and issues, send answers as comments, close issues
read:userRecognise which account the token belongs to

Fine-grained token: choose the repositories under "Repository access" and set under "Repository permissions":

PermissionWhy
Metadata: Read-onlyList repositories (GitHub grants this automatically)
Issues: Read and writeRead issues, send answers as comments, close issues

GitLab#

PermissionWhy
apiRead issues, send answers as comments, close issues

read_api is enough for reading only; without api Gitoodo cannot answer.

Forgejo and Gitea#

Forgejo and Gitea cannot preselect permissions by link. Set them by hand on the opened page (User settings > Applications): pick this access level for each category and leave all others on "No access".

CategoryAccess levelWhy
userReadRecognise which account the token belongs to
repositoryReadList the repositories of the account
issueRead and writeRead issues, send answers as comments, close issues

Per mode: orchestrator, working directly, answering#

The lists above are what answering questions needs. The wizard asks what Gitoodo should do with the repositories, preselects the operating mode chosen in onboarding (or set in the app) and shows one merged list for that mode: each category once, the highest access level wins, plus the role the account needs in the repository. It goes on only after I have set these permissions on the token is ticked; switching to a mode that needs more asks again. The rights per mode come from crates/core/src/forge/rights.rs, the merge from src/views/settings/tokenBlock.ts.

ForgeWorking directlyOrchestrator, in addition
Forgejo / Gitearepository: Read and writeorganization: Read and write, only to create or delete repositories in organisations
GitHub classic—delete_repo, only to create or delete repositories
GitHub fine-grainedContents: Read and writePull requests, Administration, Commit statuses: Read and write (Administration also creates and deletes)
GitLab—— (api covers creating and deleting)
Role in the repositoryWrite (GitLab: Developer)Admin (GitLab: Maintainer), for repository settings such as merge styles and branch protection

The organisation scope is optional (#978): Forgejo and Gitea refuse creating and deleting a repository that belongs to an organisation without write:organization, even when the token has write:repository; GitHub classic tokens delete only with delete_repo. A token without it is still stored and works on every repository; the account in the settings names the gap ("Only to create or delete repos") with Replace token …, and the removal dialog names the scope before the delete is confirmed.

A separate orchestrator (worker) account per forge host (#764, docs/orchestrator/spec.md 5.3.1) needs the orchestrator's rights without repository settings (forge::rights::worker_rights): no Administration permission and no admin role; write access (GitLab: Developer, Maintainer to merge into protected branches) is enough. Repository settings stay with the user's own account.

Creating the worker account automatically (docs/orchestrator/setup.md, "Automatic worker account") needs more on the own account, only for that moment: Forgejo/Gitea a site administrator whose token has write:admin; GitLab self-managed an administrator token with api (and Admin Mode where the instance enforces it). Without them the step falls back to the guide; the own token is never asked to gain these scopes for anything else. The worker token it creates has exactly read:user, write:repository, write:issue (Forgejo/Gitea) or api with a 364-day expiry (GitLab).

How the check finds out#

GitHub classic tokens list their scopes in a header and GitLab tokens on /personal_access_tokens/self. Forgejo and Gitea reveal nothing: reading scopes are probed with cheap reads, and the write scopes beyond answering (write:repository, write:organization) with a write the forge refuses: an empty body to POST /api/v1/repos/migrate and POST /api/v1/orgs. The forge checks the token's scopes before it reads the body, so a missing scope answers 403 with its name and a present one a validation error; nothing is ever created. Only a named scope counts as missing, so an older forge without scoped tokens reports nothing. GitHub fine-grained tokens reveal no permissions; there the forge names a missing one at the action.

The wizard stores a token only when it gives everything the chosen mode needs (writing for working directly and the orchestrator); a token without the optional organisation scope is stored and the gap stays visible on the account.

When a new version needs more#

The check runs when an account is added, its token replaced and synced, and again whenever the accounts in the settings open. If the stored token lacks a permission, the account shows what is missing and offers Replace token ….

Replacing a token#

Replace token … sits on every account in Settings > Accounts (the key icon while the token is fine, a button while it is rejected, missing or short of permissions), on the scope hint and the sync error bar, in the repository rights check, the removal dialog, the status page and the worker account section. It opens a small dialog, not the wizard: one masked paste field (with Show), a Create token on <host> link (GitHub and GitLab preselect the scopes; Forgejo and Gitea cannot) and the folded permission list. Save sends the token to the core, which:

  1. trims it and checks it against the forge; a network or forge error stores nothing;
  2. refuses a token of another user (logins compared case-insensitively) and names both logins;
  3. reads the scopes: a token without a scope the sync needs is refused, because the account would stop working; a token that only lacks scopes for answering or working is stored after Save anyway (Forgejo tokens cannot be edited later, a partial token beats a revoked one, and the account keeps the gap marked); missing scopes for creating or deleting repositories never stop it;
  4. stores it under the same keychain entry. If the write fails halfway, the old token is written back. Nothing is stored before steps 1 to 3 have passed.

Afterwards the account's token error and banners clear, its sync restarts, the scope marks and the open rights checks run again. The account keeps its id and every setting; all repositories of the account use the new token, since they share the one keychain entry.

The background services (classifier, dispatcher) read the token from the keychain on every cycle, so they use the new token from their next cycle without a restart. On macOS the app then grants the service helper access to the rewritten item where needed (restarting the services only if a grant changed something) and asks the classifier to poll now; on Windows the scheduled task reads the Credential Manager on its next cycle. A token handed to a headless service as GITOODO_TOKEN_<ID> or a systemd credential (docs/daemon.md) overrides the keychain and is replaced where it was set.

Release rule: a version that adds a required permission lists it in the changelog under "Added" or "Changed" as "New permission required: ...", and the permission appears in the lists above.

Closing can also be refused even with write permission: HTTP 412 means forge prerequisites are unmet, for example open issue dependencies. Gitoodo explains this and points to the issue in the browser; it does not remove dependencies or report the issue as closed.
