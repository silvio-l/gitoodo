This file is the single source of truth for the orchestrator; where it contradicts older docs (docs/daemon.md, docs/status-model.md, the former integration doc of the external orchestrator, docs/question-format.md), this file wins and those docs are to be updated.

1. Goal and scope#

Gitoodo grows from a tray app into an open-source orchestrator that runs many Claude Code sessions deterministically across several machines, using a forge (Forgejo or GitHub) as the ledger.

  • Open source, built for other people: all identifiers (labels, services, config keys, markers) are English and configurable. Human-facing text in the app follows the app language; what Gitoodo and its workers write on the forge follows the setting "Language on the forge" (app language, English, the issue's language or a fixed language; a repository can override it, #980).
  • The existing integration of an external agent orchestrator is removed and replaced. It was only the reference for several mechanisms below (worktrees, usage limits, remote hosts).
  • Clean start: no old German keywords or question format. Old German labels are written never and read only as their catalog role (aliases.tsv, section 5.6).

Version 1: classifier, dispatcher with local and remote workers, sweeper, gitoodo ask, answering questions in Gitoodo, orchestrator chat, Claude usage limits in the status bar, release planning (optional per repo).

Later: screenshot-based hang detection (screenwatch), mobile app (QR pairing, LAN TLS), GitLab for the orchestrator (the existing GitLab adapter for the plain app stays), releasing dev to main from Gitoodo, AI review of PRs.

2. Principles#

2.1 The system never blocks itself#

  1. Reconstructible: every state can be rebuilt from facts on the forge after a restart, crash or lost cache. Local databases are caches, never the truth.
  2. Nothing waits forever: every waiting or locked state has a deadline or a way out and becomes visible to the human at the latest then.
  3. Fallback instead of standstill: when a service or path fails, the others keep working (e.g. polling instead of webhooks). Exception: a fallback must never hide a failure. Where it would, use self-start plus a clear error instead of a silent substitute (e.g. the app in orchestrator mode, section 4).
  4. Failures stay small: a problem affects one issue or one host, never the whole queue.
  5. Every component documents where it can block and how it heals (blockade tables below).

The main host is not always on. When it is off, the system stands still; this is intended. After waking, every service first reconciles with the forge, then acts.

2.2 Facts and labels#

  • The forge is the only source of truth. Services write facts (comments, assignees, PRs, lease audit comments, question blocks) and labels.
  • Each label group has exactly one owner – the component that makes that decision. Nobody else writes labels of that group. Owners recompute their group from the facts on every run and overwrite it; there is no "conflict resolution".
  • Services are deterministic. LLMs run only inside workers and the chat.

3.2 Communication#

  • App ↔ services: local socket / named pipe (as today's daemon: mode 0600, user-only pipe).
  • Dispatcher ↔ satellite: SSH only (stdio bridge, JSON lines). No open ports on satellites.
  • Workers never talk back to the dispatcher directly; they write to the forge (gitoodo ask, PRs).
  • Writes from the app (answers, approvals, chat actions) go straight to the forge; in orchestrator mode the app then nudges the classifier to re-read immediately.

4. The app#

  • Two modes, selectable in the app, with the consequences explained in the UI:
    • Direct mode: the app polls the forges itself, as today. No orchestrator, no label maintenance; status is derived from assignees and PRs.
    • Orchestrator mode: the app shows the services' picture via the local socket (classifier: issues/labels; dispatcher: workers, queue, leases, hosts), plus chat, worker control and limits. If the services are down, the app tries to start them; if that fails it shows a clear error state instead of data. It never silently falls back to direct mode.
  • Repositories: connect a forge, Gitoodo lists all repos, the user switches them individually or in bulk. In the app a fetched repo is on (fully autonomous) or off; pausing is an action on a repo that is on, not a level picked during setup (#599). Stored states: off (not fetched, disabled_repos), observed (shown as "off": fetched, nobody writes; default for newly imported repos), paused (on and paused: classifier works, dispatcher assigns nothing), active (on). The stored values need no migration: observed reads as off, paused as on + paused, active as on. Switchable in the app and by chat (project focus, e.g. "only A and B now"). Since #569 the repository list selects all, by owner or row by row and switches the selection in one step; the repository's own settings (#926) edit the config-only options per repo (the human whose questions get assigned, whether release planning runs).
  • Guided setup (#569): the onboarding offers orchestrator mode and hands over to the setup assistant (service, account and rights, labels, repo, local copy, skill and AGENTS.md, first worker; see setup.md). The assistant writes only the marked Gitoodo section of AGENTS.md in the local copy, on request, and never commits.
  • Issues from the app (#569): the orchestrator view creates an issue per repo, optionally with the ready label set at once.
  • Questions: questions on which other issues wait are sorted first and show the number of waiting issues. After 2 h (default) unanswered – or the question's own deadline – Gitoodo notifies again.
  • Status bar: per Claude login the remaining 5-hour and weekly limit with reset time; when locked, clearly when work resumes; stale values are marked as stale.
  • Viewing sessions: live terminal view of any worker (local or remote) in the app.

5.2 Manually set labels (not by the worker account)#

The forge records who set a label.

  • ready by hand = approval; dependencies still win.
  • blocked by hand without a dependency fact = deliberate hold until the human removes it; the classifier comments once.
  • needs-clarification by hand starts a clarification worker: an approved issue (ready or a trusted author) with the label is dispatched like a ready one, its brief starts with "Clarify first" (find out what is wanted, then do it, or ask what only a person can decide), and the claim removes the label so an answer leads to the work, not to clarifying again. A dependency cycle still waits for a person.
  • The chat may set the labels a human sets (priority, host:, release:next), never service labels.

5.3 Trust and approval#

  • Issues and PRs by trusted authors (maintainers, own worker account, configurable list) become ready / are auto-merged without approval. Trusted from the start (#599): the connected account, the repo's human, the logins in trusted_authors (own worker accounts), everyone with write access and the members of the organisation owning the repo (Forgejo/Gitea and GitHub orgs/{org}/members/{login}; GitLab's inherited group members already count through the member level). The settings show this list next to the editable trusted_authors.
  • Others get an approval question (needs-human, kind approval). Yes → ready. No → the classifier closes the issue with a comment. Reopened by a trusted person = approval; by anyone else = ask again.
  • Foreign contributions (#705): the approval question is the only question a foreign contribution gets. It is addressed to the maintainer, but the author reads it too, so its English context explains the process ("A maintainer decides before an AI agent works on this; you'll get an answer here."); a short description adds a line, and the maintainer's yes also covers it (no clarification question to the stranger afterwards). It never carries a recommendation. A question counts as asked when the worker account or a trusted person wrote it, so changing the connected account does not ask again; the only second question is the one after a reopen of a refused issue. The per-repo rule foreign_intake (default on) switches new approval questions off; such issues then wait untouched. A follow-up a worker proposed becomes ready like the worker account's own issues; only a repo with the option follow_up_approval on (default dispatch.follow_up_approval, off) asks for approval first, and switching it off releases the waiting ones. The cap of five comments per repo and run stays. A paused repo (writes, but no dispatch) asks no new approval question either: nothing would work on the issue, so it waits untouched until the repo is active again. Its existing approval questions and their answers stay valid; an approval is never assumed.
  • Bundled approvals (#705): "Fragen an mich" shows "N fremde Beiträge warten auf Freigabe" above the list, with every open intake-approval-* question (title, author, repo, age), oldest first, and never inside the list. They are grouped by repo or by author (switchable), groups collapsed unless there is only one; the title opens the item. Every item still gets an explicit yes or no: per row (buttons or Y/J and N; Enter and Space never answer, arrows skip), per group or for all. A group answer first opens a confirmation that names the count and the scope (Cancel is focused, Escape cancels), then answers only the items of the group still undecided at that moment. There is no preselection and no trust that follows from it: bots and deleted accounts ("gelöschtes Konto", shown for Forgejo's/Gitea's Ghost) are asked like everyone else. A single answer waits five seconds, a group answer ten, and one undo (U, Backspace, Cmd/Ctrl+Z, the row's or the group bar's button) takes back the single answer or the whole group before it is posted through answer_question in the normal answer format, at most four at a time; leaving the view posts the answers already given. A failed post puts the item back to unanswered.
  • Approvals count apart (#705): Counts.approvals holds the open approvals, Counts.questions the other questions, total both (docs/counters.md). In this app, approvals of repos this orchestrator lists as observed or paused are hidden (Config::ungated); repos it does not list keep theirs, since another maintainer's orchestrator may have asked.
  • Optional spec link (#705): per repo (label_spec_link, default off, Settings → repo → Rules) the needs-human label description becomes "Waits for the maintainer. Questions: https://gitoodo.com/spec/questions/v2/"; (within the forges' 100 characters).
  • Turning a repo on never writes in bulk unseen (#598): the app shows the adoption preview first and stores the backlog choice (new default, ready, ask) with adopted_at. With new, items opened before adopted_at are not touched (pull requests: not updated since). The intake posts at most five comments per repo and run and reports the rest as pending. Questions address the repo's human, else the connected account, never the repo owner (may be an organisation).
  • Trust comes from the author's real permission on the forge, looked up once per repo and login: GitHub and Forgejo/Gitea collaborators/{login}/permission (owner/admin, maintain, write trusted; triage, read, none not), GitLab the project member level incl. inherited access (Maintainer 40 and up trusted; Developer 30 counts as write, below that not). A failed lookup, an unknown role or a missing user is untrusted.
  • Only a trusted commenter can approve; the approval question's "yes" makes the issue ready. The classifier closes a refused issue with a comment and the marker <!-- gitoodo:intake-rejected -->; a "no" followed by that marker is stale, so an issue reopened by anyone gets the question again (new block id). Limitation: the forge does not tell who reopened, so a trusted person approves by answering "yes" on the new question.
  • Incomplete issue of a trusted author (fewer than 20 non-whitespace body characters, deterministic): clarification question (kind clarification) to the author, who may answer it; once answered the issue is ready. Re-runs write nothing when the question or its answer is already there.
  • Every decision carries a reason in the read model (IssueModel.reason: trusted_author, approved, untrusted_author, follow_up, incomplete, backlog). untrusted_author (with IssueModel.author, the login) and follow_up (a worker's proposal in a repo that asks about them) appear only while the issue waits for that approval (needs-approval, or needs-human with the question open, #1677): a held (extern), blocked or stalled issue of an untrusted author shows its own state; the intake asks once it is due. A worker's follow-up is never shown as an untrusted author. Where no question was asked yet (paused repo, foreign intake off, run budget), the app approves with one click by setting the ready label (approve_issue).
  • The legacy label einordnung:fehlt is no longer set or read; a missing description is the clarification question.
  • Untrusted PRs never get auto-merge; they get an approval question.
  • This rule is security-critical (workers run without permission prompts, section 8) and needs tests.

5.3.1 Orchestrator account (#764)#

  • Per forge host (origin, case and trailing slash ignored) orchestration.json may name the account the orchestrator acts as: orchestrator_accounts maps the host to an account id. One resolution (orchestration::acting::write_account) picks the account for every write: the host's orchestrator account when it exists with the same forge kind and origin, else the repo's own account. The dispatcher (push, pull requests, merge, comments, leases), the classifier, workers (gitoodo ask) and satellite delivery all write through it; reads may stay on the repo account.
  • Choosing an account adds its login to trusted_authors once (clearing the choice keeps it), so the worker account's own issues and PRs stay trusted. While a worker account writes, questions still address the person: the repo's human, else the login of the repo's own account.
  • An account chosen for a host and the account of no repo rule is a pure worker account: the app does not sync it as a source of repos and leaves it out of the account list; the settings section "Orchestrator-Konto" shows, checks and renews it.
  • The onboarding asks per host before the services start (step "Worker-Konto", orchestrator mode only). A separate worker account is recommended: clear history, separate rights, revocable on its own, the human's notifications stay clean, and branch protection can require a human review. The own account stays possible and works: Gitoodo tells its comments from the human's by the machine markers (docs/question-format.md, "Gitoodo comments"), never by login alone; the history then shows the human's name and the forge does not notify about these actions.
  • The check of a worker account (check_worker_account) names its login, the token scopes it lacks and every activated repo on the host it cannot see or lacks a right in (the orchestrator's rights without repository settings), each with a link to grant access.
  • Existing installs keep their behaviour until the user chooses; the app shows a one-time hint that recommends the switch, never above a view (#919): a quiet entry in the status bar and one line with "Not now" in Settings › Accounts (orchestrator_hint_done ends it; any choice ends it too).
  • Lease audit comments count only from Gitoodo's own write logins of the host (acting::known_writers): the acting login, the repo account's login and the earlier orchestrator logins. A switch records the logins before and after it in orchestrator_writers (per host, newest last, at most 8), so a lease written before the switch still completes after it. A lease comment by any other user is never read (the fence against forged leases stays).
  • Items a separate orchestrator account opened do not wait for the user (#709): the adapters read the author of every open pull request, the sync flags pulls by acting::orchestrator_logins (current and earlier worker-account logins, never the user's own), and "Wartet auf dich" skips their failing checks. Issues the worker account opened stay in the questions list only while they carry an open question card. While the orchestrator writes as the user, nothing is told apart.

5.4 Question format v2#

  • Machine-read parts are fixed and English: <!-- gitoodo:questions v2 id="…" kind="worker|approval|clarification" --> … <!-- /gitoodo:questions -->. Human-read parts follow the language on the forge (docs/question-format.md); the machine-read parts stay English.
  • 1 to 4 questions per block, each with options and a recommendation; optional deadline.
  • Answers are understood in every supported language (yes/no, ja/nein, 1b, …).
  • Answered = the last comment after the question that is not Gitoodo's own was written by the asked human. No answered label.
  • An answer that sends a question back (<n> explain) counts as answered; the next worker's brief starts with the questions sent back and their notes and asks it to ask again, clearer, with a new id (or decide it when the repository settles it). An id already on the issue is refused by gitoodo ask.
  • Update docs/question-format.md, its parsers, tests and the skill accordingly (v1 support is dropped).

5.4.1 Routing and forwarding (#704)#

  • Routing rules per repo in orchestration.json (routes: [{label, to}], at most 50, edited in the repo's rules in the settings): gitoodo ask addresses a worker's question to the first rule whose label the issue carries (any case), else to the repo's human, else to the account's "Agents' questions go to" login (Settings → Accounts, default the account's own login, #1511). The worker's to stays only when it names one of these people; a placeholder (human, x) or the agent account that opened the issue is never asked. Older cards that name such a login are read as the decider's in the answer detection and in "Asked of me", so they show and their answer counts.
  • The asked person can forward a worker question addressed to them to another trusted person (5.3) from the app ("Forward to …"). The app posts, from the asked person's account, one comment with a forward marker and a new block per card (format: docs/question-format.md, "Forwarding"), assigns the issue to the new person and removes the forwarding person. The old card counts as answered; the new one waits for the new person.
  • Nobody receives a forward while holding 10 or more open cards in that repo; the app says so.
  • Answer detection follows the addressed logins: while a card addressed to someone is open the issue keeps needs-human and stays assigned to them; the answer may come from the repo's human or from any login a card of the issue names. "Asked of me" only lists items with an open card for me (or without an addressee).
  • The team chat mentions the person asked through the login-to-handle mapping (docs/chat-notification.md).

5.5 Dependencies#

  • Text lines Depends on #12 / Blocked by #12 (also repo#12, owner/repo#12), plus the forge's native dependencies where the adapter supports them. The classifier keeps both consistent; contradictions and cycles → needs-clarification. The dispatcher only reads the cleaned result.

5.6 Activating a repository#

Activation shows a preview: labels mapped to the catalog, labels to be created, remaining labels. Remaining labels are never deleted automatically, only after explicit confirmation.

Label migration (#464): the preview can be re-opened for an already active repo (app: "Migrate old labels…" in the repository's own settings (#926); CLI: gitoodo labels migrate <account> <owner/repo> [--yes], preview only without --yes). Only after confirmation are legacy labels (aliases.tsv) renamed on the forge, so issues keep them; a rename whose catalog name already exists is skipped (no merge, no duplicate) and missing catalog labels are created. Where a legacy name and its catalog name both exist, both stay. The classifier, the dispatcher, the read model and gitoodo status read a legacy name as its catalog role (Profile::canonical: a configured mapping first, then aliases.tsv), so an issue labelled status:bereit is ready, prio:1 ranks as priority 1 and an:mensch waits for a human, without rewriting any issue. Gitoodo writes catalog names only; when it removes a role from an issue (ready to in-progress, an answered needs-human, a cleared stalled) it removes every legacy alias of that role on the issue too, and a legacy alias beside its catalog name for a role that stays is left alone. The app's overview and default views (#467) still show catalog names only; a repo that still holds legacy labels shows a hint (settings-repo-detail-migrate-pending) pointing to the activation preview.

Legacy groups (#567): status (status:bereit/blockiert/in-arbeit/review, an:mensch), priority (prio:N) and release (release:muss, release:now, release:blocker → release:next) are renamed. Without a catalog label and therefore kept as remaining labels (no information lost, never deleted automatically): type (typ:*), severity (schwere:*), release:später/later/backlog, and the retired markers status:neu and einordnung:fehlt (no status = waits for the intake; a missing description is a clarification question). The system neither sets nor reads them; the renamed groups above are read as their catalog role where the rename could not run (pairs).

5.7 Human control (#568)#

The maintainer can stop, hold and veto anything the orchestrator does, and see what it did. The app reads and writes the same state files the services read (no extra RPC), so control works while a service is busy or restarting.

  • Global switch (control.json in the state dir, paused): while on, the classifier writes nothing (reconcile is empty, the Writer hands out no assignment) and the dispatcher starts nothing and merges nothing. It survives restarts; resuming continues where it stopped. The tray item control-pause and the commands control_get / control_set_paused toggle it. Pausing also stops every running worker (the lease is released, the in-progress label removed, the issue is not flagged needs-human), so it returns to the queue on resume.
  • Repo pause or off stops the repo's running workers the same way (the dispatcher enforces it on every push tick, also for remote workers) and releases leases and in-progress labels (Flag::Release over the classifier RPC removes only in-progress).
  • Merge gate per PR (control_set_merge_gate: open, held, vetoed, keyed <account>/<owner/repo>#<n>): a held PR is not merged and keeps waiting; a vetoed PR is never auto-merged and its issue gets needs-human. A global pause holds every merge. Limit: auto-merge that was already enabled at the forge cannot be cancelled by Gitoodo.
  • Activity log (activity/forge-writes.jsonl): every forge write of the classifier, dispatcher and worker tools (labels, comments, milestones, merges, closes) with time, repo, item, action, detail, reason and result. Append-only, mode 0600, texts redacted (never a token), bounded to 512 KiB (past that the newest half is kept). Read with activity_forge_writes.
  • Alerts (activity/alerts.jsonl): the dispatcher emits question, stalled, merge_failed (with a cause category, deduplicated per pull) and merge_vetoed events; the app polls control_alerts and shows them through notify::show with a click target (#939, docs/counters.md). Event control-changed carries the new control state.

6. Classifier#

  • Polls (or receives events for) all repos in observed (read only), paused and active; writes only in paused and active. Serves the read model to the app.
  • Recomputes groups 1 (defaults), 2, 5 and 6 per run; recreates missing catalog labels. Adds the marker gitoodo (group 7) to every open issue and open PR on GitHub, Forgejo/Gitea and GitLab when it is missing; observed repos stay untouched.
  • PR hygiene: a PR is linked when its commits reference exactly one issue → the classifier adds the link itself. Zero or several → failing status check + needs-issue-link + comment + needs-clarification. Lifted automatically once the link is recognised (re-run the status check).
  • Intake (5.3): a new open issue (no status label, no stalled/extern/blocked) becomes ready when its author is trusted and the body is complete; otherwise the approval or clarification question is asked. A worker's follow-up (8.3) gets the approval question only where the repo asks for it (follow_up_approval, off by default). Nobody labels ready by hand. Block ids intake-approval-N, intake-clarify-N. A question block asked after the newest intake block (a worker's parked question) owns needs-human: the intake leaves the issue to the answer detection, an earlier intake answer never ends that wait (#930).
  • Answer detection → removes needs-human, sets ready (worker questions: the issue continues on its branch, section 8.3). Each person's reply ends one wait only: a needs-human the dispatcher or a worker sets (a merge conflict, a stopped worker) ends only on a person's reply that is newer than that flag, or on a person removing the label; a reply that already ended a wait, an earlier intake answer included, never ends a later one. Replies to a card the worker posted right before its flag still count. The classifier keeps the newest used comment id per issue in answer-marks.json in its state folder (ids and issue keys only), so restarts of the classifier or the dispatcher change nothing. It runs in every repo: without a repo human or routing rule the asked human is the login in the card's header (docs/question-format.md, "Detecting an answered question"). A no to an approval card the intake no longer reads is no go-ahead; the issue keeps waiting.

7. Dispatcher#

7.1 Loop (push model)#

The dispatcher starts one session per issue; next/done of today's daemon are absorbed.

  1. Triggers: a slot frees up (worker done, question asked, worker ended), a forge change, an interval.
  2. Candidates: see 5.1.
  3. Host: reachable, matching os:/host:, below its own limit and the global limit, enough free memory, Claude login not locked. Prefer the host that already has the branch's worktree, then the least loaded one. If no host fits, skip the issue (never stall the queue). The host is chosen per issue, best score first: its os: (macos, linux, windows; darwin/win accepted) and host:<name> labels form the constraint. A host: name is a configured satellite name or one of the names of the machine running the dispatcher (#750): its own name (orchestration.json › local_host.name, default the sanitised short host name, e.g. mac for Mac.local, written once into the file on the first start), its aliases (local_host.aliases, e.g. added by "Is this machine" in Settings › Worker machines or by "Call this Mac “x”" on the switch card) and always local. The UI calls every machine that runs workers a worker machine ("Worker-Rechner"); this one is always one of them, with at least one slot, wherever the dispatcher runs. Names compare without case; one matcher (dispatch::host::names_host) serves the dispatcher and the daemon's next. Internally the machine stays the host id local, so leases and worker lists do not change when it is renamed. A satellite may not take one of these names (local_name error), and a rename may not take a satellite's name. Platform aliases. A host: value that names no machine but a platform means "any worker machine with that system", so labels from older setups work as meant (host:mac = needs a Mac). Built in (dispatch::host::PLATFORM_ALIASES, the one list): mac, macos, darwin → macOS; win, windows → Windows; linux, ubu, ubuntu → Linux. orchestration.json › platform_aliases adds more or overrides one ({"nixbox": "linux"}; other systems are ignored). An exact machine name always wins: with a satellite called win, host:win means that machine only. The same rule (dispatch::host::place over all hosts, label_fits for the daemon's next) serves the dispatcher, the read model's host_wait and gitoodo next; the label scan of Settings › Worker machines skips platform aliases. This machine may not take another system's alias as its name or alias (invalid_name), so a Mac never becomes win. An issue no host can take waits without blocking other issues, with one concrete reason (dispatch::host::WaitReason, checked in this order): unknown_host (the host: label names no host and is no platform alias), no_platform (no worker machine runs the system the issue needs: its os: label or the platform of its host: alias; an offline machine counts with the system stored at its setup, hosts[].platform), os_mismatch (the named host, or every host of the host: platform, runs another system than os:), offline (set up but does not answer), machine_paused (answers, but paused after a failed start until its retry, #982), disk_low (answers, but its disk is nearly full, #970; neither of the two reads as offline, #1643), build_budget (answers, but the build a worker of the issue's repository would make does not fit there above what stays free for the user, or within a build cap from the file, #1418, #1809; judged per repository, so issues of a repository with a smaller build still start, #1804), agent_missing (coding agent missing or signed out), usage_gate, login_expired (the agent says its login there no longer works, e.g. a revoked refresh token behind "Logged in", #994), low_memory, at_capacity, host_limit (the matching host runs the maximum the user set for it, below its cores, #967), global_limit or tool_missing (every host that fits lacks a command of the issue's tool: labels, docs/orchestrator/satellites.md); repo_share (the repository is at its fair share of the slots while another one below its share has ready work, #959) is the dispatcher's own and applies to unpinned issues too. The reason is written to host-wait.json and the read model (host_wait.reason), logged once per new wait or changed reason as dispatch.host_wait issue=<repo#n> host=<name|-> reason=<reason>: …, shown on the board, and notified once per issue and reason for unknown_host, os_mismatch, offline, disk_low, build_budget and agent_missing (only the user can end those). With offline, machine_paused, disk_low and build_budget the wait names the machines whose state is the reason (host_wait.held_by), and the log line, the notification, the board and the status line name them too (#1643). The dispatcher status counts the waits by reason (host_wait_reasons), the unknown host: names with their issues (unknown_hosts), the systems no machine runs (missing_platforms, e.g. {"windows": 12, "linux": 42}) and per reason the machines that hold issues back (host_wait_machines, e.g. {"disk_low": {"hp840": 1}}). Only those six reasons make the status page and the switch card say "needs you", with the concrete fix in place: one unknown name as "3 issues are marked for the machine “studio2” (label host:studio2) … This machine is called “macstudio”. Is this machine “studio2”? [Yes]" (adds the alias) and [Show labels], several names grouped with their counts and one question each. no_platform is no problem: it notifies nobody, and the card names it in one calm line ("12 issues need a Windows machine, 42 issues need a Linux machine. They start once one is connected.") with [Add machine] (Settings › Worker machines). Settings › Worker machines lists host: labels on the open issues of the paused and active repos that name no machine, with counts, and offers: set it up as another machine, treat it as this machine (adds an alias), or remove the label from those issues (forge write after a confirmation with the count). The onboarding's workers step (orchestrator mode, after accounts, repos and the setup) sets the workers at once (max_workers), this machine's name, explains host: labels and offers the alias for each unknown label once the read model has them.
  4. Order: first the next release, then the score. The next release of a repository is its release scope (release:next while it has no version), the open issues of its next release milestone (the open milestone with a version title that is due first, else the lowest version; sprints and other titles never count) and every issue they depend on; boosted issues join that first group. Inside each group: score = priority weight + age factor + manual boost + release bonus. Age grows steadily so nothing starves. Impact and effort are not part of it. (defaults: p0 1000, p1 300, p2 100, p3 30; +1 per hour of age; manual boost +500; release bonus +200, scaled by the release's due date: full without one and from one day before it, 25 % from 14 days away, linear in between, #1850). Between repositories a release due soon goes before the rotation and may take more than the equal share of the slots; see queue-order.md. A blocked issue is skipped, so the rest of the release and then the other issues still go; with no dispatchable release issue the queue runs on the score alone. Repositories with release planning off have no first group but boosted issues. A repo may carry its own score weights in its repos entry (#569); without one the global score applies. Editable in the repository's own settings, section "Order" (#926).
  5. Assign: set in-progress, write the lease audit comment, create or continue branch and worktree, start the session (section 8).
  6. Watch: liveness, hangs, leases, limits, PR state.

Limits: per host 1 worker per 2 CPU cores (default), global 8 (default), set in Gitoodo.

7.2 Branches and worktrees#

  • Branch <prefix>/<issue-number>-<short-title>, prefix default gitoodo (e.g. gitoodo/42-login-fix).
  • Worktree under a root per host, default ~/gitoodo/worktrees/<repo>/<issue-number>. Base is always dev.
  • A restart (hang, dead worker, after a question) continues branch and worktree with a new session (issue + Q&A + handoff + git log + diff as start; no --continue).
  • Only a new attempt after the old branch was merged (issue reopened) gets -2, -3.

7.3 Session environment#

  • Claude Code is started with --dangerously-skip-permissions (maintainer decision; accepted risk) unless the repo's worker_permissions is guarded (--permission-mode auto). Only the issue and trusted people's comments reach the worker (docs/security.md).
  • Sub-agents stay off unless the repo's worker_sub_agents is on (#952): Claude Code --disallowed-tools Agent, Codex -c features.multi_agent=false -c features.multi_agent_v2=false -c agents.enabled=false; another agent program started from the worker's shell is logged (dispatch.nested_agent) and, with the setting off, ended.
  • Workers start lean (no user MCP servers, plugins, skills, slash commands, memory or extra tools; the repository's instructions and Gitoodo's hooks stay); a repository can allow named MCP servers (worker_mcp_servers). See docs/orchestrator/dispatcher.md, "What a worker loads".
  • The dispatcher passes settings with a managed statusLine command and Stop/StopFailure hooks that call gitoodo (usage limits, section 7.7), the app language, and build-parallelism limits: CARGO_BUILD_JOBS, MAKEFLAGS=-jN, test thread counts = cores / workers on that host.
  • Optional shared compiler cache (e.g. sccache) across worktrees.
  • No worker starts below 1.5 GB free memory (default); under memory pressure nothing new starts there.

7.4 Hang detection (v1)#

  • Active = terminal output or git changes in the worktree. Both silent for 10 min (proposal; the board had 5 min before the screenshot stage, which is postponed) → before acting, re-read the issue: needs-human open or Claude login locked → not a hang. Otherwise restart.
  • 3 restarts (default, per issue configurable) → stalled.

7.5 Questions (gitoodo ask)#

gitoodo ask reports "done with question"; the dispatcher ends the session and frees the slot immediately (in-progress → needs-human). When the classifier sets ready after the answer, the issue is assigned like any other (preferring the host with the worktree).

7.6 Leases and dead workers#

  • Lease expired and the worker provably dead (no process, no output, session gone) → release the issue; counts as a restart.
  • Not checkable (host offline) → release after a 30 min grace period (default).
  • After the main host wakes: check liveness before releasing anything.
  • One dispatcher per config and state folder (OS file lock). A starting dispatcher releases only local leases whose owner (machine, process id, start time) is provably gone; leases of other machines or installs are never deleted, only expired by time (release-gate review M7).
  • Claiming is compare-and-confirm: status label, own login added to the assignees (others stay), lease comment, then a fresh read; the oldest active lease comment of the race wins, the loser withdraws its lease and only its own assignee (M10, docs/daemon.md).

7.7 Claude usage limits#

  • Tracked per host / Claude login: 5-hour and weekly window (percent, reset time), plus per-model weekly limits where reported.
  • Sources: (1) statusLine JSON of running sessions (rate_limits.five_hour / seven_day, Claude Code ≥ 2.1.80) – primary while sessions run; (2) the OAuth usage endpoint of the login (api.anthropic.com/api/oauth/usage) when no session runs, with a minimum interval, backoff and Retry-After; (3) the StopFailure hook (≥ 2.1.78) for "limit reached". If (2) breaks, fall back to (1)/(3) and the known reset time; show values as stale. (2) reads the login Claude Code itself keeps (macOS: the keychain item under the user's name, named after CLAUDE_CONFIG_DIR when set). An ended access token is Claude Code's to renew: the poll has it renew (claude auth status) and reads again; "not signed in" only when Claude Code itself says so or the login is refused or missing, otherwise the query failed for now (#1912).
  • At ≥ 90 % (default) in any window: no new workers on that login.
  • Limit reached: login locked until the reset; the session stays open; at reset the dispatcher types "continue". Not counted as hang or restart. Other hosts with other logins keep working.
  • While locked, the usage source is asked every 5 minutes (instead of 15), or just after a sooner known reset, at most once a minute; a report with room again ends the lock early. The app shows the pause with its end and offers "Resume now", an immediate check (recheck).
  • Satellites deliver the values through a small state file the dispatcher reads over SSH.

7.8 Pull requests and merge#

  • The worker opens a PR (Closes #N, normal description) and ends. No extra review in v1; the condition is the complete green CI (dev is protected: merge only with green status checks).
  • The dispatcher enables auto-merge to dev (squash) and sets in-review. Auto-merge is only a real gate with branch protection requiring status checks; without it, or where the forge has no usable auto-merge API, the dispatcher merges itself once all checks reported on the reviewed head SHA are green, and a head without any check only after a grace period (checked against the forges' sources; see dispatcher.md).
  • Required checks per repo (#569): repos[].required_checks lists check names that must be green on top of the forge's required checks (default: empty, i.e. exactly the forge's required checks as before). A listed check counts with the worst state its head commit reported and as pending while nobody reported it; failing ones count as red CI. With such a list the dispatcher merges itself instead of enabling forge auto-merge, because the forge does not know the extra checks. Editable in the repository's own settings, section "Merging" (#926).
  • CI red or merge conflict → new session on the same branch with the failure output; counts as a restart.
  • After the merge the dispatcher closes the issue itself (Closes #N acts only on the default branch on GitHub; Forgejo behaviour differs; closing explicitly is idempotent) and triggers the sweeper.
  • Workers never merge to main.
  • A worker holds no forge credential. It delivers with gitoodo worker pr (push, then open the PR; --title, --body) or gitoodo worker push (push only), which use the account connected in Gitoodo (keychain token, existing write adapters). Design and limits: dispatcher.md "Worker delivery".

8. Workers#

8.1 Contract#

One issue, one worktree, good commit messages, a PR with Closes #N into dev. No labels, no control of other workers, never merge to main. Asks via gitoodo ask when a decision is missing.

8.2 Prompt template (proposal)#

Issue title/body/comments (incl. Q&A and handoff), repo conventions (CLAUDE.md), branch, base dev, definition of done (green CI, PR), how to ask (gitoodo ask --help), the language on the forge for question blocks, status notes and the pull request title and description (code, commit messages and repository files follow the repository's own rules; gitoodo worker context repeats it as forge_language). A clarification worker gets the contradiction and resolves it or asks. When the human handed the issue back with a note (docs/question-format.md, "Instructions"), the newest instruction of a trusted person comes first, outside the comment budget, with the rule that it overrides the issue body and its checklist (steps left to a human included) and that the worker asks back only when truly blocked; gitoodo worker context carries it as human_instruction. When a trusted person answered the newest question block, the answer follows, also outside the comment budget and resolved against the block: every question with all its options and, next to each, what was chosen (1a 2b never has to be mapped by the worker); gitoodo worker context carries it as answered_question. Question blocks and answers in the discussion are never cut; only other comments are clipped, and older ones give way first. The brief is the worker's copy of the issue (#1431): body up to 8,000 characters, failed checks of a restart included, so the worker needs no first gitoodo worker context call.

8.3 gitoodo ask#

Required: --question (1–4, each with options and a recommendation), --next (what to do after the answer, per option if they differ). Optional: --notes (rejected approaches, pitfalls). Added automatically: issue and branch (from the worktree), commit messages since dev, changed files, worker, host. The tool refuses calls with missing fields and limits the handoff to about 15 lines.

Behaviour: commit and push the work in progress → write the question block (question on top, handoff collapsed below) → set needs-human, assign the human → tell the dispatcher (session ends, slot freed). It writes directly to the forge, so questions arrive even when the dispatcher is down. gitoodo ask --help is the worker's manual; the skill only points to it. No handoff on normal completion – the PR description is enough.

Follow-up work found by a worker (#337): work outside the worker's issue (a bug elsewhere, a missing test, outdated docs) is proposed, not done. gitoodo worker follow-up --title <t> --body-file <path|-> [--label <kind>] sends the proposal to the dispatcher with the worker's capability; the worker never creates issues itself. The dispatcher checks, in this order: the capability and the issue path (as for every worker action), title and body (title one line, at most 200 characters; body a complete description, at most 16 KiB), the repo setting worker_follow_ups (default on, Settings → repo options), a live lease of this worker on its issue, at most dispatch.max_follow_ups_per_run per run (default 3, 0–20; restarts of the same run count together) and at most 10 per repo and hour, and a chain depth of at most 3 (follow_up::MAX_DEPTH: the issue a follow-up comes from counts its own depth in the marker, a legacy marker without one counts as 1). Then it creates the issue with the account's token:

  • the worker's title and body, with <!-- defused so the text cannot forge Gitoodo markers, and a footer "Follow-up from #N (worker W)" plus the marker <!-- gitoodo:follow-up parent=N worker=W depth=D -->;
  • the intake label gitoodo (if the repo has it), so the classifier triages the issue, and the optional --label when the repo has that label and it is no workflow, priority, host or release label;
  • never ready: an open issue with the same normalised title (case, whitespace and punctuation ignored) refuses the proposal instead.

A short note on the parent issue lists the follow-up. Refusals reach the worker as one line naming the reason (setting off, cap reached, duplicate #M, unknown label, rate limit, too deep); forge errors only say that nothing was created. By default the intake makes the follow-up ready like the worker account's own issues, so it joins the queue. A repo with "Approve each follow-up before it is worked on" (follow_up_approval, default dispatch.follow_up_approval, off) has the intake treat it like a contribution from outside (5.3): it asks the repo's human for approval ("yes" makes it ready, "no" closes it) and the read model never counts it ready on its own; switching the option off releases the waiting follow-ups as if approved. Satellite workers cannot propose follow-ups yet; they mention findings in the PR description. Red CI never creates a new issue.

Splitting an issue that is too big (#1012): the brief's first section asks the worker to size up its issue before changing anything. An issue that fits into one coherent run (the usual case) is done there; one that is clearly too big is split before any code with gitoodo worker split --plan <file>, a JSON plan {"reason": "…", "parts": [{"title", "body", "label", "after"}]} of 2–8 parts, each with goal, scope and acceptance criteria; after names earlier parts (0-based) a part needs. Splitting is offered where follow-ups are (the setting worker_follow_ups, not on satellites); otherwise the brief says to do the whole issue in one run. The dispatcher checks the plan (each part like a follow-up, after only backwards, no part depending on the parent), a live lease and at most 5 splits per repo and hour, then creates the parts in order with the account's token: the worker's text, a Depends on #x line for its after parts, a footer "Part i of n of #N" with the marker <!-- gitoodo:part parent=N index=i worker=W --> and the intake label gitoodo, in the parent's release (its milestone and release:next, #2061). One note on the parent lists the parts and says that it waits for them. Parts go through the intake like follow-ups (approval only where follow_up_approval is on); independent parts are dispatched in parallel, dependent ones only after their prerequisites (5.4).

  • The parent waits while one of its parts is open (read model, dispatch pick and hygiene agree; only parts the writing account opened count). Once all are closed it is ready again, and its brief lists the parts and asks for the integration and verification of the whole; it is never split again. The parent closes only through its own pull request.
  • A part is never split again (refused, and its brief says so).
  • A split run again (after a restart) reuses the parts that exist by index and creates only the missing ones; a split of a parent whose parts are all closed is refused.
  • After a successful split the worker stops without a pull request. The run ends as split (trace dispatch.split), a good end: no restart, no "no PR" handling; the lease goes, the worktree and branch are removed and the parent returns to the queue, where it waits. A failed split reaches the worker as issue not split: <reason> and changes nothing on the parent; when the forge failed after some parts, the reason names them, and the same split run again reuses them.

9. Sweeper#

  • Triggers: event from the dispatcher (PR merged to dev, issue closed; on satellites over SSH), an interval (default hourly), and workers clean their own worktree regularly.
  • Deletes worktree, local and remote branch after the merge to dev.
  • Never deletes branches with unmerged commits or worktrees of running workers; reports them with a comment and needs-human. Offline hosts catch up on the next run.
  • Crashes, resets and leftovers: the reconcile round, remote branch cleanup, disk guard and temp root of the repo hygiene (#771).

10. Release planning (optional per repo)#

  • A release is a milestone whose title is a version; membership is the milestone. release:next marks the next release while it has no version. Once a release milestone is the next one, its release:next issues move into it and lose the label (on every forge; existing labelled issues carry over on the first poll, no separate migration).
  • An issue enters a release only through: (1) its release milestone or release:next, set by the human, the chat or an assignment rule (open priority:p0 issues by the default rule "Urgent issues join the next release"), (2) being an open dependency of a member: it joins that release with it, transitively (#1824; one in an earlier release stays, one in a later release is pulled forward; the other way round, an issue moved into a later release takes the issues of earlier releases that wait for it along, #2046). Everything else is backlog. A removal by hand sticks: no rule and no hygiene puts the issue back into that release.
  • Only milestones whose title is a version (v1.2.3, 1.2, 2026.11, build 42) are releases; sprints and other milestones are left alone. Next release milestone = the open release milestone that is due first, else the lowest version, else the oldest; default length 3 weeks. Several open release milestones are normal (the others are later releases); only a tie for the next one is a finding. One rule (release::next_release_milestone) serves the queue, the allocation of release:next issues and follow-ups, the adoption preview and the release view.
  • The due date is a decision point, not a cut: all done → question "release now?"; open items at the due date → question with the list (move, remove, extend). Nothing is cut automatically.
  • No open release milestone → question "create the next milestone?" (block intake-milestone-N, anchored on the lowest-numbered open issue, no planning issue). Yes → the classifier creates the version the question named (the version suggestion, #1142; asked again when it changed meanwhile) and writes <!-- gitoodo:intake-milestone-created -->; No → asked again after 28 days.
  • All questions and findings of release planning name the scope label release:next (never the legacy release:muss).
  • The app shows the release milestone planning works on (or none, or several without a clear next one) in the release view next to each repo and in the repository's own settings (#569, #926).
  • Issues of the next release (the scope above plus the open issues of the next release milestone and their dependencies) go first in the queue and get the score bonus (7.1 item 4).
  • In the app the user creates releases, assigns issues to the next, a later or no release, and sees each issue's release on the board row, the issue sheet and the release view. Completing a release runs its steps (close milestone, notes, tag, forge release, own commands) after a confirmation in the app (release planning).

11. Satellites#

  • gitoodo host add <host> (also from the app): copy gitoodo over SSH/SFTP into a versioned directory, verify the checksum, start gitoodo satellite. On every connect compare versions, update, roll back if the new version does not start.
  • Service per OS: Windows with a visible desktop session → task at logon (windows optionally visible); Linux without desktop → systemd user service with lingering; macOS → LaunchAgent in the GUI session (keychain access for the Claude login). If no session is logged in, the dispatcher starts the satellite detached over SSH (setsid/nohup; on Windows break away from the OpenSSH job object) without windows, and the app says so clearly.
  • The satellite owns one PTY per worker (Unix PTY / ConPTY via portable-pty), keeps a bounded scrollback, feeds output to hang and limit detection, accepts input, streams to the app, and lets gitoodo attach <issue> (local or ssh host gitoodo attach 42) attach; the most recently active viewer sets the terminal size. Workers keep running when SSH drops or the main host sleeps.
  • Delivery from a satellite (#582): gitoodo worker push|pr there sends the assigned branch as a git bundle (commits beyond origin/<base>, at most 16 MiB) over the satellite's subscribe connection (DeliverForward/DeliverDone, like questions). The main host checks that the satellite holds the issue's lease for exactly that branch, replays the bundle into a temporary bare repo, then pushes and opens the PR (Closes #n) with its own token through the same code as local workers, so gate and merge are identical. The token never leaves the main host. Failures (main host offline, no subscriber, push refused, no lease) are returned to the worker, logged and recorded as a refused activity entry; the lease and the worker stay, so the issue waits and delivery can be retried.
  • The main host runs the same PTY host locally.
  • Auth: per forge one worker account with its own token, shared by all hosts; rights: issues, labels, comments, branches, PRs, merge to dev. No rotation inside the system.

12. Orchestrator chat#

  • Claude Code headless in structured mode (claude -p with stream-json input and output), rendered as a native chat in Gitoodo. Uses the user's existing Claude login.
  • Tools only through gitoodo mcp; no file access, no shell (enforced via allowed tools). Its tools only read; every change below is a proposal the human applies with an OK in the app.
  • Can: create and sharpen issues (priority, OS, dependencies, several at once), query status, change priorities and boost, focus or pause projects, answer approvals and questions, stop or restart workers, set human labels. Cannot: write code, change repos, set service labels, merge.
  • Lean context: reset at 10 % used context (default) with a handoff of fixed fields (goal, decisions, open points), stored locally in Gitoodo; the next session starts from the handoff.

13. Configuration (proposal)#

Shared settings.json (accounts, app mode, language, repo states) plus an orchestration file: trusted authors, the orchestrator account per forge host (section 5.3.1), hosts (name, SSH target, OS, worker limit, show windows, worktree root), global limit, branch prefix, score weights, timers (hang 10 min, lease grace 30 min, reminder 2 h, sweeper interval 1 h, polling 5 min), thresholds (Claude 90 %, free memory 1.5 GB), label name mapping, release planning on/off per repo. Reloaded without restart, as today. A broken file never stops running work: the dispatcher keeps the last valid configuration for it, starts nothing new and reports the file and position once (alert, status, gitoodo doctor; M9).

14. Quality requirements#

  • Terminal fidelity: Claude Code must work in the PTYs as it does in a normal terminal. Acceptance tests on Linux, macOS and Windows: true colour, resize, full-screen UI, large paste (bracketed paste), Esc, Ctrl+C, Shift+Enter, Unicode/emoji width, scrollback, attach/detach without the session noticing.
  • Resources: event-driven, near-zero idle CPU. Budgets as acceptance criteria: gitoodo satellite idle < 15 MB RSS, classifier and dispatcher < 30 MB each, scrollback 2 MB per session. crates/cli/tests/rss_budget.rs checks the resident set and, tighter, the private memory (Linux RssAnon, macOS physical footprint) of debug builds in an empty home (#769).
  • Robustness: section 2.1 and the blockade tables.
  • Single writer: classifier and dispatcher each hold an OS-level lock (lock file with flock/LockFileEx) so that a second instance on the same host never writes to the forge.
  • Tests: table-driven tests for labels, trust (including reopening and foreign PRs), dependencies and cycles, score, host selection, leases and release scope; contract tests against recorded Forgejo and GitHub responses; terminal acceptance tests (above); RSS budgets as tests; end-to-end tests only against a dedicated Forgejo test repository, never a real project.

15. Migration plan (proposal; each step mergeable, the system stays usable in between)#

  1. Rename gitoodo-cli → gitoodo, app binary → gitoodo-app.
  2. English label catalog, question format v2, non-destructive activation preview, repo states.
  3. Split the daemon: classifier (+ read model on the socket); app direct/orchestrator mode.
  4. Dispatcher with local PTY host: push loop, worktrees, leases, gitoodo ask, hang detection, auto-merge, sweeper. The former integration of the external orchestrator (doc, modules, UI, settings) was removed afterwards (done, #306).
  5. Claude usage limits and status bar.
  6. Satellites: host add, satellite service, SSH bridge, attach, optional windows.
  7. Orchestrator chat (gitoodo mcp, stream-json UI).
  8. Release planning.

16. To verify during implementation#

  • Forgejo: does Closes #N close issues on merges into a non-default branch? Auto-merge API.
  • Native dependency APIs of Forgejo and GitHub.
  • Claude Code: statusLine rate_limits fields, StopFailure hook, --settings injection, stream-json.
  • Stability of the OAuth usage endpoint; behaviour without a subscription (API key).
  • ConPTY attach behaviour and resize on Windows; keychain access of a detached satellite on macOS.
