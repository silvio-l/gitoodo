Mental model, as the app says it: a release is one goal per repository: which issues have to be in before you publish. Gitoodo works on release issues first.

Using releases#

The board tab "Release" shows every repository with release planning on as a tree: below each repository its open releases, the next one first, and last "Ohne Release" with its open issues in no release, so every open issue of the repository is found below it (see "Release tree" under "App"). A short walk through it:

  1. Plan. "Neues Release" on a repository row creates a release, a milestone named with a version (the dialog suggests the next one). The flag on a board row or "Ändern" in the issue sheet puts an issue into the next release, a later one or none. Without any release, the empty state offers both: add issues to the next release, or create a release with a version.
  2. Let the autopilot work. Issues of the next release go first in the queue, and the issues they depend on with them. Nothing else changes; the rest of the queue runs as before.
  3. Set it up once (gear "Release-Einstellungen" on the repository row, always shown): pick a template and "Übernehmen", then adjust the tabs. Versionierung decides the version suggestion, Zuordnung the rules that put issues into a release or suggest them, Abschluss the steps that run when you complete a release, Sitzung the task of the release session. Every change saves by itself, like the other repository settings (#926); a part with problems stays unsaved and says so.
  4. Prepare ("Release-Sitzung …" in the release's "…"): a release session gives a coding agent or a plain terminal the version, the issues and the notes, in the working copy or a fresh worktree.
  5. Complete ("Release abschließen", a ticked circle, once every issue is done): the dialog shows the plan first, where open issues go and every step, the irreversible ones marked, and nothing runs before you confirm. A token that lacks a right the steps need refuses the plan before anything is written. A failed step can be retried or skipped from the run row. "Danach" decides what the autopilot does once the release is closed: "Autopilot anhalten" (the default) pauses it, and the tree then offers "Mit 1.6.0 starten"; "Gleich mit 1.6.0 weitermachen" lets it go straight on with the next release.

The help center has a topic "Releases" of its own (the release page's help link opens it).

Command steps run your own scripts in the local checkout of the repository. The templates point at ./scripts/release/*.sh, which the repository provides; until it does, the step fails with the script's error and nothing else happens. A minimal skeleton:

#!/bin/sh
# scripts/release/upload.sh: upload the build of this release.
set -eu
echo "Uploading ${GITOODO_RELEASE_TAG} of ${GITOODO_REPO}"
# The notes are in "$GITOODO_RELEASE_NOTES_FILE", the issues as JSON in "$GITOODO_RELEASE_ISSUES".
# Exit 0 when done; any other exit fails the step and shows the last lines of the output.

A step gets no token; a script that needs one reads it from the system's own secret store. A version script (scheme "Eigenes Skript") prints the next version and gets GITOODO_LAST_VERSION, GITOODO_VERSION_RAISE and the release's issues (see "Own script" below).

Scope#

Per repository, an issue belongs to the next release when

  1. it is in the next release milestone (see "Queue order"), open or closed (reason milestone),
  2. it carries release:next (reason label), or
  3. it is a dependency, recursively, of a member (reason dependency).

Only dependencies inside the same repository count. A closed issue stays in only through the milestone, the label or as a dependency, so a finished dependency stays part of the release. While no release milestone is open, release:next alone is the next release.

Dependencies join the release (#1824, before: pulled-in issues, #1530)#

The sub-tasks and blockers of an issue are needed for it, so they join its release on their own; nobody has to add them by hand. A dependency is what the release view shows as one: a dependency line (Depends on #12, Wartet auf: #12, …) in the issue's body or in a person's comment, the forge's own dependencies, and the open parts of a split issue (#2061; only parts Gitoodo's own accounts opened, the same rule as for the parent's wait). A split gives each new part the parent's milestone and release:next at once; a part without one (split before, or the write failed) joins in the hygiene's next pass.

  • When an issue goes into a release (the add dialog, "+", "Change release …", the chat), its open dependencies in the same repository go with it in the same operation, transitively. The add dialog says so before saving ("+ 3 dependencies (sub-tasks and blockers) come along") and marks each one on its row. After saving, the release view shows them at once, already below the issue that needs them (the same rule as the report's, among the added issues); the next poll confirms the place and may move one below a member that was in the release before.
  • The hygiene pass adds dependencies that appear later: for every open issue in an open release, its open dependencies join that release, the earliest release first. Each join is logged (release.dependency_joined) and named in the classifier's activity ("#12 joined v1.4 as a dependency of #10"). These writes count towards the pass's limit of release writes. Without the milestone rule the pass only writes release:next; a dependency of a release milestone then joins when its issue is put into the release in the app.
  • Where a dependency already is decides: in the same release or an earlier one it stays (the earlier release ships it first anyway); in no release it joins. In a later release it is pulled forward into the release that needs it (the activity says so: "pulled forward from v1.5") only when a pass of Gitoodo put it there (a rule or an earlier join, kept as placed in release-rules.json while the issue is still there). One a person put into a later release, in the app or on the forge, stays where they put it (#2061): the hygiene never undoes a person's release choice. Its release then waits for it ("Out of order" below), and the focus never starts it for the earlier release; moving one of the two in the app resolves it. Putting an issue into a release in the app ("Change release …") is the person's own choice and takes its dependencies along from a later release too.
  • Moving an issue into a later release takes the issues that wait for it along (#2046). An issue in an earlier release that waits for the moved one (directly or over another such issue) could not be done before it, so its release could not ship either; it goes into the same later release in the same operation. "Change release …" says so before saving ("+ 2 issues waiting for it go along: #154, #300"), and each move is logged (release.dependent_followed). Issues already in that release or a later one, and issues in no release, stay where they are.
  • The order stays visible. Every row says what it waits for ("waits for #249, #2160"); a blocker that is planned in a later release or in none is named in red below it ("Out of order: #2160 is planned later or in no release"), so a split that came from the forge, a removal by hand or an older build is seen at once. Taking an issue out of every release while issues in a release wait for it says so in "Change release …" before saving; they stay.
  • Closed dependencies are done and are ignored.
  • Another repository: a dependency there never joins (each repository plans its own releases). It is listed under its member ("belongs to #44 · other repo (owner/lib) · not in the release"), does not count, and while it is open it still holds the release's completion.
  • A removal by hand sticks: a dependency a person takes out of the release stays out while its issue still needs it, like for the assignment rules. It is then listed under its member as "belongs to #44 · not in the release" and holds the completion while open.
  • The counts name what they leave out. The release's summary line counts members only ("2 open · 1 in progress") and adds the open items it lists without counting them ("+1 not in the release"), so the rows and the numbers add up.
  • Taking an issue out keeps its dependencies. Gitoodo has no reliable record of whether a person also wanted a dependency in the release on its own (it may have been added by hand before, or be needed by another issue), so it leaves them where they are; take them out by hand if they should go too.

Dependencies that joined are members like every other issue: they count in the progress (3/5, "1 open · 1 in progress"), the same as the forge's milestone. The release view lists every item below the item of the same release that needs it (via: the first item, by number, at the top of its dependency chain), one level indented; a later release does the same.

Every issue that is a member gets a release chip (flag and version) on its rows: the Issues list of a repository, the board of all repositories and the detail sheet. Its milestone is the one source; a label or a pulled-in issue never makes a chip. The chip opens the release view at that release (a later one opened too). The row's release choice then reads "Change release …".

Open priority:p0 issues used to be members by themselves (reason priority), without anything on the forge. Since #1143 the assignment rule "Urgent issues join the next release" (on by default, see "Assignment rules") writes them into the next release instead, so they are visible on the forge and a person can take them out again. The reason priority is no longer sent.

Gitoodo writes only release:next. It reads the legacy release:muss as release:next and release:später as "not in the next release" (it adds nothing); neither is ever written. Adding an issue through the app removes a legacy later label from it.

Planning is switched per repository in the settings, right beside the repository's activation ("Release planning", default on; stored as releases in the repository options). With it off, the repository has no scope, no bonus and does not appear in the views.

Labels and milestones#

A repository plans its releases as milestones: **a milestone whose title is a version is a release**, and release:next stands for "the next release, version not decided yet". Other milestones (sprints, themes) stay the user's own and are never treated as releases. Several open release milestones are a normal state: the next one is picked as in "Queue order", the others are later releases (see "Releases by hand").

Membership is the milestone. release:next only marks issues for the next release while it has no version; as soon as a release milestone becomes the next release (created in the app, on the forge or by the user's answer to the milestone question), the hygiene moves every open release:next issue without a milestone into it and takes the label off (hygiene::takes_over). This also carries data from before the milestone model over without a migration step: an existing release:next issue keeps counting as the next release and moves into the milestone on the first poll after it exists. It uses only the forge adapter's milestone and label calls, so it works the same on Forgejo/Gitea, GitHub and GitLab (the calls per forge: crates/core/tests/release_forge.rs). The forge calls behind it came with step 1 of epic #1139 (#1140); the app shows all of it since #1148.

A milestone title counts as a release version (forge::release::release_version) when, after trimming, it is

  1. optionally v/V directly before the number, or one of the words version, release, build, ver (any case) followed by a space, - or _,
  2. then one to four numbers separated by dots (each at most nine digits),
  3. then optionally a pre-release or build part after - or + of letters, digits, dots and hyphens (-rc.1, +20261119), allowed only after a dotted number or a prefix word,

and nothing else. So v1.2.3, 1.2, 2026.11, 42, build 42, Release 1.4 and 1.0.0-rc.1 are releases; Sprint 12, Q4 2026, Milestone 3, v1.2 Winter, 1.x, 1.2.3.4.5, 12-sprint and 2026-11-19 are not.

Rules that hold on every forge:

  • Creating a tag is idempotent: the same tag on the same commit is success, on another commit it is refused and the tag is never moved or deleted.
  • A release is created as a draft where the forge has drafts. An existing draft is reused (name and notes updated, it stays a draft); a published release is left as it is and only changed on an explicit call. GitLab has no drafts: a draft request is refused before anything is sent, and a GitLab release is public as soon as it exists.
  • GitLab group milestones can be read and assigned, but not edited or closed through the project; the error says to change them in the group's milestones or to use a project milestone. Gitoodo never edits a group milestone, because that would change other repositories too.
  • Every write goes through the audit log (milestone_create, milestone_edit, tag_create, release_create, release_edit, milestone_delete, tag_delete). Refusals (403, 404, 405, 409, 422) name the missing right or the cause and never contain the token.
  • The release rights (rights::check_release) are checked separately from the mode check, so they do not appear as missing in the app yet.

Known limits: Forgejo and Gitea cannot clear a due date once set (their API ignores an empty one), so the app offers "Kein Datum" only on GitHub and GitLab (release::can_clear_due); tag protection rules (GitHub rulesets, Forgejo/Gitea tag protection, GitLab protected tags) are not read in advance, so a protected tag shows up as a refusal when it is created; GitLab has no pre-release flag.

Version logic and suggestion (#1142)#

Step 3 of #1139 adds the version rules in the Rust core (orchestration::version). They are set in the release settings (tab Versionierung, #1147); the release dialogs show the suggestion with its reason (see "Surfaces" below).

Config. Each repository can have a version entry in its rule in orchestration.json in the app's config folder. It is never stored in the repository. Without the entry the repository uses SemVer with every preset.

{
  "scheme": { "kind": "semver" },
  "raises": [{ "source": "label", "name": "api-change", "part": "major" }],
  "presets": ["plain", "prefixed", "issue_types"],
  "default_part": "patch"
}
scheme.kindVersion
semverv1.4.2
calendarpattern from YYYY, YY, MM, M, DD, D and the counter N: YYYY.MM, YYYY.MM.N
buildone rising number: 42, build 42
patterntext around {major}, {minor}, {patch} or {n}: v{major}.{minor}.{patch}, release-{major}.{minor}, build-{n}
scriptcommand runs in the local checkout and prints the version

A pattern is refused when it cannot be read back as a version: a field twice or two fields without text between them, digits in the text, a calendar without year or month, the counter not last, {n} mixed with the other fields, fields out of order, or a result that is no release title (b{n} gives b0, which is not a version; build-{n} is). Patterns and commands are limited to 1000 characters, own rules to 200. version_config_validate lists the problems with field, code and text.

Raise of an issue. Each label (source: label) and the native issue type (source: type) is looked up, case-insensitive: first the repository's own raises, then the presets. An own rule replaces the preset for that name. The issue raises the highest part found; an issue that no rule matches raises default_part. Native types are GitHub's organisation issue types (type.name) and GitLab's issue_type (issue, incident, task); Forgejo/Gitea have none and use labels only. The prefixed preset takes the plain words after type:, type::, type/, typ:, kind/ or kind: (type::feature, kind/bug).

Presetmajorminorpatch
plainbreaking, breaking-changefeature, enhancementbug, fix, bugfix, security
prefixedtype:breaking, …type::feature, …kind/bug, …

Suggestion.

  • The release's issues are the issues of the next release milestone (see "Queue order") plus the release scope, open or closed.
  • The highest raise among them is applied to the last released version. The reason names the issues at that raise: "minor because of #12, #15" (the first ten, then "and N more"), or "patch, no issue asks for more".
  • The last released version is the highest version that fits the scheme among the closed release milestones and the tags. Neither source wins by kind; the higher version wins, so a tag made without a milestone counts as much as a milestone closed without a tag. On a tie the milestone's spelling is kept and the origin is both. Pre-release versions (1.3.0-rc.1) never count, build metadata (+…) is ignored. If the forge refuses the tags, the milestones alone are used and tags_read is false.
  • Before 1.0 (SemVer and patterns with major and minor) a breaking change raises the minor part (0.4.2 → 0.5.0). 1.0.0 is never suggested; the user sets it by changing the suggestion.
  • A part the pattern does not have raises the lowest part it has (release-{major}.{minor}: a patch raises the minor part).
  • Without a previous version: SemVer 0.1.0 (plain numbers; a prefix such as v only comes from an earlier release or tag), a pattern with major and minor 0.1.0 in its form, a major-only pattern, {n} and build give 1, calendar gives today's period with counter 0.
  • Calendar ignores the raise: today's period (UTC) with counter 0, or the next counter while the last version is in the same period. Without a counter, a second release in one period is an error, as is a last version later than today.

Own script. The script runs only in the user's local checkout of the repository (a plain clone outside the worktree root, never a worktree), through the same runner as the automations' prechecks (automations::command): environment cleared down to the automations' allow-list, so no token is passed, stdin closed, 60 s timeout, at most 64 KiB of stdout and of stderr each. Inputs:

VariableValue
GITOODO_LAST_VERSIONthe last released version, empty without one
GITOODO_RELEASE_ISSUESpath of a JSON temp file with the release's issues, removed afterwards
GITOODO_VERSION_RAISEmajor, minor or patch
GITOODO_REPOowner/name

Its stdout must be exactly one line (one trailing line break allowed) that is a release title of at most 100 characters. Anything else (exit code not 0, a timeout, too much output, no line, several lines, no version) is an error that shows stdout and stderr; it never becomes a version. The hygiene and the MCP tool never run the script: the hygiene skips the milestone question with a notice, the MCP tool answers that the app or the CLI runs it.

Naming the next milestone. The hygiene's question to create the next release milestone proposes the suggestion's version (it used to count up the last number of the newest milestone).

In the dialogs. "Release anlegen …", "Neues Release" and the next release in "Release abschließen" prefill the suggestion and say why under the field, written in the person's language from basis and last (for example "Vorschlag: Minor steigt wegen #12, #15. Ausgehend von v1.4.2."; last is an open release when the new one comes after it); the script scheme adds what the script wrote to stderr under "Ausgabe des Skripts". The reason disappears once another version is typed. A suggestion that fails (invalid settings, a scheme that cannot count on, a script that cannot run or fails, an unreachable forge) says so there and asks for the version, with the details below it: the settings' problems, or the message and, for a failed script, its stdout and stderr, open from the start. The field stays empty; a failure never becomes a version, and nothing counts up the last number of a title any more.

Surfaces. The release settings (tab Versionierung, #1147) and the dialogs' version suggestion, and:

  • Tauri: version_suggest(account, repo) (outcome: suggested with the suggestion, or failed with the failure), version_config(account, repo), version_config_validate(config) and set_version_config(account, repo, config | null) (saved or invalid with the problems).
  • CLI: gitoodo release-version --repo owner/name [--account id] [--json] [--check], for example v1.5.0 (minor because of #11, #13; last v1.4.2 from a closed milestone). --check only checks the stored config.
  • MCP tool ledger_version_suggestion (optional repo).

Assignment rules (#1143)#

Each repository has a list of assignment rules in the app's orchestration config (orchestration.json, release_rules in the repository's entry; never in the repository). The rules decide which issues join which release by themselves; they are edited in the release settings (tab Zuordnung, #1147).

A rule (orchestration::assignment::AssignmentRule) has

  • an id (unique in the list) and a name, enabled (default on);
  • conditions over the issue and combine: all (default) or any. Attributes:
    attributecondition
    labelcarries the label value (any case; the catalog's name is resolved per repo)
    stateopen or closed
    authoropened by the login value (any case, @ optional)
    originfollow_up (a worker follow-up by its marker, or a body that names
    "Follow-up of #n"/"Follow-up from #n"/"Folge von #n") or follow_up_in_release
    (the parent, open or closed, is in an open release milestone or carries
    release:next)
    agedays since it was opened, at_least and/or at_most
    prioritythe priority label's level: value p0…p3, or at_least/at_most as numbers
    issue_typethe forge's native issue type value (GitHub types, GitLab issue/incident/task)
  • a target: {"kind":"next"} (the next release: its milestone when one with a version is open, else release:next), {"kind":"parent"} (the release of the issue's parent; used with origin) or {"kind":"named","title":"v2.0"} (an open release milestone by title);
  • an effect: assign writes the release on the forge, suggest stores a suggestion and writes nothing.

Evaluation. The rules run on every poll inside the existing hygiene pass (no loop of their own, the same writer lock) whenever release planning or the milestone rule is on. With the milestone rule off, they write no milestone: the next release is then always release:next, and a rule whose release is a milestone (a named release, a parent in a milestone) does nothing. So an open priority:p0 issue gets release:next in a repository with release planning on and the milestone rule off, and the queue takes it first as before. They look at open issues (closed ones only for a rule with a state condition) of kind issue that are in no milestone and carry no release:next; an issue in a sprint or any other milestone is never moved. The first enabled, valid rule that matches decides. Writing the milestone or the label is idempotent: an issue that is in a release is left alone, so the next pass writes nothing. At most MAX_WRITES_PER_RUN (10) assignments are written per repository and pass; the rest follow on the next passes with a notice ("N more release assignments pending").

Validation. Storing rules refuses an empty condition list, a condition without a value or with an invalid one (state: merged, priority: high, age without bounds or with at_least above at_most), an unknown attribute, a named target that is not a version, more than 50 rules or 20 conditions, an empty or duplicate id; each problem names its field (rules[0].conditions[1].value) and a code. A named release that is not open on the forge is only a warning when storing (unknown_release). During a pass an invalid rule, or one whose named release is gone, is skipped with a notice and never stops the pass; a config from a newer version with an attribute this one does not know still loads.

Removals by hand stick. Each pass remembers which issues were in which release (release-rules.json in the state folder, per account and repository). An issue that was in a release and is in none on the next pass was taken out by a person (on the forge or in the app): a removal marker for that issue and release keeps every rule from putting it back there. A removal of release:next binds to the milestone that becomes the next release, so it also holds when the version is decided. Moving an issue to another release is no removal, but a later release a person chose is kept: the file also remembers where a pass itself put an issue (placed), and only such an issue is ever pulled forward for a dependency (#2061). A closed milestone sending its issues to the backlog is none either. Markers of a release are dropped once it is closed or gone, so the rules may act again in a later release. Dismissing a suggestion counts as a removal. The file holds only issue numbers, milestone ids, rule ids and times; deleting it loses the markers and the waiting suggestions, nothing else.

Templates. assignment::templates() offers three rules:

idnamerule
follow_upsFollow-ups join their parent's releaseorigin = follow_up_in_release, target parent, assign
urgentUrgent issues join the next releasepriority at most 0 (p0), target next, assign
bugsBugs join the next releaseany of the bug labels or the issue type Bug, target next, suggest

A repository without its own list (release_rules absent) uses the defaults: follow_ups, and urgent when release planning is on. They replace the former fixed behaviour without a migration step: follow-ups of an issue in the next release milestone still join it (now also of a later open release, and of an issue with release:next), and open priority:p0 issues are in the next release as before, now written on the forge. Storing an own list replaces the defaults; null goes back to them.

Suggestions. A suggesting rule's match is kept as a suggestion (issue, title, link, release, rule, since when) until it is approved, dismissed or no longer matches. Approving writes the release like an assigning rule (a suggested release:next goes to the next release milestone if one is open by then); dismissing writes nothing and leaves a removal marker.

Surfaces. The release view's dialogs (below), and:

  • Tauri: release_rules(account, repo) (rules, defaults), release_rules_validate(rules), release_rule_templates(), set_release_rules(account, repo, rules | null) (saved with the rules in effect and warnings, or invalid with the problems), release_suggestions(account?, repo?), release_suggestion_approve(account, repo, issue) and release_suggestion_dismiss(account, repo, issue).
  • CLI: gitoodo release-rules --repo owner/name [--account id] [--json]: the rules in effect, their problems and the waiting suggestions (read only).
  • MCP tool ledger_release_suggestions (optional repo, read only).

Completing a release and its automations (#1145)#

Completing a release is a deliberate act of the user in the app. It raises the event "release completed" and then runs the repository's release automation steps in order, with visible progress per step. The dialogs are part of the release view (see "Release view: completing, runs, settings and sessions"). The code is orchestration::release_run in the core.

Completion (release_run::prepare, then release_run::complete). The request names the release milestone, the confirmed version (the suggestion of the version logic, editable), optionally a commit, and where open issues go. Completing is refused, with a reason in words, when

  • the milestone is gone, closed, or no release (its title is no version);
  • the version is no version or no valid tag name (the version is also the tag's name);
  • issues of the release are still open: the refusal lists them and the open release milestones they can move to. With move_open ({"to":"milestone","id":…} or {"to":"next_label"}, which takes the milestone off and adds release:next) they move first, then the release is completed without them;
  • the release was completed already (then its run is retried or skipped instead);
  • a step needs the base branch and the forge names no default branch, or the chosen commit is no SHA;
  • a step that cannot be undone has no confirmation (below).

The plan the app shows before "Complete" lists every step with what it will do ("Create the annotated tag 1.2.0 on commit 0123456789"), the closed issues and merged pull requests for the notes, the notes themselves, the base branch and the commit (the base branch's head at the time of the preview, or the chosen commit). Preparing reads the forge and writes nothing.

Confirmation of irreversible steps. Creating a tag, creating a forge release and a command step marked irreversible (on by default) cannot be undone. They run only with a confirmation the app alone can create, built like the other approvals (the typed confirmation of a repository delete and the chat proposals that apply only after the human's OK):

  • release_complete_preview computes the plan and its fingerprint (SHA-256 over account, repository, milestone, version, tag, base branch, commit, the step list and the issues that move; not the notes) and asks the ConfirmationBook for a token: 128 random bits, bound to that fingerprint, used once, valid for 10 minutes. The book lives only in the memory of the app process (Tauri state); the token goes to the window and is never written to a file or a log.
  • release_complete re-plans and redeems the token for the new fingerprint. A plan that changed meanwhile (someone pushed to the base branch, the steps were edited) has another fingerprint, and the token confirms nothing. Only a redeemed token yields the Confirmed proof the irreversible steps need; the proof has no public constructor and is not deserialisable, so nothing read from a file, the forge, the CLI or the MCP becomes one.
  • Without a valid token completion is refused (needs_confirmation with the steps), nothing is written and no event is raised. A run driven without the proof (anything outside the app) stops at the first irreversible step and waits ("waiting for your confirmation in the app").
  • The CLI, gitoodo mcp (and so the chat and the agents) and the background services run in other processes and have no book. They only read the runs; there is no tool or command that completes, retries or skips.
  • Retrying a step, or skipping one while irreversible steps follow, needs a new token for the run's fingerprint (release_run_confirmation), which the window asks for when the user confirms the dialog naming those steps.

Steps. Each repository has an ordered list in the app's orchestration config (release_automations in the repository's entry of orchestration.json; never in the repository). Without one it uses the defaults on every forge: close milestone, notes, create tag, create forge release (draft).

A command step runs through the automations' shared runner: only the allow-listed environment (PATH, HOME, USER, LANG, LC_ALL, TMPDIR, SHELL, on Windows SystemRoot, COMSPEC), never a token, plus GITOODO_RELEASE_VERSION, GITOODO_RELEASE_TAG, GITOODO_RELEASE_COMMIT, GITOODO_RELEASE_BASE, GITOODO_RELEASE_MILESTONE, GITOODO_REPO, GITOODO_RELEASE_ISSUES (a JSON file with the items: kind, number, title, labels, type, html_url, group), GITOODO_RELEASE_NOTES (at most 32 KiB) and GITOODO_RELEASE_NOTES_FILE (all of them). It is stopped after its timeout or 1 MiB of output; exit 0 is done, anything else failed. The step keeps the last 2000 characters of its output without escape sequences and with secrets scrubbed.

Storing steps refuses more than 20 steps, a built-in step twice, a changelog path that is absolute or has .., an empty command or name, a command or message over 1000 characters and a timeout out of range; each problem names the step index, the field and a code.

Progress. The event and the run of its steps are stored in release-runs.json in the state folder (20 runs per repository) after every change, so they survive a restart. Each step is pending, running, done, failed (with the result line and the output) or skipped, with its attempts, start and end, and a link to what it made (the release, the pull request). The run is pending (steps left, nothing running, e.g. waiting for the confirmation), running, failed or done. A failed step stops the chain. "Retry this step" (retry) runs only the first unfinished step again and goes on; "Skip" (skip) marks it skipped and goes on. Done and skipped steps never run again, and tag and release creation check the forge first, so a retry after a crash creates nothing twice; the notes step finds an open pull request or an existing section. A step that was running when the app stopped is failed as "interrupted" at the next app start (recover), so the user checks the forge and retries or skips it. One run is driven by one task at a time.

A version whose tag exists already. With a tag or release step, prepare reads the version's tag before anything is written (forge::release::check_tag). On the plan's commit it goes on. On another commit the preview and completing are refused (tag_taken) with the facts (TagTaken: tag, its commit, the wanted commit, when it was made where the forge says, how many commits it is behind via the forge's compare, and its forge release if any) and next, the next version no tag and no other milestone has (next_free_version: the last number counts up, v and other prefixes stay, a pre-release counts up its last number or gets .1, build metadata is dropped). The milestone is not touched. The request's tag then picks use_existing (the plan's commit becomes the tag's) or replace (the tag step moves it; the plan's fingerprint covers the commit it moves from); a tag with a forge release refuses both, only another version helps. Moving deletes and recreates the tag on Forgejo/Gitea and GitLab and forces the ref (PATCH git/refs/tags/… with force) on GitHub; it is audited as tag_move and never touches a tag that moved meanwhile.

A tag made between the preview and the step fails the step with the same facts in conflict, and a run from before this check gets them when its dialog opens (refresh_conflict, reads only). resolve(id, step, choice, token) goes on with next_version (checked free again; the milestone the run closed is renamed, a changelog notes step runs again for the new version), use_existing or replace, with a fresh confirmation for the steps ahead. Discarding (discard(id, reopen)) removes a failed or waiting run from the list into discarded in the same file (20 kept); nothing on the forge is undone, and with reopen the milestone the run closed opens again.

Forge calls (core only, audited writes): the merged pull requests of a milestone (Forgejo/Gitea closed pulls of the issue list with merged, GitHub closed issues with pull_request.merged_at, GitLab merged merge requests), a branch head, a file on a ref, and one file as one commit on a new branch (Forgejo/Gitea contents with new_branch, GitHub a branch ref and contents, GitLab repository/commits with start_branch; a branch equal to the base is refused before any request; audit action file_commit).

Rights before the plan (#1139). prepare checks the token's rights for the configured steps before the plan is shown (rights::missing_release_rights): closing the milestone and moving open issues need the issues right, tag, release and a CHANGELOG commit the releases right. A right the forge surely does not give refuses with missing_rights (each with its key and what to grant), so nothing is written; a user, role or scope list the forge does not reveal counts as given, and the step's own refusal still names the right then.

Closing a release#

"Release abschließen" appears once every member is merged or closed. After a confirmation Gitoodo

  1. removes release:next from the closed members (dependency members need nothing),
  2. closes the planned milestone if the user asks and no other open issue is still in it (otherwise it says so and keeps it),
  3. creates the next release with the given version only when the user ticks "Nächstes Release auch anlegen" (off by default, #1476; the dialog proposes the version suggestion for a release after the open ones, else counts up the last number); the name must be a free version, checked before anything is written.

Members of the next milestone lose release:next too, so a closed issue does not come back into the next scope through a stale label. This label-only dialog serves a next release without a version; the tag, the notes and the steps of the release settings run only for a release with a version, and the dialog says so in one line. Writes use the account's token in the Rust core (release_membership, release_assign, release_create, release_cut, release_remove), go through the forge write log (activity/forge-writes.jsonl, reason app: release …) and trigger a poll; the app shows the change at once until the poll confirms it.

An opened candidate in "Issues hinzufügen" can also be acted on right there (#1818): next to "Auf der Forge öffnen" it shows its priority with raise and lower (the repository's own priority labels, the same set_issue_priority command and pending store as the board, so the chip and "Wichtigste zuerst" change at once) and "Schließen", which asks once in the row ("Ja, schließen" takes the focus) and then closes the issue with close_issue, without a comment. A closed issue leaves the list and the selection at once and stays out until the read model drops it, at most CLOSING_MS (10 min, src/state/closing.ts); a refused close or priority step is taken back and the dialog says why.

A release milestone is created only by a deliberate act of the user, and each creation is logged with its trigger (release.milestone_created, docs/logging.md):

It has no recommended default and no deadline, so silence never creates anything. Gitoodo creates the version the question named; when the suggestion has changed since, it asks again instead.
  • Views and reads never write. Opening the release view, a dialog or the milestone line only reads; the button that writes names the version. crates/core/tests/no_auto_milestones.rs and src/views/dashboard/releaseRemove.test.ts fail as soon as another place calls a creating command.
  • Agents never touch releases. Workers, release sessions and the question skill are told never to create, rename, close or delete milestones, forge releases or tags, nor to move issues between milestones (brief::RELEASE_RULE); workers have no forge credentials anyway.

Removing a release (#1476)#

"Release entfernen …" in the hover actions of every release in the release view removes a release the user does not want, in one confirmed step (release_remove_preview, release_remove, orchestration::release_remove). The dialog first reads what would happen (it writes nothing):

  • Open issues go where the user picks: into the next release (default; the release that is next once this one is gone, else release:next), into another open release, or into no release. They move first, in chunks of 100, the same way as "Release zuordnen".
  • Delete or only close. Deleting removes the milestone on the forge (Forgejo/Gitea DELETE milestones/{id}, GitHub DELETE milestones/{number}, GitLab DELETE milestones/{id}); every forge then unlinks it from its finished issues, so they lose the link, and the dialog says how many. "Nur schließen" closes the milestone instead and the finished issues keep it, unless the user also unlinks them. A deleted milestone cannot be restored; the dialog says so once, next to the button.
  • Tags. A tag Gitoodo made for this release (a release run's tag step, on the run's commit) can go with it when the release was never published. A tag with a forge release, a tag on another commit and a tag Gitoodo did not make are never offered.
  • Refused, with the reason and nothing written: a GitLab group milestone (it belongs to the group and every project in it; change it in the group), a release whose run is pending, running or failed (complete or discard it first), and deleting a published release (it can be closed).

Feedback while it runs (#1512). Confirming closes the sheet at once. The release's row dims and shows the working mark with "Wird entfernt …" ("Wird geschlossen …"); after about 2.5 s it names the steps the core reports through a channel (Progress: move/unlink with done and total, milestone, tag), e.g. "Issues verschieben 3 von 4 · Release löschen". The issue writes of a chunk run with bounded parallelism (PARALLEL_WRITES = 4, results in issue order), the same for "Release zuordnen" and the unlinking of finished issues. Once the forge confirmed it, the release leaves the row, the later releases and the pickers at once and its open issues show where they went (from the outcome's moved and moved_to), without waiting for the classifier's next poll; a deletion says so in the toast ("v1.0.0 entfernt · 4 Issues nach v0.1.0 verschoben"), a closing in the note with "Wieder öffnen", which brings the release back at once the same way. A failure or refusal brings the row back as it was and says what happened, including issues that had already moved and stay there. These view states hold until the report shows the change, at most PENDING_MS (3 min); before #1512 the view dropped them on the first report after the save, which could still be stale, and only the classifier's next poll (minutes on many repositories) made the release go, with nothing shown meanwhile.

After the only release is removed, the next release has no version again; the hygiene may ask the milestone question again, which never creates anything by itself. Every removal is an audit event (release.milestone_removed) and goes through the forge write log (milestone_delete, milestone_close, milestone_set, label_add, label_remove, tag_delete).

Editing a release (#1499)#

For the user a release is one thing, the "Release"; that the forge keeps it as a milestone is said only where the forge matters (the tooltip of the release's "…", a GitLab group milestone, forge errors and fields). A test (src/i18n/terminology.test.ts) keeps the German and English texts to that.

Every open release is a node of its own below its repository, e.g. "v1.5.5 · fällig 11. Nov." ("überfällig seit 11. Nov." once the date has passed, calm, in the text's colour). Its "…" at the node's end opens the release's menu ("Issues hinzufügen", "Release abschließen …", "Release-Sitzung …" while none runs, then):

  • Bearbeiten …: version, due date (date picker, "Kein Datum" where the forge can clear it) and description in one sheet (release_edit_view, release_edit, orchestration::release_edit). The version is checked as typed (a version, not taken by another milestone of the repository, open or closed; it stays while a release run of it is in progress). The core checks again and asks first ("Trotzdem speichern") when the version does not fit the repository's version scheme, when a tag named like the new version exists already (#1419: "Tag v1.6.0 gibt es schon (auf 0123456)"; completing the release then offers to use it, move it or take another version, see "A version whose tag exists already"; a tag that cannot be read never warns) or when the save changes which release is next (and so what the autopilot works on). A GitLab group milestone is refused with the hint to edit it in the group.
  • Datum verschieben (only when overdue): the same sheet with only the date, a week from today suggested.
  • Schließen …: the removal sheet set to closing (open issues move as there). Afterwards the note offers Wieder öffnen (release_edit with open: true, trigger reopen, no confirm).
  • Release entfernen … as above.
  • Autopilot ("▷" beside "…" on every node): the release focus (#1442), the same choice on every node of the repository ("Next release", "Only v1.5.0" per open release, "All issues"). Making a later release the current one (#1419) is this choice: picking a later release makes the autopilot work on it, while which release is next stays the one rule of "Next model" (due first, else the lowest version), so the order never depends on a hidden flag. The node the autopilot works on carries "aktiv" and a filled "▷"; "All issues" says so once in the repository's line ("Autopilot: all issues").

Closed releases (#1419). Under its open releases each repository has a quiet row "N geschlossen" (release-closed-<repo>), collapsed by default and left out while a search narrows the tree. Opened, it lists the repository's closed releases (closed milestones whose title is a version, highest version first; GitLab group milestones stay out, they are reopened in the group), each with its version, its former due date and Wieder öffnen. The read model carries them as release.closed (orchestration::release::closed_releases, from the milestone read the poll does anyway, so nothing more is fetched). Reopening calls release_edit with open: true and trigger reopen_closed: unlike the undo right after closing it asks first when the reopened release would become the next one (the note names the change and offers "Trotzdem wieder öffnen"), then the release shows among the open ones at once and leaves the closed ones.

A release without issues yet is a node like any other (#1701, "Keine offenen Issues"), so an empty or mistaken release can be edited, closed or removed there; without any open release the repository row keeps the plain milestone line with "Release anlegen".

A save writes the milestone once, only with what changed, shows at once in the row (rolled back on a failure or a refusal, held until the report has it, #1512) and asks the classifier to poll. The autopilot choice from the menu works the same way: the row and the menu read the one focus of the repository, which shows the choice at once with a turning mark while it is saved, keeps it until the report has it and goes back with a note when saving fails (before #1512 the menu kept its own choice while the row waited for the next poll, so they disagreed). Every save is an audit event (release.milestone_edited with trigger edit_dialog, move_date, reopen or reopen_closed) and goes through the forge write log (milestone_edit, reason app: release edit).

Releases by hand (#1141)#

Step 2 of #1139: several planned releases per repository, created and filled by hand, in the core, the read model and the app (unlocked for everyone with #1148).

  • Several releases are normal. Every open milestone with a version title is a planned release; the next one is picked as in "Queue order", the others are later releases. Sprints and other milestones are never releases and never count. The findings report "several open release milestones" only when two of them tie for the next release (same due date and version), never for later releases or sprints.
  • New release (release_create(account, repo, title, trigger), release::create_release): creates an open milestone named with a version. The title must be a version (forge::release) that no open or closed milestone of the repository has yet (any case); an open sprint or another release never blocks it. The dialog prefills the version suggestion (#1142) for a release after the open ones (version_suggest with newRelease: true, which treats the open releases as released; a calendar version counts from the period of a planned release that lies ahead, so 2026.12.1 follows a planned 2026.12.0 instead of failing, version::new_release_day). When the new release is the next one, the open release:next issues without a milestone move into it and lose the label.
  • Assign and remove (release_assign(account, repo, numbers, to), release::assign) with to one of {"kind": "next"}, {"kind": "release", "id": n} and {"kind": "none"}. "Next" sets the next release milestone, or release:next while the next release has no version; a release sets its milestone and removes release:next (for a later release); "none" removes both the release milestone and release:next. A sprint or another non-release milestone stays: an issue in a sprint keeps it unless it goes into a release. Issues whose place does not change are not written; the answer lists the ones that changed. Dependencies follow the issue that needs them as before; "none" cannot take out an issue that is in only as a dependency.
  • The release on the issue: the read model carries release_title per issue, the version of its open release milestone, else the next release's version when the issue is in its scope. The board shows it as a small tag in the row's meta line, the issue sheet as the fact "Release" with "Ändern", and the flag button opens the release choice instead of toggling (open releases, the next one marked; "Next release" while it has no version; "No release"). p0 issues stay in by rule.
  • Release view: every open release of a repository as a node with its milestone members (see "Release tree"). Every item has "Release ändern" (on hover or focus) instead of the plain remove, and every repository row "Neues Release" beside "+". Every release's "…" has "Issues hinzufügen" (#1683) with that release chosen, also while it has no issue yet.
  • Hygiene: an open issue in the next release milestone loses release:next; the milestone says it all.

The report and the read model add releases per repository, the open releases in planning order:

"releases": [

  { "id": 5, "title": "v1.5.0", "items": [{ "number": 14, "reason": "milestone", "...": "..." }] }
]

The next release's items are the scope (release.items); a later release lists its issues, open and closed.

Release settings, templates and suggestions (#1147)#

Queue order#

The autopilot works on the next release first (release management rule 12, spec 7.1 item 4). The next release of a repository is:

  • every scope member (release:next and their dependencies), and
  • every open issue of the next release milestone, with the issues it depends on. The next release milestone is the open milestone whose title is a version (v1.2.3, 1.2, 2026.11, build 42; not Sprint 12) that is due first, else the one with the lowest version, else the oldest. Two that tie on due date and version are not guessed: then only the label counts until the tie is resolved (the findings name it). Later and closed milestones do not count.

These issues and boosted ones form the queue's first group; the score (priority, age, boost, release bonus score.release_bonus) orders each group. The release bonus grows as the next release's due date nears (#1850): in full without a due date and from one day before it (also overdue), score.release_far_percent (25 %) of it from score.release_due_days (14) days away, linear in between; a release due soon also moves its repository ahead in the share of the worker slots and may take more than the equal share when it cannot make its date otherwise. See Queue order and slot share. A blocked release issue is skipped like any blocked issue, so the rest of the release and then the other issues still go, and without a dispatchable release issue the queue runs on the score as before. Each repository has its own next release; with release planning off nothing but a boost moves an issue forward. The same rule (release::next_release_milestone) picks the milestone the hygiene puts release:next issues and follow-ups on, so a sprint never gets them.

The dispatcher does not read the milestones for every pick: each reconcile pass leaves the next release milestone it read with the writer, and a pick reuses it for up to the default sync interval (NEXT_RELEASE_TTL, 60 s) before it reads the list again. A pass that creates a milestone drops the kept value; a milestone changed in the app shows after the poll the app triggers. The app's queue, the dispatcher's pick and the chat's item list (next_release per issue) use the same order. The release view lists the same issues (milestone members since #1141).

Release focus (#1442)#

Per repository the autopilot works on one release: the queue order above says what goes first, the focus says what starts at all. It is a setting per repository (release_focus in the repository's orchestration config, set with the Tauri command set_release_focus(account, repo, focus)):

choicethe autopilot starts new workers on
{"kind":"next"} (default)the next release as in "Queue order" (milestone members, release:next issues) and the issues in no release they depend on; without any release, on every issue
{"kind":"release","id":7,"title":"v1.5.0"}the open issues of that milestone and the issues in no release they depend on (the release:next issues too when it is the next one)
{"kind":"all"}every ready issue in queue order, as before #1442
  • Only new worker starts are limited. Triage, the resolver of stuck issues, reviews and running workers go on; an issue outside the focus keeps its labels and simply waits.
  • A restart is a new start (whispaste #1843: a worker outside the focus ended with code 143 and was started again). A worker running outside the focus may finish its current run, but every start after that run ended passes the focus like a claim: the restart after an end without a result (a crash, a hang, a host that went away, a review round, failed checks), the restart that waited for a host or a slot, the run a new dispatcher takes over after an update of the app, and the resume after a worker machine's update, after its sign-in screen and with this computer's account at another account's limit. An issue the focus leaves out is not started again: its restart waits among the deferred restarts without a slot, its lease, branch, worktree and pull request stay as they are and its labels unchanged, until the focus lets it in (the release is closed, the person chooses "All issues", the issue joins the release, or the option below lets it in); then it starts again as a counted restart. A worker paused at a limit is not ended for the resume with another account; it stays where it is. The dispatcher reads this from outside_focus of each round's read model (before the first round, from the model the classifier kept) and logs dispatch.restart_held (issue, reason = outside_focus) once per hold and dispatch.restart_admitted when the focus lets the issue in. The resolver of stuck issues runs in a system slot and stays exempt, as does a run moved to another machine for its desktop tests (the same run going on there).
  • Never an issue of another release (the user's rule): an issue another open release holds (its open release milestone is another one, or, without one, it carries a legacy "later" label such as release:später, or release:next while a later release is chosen) never starts while the focus is active, not as a dependency and not while the focus holds (Focus::other_release). The milestone decides before the label. A milestone that is no release (a sprint) or a closed one puts an issue in no release.
  • Every focus holds fully (the user's rule, 2026-11-24): the next release ({"kind":"next"}, the default) is as strict as a release the person chose ({"kind":"release",…}) and as a chosen release that fell back to the next one. Only its issues and the issues in no release it waits for start; nothing outside it starts, not even while nothing in it can. Only "All issues" ({"kind":"all"}) lifts the limit; the option below lets a held focus take the issues in no release, and only when the person allows it.
  • Dependencies in no release belong to the focus: an issue the release waits for starts even when it has no milestone. A dependency in another release does not; the hygiene pulls it into the release that needs it ("Dependencies join the release"), and then it starts as a member. What only such a dependency leads to stays out too. The claim reads the dependency lines and the open split parts itself and takes those from comments and the forge from the last read model (Writer::note_focus, valid for a few polls); an issue noted there that another release holds now still stays out (Focus::admits_noted).
  • A chosen release that is closed or deleted falls back to the next release (fallback); a rename keeps the choice, it holds the milestone id. When nothing is open any more, the autopilot works on every issue again.
  • Unreadable milestones with a focus other than all start nothing new in that repository until they read again (unknown), rather than work outside the release.
  • Nothing to start: the focus holds. When none of its open issues can start (all done, held by extern, blocked, in progress or waiting for a person) while ready issues wait outside it, the focus is held and the autopilot starts nothing new in that repository until an issue of the release is ready again, or the person closes the release (then the next one is the focus) or chooses "All issues". The read model decides this from the readiness (read_model::settle_focus); the claim follows the focus through Writer::note_focus, so a stale or missing read model keeps the strict focus too. Unreadable milestones never hold. This replaced the idle fallback of #1691, which let the automatic focus take the ready issues in no release meanwhile: a release that looked done while a worker ran outside it read as a contradiction (whispaste 1.5.5 at 209/209 with a worker on #1988).
  • Going on with the issues in no release is the person's explicit permission (the user's decision, 2026-11-24: "normally, when I say it should work on a release, only the issues of that release belong in; when nothing is left, the autopilot stops"). The default is strict, as above. Per repository the option "When nothing in the release can start: go on with ready issues in no release" (release_focus_overflow in the repository's orchestration config, serde default false, so older configs stay strict; set with the Tauri command set_release_focus_overflow(account, repo, allowed)) lets a held focus take the ready issues in no release meanwhile (overflow). It never lets in an issue of another open release, which stays absolute, and it means nothing with "All issues" (the app hides it there). held keeps saying that nothing in the release can start; overflow is set beside it only while the option is on and an issue in no release is ready. As soon as an issue of the release is ready again, the next read model clears overflow and only the release starts; running workers go on. While it holds, an issue in no release that is already in progress counts as let in for its restart too, even when none in no release is ready (Focus::admits_restart). Until then a claim puts every issue of the focus before the issues let in this way (Noted::overflow in Writer::note_focus), so one of the release that can start by then goes first. Unreadable milestones never overflow.

The read model and release_status carry the focus as release.focus (choice, active, release_id, title, fallback, unknown, held, overflow_allowed, overflow) and mark each issue outside it with outside_focus: true. Where the app shows it:

  • The queue on "Sitzungen" leaves those issues out and says in one line how many wait ("Only v1.5.0 – 3 other issues wait"). A held focus gets a card of its own (test id repo-queue-focus-held): one line that nothing can start ("0.1.0: nothing can start"), one sentence on what the autopilot does now ("The autopilot stops until an issue of the release is ready.", or with the option "Meanwhile the autopilot takes ready issues in no release (allowed in the release settings).") and, under "What holds it up", at most three of the issues that hold the release up, not every dependency edge. Those are its root blockers: open issues of the release that others wait on, directly or through others, and that wait on no other open issue of the release themselves (issues waiting on each other in a circle count as one, by their lowest number), plus one that waits on an issue outside the release. Each row shows the number and the title on one line (the full title on hover; a click opens the issue as in the queue), what it waits for itself in the board's readiness words ("In progress", "Needs clarification", "waits on #9 outside the release", "waits in a circle on #3") and how many it holds up ("holds up 21 more"); more roots are counted ("+2 more"). The most holding come first.
  • The node of the release the focus holds says it under itself, wrapped at every width (test id release-focus-line-<repo>-<release>): a release whose members are all done "v1.5.5 is done – close the release, then work goes on with v1.6.0" ("… with all issues" without a later release), beside "Release abschließen"; a held one the queue's state line, which says whether the autopilot stops or takes the issues in no release, and the issues that hold it up ("held up by #66, #67, #33 +2 more").   • A worker whose issue the focus leaves out (it started before the focus took effect, or a person started it) carries "outside the focus" on its tile on "Sitzungen", and its issue the same tag in the repository's issue list, with the reason on hover and in the accessible name: the worker runs to its end and does not start again; the issue waits until the focus takes it in.

The classifier logs classifier.focus when a repository's focus changes (fields fallback, unknown, held, overflow), the app release_focus_set when one is chosen and release_focus_overflow_set (repo, allowed) when the option changes.
