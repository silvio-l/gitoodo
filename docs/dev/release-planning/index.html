Mental model, as the app says it: a release is one goal per repository: which issues have to be in before you publish. Gitoodo works on release issues first.

Scope#

Per repository, an issue belongs to the next release when

  1. it carries release:next (reason label), or
  2. it is a dependency, recursively, of a member (reason dependency).

Only dependencies inside the same repository count. A closed issue stays in only through the label or as a dependency, so a finished dependency stays part of the release.

Open priority:p0 issues used to be members by themselves (reason priority), without anything on the forge. Since #1143 the assignment rule "Urgent issues join the next release" (on by default, see "Assignment rules") writes them into the next release instead, so they are visible on the forge and a person can take them out again. The reason priority is no longer sent.

Gitoodo writes only release:next. It reads the legacy release:muss as release:next and release:später as "not in the next release" (it adds nothing); neither is ever written. Adding an issue through the app removes a legacy later label from it.

Planning is switched per repository in the settings, right beside the repository's activation ("Release planning", default on; stored as releases in the repository options). With it off, the repository has no scope, no bonus and does not appear in the views.

Labels and milestones#

Today the label is the source of truth: it works the same on every forge, needs no setup and is what the classifier already reads. A milestone only names the release and gives it a due date; the existing milestone rule keeps members in the planned milestone.

Next model: a milestone is a release with a version (#1139)#

Release management (epic #1139) moves to this model: **a milestone whose title is a version is a release**, and release:next stays as "the next release, version not decided yet". Other milestones (sprints, themes) stay the user's own and are never treated as releases. Step 1 (#1140) adds the forge calls in the Rust core only; nothing of it is visible in the app yet, and the planning, scope and closing described here are unchanged until the later steps switch over.

A milestone title counts as a release version (forge::release::release_version) when, after trimming, it is

  1. optionally v/V directly before the number, or one of the words version, release, build, ver (any case) followed by a space, - or _,
  2. then one to four numbers separated by dots (each at most nine digits),
  3. then optionally a pre-release or build part after - or + of letters, digits, dots and hyphens (-rc.1, +20261119), allowed only after a dotted number or a prefix word,

and nothing else. So v1.2.3, 1.2, 2026.11, 42, build 42, Release 1.4 and 1.0.0-rc.1 are releases; Sprint 12, Q4 2026, Milestone 3, v1.2 Winter, 1.x, 1.2.3.4.5, 12-sprint and 2026-11-19 are not.

Rules that hold on every forge:

  • Creating a tag is idempotent: the same tag on the same commit is success, on another commit it is refused and the tag is never moved or deleted.
  • A release is created as a draft where the forge has drafts. An existing draft is reused (name and notes updated, it stays a draft); a published release is left as it is and only changed on an explicit call. GitLab has no drafts: a draft request is refused before anything is sent, and a GitLab release is public as soon as it exists.
  • GitLab group milestones can be read and assigned, but not edited or closed through the project; the error says to change them in the group's milestones or to use a project milestone. Gitoodo never edits a group milestone, because that would change other repositories too.
  • Every write goes through the audit log (milestone_create, milestone_edit, tag_create, release_create, release_edit). Refusals (403, 404, 405, 409, 422) name the missing right or the cause and never contain the token.
  • The release rights (rights::check_release) are checked separately from the mode check, so they do not appear as missing in the app yet.

Known limits of step 1: a due date can be set or changed but not cleared; tag protection rules (GitHub rulesets, Forgejo/Gitea tag protection, GitLab protected tags) are not read in advance, so a protected tag shows up as a refusal when it is created; GitLab has no pre-release flag.

Version logic and suggestion (#1142)#

Step 3 of #1139 adds the version rules in the Rust core (orchestration::version). There is no screen for them yet; the settings come with the repository settings page (#926).

Config. Each repository can have a version entry in its rule in orchestration.json in the app's config folder. It is never stored in the repository. Without the entry the repository uses SemVer with every preset.

{
  "scheme": { "kind": "semver" },
  "raises": [{ "source": "label", "name": "api-change", "part": "major" }],
  "presets": ["plain", "prefixed", "issue_types"],
  "default_part": "patch"
}
scheme.kindVersion
semverv1.4.2
calendarpattern from YYYY, YY, MM, M, DD, D and the counter N: YYYY.MM, YYYY.MM.N
buildone rising number: 42, build 42
patterntext around {major}, {minor}, {patch} or {n}: v{major}.{minor}.{patch}, release-{major}.{minor}, build-{n}
scriptcommand runs in the local checkout and prints the version

A pattern is refused when it cannot be read back as a version: a field twice or two fields without text between them, digits in the text, a calendar without year or month, the counter not last, {n} mixed with the other fields, fields out of order, or a result that is no release title (b{n} gives b0, which is not a version; build-{n} is). Patterns and commands are limited to 1000 characters, own rules to 200. version_config_validate lists the problems with field, code and text.

Raise of an issue. Each label (source: label) and the native issue type (source: type) is looked up, case-insensitive: first the repository's own raises, then the presets. An own rule replaces the preset for that name. The issue raises the highest part found; an issue that no rule matches raises default_part. Native types are GitHub's organisation issue types (type.name) and GitLab's issue_type (issue, incident, task); Forgejo/Gitea have none and use labels only. The prefixed preset takes the plain words after type:, type::, type/, typ:, kind/ or kind: (type::feature, kind/bug).

Presetmajorminorpatch
plainbreaking, breaking-changefeature, enhancementbug, fix, bugfix, security
prefixedtype:breaking, …type::feature, …kind/bug, …
issue_typesBreaking, Breaking changeFeature, EnhancementBug, Incident

Suggestion.

  • The release's issues are the issues of the next release milestone (see "Queue order") plus the release scope, open or closed.
  • The highest raise among them is applied to the last released version. The reason names the issues at that raise: "minor because of #12, #15" (the first ten, then "and N more"), or "patch, no issue asks for more".
  • The last released version is the highest version that fits the scheme among the closed release milestones and the tags. Neither source wins by kind; the higher version wins, so a tag made without a milestone counts as much as a milestone closed without a tag. On a tie the milestone's spelling is kept and the origin is both. Pre-release versions (1.3.0-rc.1) never count, build metadata (+…) is ignored. If the forge refuses the tags, the milestones alone are used and tags_read is false.
  • Before 1.0 (SemVer and patterns with major and minor) a breaking change raises the minor part (0.4.2 → 0.5.0). 1.0.0 is never suggested; the user sets it by changing the suggestion.
  • A part the pattern does not have raises the lowest part it has (release-{major}.{minor}: a patch raises the minor part).
  • Without a previous version: SemVer v0.1.0, a pattern with major and minor 0.1.0 in its form, a major-only pattern, {n} and build give 1, calendar gives today's period with counter 0.
  • Calendar ignores the raise: today's period (UTC) with counter 0, or the next counter while the last version is in the same period. Without a counter, a second release in one period is an error, as is a last version later than today.

Own script. The script runs only in the user's local checkout of the repository (a plain clone outside the worktree root, never a worktree), through the same runner as the automations' prechecks (automations::command): environment cleared down to the automations' allow-list, so no token is passed, stdin closed, 60 s timeout, at most 64 KiB of stdout and of stderr each. Inputs:

VariableValue
GITOODO_LAST_VERSIONthe last released version, empty without one
GITOODO_RELEASE_ISSUESpath of a JSON temp file with the release's issues, removed afterwards
GITOODO_VERSION_RAISEmajor, minor or patch
GITOODO_REPOowner/name

Its stdout must be exactly one line (one trailing line break allowed) that is a release title of at most 100 characters. Anything else (exit code not 0, a timeout, too much output, no line, several lines, no version) is an error that shows stdout and stderr; it never becomes a version. The hygiene and the MCP tool never run the script: the hygiene skips the milestone question with a notice, the MCP tool answers that the app or the CLI runs it.

Naming the next milestone. The hygiene's question to create the next release milestone proposes the suggestion's version (it used to count up the last number of the newest milestone).

Surfaces. Read only, no UI yet:

  • Tauri: version_suggest(account, repo) (outcome: suggested with the suggestion, or failed with the failure), version_config(account, repo), version_config_validate(config) and set_version_config(account, repo, config | null) (saved or invalid with the problems).
  • CLI: gitoodo release-version --repo owner/name [--account id] [--json] [--check], for example v1.5.0 (minor because of #11, #13; last v1.4.2 from a closed milestone). --check only checks the stored config.
  • MCP tool ledger_version_suggestion (optional repo).

Assignment rules (#1143)#

Each repository has a list of assignment rules in the app's orchestration config (orchestration.json, release_rules in the repository's entry; never in the repository). The rules decide which issues join which release by themselves. No view uses them yet; the rules come with the release settings on the repository settings page.

A rule (orchestration::assignment::AssignmentRule) has

  • an id (unique in the list) and a name, enabled (default on);
  • conditions over the issue and combine: all (default) or any. Attributes:
    attributecondition
    labelcarries the label value (any case; the catalog's name is resolved per repo)
    stateopen or closed
    authoropened by the login value (any case, @ optional)
    originfollow_up (body names "Follow-up of #n"/"Folge von #n") or follow_up_in_release
    (the parent is in an open release milestone or carries release:next)
    agedays since it was opened, at_least and/or at_most
    prioritythe priority label's level: value p0…p3, or at_least/at_most as numbers
    issue_typethe forge's native issue type value (GitHub types, GitLab issue/incident/task)
  • a target: {"kind":"next"} (the next release: its milestone when one with a version is open, else release:next), {"kind":"parent"} (the release of the issue's parent; used with origin) or {"kind":"named","title":"v2.0"} (an open release milestone by title);
  • an effect: assign writes the release on the forge, suggest stores a suggestion and writes nothing.

Evaluation. The rules run on every poll inside the existing hygiene pass (no loop of their own, the same writer lock) whenever release planning or the milestone rule is on. With the milestone rule off, they write no milestone: the next release is then always release:next, and a rule whose release is a milestone (a named release, a parent in a milestone) does nothing. So an open priority:p0 issue gets release:next in a repository with release planning on and the milestone rule off, and the queue takes it first as before. They look at open issues (closed ones only for a rule with a state condition) of kind issue that are in no milestone and carry no release:next; an issue in a sprint or any other milestone is never moved. The first enabled, valid rule that matches decides. Writing the milestone or the label is idempotent: an issue that is in a release is left alone, so the next pass writes nothing. At most MAX_WRITES_PER_RUN (10) assignments are written per repository and pass; the rest follow on the next passes with a notice ("N more release assignments pending").

Validation. Storing rules refuses an empty condition list, a condition without a value or with an invalid one (state: merged, priority: high, age without bounds or with at_least above at_most), an unknown attribute, a named target that is not a version, more than 50 rules or 20 conditions, an empty or duplicate id; each problem names its field (rules[0].conditions[1].value) and a code. A named release that is not open on the forge is only a warning when storing (unknown_release). During a pass an invalid rule, or one whose named release is gone, is skipped with a notice and never stops the pass; a config from a newer version with an attribute this one does not know still loads.

Removals by hand stick. Each pass remembers which issues were in which release (release-rules.json in the state folder, per account and repository). An issue that was in a release and is in none on the next pass was taken out by a person (on the forge or in the app): a removal marker for that issue and release keeps every rule from putting it back there. A removal of release:next binds to the milestone that becomes the next release, so it also holds when the version is decided. Moving an issue to another release is no removal; a closed milestone sending its issues to the backlog is none either. Markers of a release are dropped once it is closed or gone, so the rules may act again in a later release. Dismissing a suggestion counts as a removal. The file holds only issue numbers, milestone ids, rule ids and times; deleting it loses the markers and the waiting suggestions, nothing else.

Templates. assignment::templates() offers three rules:

idnamerule
follow_upsFollow-ups join their parent's releaseorigin = follow_up_in_release, target parent, assign
urgentUrgent issues join the next releasepriority at most 0 (p0), target next, assign
bugsBugs join the next releaseany of the bug labels or the issue type Bug, target next, suggest

A repository without its own list (release_rules absent) uses the defaults: follow_ups, and urgent when release planning is on. They replace the former fixed behaviour without a migration step: follow-ups of an issue in the next release milestone still join it (now also of a later open release, and of an issue with release:next), and open priority:p0 issues are in the next release as before, now written on the forge. Storing an own list replaces the defaults; null goes back to them.

Suggestions. A suggesting rule's match is kept as a suggestion (issue, title, link, release, rule, since when) until it is approved, dismissed or no longer matches. Approving writes the release like an assigning rule (a suggested release:next goes to the next release milestone if one is open by then); dismissing writes nothing and leaves a removal marker.

Surfaces. No UI yet:

  • Tauri: release_rules(account, repo) (rules, defaults), release_rules_validate(rules), release_rule_templates(), set_release_rules(account, repo, rules | null) (saved with the rules in effect and warnings, or invalid with the problems), release_suggestions(account?, repo?), release_suggestion_approve(account, repo, issue) and release_suggestion_dismiss(account, repo, issue).
  • CLI: gitoodo release-rules --repo owner/name [--account id] [--json]: the rules in effect, their problems and the waiting suggestions (read only).
  • MCP tool ledger_release_suggestions (optional repo, read only).

Completing a release and its automations (#1145)#

Completing a release is a deliberate act of the user in the app. It raises the event "release completed" and then runs the repository's release automation steps in order, with visible progress per step. No view uses it yet; the dialog comes with the release management UI. The code is orchestration::release_run in the core.

Completion (release_run::prepare, then release_run::complete). The request names the release milestone, the confirmed version (the suggestion of the version logic, editable), optionally a commit, and where open issues go. Completing is refused, with a reason in words, when

  • the milestone is gone, closed, or no release (its title is no version);
  • the version is no version or no valid tag name (the version is also the tag's name);
  • issues of the release are still open: the refusal lists them and the open release milestones they can move to. With move_open ({"to":"milestone","id":…} or {"to":"next_label"}, which takes the milestone off and adds release:next) they move first, then the release is completed without them;
  • the release was completed already (then its run is retried or skipped instead);
  • a step needs the base branch and the forge names no default branch, or the chosen commit is no SHA;
  • a step that cannot be undone has no confirmation (below).

The plan the app shows before "Complete" lists every step with what it will do ("Create the annotated tag 1.2.0 on commit 0123456789"), the closed issues and merged pull requests for the notes, the notes themselves, the base branch and the commit (the base branch's head at the time of the preview, or the chosen commit). Preparing reads the forge and writes nothing.

Confirmation of irreversible steps. Creating a tag, creating a forge release and a command step marked irreversible (on by default) cannot be undone. They run only with a confirmation the app alone can create, built like the other approvals (the typed confirmation of a repository delete and the chat proposals that apply only after the human's OK):

  • release_complete_preview computes the plan and its fingerprint (SHA-256 over account, repository, milestone, version, tag, base branch, commit, the step list and the issues that move; not the notes) and asks the ConfirmationBook for a token: 128 random bits, bound to that fingerprint, used once, valid for 10 minutes. The book lives only in the memory of the app process (Tauri state); the token goes to the window and is never written to a file or a log.
  • release_complete re-plans and redeems the token for the new fingerprint. A plan that changed meanwhile (someone pushed to the base branch, the steps were edited) has another fingerprint, and the token confirms nothing. Only a redeemed token yields the Confirmed proof the irreversible steps need; the proof has no public constructor and is not deserialisable, so nothing read from a file, the forge, the CLI or the MCP becomes one.
  • Without a valid token completion is refused (needs_confirmation with the steps), nothing is written and no event is raised. A run driven without the proof (anything outside the app) stops at the first irreversible step and waits ("waiting for your confirmation in the app").
  • The CLI, gitoodo mcp (and so the chat and the agents) and the background services run in other processes and have no book. They only read the runs; there is no tool or command that completes, retries or skips.
  • Retrying a step, or skipping one while irreversible steps follow, needs a new token for the run's fingerprint (release_run_confirmation), which the window asks for when the user confirms the dialog naming those steps.

Steps. Each repository has an ordered list in the app's orchestration config (release_automations in the repository's entry of orchestration.json; never in the repository). Without one it uses the defaults on every forge: close milestone, notes, create tag, create forge release (draft).

kindfieldsdoes
close_milestonerenames the milestone to the version when its title differs, then closes it; already closed: done
noteschangelog (optional path, e.g. CHANGELOG.md)the notes from the release's closed issues and merged pull requests, grouped by the version logic's raise (breaking, features, fixes, other); with changelog also a section ## 1.2.0 - date in that file, committed on the branch release/<tag>-notes with a pull request into the base branch, never on it

A command step runs through the automations' shared runner: only the allow-listed environment (PATH, HOME, USER, LANG, LC_ALL, TMPDIR, SHELL, on Windows SystemRoot, COMSPEC), never a token, plus GITOODO_RELEASE_VERSION, GITOODO_RELEASE_TAG, GITOODO_RELEASE_COMMIT, GITOODO_RELEASE_BASE, GITOODO_RELEASE_MILESTONE, GITOODO_REPO, GITOODO_RELEASE_ISSUES (a JSON file with the items: kind, number, title, labels, type, html_url, group), GITOODO_RELEASE_NOTES (at most 32 KiB) and GITOODO_RELEASE_NOTES_FILE (all of them). It is stopped after its timeout or 1 MiB of output; exit 0 is done, anything else failed. The step keeps the last 2000 characters of its output without escape sequences and with secrets scrubbed.

Storing steps refuses more than 20 steps, a built-in step twice, a changelog path that is absolute or has .., an empty command or name, a command or message over 1000 characters and a timeout out of range; each problem names the step index, the field and a code.

Progress. The event and the run of its steps are stored in release-runs.json in the state folder (20 runs per repository) after every change, so they survive a restart. Each step is pending, running, done, failed (with the result line and the output) or skipped, with its attempts, start and end, and a link to what it made (the release, the pull request). The run is pending (steps left, nothing running, e.g. waiting for the confirmation), running, failed or done. A failed step stops the chain. "Retry this step" (retry) runs only the first unfinished step again and goes on; "Skip" (skip) marks it skipped and goes on. Done and skipped steps never run again, and tag and release creation check the forge first, so a retry after a crash creates nothing twice; the notes step finds an open pull request or an existing section. A step that was running when the app stopped is failed as "interrupted" at the next app start (recover), so the user checks the forge and retries or skips it. One run is driven by one task at a time.

Forge calls (core only, audited writes): the merged pull requests of a milestone (Forgejo/Gitea closed pulls of the issue list with merged, GitHub closed issues with pull_request.merged_at, GitLab merged merge requests), a branch head, a file on a ref, and one file as one commit on a new branch (Forgejo/Gitea contents with new_branch, GitHub a branch ref and contents, GitLab repository/commits with start_branch; a branch equal to the base is refused before any request; audit action file_commit).

Surfaces. No UI yet:

  • Tauri: release_steps(account, repo) (steps, defaults), release_steps_validate(steps), set_release_steps(account, repo, steps | null) (saved or invalid with the problems), release_complete_preview(account, repo, request) (plan with the plan and the token, or refused with the reason), release_complete(account, repo, request, token) (started with the run, whose steps go on in the background, or refused), release_runs(account?, repo?), release_run_confirmation(id), release_run_retry(id, step, token?) and release_run_skip(id, step, token?).
  • CLI: gitoodo release-runs [--repo owner/name] [--account id] [--json] (read only).
  • MCP tool ledger_release_runs (optional repo, read only).

Closing a release#

"Release abschließen" appears once every member is merged or closed. After a confirmation Gitoodo

  1. removes release:next from the closed members (dependency members need nothing),
  2. closes the planned milestone if the user asks and no other open issue is still in it (otherwise it says so and keeps it),
  3. optionally creates the next milestone with the given name (in the app's dialog a version or sprint number is still counted up as a suggestion; it moves to the version suggestion with the release settings).

Tagging, building and publishing stay with the user's own pipeline; the dialog says so in one line. Writes use the account's token in the Rust core (release_membership, release_cut, release_name) and trigger a poll; the app shows the change at once until the poll confirms it.

Queue order#

The autopilot works on the next release first (release management rule 12, spec 7.1 item 4). The next release of a repository is:

  • every scope member (release:next and their dependencies), and
  • every open issue of the next release milestone, with the issues it depends on. The next release milestone is the open milestone whose title is a version (v1.2.3, 1.2, 2026.11, build 42; not Sprint 12) that is due first, else the one with the lowest version, else the oldest. Two that tie on due date and version are not guessed: then only the label counts until the tie is resolved (the findings name it). Later and closed milestones do not count.

These issues and boosted ones form the queue's first group; the score (priority, age, boost, release bonus score.release_bonus) orders each group. A blocked release issue is skipped like any blocked issue, so the rest of the release and then the other issues still go, and without a dispatchable release issue the queue runs on the score as before. Each repository has its own next release; with release planning off nothing but a boost moves an issue forward. The same rule (release::next_release_milestone) picks the milestone the hygiene puts release:next issues and follow-ups on, so a sprint never gets them.

The dispatcher does not read the milestones for every pick: each reconcile pass leaves the next release milestone it read with the writer, and a pick reuses it for up to the default sync interval (NEXT_RELEASE_TTL, 60 s) before it reads the list again. A pass that creates a milestone drops the kept value; a milestone changed in the app shows after the poll the app triggers. The app's queue, the dispatcher's pick and the chat's item list (next_release per issue) use the same order. The release view still lists the scope only; milestone members join it with the release view rework.

The read model (orchestrator_read_model) carries the same data per repository as release.

App#

  • Release view (board tab "Release"): the mental-model sentence, per repository the release name (milestone, or "Benennen" to give it one), a bar for done / in progress / open, the items with state, reason, blockers and a remove button for label members, a "+" per repository and "Issues hinzufügen" on top. The add dialog picks the repository, searches open issues by title or number and adds several at once. "Release abschließen" replaces the open count once everything is done. Without any planned issue a teaching empty state explains the idea and offers "Issues hinzufügen".
  • Board: a flag button per issue row and "Ins nächste Release" / "Aus Release entfernen" in the issue sheet. Issues in as a dependency show why and cannot be removed there.
  • Settings: the per-repository switch beside the activation, with one line on what it does and the milestone line.

The panel fetches release_status on open, every 30 seconds and via release-refresh; a failed fetch shows release-error and keeps the last picture. Test ids: release-* (release-repo-<repo>, release-progress-<repo>, release-item-<repo>-<number>, release-add-<repo>, release-remove-<repo>-<number>, release-cut-<repo>, release-none-add; / in the repo name becomes -), board toggles dashboard-orchestrator-release-<repo>-<number> and dashboard-orchestrator-sheet-release.
