The normal app drops its Dock icon while its window is closed to the tray (then it is hidden from the accessibility tree) and, docked to the tray icon, opens only on a tray click and hides on blur. The test access build removes those obstacles so a worker can operate it with Agent Desktop (agent-desktop, see below). It is a separate Cargo feature (test-access); release and store builds contain none of it.

What the test build changes:

  • Window mode: a regular, decorated window, visible at start, never dismissed on blur. The app is a Dock app, so agent-desktop list-windows lists it as Gitoodo Test. It opens in the detached window's frame (remembered, else 900 x 700 centred, clamped to the screen; #363), not in the popover size (docs/window-frame.md, "Test build").
  • Own identity: bundle ID de.gitoodo.app.testaccess, own config and log directory. It runs next to the installed app and never touches it (single instance, keychain, settings). Several test instances run side by side with their own folders (see "Folders and parallel instances").
  • Test account: a fixture forge (fixture/demo, user tester) and an in-memory token store. No real token, no network, no keychain. The account keeps the fixed id acc-fixture across restarts, so per-account state such as folded groups persists; other accounts are removed.
  • Own keychain service: the secrets the test build does keep in the keychain (chat webhook, remote machine passwords) live under the service gitoodo.testaccess, never under the production service gitoodo (src-tauri/src/keychain.rs, #1192). Saving, testing or clearing them leaves the entries of an installed Gitoodo unchanged.
  • Test IDs in the accessibility tree: each data-testid is mirrored into the DOM id (Agent Desktop's native_id of kind ax_dom_identifier, searchable with find --native-id) and into aria-roledescription. An element that already has its own id (label association) keeps it. A screen reader speaks that role description in place of the role ("shell-settings" instead of "button"); for a screen-reader check start the test app with GITOODO_TEST_REAL_ROLES=1, which keeps the page's own roles and leaves out the mirror (#1163). Address controls by name then.
  • Notifications: the permission reads as granted; posts are logged as test_notification.
  • Usage statistics: hard stop. The test build, like any run with GITOODO_UI_AUTOMATION=1, records, writes and sends nothing, whatever the onboarding switch says (docs/privacy.md).

Build and start#

VITE_TEST_ACCESS=1 npx tauri build --debug --bundles app \
  --features test-access --config src-tauri/tauri.test-access.conf.json
open -n "target/debug/bundle/macos/Gitoodo Test.app"

The panel is open right away. Nothing needs a tray click.

Address elements by test ID#

Scripts use Agent Desktop. Point GITOODO_AGENT_DESKTOP at it (default: agent-desktop on PATH, which Gitoodo installs as ~/.local/bin/agent-desktop); the scripts in this repo never hardcode its location. Workers go through gitoodo desktop [--on NAME] <command> instead, which waits for their turn at that machine's desktop and reaches another machine's desktop over SSH (dispatcher).

agent-desktop find --app "Gitoodo Test" --native-id shell-settings --first   # exact test ID
agent-desktop click @<snapshot>:e<n>                                         # ref from the line above

Every command prints one JSON envelope; matches carry ref_id (@<snapshot>:e<n>), role, name and native_id. Refs belong to one snapshot; the test ID does not change. snapshot --app "Gitoodo Test" prints the whole tree (--max-depth 50 for deep screens). Ref actions are headless: they neither move the pointer nor take the focus. Look again after each action.

One session at a time uses a desktop. Workers take turns through gitoodo desktop-turn; a script is run while nobody else uses this desktop.

Fixture content: three questions in fixture/demo. #1 has a question block with a deadline (tomorrow), #2 is free text, #3 has a deadline two days in the past (the overdue label of the list, #73). GITOODO_TEST_EXTRA_QUESTIONS=<n> at start adds n free-form questions (#4 on, at most 200) to check many open questions (#237). Rows are questions-row-…, copy and share buttons are questions-copy-… and questions-share-…, the detail screen uses detail-….

For long-string layout checks (#337), set GITOODO_TEST_LONG_TEXT=1. Every fixture title (default, scale and showcase mode; in the showcase also the board, session and release titles of the orchestrator's read model, #1161) gains a long sentence and one long word without break opportunities, so wrapping, clipping and ellipses show at the minimum window size. Bodies, numbers and labels stay unchanged.

For large-list navigation (#337), set both GITOODO_TEST_REPOS=300 and GITOODO_TEST_ISSUES_PER_REPO=5 in the test app's launch environment. This replaces the default fixture with 300 repositories (fixture/scale-001 through fixture/scale-300) and 1,500 distinct issues. Each issue is assigned to tester, has needs-human and a cycling ready, in-progress, in-review or blocked status label. Question bodies reuse the three default question types. Each repo also has two fixture pulls, with the green pull linked to that repo's first issue. Dashboard groups and counts come through the normal Rust adapter and sync path.

Both values must be positive integers; missing, invalid or zero input keeps the default fixture and its existing extra-question behavior. Valid scale inputs are capped at 300 repos and 20 issues per repo (6,000 issues total); GITOODO_TEST_EXTRA_QUESTIONS is ignored in scale mode. The scale dataset is seeded once at startup. Repo names, forge IDs and issue URLs are unique; issue numbers are globally unique within this fixture. Comments and closures are scoped to their repository and remain in memory until exit. Other unsupported adapter mutations stay unsupported. This creates test data, not a performance result; navigation and responsiveness still need an explicit runtime check.

For clarity checks with many repositories (#1165), add GITOODO_TEST_SIMILAR_NAMES=1 to a scale launch. Repo i becomes <owner>/<stem>-<nnn>: the owner cycles through fixture, fixture-platform-engineering and fixture-archive, the stem through four long names that share their start (customer-portal-backend-service, …-integration-tests, customer-portal-frontend, …-legacy). Every short name exists under all three owners and names differ only at their end, so a cut name or a missing owner shows. Issues keep their numbers and follow their repo. GITOODO_TEST_VARIED=1 (repo n keeps per_repo - n issues, at least one, and only its first waits for a human) combines with it.

Showcase data for screenshots#

GITOODO_TEST_FIXTURE_LANG=de or =en replaces the fixture with an invented open-source team in that language (src-tauri/src/test_showcase.rs): three repositories (kiezwerk/pegelstand, kiezwerk/radkeller and kiezwerk/hofladen, in English harborlight/tidewatch, harborlight/trailkit and harborlight/driftlog), four questions to the user (one with a deadline tomorrow, one free text, one overdue, one approval), the board with three running workers, pull requests (one with a failing ci/test), a week of closed issues and merged pulls for the weekly review, eight weeks of throughput, the readiness checklist of a well kept repo and a scripted orchestrator chat that proposes one comment. Workers, usage, setup checks and the chat are answered by the fixture, never by a running classifier, dispatcher or agent. A simulated dispatcher (src-tauri/src/test_showcase_dispatcher.rs, #915) gives each session a live terminal over the real attach protocol (backlog, a step line every few seconds, typed keys echo back) and applies steering: Hold and Resume mark the worker held, an instruction appears in its terminal, Cancel, Stop and Park end it, Restart counts a restart. Any other value keeps the plain fixture above.

The first two repositories plan two releases each (#1552, #1540), all with due dates. The first one: 1.4, the next one, with open, running and three merged issues plus the sub-issues #221 and #226, which their parent #224 depends on and pulls in (#1530), and 1.5 with one. The second one: 2.0, the next one, with a running, an open and two merged issues, and 2.1 with one. The third repository plans no release; the extra sessions' issues are in none either. Each planning repository holds the tag of an earlier release (1.3, 1.9): naming a release like it in "Bearbeiten …" shows the warning about an existing tag. The fixture forge keeps the milestones in memory, so the release dialogs work on them until the app exits: issues are added, moved and taken out, releases are created, edited, closed and removed (no forge releases exist), and the release view, the board's release chips and the autopilot's release focus follow at once.

GITOODO_TEST_SHOWCASE_SESSIONS=N (with the showcase) runs N sessions in total instead of three, at most 24: the extra ones are in-progress issues numbered from 300 in both repositories, for checks of a crowded session grid.

GITOODO_TEST_SHOWCASE_BACKLOG=N (with the showcase) adds N ready issues in no release to the first repository, at most 300, numbered from 1000: a long list in "Issues hinzufügen" for checks of the release dialogs, e.g. adding more issues than one membership change takes (100, #1685).

Three switches drive the failure and slow paths of the showcase for real-app checks (#1218): GITOODO_TEST_CHAT_PAUSE_MS=<ms> pauses that long between the events of a scripted chat turn (default 250, at most 60000), so a long turn can be watched; GITOODO_TEST_CHAT_SEND_FAIL=1 makes the first chat message fail to reach the session; GITOODO_TEST_WRITE_FAIL=1 makes the first fixture write (a comment, closing a milestone) fail with a server error (502). Each failure comes once, so the retry goes through and shows whether the first attempt wrote anything. The first repository's findings follow its milestones as the classifier's do: two releases with the same version and due date (set in the release dialogs) show the "several open milestones" card.

GITOODO_TEST_HOST_WAIT=offline, machine_paused, disk_low or build_budget (with the showcase) makes the simulated dispatcher report one ready issue held back by the worker machine werkbank for that reason (#1643), so the status line and the status page name it.

GITOODO_TEST_SERVICES_DOWN=<file> (with the showcase) takes the board's services down while that file exists (#1649): the classifier's read model fails as a failed start ("start_failed") and the dispatcher reads as offline. Create the file during a run to watch the services fail, remove it to watch them come back; without the variable, or while the file is missing, the showcase answers.

GITOODO_TEST_SHOWCASE_IDLE=1 (with the showcase) makes the simulated dispatcher run without a worker (#1649), so the setup assistant's last step shows its waiting marker; the repos then hold the whole label catalogue, so the steps before it are done. The board keeps its sessions.

GITOODO_TEST_WEEKLY_REVIEW=1 (with the showcase) makes the weekly review due at start. The status bar shows the version only in every build; commit and build time are on the About page.

The landing page's shots in site/shots/ come from the browser demo (scripts/site-shots.mjs).

Folders and parallel instances (#1191)#

Without any variable, every test instance uses the folders of its identifier de.gitoodo.app.testaccess (config and logs) and the default state and CLI folders of Gitoodo, and the single-instance lock keeps a second start from running beside the first. Which variable moves which folder of the test app:

  • GITOODO_CONFIG_DIR: the config folder (settings.json, window size and mode, accounts, every store of the app, the fixture home fixture-home). With it set the instance also skips the single-instance lock and opens its own page storage (localStorage: language, drafts, last view, folded groups). Without it: Tauri's config folder of the test identifier and its shared page storage.
  • GITOODO_STATE_DIR: the state folder (SQLite, daemon socket, release runs, activity, …) and the logs, as <dir>/logs. Without it: Gitoodo's state folder (docs/daemon.md).
  • GITOODO_LOG_DIR: the app log; wins over GITOODO_STATE_DIR. Without both: Tauri's log folder of the test identifier.
  • GITOODO_BIN_DIR: the folder of the stable CLI copy. Without it: Gitoodo's CLI folder.
  • GITOODO_TEST_PROFILE: all four at once, below one folder (config, state, logs, bin); it wins over the four variables above.

So two instances started with different GITOODO_CONFIG_DIR values (or different GITOODO_TEST_PROFILE folders) run side by side and share no settings, window state or page storage; changing one leaves the other's files unchanged. With the same folder (or none) they share it, and the second start only brings the first one's window up. Page storage per folder needs macOS 14 or later; Windows and Linux keep it in <config dir>/webview. The test profile is read only by the test app itself, and only the test build reads it at all: release and store builds keep their folders and ignore it. Processes you start yourself (gitoodo classifier, gitoodo dispatcher) need the four folder variables, not the profile.

The test build still reads services and files outside its config dir (the classifier socket, the dispatcher, state_dir). For recordings, set GITOODO_TEST_PROFILE (or GITOODO_STATE_DIR, GITOODO_CONFIG_DIR and GITOODO_BIN_DIR) to an empty temporary folder so nothing of an installed Gitoodo or another test instance shows up or is touched:

GITOODO_TEST_PROFILE="$(mktemp -d)" \
  "target/debug/bundle/macos/Gitoodo Test.app/Contents/MacOS/gitoodo-app" &

A real test repository beside the fixture#

For flows the fixture cannot show (a real clone, worktree and agent session, e.g. "Solve with an agent", #919), an account of the test config may reach its real forge: add it to settings.json of the test config dir and hand its token to the test app in the launch environment as GITOODO_TOKEN_<ID> (the id in upper case, other characters as _, as for a headless service; docs/daemon.md). Start the binary directly (not open --env), so the token is not in an argument list. Such an account stays across starts and uses the real forge adapter; an account without the variable is removed as before, and the showcase never keeps one. The keychain is never read or written. Point GITOODO_STATE_DIR, GITOODO_LOG_DIR and GITOODO_BIN_DIR at a temporary folder, set the repository's local_path and dispatch.worktree_root in the test config's orchestration.json to that folder too, and run your own gitoodo classifier (and gitoodo dispatcher, with a stub agent first on PATH) with the same variables and GITOODO_CONFIG_DIR set to the test config dir before the app starts: the test build shares the service labels with an installed release, so it would otherwise ask the release's services. Use a dedicated test repository only.

Optional native navigation measurements (#337)#

Add VITE_TEST_PERFORMANCE=1 alongside VITE_TEST_ACCESS=1 to the build command. Both build flags are required; the dynamically imported probe is excluded from normal builds. Runtime automation alone does not enable it. Launch the scale fixture as above.

Before the actual run, calibrate accessibility visibility in the real test app: use agent-desktop snapshot --app "Gitoodo Test" --max-depth 50 and reconstruct the readonly report fields as described below, then perform one native input and read them after a quiet pause. If the platform omits this offscreen field or its value, the measurement is not validated. Restart the test process after calibration; only a fresh process resets it.

The probe counts trusted keydown, pointerdown, wheel and actual scroll events. Scroll includes browser-generated scroll events, including programmatic scrolling; trust alone does not prove a human caused a scroll. Non-trusted events and non-finite, zero, negative or future timestamps are rejected. Timestamps must share the performance.now() time origin. It records event timestamp to next animation callback scheduling latency, and gaps between animation callbacks during an input/scroll burst and its 250 ms quiet tail. These are neither pixel-paint/full-response latency nor displayed FPS. A delayed callback can extend that tail; no idle loop runs afterward. Use a foreground, visible window and record the native actions, dataset and environment with the result. No pass/fail threshold is inferred from these numbers.

Read the fields only after the burst is quiet: reporting updates values and creates any additional fragment fields after sampling stops, without live announcements, focus changes or page layout changes. The JSON contains accepted counts by event type, rejected counts, pending queue overflow, burst count, elapsed process window and accumulated active window in milliseconds. eventToNextRafSchedulingMs and frameGapMs each include observed/retained/dropped counts and nearest-rank p50/p95/max of the first 4,096 retained samples (zero when empty). recentBursts keeps the latest 48 bursts as [first, last] pairs (#1165): the burst's first event to the next animation callback, and its last event to the callback after it, in milliseconds rounded to 0.1. Read the report after each action, quietly, to get one value per action; a burst that takes several inputs counts once. Pending event timestamps also cap at 4,096; overflow events are counted but not measured. Results are cumulative until process exit. No targets, key values, content, account data, network requests or logs are collected. The probe adds measurement overhead; corroborate the numbers with native navigation observations, rather than treating them as paint proof.

The accessibility helper caps individual values at 120 characters. Read the header test-performance and test-performance-part-0 through parts - 1 using a full snapshot (without -i). Each part is sequence:index:fragment with at most 96 characters of JSON. Require every sequence to match the header, join fragments by index and check the header character count before parsing. Discard mixed or incomplete reads; do not focus the fields to read them. The report is published only after a quiet burst.

The installed store preview (#235)#

The signed, sandboxed store preview has no test build features, but it has one runtime switch: start it with GITOODO_UI_AUTOMATION=1 in its environment. Without the variable nothing differs from a normal start (no visible change, no permission prompt).

osascript -e 'quit app "Gitoodo"'   # single instance: a running app ignores the variable
open -n --env GITOODO_UI_AUTOMATION=1 /Applications/Gitoodo.app
"${GITOODO_AGENT_DESKTOP:-agent-desktop}" find --app Gitoodo --native-id shell-root --first

With the switch on, the app is a regular (Dock) app so the accessibility API lists it, the real borderless popover opens at start (no tray click) and stays open on blur or the shortcut, and every data-testid is mirrored into the accessibility tree as in the test build. Accounts, keychain, settings and the skill folder are the real ones (no fixture): use it for what the fixture cannot show (#222). Snapshot, find and click work as above; python3 -I scripts/check-test-ids.py Gitoodo lists elements without a test ID.

The ids the #222 checks need are fixed by tests/popover-test-ids.test.ts (it fails if one disappears): shell-root, shell-tab-home, shell-tab-questions, shell-tab-dashboard, shell-settings, shell-sync, questions-row-…, questions-share-…, questions-copy-… (#71), …-repos-<repo> repo switches and …-toggle filter (#135, multi-select), dashboard-quiet-toggle, dashboard-row-… (#85), settings-shortcut-recorder (#83), settings-skill-refresh, settings-skill-<name>-status, settings-agents-copy (#160), settings-desktop-action and the "Request permissions" buttons …-request-button (#995), and in store builds settings-rating-switch, settings-rating-decline, settings-rating-confirm-yes, settings-rating-cancel, settings-rating-declined (#76).

The dashboard opens grouped by status (#193): dashboard-groupby-{status,repo,account,counts} switch the grouping, dashboard-groups is the grouped list, headers are dashboard-group-<kind>-<key> (repo keys read <account>-<owner>/<repo>) and items dashboard-item-<account>-<owner>/<repo>-<number>. The table with dashboard-row-… and dashboard-quiet-toggle is the "Numbers" view: click dashboard-groupby-counts first. The choice is remembered, so a later run may start in any grouping.

"Braucht dich" (#194): dashboard-signals is the counter area at the top with one dashboard-signal-{question,blocked,ci,stale} toggle per signal (pressed = list filtered to it), dashboard-signal-clear removes the filter and dashboard-signals-quiet replaces the toggles when nothing needs the user. dashboard-groupby-signal groups by signal (dashboard-group-signal-<kind>, dashboard-no-signals when empty). Row markers read dashboard-item-signal-<kind>-<item>.

Check that every element has a test ID#

python3 -I scripts/check-test-ids.py     # optional first argument: app name

It reads the live tree of the app's focused window through Agent Desktop (GITOODO_AGENT_DESKTOP) for the screen that is open and lists every button, link, tab, field, toggle and heading in the web view that has no test ID as its DOM id. Exit code 1 if any is missing (2 if the tree cannot be read). Run it once per screen: main, settings, detail, onboarding.

Flows#

  • Mark as read: click a questions-row-… element. The question lands in seen.json of the test config dir (~/Library/Application Support/de.gitoodo.app.testaccess/).
  • Share: click questions-share-… (the system share sheet) or questions-copy-….
  • Deadline reminder: the first sync arms it (reminders.json, "fired": false). With GITOODO_TEST_CLOCK_HOURS=40 set at start, the clock runs 40 h ahead from the second check on, so clicking shell-sync makes it fall due. The log then has a test_notification event (~/Library/Logs/de.gitoodo.app.testaccess/gitoodo.log).
  • Notification permission: always Granted in this build; no system dialog appears.
  • Skills (#160, #995): the "home folder" of this build is fixture-home/ in the test config dir, recreated empty at every start, so the assistants' skill folders (.claude/skills, .agents/skills, .gemini/skills) are fixture folders. The automatic rollout and the status per folder work against them; the real folders in the home folder are untouched. Agent Desktop is neither installed nor updated in this build. The folder bookmark exists only in the store build: build with --features test-access,store to drive it (not verified in the sandbox).
  • Shortcut recording (#83): synthetic key events do not reliably reach the recorder, so the test build adds two buttons below it, settings-shortcut-test-press-alt-meta-j and settings-shortcut-test-press-escape. Click settings-shortcut-recorder (recording starts, the global shortcut is released), then click a test key button: it goes through the same handler as a real key press (save, or cancel and resume the shortcut). They are enabled only while recording.
  • Mark as read on the forge (#159): obsolete. The Eingang and forge notifications were removed (#189), so there is nothing left to mark and no write:notification scope to check.
  • Detached window (#197): only with docking on (settings-docked-switch, #1614); without it the header has no window button and the window is the regular one. Click shell-detach. The window gets its title bar and the button turns into shell-attach; clicking it (or closing the window) returns to the popover. The frame is stored in detached-window.json of the test config dir. The test build is always decorated and never hides, so the visible change is the button and, after attaching, a hidden window that the tray icon reopens.
  • Reply: detail-send posts a comment to the fixture forge; it shows up in the thread until the app exits.
  • Answer leaves at once (#941): after detail-send the sheet closes (or the next card opens) and the question leaves the list and the counts before the forge answered; a failed post brings it back with its draft and the answered-toast reads "Antwort nicht gesendet …".
  • Open the next question (#245): tick detail-next-toggle (kept across cards and restarts), then detail-send: the card of the next open question of the list opens; after the last one the list returns with the "all answered" toast.

Known gap: the global shortcut#

Recording a new shortcut is covered by the test key buttons (see Flows). Triggering the registered shortcut system-wide (outside the app) cannot be done reliably with UI automation and is not covered. In the test build the panel never hides, so the shortcut has nothing to toggle anyway.

Restore the desktop after a test#

Record the installed app’s running and visible state before using the separate test app. Afterward, quit the test app and restore its isolated Application Support and WebKit stores. Do not open or activate an already-running normal Gitoodo app: macOS sends a reopen event and Gitoodo intentionally shows its main window. Preserve the user's previous visibility instead. Only restart a production instance when the test actually started that instance with automation enabled, and restore its previous visibility.

Agent skill lifecycle verification (#545)#

Historical: this run predates the automatic rollout to every assistant's folder (#995), which replaced the per-assistant choice and the install and remove buttons.

The macOS test app at code revision 70cd885 was exercised with isolated skill folders on 2026-11-14. Explicit Codex/shared radio selections produced matching confirmation destinations; selection survived transitions between split and compact settings layouts. Installation, a simulated older managed package update, removal, local-change protection and recovery after a folder write error passed. Updated skill content and the package manifest matched the current bundled bytes. Use fresh accessibility refs after target changes, because the package rows rerender.

Test Application Support and WebKit data were restored byte-for-byte. The normal production instance remained running and hidden. Store permission/bookmark runtime, Windows runtime and VoiceOver were not verified by this test; store compilation alone does not establish those results.
