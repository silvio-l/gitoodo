A satellite is another machine that runs workers for the main host's dispatcher (spec 7.9). Network and SSH live only in crates/core; no port is opened. Forge credentials stay on the main host; assistant subscriptions are provisioned separately as described below.

Pieces#

  • gitoodo satellite: persistent service on satellite.sock (0600) holding worker PTYs; on Windows on the named pipe \\.\pipe\gitoodo-satellite-<user> that only this user may open. gitoodo satellite --stdio is a pipe to it (it starts the service when missing, on Windows detached from the SSH session), so workers survive SSH drops. Only a missing service is started: a busy pipe has one behind it, and a second service would only end at once. The bridge ends when its stdin closes, the SSH session hangs up (SIGHUP), the service closes the connection, or nothing moved either way for 15 minutes; a subscription sends a sign of life every minute so it never idles out. Bridges of gone sessions used to stay forever (#965).
  • Protocol: JSON lines, the same cmd/reply/frame vocabulary as the dispatcher socket (dispatcher_rpc.rs), plus hello, spawn, kill, subscribe, ask, ask_done, copy_state, copy_receive, inputs_receive (the local files an issue names, see local inputs), input and input_done (a worker fetching one more). A bridge session runs requests in a row; subscribe and attach turn it into a stream.
  • Bridge: system ssh -o BatchMode=yes ... -- <target> gitoodo satellite --stdio (GITOODO_SSH replaces the program, used by tests); on Windows .local\bin\gitoodo.exe satellite --stdio, relative to the home folder the SSH session starts in.
  • gitoodo host add <name> <ssh-target>: detects the remote shell, connects, compares versions, saves {name, ssh, shell, platform} only. platform (macos, windows, linux) is the system the machine reported; the app saves it too when it adds, installs, checks or probes a machine and the system differs from the stored one. A machine set up before the system was stored gets it in the background: 30 seconds after the app starts it checks each machine without one, and again every 10 minutes while one is still unknown (offline). The dispatcher starts every machine with it, so an issue for that system waits as offline while the machine is away, not as no_platform. A version mismatch is a clear error with the check command (ssh <target> gitoodo --version). The handshake also compares builds, see "Build identity" below.
  • Dispatcher: polls every host (20 s), offers satellites as host candidates, starts workers with spawn (the satellite creates the worktree in its own clone). Unreachable host: no new work, leases wait for the grace and are then released (lease_action).
  • Own copies (#965): a satellite keeps its clones under ~/gitoodo/repos/<owner>/<repo> in its own home; the main host never sends one of its own paths. spawn's prepare carries the repository's credential-free forge address (origin). The main host makes and updates the copy itself before each spawn (satellite_copy.rs), so the machine needs no forge access and no network permission for its own git: it fetches the base (and the worker branch, when the forge has it) with the connected account into its own copy, filling in whatever a partial copy lacks, asks the satellite what it holds (copy_state: tracking refs, partial or not) and sends a git bundle of the rest (copy_receive: a header with refs, size and SHA-256, then base64 chunks of 512 KiB; at most 4 GiB). The first copy gets the full history, later starts only what is new (the satellite's heads are the bundle's prerequisites); a copy left partial by an older build gets the full history once and then stops being partial, so no lazy fetch is ever needed there. The satellite checks size and checksum, unbundles, moves origin/<base> (and origin/<branch>, or drops it when the forge no longer has the branch), sets origin to the forge address and starts the worktree from it (prepare.synced); a restarted worker so gets its pushed branch back. The forge's branch wins over what an earlier run left on the machine: a local branch behind it is fast-forwarded, one apart from it (the branch was updated onto the base, or someone pushed) is set to it, and commits of its own the forge lacks stay under refs/gitoodo/kept/<branch>/<sha> (log satellite.branch_kept); a kept worktree that is clean and only behind is fast-forwarded, one with uncommitted work or own commits stays as it is. The token stays on the main host: it is in no bundle, frame, error or log.
  • Satellite paths (#965): the main host sends none of its own paths. The worker's cwd is ~/gitoodo/worktrees/<repo>/<number> (or below a ~-relative worktree root), the hygiene requests name the satellite's own roots, a configured absolute agent path that does not exist there falls back to the agent's name, and the hook and status-line commands in --settings (Claude Code) and in -c hooks.* (Codex) carry a placeholder the satellite replaces with its own gitoodo, quoted as one shell word (for Codex on Windows as a command PowerShell runs: the bare path, or & '<path>', see dispatcher.md, "Worker launch per agent").
  • Delivery speed (#1491): the delivery's scratch repository borrows the objects of the main host's own copy of the repository (objects/info/alternates) and starts from its origin/<base>, so the base fetch brings only what the copy lacks instead of the whole history (about 300 MB for a large repository). Without a full copy it fetches as before. The main host allows 180 s and the satellite waits 200 s; a forge that did not answer (a timeout, a broken-off connection, 502/503/504) is tried again after 5 and then 15 s within that time; a delivery that fails is recorded with its own cause delivery and the machine's name, and the next success (delivered) ends it, so a single timeout shows nowhere. satellite.delivered and satellite.delivery_failed log the bundle size, whether the copy was reused, the phase and the time of each phase.
  • Delivery when the forge moved on: the main host fetches the forge's worker branch into the delivery's scratch repository; a bundle that lacks its commits is not pushed. The one exception is a branch the worker rebased itself (#1565): the delivery carries the satellite's origin/<branch>, and when that is still the forge's head and the bundle contains the base's current head, the main host replaces the branch with a push leased on that head; so does a gitoodo worker pr --replace that a person approved on the issue (#1644, see dispatcher.md, "Worker delivery"), while that head is still the forge's. Otherwise the main host sends them to the satellite's copy as origin/<branch>, and the worker gets a reason that says to rebase or merge origin/<branch> and deliver again. A satellite whose build lacks copy_state is the machine fault outdated (see below) and gets no start; any other failure of the transfer falls back to the machine's own git clone, and its reason is added to the checkout: error.
  • Copy failed here (#2068): when git on this computer cannot reach the forge at all ("No route to host", EHOSTUNREACH, "Network is unreachable", or a failed connection "after 0 ms", fault::local_network_failure) and the machine's own git access fails after it, the fault is still a no_checkout of that machine, but its reason starts with "this computer cannot reach the forge with git" and carries the cause local_git_network (fault::cause_of). Like any copy fault it is retried quietly three times; then the status and the notification name this computer (macOS: the "Local Network" permission, or services still running a replaced program, see dispatcher.md, "Replaced program") with a restart of the dispatcher as the fix, never the worker machine's forge access. Logged as dispatch.copy_local_network.
  • The machine's own git access (the fallback above, and its first clone) never asks anyone: it keeps the machine's configured credential helper, its only way to the forge, but runs with credential.interactive=false, an empty core.askPass, GIT_TERMINAL_PROMPT=0, GCM_INTERACTIVE=never and without GIT_ASKPASS/SSH_ASKPASS (worktree::own_access_git). In a service without a terminal it fails at once, and its reason is git's last fatal: line (worktree::short_reason), not every line a credential manager wrote before it.
  • Branch updates (#383) on a satellite go the same way: the main host sends the base first, update_branch with via_host rebases or merges offline and answers with a bundle of the new head, which the main host pushes with the account (--force-with-lease on the old head).
  • Worker PATH (#965): a satellite service started by ssh or launchd has a short PATH; its workers get the agent's folder, the service's PATH, the login shell's folders and the known install folders that exist (~/.local/bin, ~/.cargo/bin, Homebrew, ...), so the agent and the tools it calls are found as in a terminal.
  • Failed remote starts are sorted by who answered (#965): a satellite that answered with a reason was reached, its fault is the reason's class (agent_missing, agent_login, no_checkout, start_failed, outdated); only no answer at all is unreachable. Each class pauses new workers on that machine once (one notice per machine, not per issue) and names the machine, the agent, the repository and one action there ("update Gitoodo there" for an outdated build); "restart the service" is offered only for this computer. An unreachable machine gives no notice: nobody can fix it from here, it is retried by itself, the work goes to the other machines, and Settings → Worker machines shows it offline.
  • gitoodo attach [<host>] <issue>: raw terminal, detach with Ctrl-], the worker keeps running.
  • Questions: gitoodo ask on a satellite (GITOODO_SATELLITE=1) asks the service, which forwards it on the main host's subscription; the main host posts and confirms, then the worker is parked.
  • Context: gitoodo worker context on a satellite asks the service, which forwards it on the same subscription (ContextForward); the main host reads the issue with its own token, only while its lease says the worker runs on that machine, and sends the JSON back (ContextDone, at most 1 MB). The satellite never sees a token.
  • Umbrella close (#1816): gitoodo worker close --summary <text> on a satellite asks the service, which forwards it on the same subscription (CloseForward); the main host checks and closes the umbrella issue with its own token, only while a live lease says the worker runs on that machine, and confirms (CloseDone). The service then ends the worker without an exit record, and the main host ends the run as closed. See docs/orchestrator/dispatcher.md, "Umbrella issues".
  • Hooks: gitoodo hook stop|stop-failure|status-line|activity|tool-start|tool-end|needs-you on a satellite (GITOODO_SATELLITE=1) sends hook to the service instead of a dispatcher socket (see "Hook events" below); the live state (docs/orchestrator/dispatcher.md, "Live state of a session") goes to the host in the worker's facts.

Remote worker lifecycle#

  • The satellite records workers that end on their own and measures output silence. The main host polls with report (exits are drained, so each is delivered once) and applies the same hang policy as for local workers: silence for the timeout restarts the worker (a spawn without prepare, in the worktree that already exists there), after the maximum it is stalled.
  • report also carries the satellite's own subscription usage. The satellite starts reading it (keychain, usage endpoint, codex app-server) with the first report, not at service start, so a satellite no main host talks to stays idle and small (#769).
  • A login that no longer works is reported apart from a reached limit (#994): the agent's usage.problem is not_signed_in and no old values stand for it. The satellite says so only on the agent's own word: Codex's account/rateLimits/read answers with an auth error, or Codex says so in a notification or on its stderr while the query fails ("could not be refreshed", "sign in again", a rejected refresh token, HTTP 401, "authentication required"); Claude's usage endpoint refuses a token that has not expired yet (401/403). A query that only times out or fails otherwise stays unknown. Such a login typically still passes codex login status ("Logged in") after its refresh token was revoked. The main host then waits with login_expired ("the agent's login there no longer works; sign in again on that machine") instead of usage_gate for that agent there; with the worker pool it names this reason over a usage limit of the other agent, because only a person ends it. After signing in again the next query (at most five minutes later) clears it.
  • A worker that exits on its own is handled like a local one (finish/merge flow). A worker killed by the main host leaves no exit record.
  • report carries what the workers there used (#1859, crates/cli/src/satellite_spend.rs): the satellite reads a run's tokens from the agent's session log in its worktree with the same readers as the dispatcher (docs/agents.md), at every run end (own exit, idle exit, close, kill) and every ten minutes for runs still going, plus Claude Code's status-line cost that the worker's hook hands over. Each reading goes out as spend (run, agent, from, at, tokens, cost, the billing read there, and owner, the main host that started the run) and is repeated in every report for 15 minutes after the run ended, so a lost reply loses nothing; a restarted run keeps its first start and its cost for two days. billing names, per agent, what the login files there say (cached for five minutes). The main host takes only readings of its own runs, stores them in its agent-spend.json with the machine's name (a newer reading replaces an older one of the same run, so repeats count once) and the machines' billing with them. Both fields are optional and they did not raise the protocol version: a satellite of an older build sends neither, and the app says its spend is not reported until Gitoodo is updated there.

Memory entries#

A worker on a satellite that proposes or disputes a memory entry (gitoodo worker remember|dispute, #2073) sends the memory request to the satellite service; the memory file is the main host's, so the service forwards it on its subscription (memory_forward) and the main host answers with memory_done. These requests raised the protocol to 5: a satellite of an older build cannot serve them and counts as outdated until it is updated.

Hook events#

A satellite has no dispatcher, so a worker's gitoodo hook <event> there talks to the satellite service (satellite.sock, on Windows its named pipe) with the dispatcher's hook request (issue, event, usage). The service holds the worker's terminal, knows its delivery and reads its own agent login, so it applies the event itself, exactly as the dispatcher does for a local worker (crates/cli/src/satellite_turns.rs; locally Hub::hook and Hub::check):

  • Every hook is a sign of life: report.silent counts from the later of the last output and the last hook, which the main host's hang policy reads.
  • stop without a result (no pull request yet) is looked at after the same 30 s grace: a worker stopped at its usage limit (this machine's lock or a blocked Codex report; a window at 100 % alone is no stop) whose reset is at most 30 minutes away or unknown keeps its slot (satellite.worker_limit_wait; Claude Code's login is locked and continue follows at the lock's end, Codex gets continue once its login is no longer stopped); one a person typed into lately (attached from the main host) is marked idle; one at a limit whose reset is further off ends (satellite.worker_limit_idle); the others get the reminder once (satellite.worker_nudged; it names gitoodo worker pr and gitoodo ask, the ways a satellite worker has) and end at the next such turn end (satellite.worker_idle). 5 minutes without output and hook from Claude Code or Codex get the reminder too, once, but never the end: the main host's hang policy decides then. A worker being ended gets nothing typed any more.
  • Such an end goes in this order: the process is killed and its end awaited, so nothing writes to the worktree any more; then what was not committed becomes one WIP: commit on the assigned branch (with the same rules for new files and the same branch and rebase checks as on the main host) and the branch is delivered through the main host as with gitoodo worker push (satellite.idle_save_failed, satellite.idle_push_failed when that fails; the work then stays in the worktree there). A worker that changed nothing beyond the base has nothing to deliver; that counts as saved. While this runs the worker is reported as not silent, so the main host's hang policy does not restart it in the middle. Only then the worker's entry goes and its exit record says why (ended: limited, or idle after the reminder and whenever the delivery failed or a new file named like a secret stayed behind): the main host neither restarts nor kills the worker; at the limit it frees the slot, holds that agent off the issue until the reset and sends the issue back into the queue, otherwise the issue stalls with no_result. activity and stop-failure cancel a pending look.
  • Mixed builds: an older main host ignores ended and takes such an exit as one without a pull request (a restart, the work already on the branch); an older satellite never ends an idle worker this way, so the main host's hang policy watches it as before. The automatic update (#1181) brings both to the same build.
  • stop after the pull request (gitoodo worker pr confirmed by the main host) ends the worker (Claude Code, Codex; satellite.worker_finished), and its exit record says code 0, so the main host merges at once as for a local worker. A Codex stop asks this machine's Codex limits again (at most every 30 s).
  • stop-failure marks the worker limited and locks this machine's Claude login (Tracker::limit_reached); status-line brings the status line's usage windows. Both go into the next usage round, so they show in report.providers; the lock outlives the next usage query until a report shows room or its end passes. At the end the worker gets continue (satellite.worker_continued).
  • list carries the satellite's idle, limited and limited_until (this machine's lock end). The main host shows them on the worker's tile and does not take a limited worker's silence for a hang (login_locked), as for a local worker. The main host's own usage figures stay its own: a satellite's status line describes the satellite's login.

Robustness: the state lives on the satellite, so nothing is lost while the main host is away; it reads the result with its next list and report. The hook waits at most 3 s for the service and never fails or prints; no service, a busy one or an older one that refuses hook (bad request or "does not handle") is silent, as a missing dispatcher is locally. An older satellite sends nothing and lists no states, so the main host behaves as before; an older main host ignores the states. The events carry an issue key, the event's name and usage percentages, never a token or a path.

  • A run the main host tracks is not released as vanished for 45 s after start, so a slow poll cannot drop a fresh worker. Unreachable satellites keep the lease grace rules above.
  • Run state of remote workers is kept in <state>/remote-runs.json on the main host (no environment, so no token), written right after each start and restart and after every poll. Updating the main host's app or dispatcher does not touch a satellite's workers: they run on the satellite, and the new dispatcher takes them over from that file before its first poll (dispatch.remote_reattached), with their lease, start time, start command and restarts, so their exits, hangs, idle and limit ends, delivery and cleanup are handled as before, and they show in the overview (see dispatcher). Before this file existed a restart left them running unseen: their lease was renewed forever, their slot stayed taken, the automatic update waited for them and unknown usage there held the machine back.

Workers no main host owns#

Each main host has a stable id for its satellites (dispatcher_rpc::main_host_id: its machine name and a short hash of its state folder, so a restart keeps it and a second instance on the same machine differs). It starts every worker under that id (spawn field owner) and, after every report, sends claim with its id and the issues of the workers it supervises on that machine (its tracked runs; none before it took over its predecessor's). The satellite keeps the presence of each main host apart and notes per worker its owner and when that owner last named it.

A worker is an orphan (satellite.worker_orphaned) only when its own main host keeps polling (its last claim at most 2 minutes old, CLAIM_PRESENT_SECS) and has not named it for 15 minutes (CLAIM_ORPHAN_SECS; counted from the later of the worker's start or last claim and the start of that polling, so a main host back from a sleep has the full time). The claims of another main host never touch it: two main hosts sharing a satellite, or an old and a new install during a rollout, cannot end each other's workers. The satellite ends an orphan like an idle worker: the process first, then a commit of what was not committed (WIP: unfinished work, saved when no main host supervised the run any more; main hosts only read the WIP: prefix) and the delivery through the main host (which accepts it while the worker's lease is still there), then the slot frees, so an update waiting for the workers can go on. Its exit says idle, which every main host understands.

Nothing ends:

  • while no main host claims at all, or while the owner is asleep or offline (not polling);
  • for a worker without an owner: one started by an older main host, which never sends claim (an older satellite answers it with an error, after the poll's other requests). A claim without an id changes nothing either;
  • when a main host's id changes (renamed machine, moved state folder): its next claim names its workers under the new id, and the satellite moves them over;
  • when a satellite is renamed in the settings: the main host claims the workers it recorded under a name no longer configured on every satellite. Until the next dispatcher start their runs keep the old name, so their exits and hangs are not seen; after a restart the takeover drops them (the lease names the old machine) and the satellite's claims run out, so they end as orphans with their work saved.
  • Worktrees on the satellite carry the ownership marker; hygiene_scan and hygiene_apply let the main host clean them up, and the satellite runs its own safe round (see repo hygiene).
  • The satellite frees its disk by itself like the main host (#1675): build output of ended and waiting runs in its worktrees, then caches and old temp files, scheduled and at once when its disk runs low, under the main host's cleanup settings (HygieneScope.cleanup) and with the worktrees the main host holds (HygieneScope.held); both fields are optional, so older main hosts and satellites keep working (see repo hygiene, "On a satellite").
  • What only the user may remove there (build output of other projects, also ad-hoc checkouts right in the home folder) comes with the satellite's disk report as suggestions (#1680); the Storage page lists them per machine, and a confirmed one goes with suggestion_remove after the satellite checked it once more. The satellite also removes the scratch folders (~/.gitoodo-scratch/<run>) of ended runs that workers of other machines checked there over ssh, and first ends what such a check left running after its run ended (#1931; see automatic disk cleanup).

Updating a satellite (#965)#

A satellite keeps its run state in memory, and its workers are children of the satellite process (not hosted like the main host's). An update therefore never ends the service while a worker runs there: installing replaces only the file, and the long-running service takes up the new build once it is idle (see "Build identity" below). A service that ends anyway (a reboot) loses nothing and runs nothing twice: the worktrees stay on the satellite, the main host no longer finds the runs in the satellite's list and releases their leases (after the 45 s start grace and the unreachable grace while the satellite is away), and the issues go back into the queue with their worktrees and commits kept on the satellite.

Waiting workers never hold an update back#

"Once it is idle" must not mean "never": a worker paused at its usage limit (a weekly limit can last days), idle at a turn end or waiting for a person runs no work, yet it kept the service on the old build, and with it the sign-in only the new build takes (a deadlock: the old build closes the connection on Request::Logins, so the paused worker never got the sign-in that would end its pause). The dispatcher (crates/cli/src/dispatcher_resume.rs) therefore:

  • Drains. When a satellite reports updating (the installed build waits) and every worker it lists is this dispatcher's, has a start command and is parked there (limited, idle or held), it ends them with Request::Kill (dispatch.update_drained). The runs stay tracked (marked ended before the kill, so their exit is not taken for the end of their work) and their leases are renewed while the machine answers. With no worker left, the service takes up the new build within a minute (watch_binary), also on an older build.
  • Upper bound (#1464). An installed update waits at most 10 minutes (FORCE_SECS) for the workers there. Then every worker of this dispatcher there is drained the same way, also one that still works and whatever state the machine reports (an older build reports none): dispatch.wait_stuck (wait = machine_update). Each resumes its own session on the new build right after the switch (below), so its step goes on where it stopped. A worker of another dispatcher is never ended; nobody here could resume it. The wait is counted across restarts of the dispatcher (update-waits.json in its state folder; one older than 6 hours counts anew), so app updates in a row never start the 10 minutes over.
  • Resumes. Once the machine runs the new build (not outdated any more), each drained run starts again in its worktree with Request::Spawn's resume (dispatch.update_resumed), after this computer's sign-ins were pushed: Claude Code continues its session with --resume <id> (the id preset at the start with --session-id; for a worker started without one, its newest session in the worktree), Codex with codex resume <id> (its newest session log in the worktree since the run's start), each with the resume prompt instead of the brief. Where no session is found, the worker starts afresh in the same worktree, with its commits and files kept (satellite.resume_missing). A machine that does not come back on the new build within 30 minutes gets its workers back anyway on the build it runs. The restart is not counted as one after a hang.
  • Resolver runs are drained the same way but not resumed in place: the attempt goes back into the resolver's queue without costing one of its starts and starts again like any waiting one, in a system slot within the limits, on any machine with room (resolver.requeued, cause = machine_update; docs/orchestrator/resolver.md).

A process cannot be handed from the old service to the new one (the PTY master closes with the service), so resuming the agent's own session is how the conversation is kept. The same restart also picks up an agent CLI that updated itself on disk meanwhile. A drained run that a restart of this dispatcher interrupts is not taken over (its record says it ended); its lease runs out and the issue goes back into the queue with its worktree kept.

Build identity and outdated builds#

Every development build reports the same version (0.1.0), so a version string cannot tell an old build from a new one. A machine that kept an older CLI then failed starts with errors from code it lacked (git fetch origin dev failed: fatal: cannot change to '~/gitoodo/repos/...'). Builds are therefore compared by their identity, the SHA-256 of the executable (crates/core/src/build_id.rs):

  • Each long-running process (satellite service, dispatcher) measures its own build once at start, before an update could replace the file. The app compares with the CLI it installs on machines (the gitoodo next to it), not with its own binary.
  • hello replies carry build (the satellite's running build), arch (its processor) and, while an installed update waits for the workers, installed (that build). All three are optional; older satellites omit them.
  • Comparison (satellite::compare_builds): another version string fails the handshake as before. With the same version on the same system and processor, the builds must match; a satellite that names no build is too old to and counts as outdated. On another system the release build of the version is installed, so the version alone decides there.
  • An outdated satellite stays connected: lists, reports, kills and branch updates of the workers running there go on, but spawn is refused before it is sent, with an outdated build: ... reason. A request an older satellite does not understand (bad request: ...) is reported the same way, never as a git or copy error.
  • The update window is not a fault (#1463). A new start refused for it ends its run update_pending and the issue goes back into the queue for another machine; nothing is paused. A restart or resume refused for it waits (dispatch.update_hold) and is retried with every dispatcher round; after 30 minutes it gives up the machine and starts again where there is room, unless the update provably goes on (#1466): a build there that reported within the last two minutes and compiled a new crate within 20, or an installed build waiting less than 15 minutes for its switch. Hard bound: 2 hours 15 minutes (the longest build and the switch). Past it the issue starts elsewhere or on the build the machine runs; the machine's row keeps saying that it builds, and is never shown as a fault for it. The machine's own update is the fleet watcher's (below). A fault an older dispatcher left with an outdated build reason ends as soon as the machine runs this build.
  • The handshake also carries commit (the Git commit the build was made from, embedded by crates/core/build.rs; GITOODO_COMMIT overrides it for builds from an archive) and protocol (dispatcher_rpc::PROTOCOL, raised with every change of the requests and replies; a test pins their source to the number). On another system the hashes never match, so there the commit and the protocol decide: another commit (or none, from an older satellite) or another protocol is outdated as well (#1435), since every dev build has the same version. Such a machine gets no new worker until it was updated by itself (built from this commit there, see below); workers running there go on. The machine list shows the commit, short, as "Build".
  • An outdated machine whose protocol matches still restarts its workers in place: a spawn without a fresh checkout (prepare: None, the restart of a parked or ended worker) is sent to the old service, only a new checkout is refused (#1463).
  • host_version hashes the installed file too (sha256sum/shasum -a 256, Get-FileHash on Windows) and reports other with other_build: true for the same version with another build on this system; the assistant then says "an older build" instead of naming two equal versions.

Taking up an update without stopping workers:

  • After an install the app runs gitoodo satellite --restart-idle there. It prints one restart=<word> line: none (no service ran), current (it already runs the installed build), done (the idle service ended, the next connection starts the new one), busy (workers run; the service takes it up after them) or unsupported (an older service on Windows that cannot be ended from outside; it takes the update up when it ends).
  • restart_service asks the service to end; it answers ok only while no worker runs and then ends, otherwise a busy: error. An older service that does not know the request is ended with SIGTERM (its peer process id from the socket) after a second hello showed no workers.
  • The service also checks its own file every 60 seconds; once another build is installed it reports it as installed and ends as soon as no worker runs, so a machine updated while busy needs no further step.
  • The machine list shows "Updating automatically …" for such a machine and for every outdated machine the dispatcher updates by itself (no button), "Needs update" with "Update" only where that failed or no dispatcher runs, and "Up to date" otherwise; the version is the chip's tooltip.

Automatic update (#1181)#

Worker machines are kept on the shipped build without a click. The dispatcher's fleet watcher (crates/cli/src/fleet.rs) shakes hands with each satellite every 20 seconds anyway; the decision and its memory live in crates/core/src/satellite_update.rs (pure, tested with a fake ssh/scp and a mocked release download):

  • Trigger: a hello that fails with another build or version (need_of → Update). A machine that already runs this build, or whose service already holds the installed update and waits for its workers (updating), is left alone. A machine that runs a newer version than the app is never downgraded (Newer); "Update" in Settings still lets the user do it by hand.
  • Install: the same verified path as the app (remote_version::update). On the same system the dispatcher copies its own CLI (build_id::own_cli, only while the file still is the build that runs; after an app update the app restarts the dispatcher with the new one); on another system it downloads the release build in Rust and checks its SHA-256 first. Either way the upload goes to gitoodo.upload, is checked by hash on the machine and only then moved over the old file, which keeps serving until then; a failure leaves the installed build untouched.
  • Switch: gitoodo satellite --restart-idle. Working workers are not ended at once; a busy machine takes the installed build up after them (phase waiting), at the latest after 10 minutes (the upper bound above: they are ended and resume their sessions on the new build). Workers that only wait (usage limit, turn end, a person) are ended and resume after the switch ("Waiting workers never hold an update back" above).
  • The CLI copied is always the file whose hash is the reference build: on macOS the app bundle's Contents/MacOS/gitoodo, not the service helper's own copy, which is signed apart and has another hash. An install that reports success but is followed by another build at the next poll counts as a failure (still_outdated), so it is never repeated in a loop.
  • One install per machine at a time. A failure retries after 1, 2, 5, 10 and then every 15 minutes. The first two failures stay quiet; the third brings one notice that says in plain words what failed (copy, checksum, download, …) and keeps "Update" in Settings → Worker machines as the manual retry. No further notice follows until it works.
  • Another system (#1435): a release build downloads the release asset. Any other build is made on the machine from this build's source (crates/core/src/remote_build.rs): git archive of the commit (workspace manifest, lock file, crates/, src-tauri/) is copied to ~/.cache/gitoodo-build/, built there with cargo build --profile satellite --locked -p gitoodo-cli and GITOODO_COMMIT set (#1927: [profile.satellite] is release code without fat LTO and with parallel, incremental code generation, so an update recompiles in minutes what changed instead of linking the whole program on one core for 20 minutes and more), and installed through the same checked gitoodo.upload path. A marker (installed-commit) keeps a built commit from being built twice. While it builds the machine list says so (building in machine_updates, with build_step, the crates compiled so far: "builds the update (step 212)"), and running workers go on. One build at a time uses that folder, whichever computer started it (#1466): a lock folder there, made with one atomic mkdir, names its holder and carries a beat (<unix seconds> <steps>) that the build renews every 5 seconds while cargo runs; the controller reads it every 30 seconds. A second computer waits for it calmly (satellite.build_lock_wait) and builds nothing when the first one installed the same commit. A lock without a beat for 5 minutes was left behind (a crash, a cut connection) and is taken over (satellite.build_lock_stale); a build whose lock was taken over stops. Windows keeps a build running after its connection was cut, and its open files keep the folder from being unpacked: with the lock held, a build there first ends the builds that still work in the folder (their program or command line names it) with their process tree (satellite.build_foreign_ended). A build that takes longer than 2 hours, the wait for the folder included, counts as failed. Without cargo there (no_toolchain), with a failing build (build_failed, with the last lines of its log) or without the source (no_source, an app not built from a checkout) it is one notice with what to do; "Install Rust there once" for a missing toolchain.
  • No build for the machine (an Intel Mac, a system without a release asset, a missing asset): one notice, and no automatic attempt again until the dispatcher restarts.
  • Switch point: a service that holds an installed build checks every 2 seconds whether its last worker ended and then ends (instead of every 60 seconds), and the fleet watcher asks it with --restart-idle once a minute while it waits (satellite.switch_asked). A machine offline meanwhile is asked again once it answers; an install is never repeated for a waiting machine.
  • The dispatcher status (machine_updates) lists each machine's phase (updating, waiting, retrying, failed, no_build, newer), reason and next attempt; the app reads it for the machine list. While the update is automatic, the outdated fault is left out of the status page and its notice.
  • Fault texts (#1466): the app words every machine fault itself, by its kind and cause (fault::cause_of, e.g. start_confirmation); the English reason shows only as the tooltip of the fault line in the machine list. A status notice and a notification come only where the user has something to do: a missing or signed-out agent, an update that is stuck, or a start or copy that failed three times in a row (NOTICED_FAILURES); a first failure is retried quietly. A start confirmation also counts only from its third time in a row, never by age alone (#1703): Gitoodo marks every worktree trusted before the start, so a single prompt is a passing race on the agent's config file.

Install and upgrade: gitoodo host install <name>#

Uses the system ssh/scp only (BatchMode, no stored secrets). On a Windows machine every step is the PowerShell equivalent (see "Windows machines" below). Steps: uname -sm must match this build's OS and CPU, upload to .local/bin/gitoodo.upload, compare the SHA-256 computed on the satellite with the local one, only then move it over .local/bin/gitoodo, and finish with a handshake. A mismatch deletes the upload and leaves the installed binary untouched. On a version mismatch host add points to this command as the upgrade.

Version check and other systems in the app (#441)#

host_version runs one command on the machine (uname -sm and gitoodo --version, from PATH or ~/.local/bin) and reports same, missing or other plus where an install comes from (crates/core/src/remote_version.rs):

  • this_build: same system and processor, the app copies its own CLI as above.
  • release: another supported system (macOS on Apple silicon, Linux x86_64/aarch64, Windows x86_64). The app downloads {base}/v{version}/gitoodo-{triple} and gitoodo-{triple}.sha256 in Rust (size capped, no tokens), compares the SHA-256 before anything is copied and then uses the same verified upload. base is GITOODO_RELEASE_URL at build time, by default the GitHub releases download URL. The release pipeline must publish both assets per target triple.
  • intel_mac: a Mac with an Intel processor. Gitoodo for macOS runs on Apple silicon only (docs/release.md), so the assistant explains that and offers no install; update refuses with no_build without downloading. The system is uname -sm, corrected to Darwin arm64 via sysctl hw.optional.arm64 when the login shell runs under Rosetta.
  • none: no build for that system; the error no_build names the system and asks to build Gitoodo there and place it at ~/.local/bin/gitoodo. A missing asset (404) is also no_build, any other download failure download_failed.

The "Add remote machine" assistant runs the check after connecting and offers install or update as its own step, which the user can skip; the machine list offers "Update all" for every machine whose probe reports another version or an outdated build and that the dispatcher does not update by itself (it failed, or no dispatcher runs). On the same system the check also compares the installed file's hash with this build ("Build identity" above), so another build of the same version is offered as an update too.

Machine suggestions and network search (#440)#

The address step of the assistant lists machines the user probably means (crates/core/src/discovery, Tauri commands discovery_known, discovery_search, discovery_cancel in src-tauri/src/discovery.rs):

  • Right away, without network: hosts from ~/.ssh/config (with Include, globs and paths relative to ~/.ssh; HostName, Port, User, IdentityFile; wildcard patterns skipped) and plain entries from known_hosts. Hashed known_hosts entries only mark a suggestion as "connected before", they never add one.
  • Only after "Search network": TCP port 22 on every address of the local subnets, derived from the interfaces and capped at /24 (at most 254 addresses per interface; loopback, link-local and public addresses skipped), with at most 64 probes at once, 500 ms connect and 1.5 s banner timeout; a hit must answer with an SSH- banner. In parallel the search listens 3 s for mDNS _ssh._tcp and _sftp-ssh._tcp announcements. Progress reaches the page through a channel; "Stop search" sets a cancel flag, no new probe starts and the result so far is kept.
  • Suggestions are merged by address and port, keep every source (SSH config, network, connected before) and are marked "already added" when a saved machine uses that host. Picking one fills name, address, port and user of the manual entry; nothing is saved before the usual steps.

Forge access and assistant subscriptions#

The satellite has no forge account configuration. Questions reach the forge only through the main host (ask forwarding), tested in crates/cli/tests/satellite_bridge.rs.

“Install” also provisions enabled coding assistants, the bundled question skill and Agent Desktop with its version-matched skills (desktop control, permissions). The app keeps Agent Desktop there current by itself (at start and daily); a failure shows on the computer's card, and on a Mac the person there approves its permissions once. Install copies no sign-in (#1259): a copied refresh token works on one machine only, so the next renewal on either side would end the other's sign-in. Worker machines use this computer's sign-in at run time instead (next section). A setup request from an older app that still carries sign-ins is accepted and its sign-ins are dropped unread. Install needs access to the official Node.js download service and package registry. The destination does not need GitHub access when the app carries a matching satellite executable.

This computer's sign-ins on worker machines (#1259)#

Worker machines use the subscriptions of the main computer; nobody has to sign in on each machine. For Claude Code and Codex this computer owns every renewal, the worker machines never renew; Gemini CLI there renews its own copy (#1408):

  • Claude Code: the current access token of this computer's own Claude Code login, read from Claude Code's own credential store (macOS: the keychain item Claude Code-credentials, read with the system's security tool, which Claude Code itself uses to keep it, so there is no approval prompt; Linux and Windows: ~/.claude/.credentials.json). Only the access token, when it ends and the fingerprint of its account (from the account and organisation ids in the same item) are taken; the refresh token and everything else in the store are never read into the grant and never leave this computer. Nothing needs setting up. Claude Code's access token lasts a few hours: every usage round (30 seconds) the dispatcher reads the store again, and when Claude Code here renewed its login (a new token), the machines that use it get the new one in their next poll. Claude Code renews only in the last five minutes and only while it runs; when less than 4.5 minutes are left the dispatcher runs claude auth status --json here once a minute. That command calls no model, and Claude Code renews its own login before it answers (checked against Claude Code 2.1.328 with fake credentials behind a local proxy: with less than five minutes left it asks Claude's token endpoint and waits for it; with more it does not). Gitoodo never writes Claude Code's store and never renews with the refresh token itself; Claude Code on this computer stays the only one that renews. When the token ends anyway (Claude Code here signed out, offline, or the renewal refused), the settings say "Claude Code's sign-in here ran out and Claude Code did not renew it. Meanwhile worker machines signed in with the same account use their own sign-in; the others start no Claude Code workers. Start Claude Code here once." Machines signed in with the same account keep their own sign-in; machines signed in with another account start no Claude Code worker until the renewed token arrives (#1634). The long-lived tokens of the former setup (claude setup-token, keychain entries worker-login-claude…) are removed from the keychain at the next app start; Claude Code's tokens themselves stay valid until they end and can be ended in the Claude account settings.

    Terms: Claude Code stays the only program that uses the login, on the person's own machines, with the person's own subscription; Gitoodo only hands Claude Code its own access token, in Claude Code's own credential format; on the worker machines nothing else uses it.

  • Codex: this computer's own auth.json (ChatGPT sign-in only, never an API key), with the refresh token emptied and last_refresh set to now. Before it goes out the dispatcher asks Codex here to renew its access token when less than a day is left (account/read with refreshToken: true on its app server); a copy with less than a day left is not sent. Codex keeping its sign-in in the system keychain here (cli_auth_credentials_store = "keyring") cannot be handed on; the settings say so.
  • Gemini CLI (#1408): this computer's Google sign-in from Gemini CLI's own login file oauth_creds.json in its home ($GEMINI_CLI_HOME/.gemini, else ~/.gemini; the same path on macOS, Linux and Windows, checked against Gemini CLI 0.70.0). Taken are the access token, when it ends (expiry_date), the refresh token, scope and token type; the identity token (it names the person) and everything else stay here. Unlike Claude Code and Codex the refresh token travels: Gemini CLI renews its access token about every hour, and Google's refresh tokens are not used up by a renewal, so this computer and the worker machine both renew with the same one and neither ends the other's sign-in. The person chose this in #1408 against the decision of #1259, knowing that Google's terms may not cover it and that a machine that leaks the file holds a renewable sign-in until it is ended in the Google account (Security → third-party access) or taken back here. The grant's stamp is that of the refresh token alone, so an access token Gemini CLI renewed here or there is nothing new to send; another sign-in here is. Nothing is handed on while Gemini CLI keeps its login encrypted here (GEMINI_FORCE_ENCRYPTED_FILE_STORAGE=true), while another sign-in method than the Google sign-in is chosen here (security.auth.selectedType: an API key, Vertex AI, a gateway), or while Gemini CLI itself shows its sign-in screen here (signed out, expired or revoked): then every machine drops what it holds.

The dispatcher reads what it can hand on every five minutes (Claude Code: every usage round) and at once after a change in the settings, and sends it over the authenticated satellite connection (Request::Logins, after Claim in each poll) to a machine only when that machine reports the agent signed out, already uses the transferred one, reports another account (#1274), or a start there was just refused for a sign-in; before each start on a machine it sends what that machine needs first. A machine holds at most one per agent and reports which (Held: agent, a 12-digit SHA-256 stamp, whether its workers use it), never the value; the same stamp is not sent twice. A machine that does not take it (an older satellite does not know Request::Logins and ends the session; its update waits until its workers are done) is not asked every poll: the dispatcher leaves it alone for 5, then 15, then 60 minutes after each refusal in a row, logs the first refusal as a warning (dispatch.login_failed) and the repeats only at debug level, and asks again at once when the machine's handshake reports another build or a sign-in was taken. The user sees nothing for this; the machine's update brings the request along.

On the worker machine the sign-in is used while the machine's own does not work or belongs to another account (see "Following this computer's account" below):

  • Claude Code: the token goes into a credential store of the service's own, and the worker gets only that store's folder as CLAUDE_SECURESTORAGE_CONFIG_DIR (agent::claude_store). Claude Code reads its login from the store that variable names (on macOS a keychain item named after the folder, Claude Code-credentials- and the first eight hex digits of the folder's SHA-256, else .credentials.json in it), and before each request it compares that file's modification time with the last one it saw and reads its store again when it changed. So each renewed token the main computer sends replaces the one in the store at once, and a running worker uses it from its next request on: a worker outlives the token it started with, without a restart. Settings, history and the machine's own login stay where they are; the variable moves only the credentials. The store holds the access token, when it ends and the scope user:inference, never a refresh token, so Claude Code there never renews or rewrites it and fetches no profile with it (the machine's own oauthAccount stays). On macOS the token is in the keychain item, written through /usr/bin/security (the program Claude Code reads it with, so no approval prompt; the value goes over its standard input, never into a process list), and the file holds {} only, as the signal of a change. Linux and Windows have no system store Claude Code reads; there the file holds the token, readable only by the user, in the service's state folder (claude-sign-in), like Claude Code's own login file there: mode 0600 in a 0700 folder on Linux, on Windows a protected DACL with one entry for the user (no inherited SYSTEM or administrator entries), set on the staged file before the token is written (#1406). "Stop transferring", removing the machine and gitoodo satellite --drop-carried empty the store; the service also empties it at its start (a store left by an ended or crashed run has no grant behind it, the main host sends the sign-in again) and at its end, after stopping the workers. Checked against Claude Code 2.1.328 offline, with a local fake API and fake tokens: a token replaced during a 25-second tool call was the one the next request carried, in the file form and in the keychain form; a token only in the keychain without the file signal was not picked up, which is why the file is always rewritten too.

    The store is filled when a worker needs the token (claude auth status says signed out there, or another account, #1274). Its usage report then carries this computer's login fingerprint, so its workers count against the same limits. A worker starts with it while at least two minutes are left (Grant.expires_at): the renewed token replaces it in the store before it ends, and the running worker takes it up. With less, the machine's own sign-in stands in only when it is this computer's account (or the grant names none) and works; a login of another account never stands in (#1634): a worker started with it stayed with that account and its limit for its whole run, although this computer's renewed token arrived seconds later. The start is then refused ("Claude Code is not signed in on this machine with the main computer's account: the sign-in handed on from there runs out and the renewed one has not arrived yet …"). The dispatcher takes that refusal by its mark (SIGN_IN_RENEWING) as no machine fault and no failed attempt (#1673): the issue goes back into the queue (a restart into the deferred restarts, not counted), the usage round runs at once so Claude Code here is asked to renew, and the machine takes no Claude Code start until it holds another sign-in than the one it refused with (fleet::RenewalWait; the issue goes to another machine meanwhile). Only a refusal after 15 minutes of waiting for the same sign-in (RENEWAL_WAIT_SECS) counts as a fault and is told. On 2026-11-21 that gap took about eleven minutes, and every start in it was a failed attempt that paused the machine beyond the renewal. A renewed Claude Code sign-in goes to the machines that use it as soon as the usage round reads it, not with their next poll. The report goes on naming this computer's account, so the renewed token is sent and no other account's figures count. Only when the store cannot be written (no state folder, the keychain or the file refused) the worker gets the token as CLAUDE_CODE_OAUTH_TOKEN, which Claude Code reads once at its start, and only while at least ten minutes are left; such a worker loses its sign-in when it runs past the token's end. A worker also loses it when no renewed token comes in time (this computer asleep or offline at the end); the next start uses the renewed one.

  • Codex: when Codex says it is signed out there, the copy is written to Codex's own login file ~/.codex/auth.json (its documented file store; readable only by the user, written through a temporary file). An existing file is kept once as auth.json.before-gitoodo, and auth.json.gitoodo notes the stamp of the copy. A newer copy replaces it in place. Without a refresh token Codex there cannot renew; this computer sends a fresh copy before it runs out.
  • Gemini CLI (#1408): when Gemini CLI shows its sign-in screen there (none, expired or revoked; the check before a start and in the usage report, see "Start confirmations and sign-in" in docs/agents.md) or its active Google account (google_accounts.json) is another than this computer's, the copy is written to Gemini CLI's own login file oauth_creds.json the same way as Codex's: owner-only through a temporary file, an existing file kept once as oauth_creds.json.before-gitoodo, the stamp in oauth_creds.json.gitoodo, and Gemini CLI is asked once more with it. A machine that chose another sign-in method than the Google sign-in keeps its own. Where no method was ever chosen there, the Google sign-in is chosen in Gemini CLI's settings.json (security.auth.selectedType: "oauth-personal", what its own sign-in writes; the other settings stay, a file with comments is left alone), noted in settings.json.gitoodo and taken back on revoke: without it Gemini CLI 0.70.0 shows its method chooser in a worker and never reads the file, and its agent mode ends at once without checking any sign-in. Neither GOOGLE_GENAI_USE_GCA (read only in its one-shot mode) nor a defaults file through GEMINI_CLI_SYSTEM_DEFAULTS_PATH (skipped unless its folder belongs to root) works for that. Gemini CLI there renews the access token in the file itself when it ends (about every hour) and writes it back; the same grant sent again leaves that file alone. Expired: the next request renews it, nothing to do. Revoked at Google or signed out for good: Gemini CLI shows its sign-in screen with it, the machine refuses the start as a sign-in fault, and once Gemini CLI here finds the same, the dispatcher withdraws it everywhere and the own file comes back; a new sign-in here goes on as a new grant. Signed out here (/auth sign-out removes oauth_creds.json): nothing to hand on, every machine drops its copy. Stop transferring removes the copy and puts the kept file back.

Following this computer's account (#1274)#

Worker machines work with the account this computer is signed in with, per agent, also after a switch here (for example from one subscription to another). Accounts are compared only by fingerprint (agent::login: the first 12 hex digits of a SHA-256 over Claude Code's account and organisation ids in .claude.json, Codex's workspace and user id in auth.json, Gemini CLI's active account in ~/.gemini/google_accounts.json); no id, address or token leaves a machine or reaches a log, and the settings show only the first four digits (·b7c1).

  • Every usage round (30 seconds) the dispatcher reads this computer's fingerprints. When one changed it logs dispatch.login_switched (agent only), drops the old account's figures, limit and limit holds, asks the new account's usage at once and reads the sign-ins again, which go to the machines in the same round.
  • Each machine reports per agent the account its workers use (ProviderUsage.login): the transferred one while its workers use it, else its own. A report that names another account than the one this computer hands on gets this computer's sign-in, as a signed-out agent does. On the machine, Claude Code then uses the token instead of its own sign-in (its own files stay untouched) and reports no figures of its own (the dispatcher uses this computer's, same fingerprint); Codex gets the copy written into its login file (its own file kept, back on revoke). When the account there changed, the machine drops the old account's figures and limit (satellite.login_switched).
  • Right after the dispatcher's start, a machine that reports another account than this computer's takes no worker of that agent while this computer's sign-in is not read yet or is being renewed (Unavailable::ExpiresSoon), for at most five minutes (SIGN_IN_WAIT): a worker started then ran with the machine's own account, hit its limit and stayed paused until that limit's reset, although this computer's sign-in arrived a minute later. Once the sign-in is offered the start sends it first; with none to hand on the machine works with its own.
  • After a switch here the next round hands on the new account's sign-in by itself (Claude Code: the new account's live access token; nothing to set up per account). When this computer has nothing to hand on (an agent signed out or on an API key here), every machine drops what it holds of that agent, so none goes on with the old account.
  • Workers paused at the old account's limit go on with the new one: here, once the switch is read and the new account is not at its limit, they are restarted in their worktree; on a machine, once it reports this computer's account and that is not at its limit. A machine restart resumes the agent's session (Request::Spawn's resume, see "Waiting workers never hold an update back"), so the conversation goes on instead of starting over with the brief. The trigger is the state, not only the switch: a machine that works with this computer's free account while a worker there is paused at a limit resumes it also when no switch was seen (this dispatcher or the machine's build started after it). Each issue is restarted this way at most once per 15 minutes, so a worker that hits a limit again waits for its reset. If the new account is at its limit too, they wait for its reset as before.
  • Gemini CLI follows the same way (#1408): a machine whose Gemini CLI is signed in with another Google account gets this computer's copy in its login file (its own kept, back on revoke) and reports this computer's account while it uses it.

The dispatcher status carries accounts (this computer's tags per agent) and other_account (per machine the agents with another account and its tag); a machine row shows "Other account (·b7c1); switches to this computer's sign-in before its next start." until it follows.

The settings show per machine and agent "Uses this computer's sign-in." with **Stop transferring, and where an agent is signed out Transfer sign-in** (sends it now; for Claude Code without a token it starts the setup) or why this computer has nothing to hand on; the agent's own line keeps the command to sign in on that machine instead. Stop transferring stores the agent in login_transfer_off of the machine (host_login_transfer_set); with its next poll the machine drops the token, or removes Codex's or Gemini CLI's copy and puts the kept file back. A machine that answers but whose every enabled agent is signed out with nothing to stand in is listed as stranded in the dispatcher status; the status shows it at once ("No coding agent is signed in on <machine> any more …") with the way to Settings → Worker machines.

Before a worker starts, each machine checks the sign-in of the agent it is asked to start (at most once a minute per agent), and the dispatcher does the same for this computer. A start refused for a sign-in sends this computer's sign-in right away, so the next try works.

Codex's own codex login status says "signed in" for a ChatGPT login whose access token has ended, as long as a refresh token is there. A copy of this computer's login made earlier (by hand or by an old install) carries a refresh token that this computer has rotated since, so Codex cannot renew it and waits at its sign-in screen ("Provide your own API key … Press enter to continue", #1045). A machine therefore counts Codex as signed out when its auth.json holds an ended access token (login_transfer::codex_access_ended), before a start and in its usage round: no worker starts into that screen, and this computer's sign-in replaces the file at once, also when it is the same account. A worker that sits at a sign-in screen there anyway (the screen and the output tail are both read) gets this computer's sign-in pushed and starts once more in place, resuming its session (dispatch.sign_in_retry); only when the machine does not take the sign-in, or the retry within 15 minutes fails again, does the issue go to another machine or agent.

The terms of both subscriptions apply as they are: the Claude Code token is made by Claude Code itself for one person's use; the Codex copy carries no refresh token, so no second machine takes part in renewing the sign-in. The Gemini CLI copy carries its refresh token by the person's choice (#1408, see above).

New hosts and hosts undergoing setup remain excluded from worker dispatch until setup succeeds. A failed setup can be retried using “Install”. Existing assistant launchers are backed up before replacement; modified skills are protected rather than overwritten.

App: Settings → Satellite hosts (#357)#

The page calls the same core functions as the CLI (crates/core/src/satellite_host.rs: probe, install) through the Tauri commands hosts_list, host_probe, host_add, host_install and host_remove (src-tauri/src/hosts.rs); the frontend never runs ssh itself.

  • Every host is checked when the page opens, per row or all at once. A probe always returns a state (online, version_mismatch, unreachable, protocol); an offline host is not an error.
  • Adding saves the host only when it answers online with this version, optionally after a first install. Remove only drops the entry; nothing changes on the host.
  • Failures carry a stable reason (CmdError::Host), e.g. invalid_name, duplicate, unreachable, platform_mismatch, checksum_mismatch; the page shows a translated title and the technical text under details.
  • The store build cannot run ssh: hosts_list reports supported: false and the page shows a hint to the direct build.

Workers per machine (#967)#

Every machine, this one and each satellite, has its own "Workers at once" field in its row: "Automatic (N)" (default, one worker per dispatch.cores_per_worker cores; for a satellite N shows once a check reported its cores) or a smaller number for a less powerful machine. A number at or above the automatic value would change nothing, so the field offers only smaller ones, and a machine that runs one worker automatically shows no field. The choice saves at once through host_max_workers_set(name, max) (name = a satellite or local, max = null for automatic), also in the store build, and the dispatcher uses it from its next round.

  • Stored as max_workers on the satellite's entry in hosts and on local_host in orchestration.json; absent means automatic, 0 is refused (invalid_max; validate refuses a hand-written 0 too). Adding the same machine again keeps its value.
  • The machine's capacity is the smaller of the automatic value and the maximum (dispatch::host::capped_capacity); the dispatcher's host choice, the load order and the fair share use it (docs/orchestrator/dispatcher.md).

Desktop tests per machine (#995)#

Next to "Workers at once", each machine has "Desktop tests": not allowed, when nobody worked there for 1/2/5/10/30 minutes (default 2), or any time. It shows on this machine's row when Agent Desktop can run here (not in the store build) and on a satellite's row once its setup reported Agent Desktop. The choice saves at once through host_desktop_use_set(name, desktop) (name = a satellite or local; refused with unknown_host or invalid_desktop) as desktop on the machine's entry; adding the same machine again keeps it. A satellite worker reaches only its own desktop, because the satellite has no SSH sign-in for the other machines; it learns the other test desktops as unreachable and hands an issue that needs one over to this machine with gitoodo worker needs --desktop NAME (docs/orchestrator/dispatcher.md, "Test desktop for desktop checks"). A worker on this machine that waits 3 minutes for a desktop moves once to a satellite of the same system whose desktop is free under that satellite's own setting; its work is committed and pushed first ("Moving to a free desktop elsewhere" there).

Windows machines and the remote shell (#958)#

Windows OpenSSH runs commands in PowerShell (usual DefaultShell) or cmd.exe, not sh. So the first command on every machine is a probe that runs in all three, echo gitoodo-shell %OS% $PSEdition (remote_machine::SHELL_PROBE): sh prints %OS% as it is, cmd expands it to Windows_NT, PowerShell prints each word on its own line and its edition. The result is stored with the machine (shell in hosts[]: absent = POSIX, powershell or cmd), and every later command is written for it:

  • Windows commands go out as powershell -NoProfile -NonInteractive -ExecutionPolicy Bypass -EncodedCommand <base64 UTF-16LE>, which needs no quoting in PowerShell or cmd (the check is about 4 KB, below cmd's 8191-character limit). Progress output is off, and a stopping error leaves as one plain line on stderr with status 1.
  • Check (assistant): os=Windows x86_64, cores, git, and per agent the program (Get-Command, then ~\.local\bin, ~\.claude\local, %APPDATA%\npm, ~\.npm-global, ~\.bun\bin, ~\.volta\bin), the first line of its --version and whether its credential file exists.
  • Install: New-Item for ~\.local\bin, scp to .local/bin/gitoodo.exe.upload, Get-FileHash, then the running gitoodo.exe (a service may hold it) is renamed to gitoodo.exe.old-<id> and the upload moved in; old copies are removed once their service has ended. The release asset is gitoodo-x86_64-pc-windows-msvc (docs/release.md); Windows on arm64 has no build (none).
  • Version check: the same lines from PowerShell for ~\.local\bin\gitoodo.exe.
  • Service: the named pipe above, created with a descriptor for the current user only; the bridge starts it with DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP and, where allowed, out of the SSH session's job, so it outlives the connection. The state folder is %LOCALAPPDATA%'s app folder.

ssh itself fails with status 255 (no route, refused, host key, sign-in). Any other failing status means the machine was reached and a command failed there: the assistant reports command_failed ("The check failed on the machine") with the last lines of the command's stderr, the install steps do the same, and a bridge that does not start on a reached machine is a protocol state ("was reached, but gitoodo satellite did not start there"), never "unreachable".

Commands a worker machine lacks#

A worker runs under the setup of the machine it is on. Helper commands, global git hooks, agent hooks, skills and MCP servers a person keeps on one computer are often missing on another, and that is no fault of the repository. Without a word on it, workers used to open follow-up issues or ask questions about such gaps ("the global hooks and labctl are missing"), or work around them without saying so.

The brief names the machine. Every worker's brief says which machine it runs on (name, system, this computer or a worker machine) and that personal tools may be missing there (brief::machine_rule). The worker never files an issue or a question about such a gap and does not stop for it. A global git hook that the git configuration names but that is absent on the machine runs nothing: the worker leaves out only that hook with a one-off git -c override, keeps every hook that exists (never --no-verify) and runs the repository's checks itself.

Handing an issue back. When the issue cannot be done without a missing command, the worker runs gitoodo worker needs --tool NAME[,NAME…] --reason "why" (after gitoodo worker push if it committed work) and stops. On this computer the request goes to the dispatcher's broker, on a worker machine to its satellite, which reports it with the worker's exit (ExitInfo.needs). The dispatcher then ends the run as needs_tools (no failed attempt, the lease is released and the issue is queued again) and

  • puts a tool:<name> label on the issue, so it only goes to a machine that has the command;
  • checks the claim: it probes the machine for the command right away (this computer) or takes its latest probe (a worker machine). A command the probe does not find marks the machine as lacking it, until a probe there says otherwise, at most 24 hours. A command the probe finds is no missing command: the machine gets no mark but a hint, and the next worker's brief there names the command with its folder, tells it to use it and, if it fails, to read and fix the error output. Only when a worker that had the hint hands it back again is the command marked as installed but unusable on that machine, with the worker's reason (its command and error output);
  • remembers that the repository's workers needed it (machine-tools.json in the state folder), so its other issues prefer machines that have it.

A hand-back from a worker machine for a command that no machine is known to have goes to this computer instead (host: label, no tool: label), and so does gitoodo worker needs --data for local files only this computer has (local inputs). Only a worker here that hands the issue back for the same command makes the tool: label.

Nothing names a particular tool: the names come from tool: labels (a person may set them too) and from hand-backs. Names are letters, digits and _ - . +, at most 64 characters, at most 8 per hand-back.

Probing. The dispatcher looks for each needed command on this computer every minute and on each worker machine at every poll (Request::Tools, answered with Reply::Tools), with PATHEXT on Windows. It searches exactly the folders a worker gets as its PATH (detect::worker_dirs): the agent's own folder, the process PATH, the login shell's PATH (on Windows the machine and user Path from the registry, which a service started at logon does not see updated) and the usual package-manager folders that exist (/opt/homebrew/bin, /usr/local/bin, /home/linuxbrew/.linuxbrew/bin). A service starts with a bare PATH, so every worker, on this computer and on worker machines, gets this one instead; probe and worker cannot disagree about what is installed. A command that is installed but not in these folders counts as missing, as it would for the worker. A probe that finds a command a hand-back marked turns the mark into a hint; only a mark of a command that failed despite the hint stays. A worker machine on an older build answers nothing; for it only the 24-hour marks of hand-backs count.

Placement. A machine that lacks a command of the issue's tool: labels does not take it (HostCandidate::lacks). Among the machines that fit, one with the commands its repository needed before comes first. When no machine fits for that reason alone, the issue waits as tool_missing, and "Asked of me" shows one line: "None of the machines that can take this issue has labctl. Install it on one of them and the issue starts by itself." Its "Solve" opens the ways out (docs/states.md): "Check the machines again" (Request::RecheckTools: the dispatcher forgets every hand-back mark and probes this computer at its next round, the worker machines with their next polls), "Run on <machine>" for the machines that would take it but for the commands (host::tool_hosts; sets host: and drops the tool: labels), "Remove label tool:<command>" for each, "Run without …" when there are several, then looking at the issue, "Solve with an agent" and pausing. The wait names only what the closest fitting machine lacks, not every tool: label. A command marked as installed but unusable is said as such ("pod is installed but did not work for the worker; installing it will not help"), and "Solve with an agent" comes first. Nothing shows while every issue finds a machine.

Solving a wait with an agent. "Solve with an agent" among the ways of a machine wait opens the same session as for a stuck issue (stall_solve), in the issue's folder and branch, but its opening message says why the autopilot cannot start the issue: the wait's reason, the machines that could take it, and for commands what the workers said about them. While the session runs, the dispatcher does not start the issue. An expired sign-in on this computer offers no session: its agent would hit the same sign-in.

Taking this computer's setup along#

Many gaps never need a hand-back: the setup a person keeps in the home folder of this computer (git hooks, agent instructions and hooks, the scripts they call, and the credentials those use) goes along to the worker machines (gitoodo_core::carry) and applies there to Gitoodo's workers only. The machine's own configuration is never written.

What is found. Discovery reads only what this computer's setup names, never a list of known tools, so it fits any person's setup, including none at all:

  • git: core.hooksPath, the hooks of init.templateDir and the config hooks (hook.<name>), from git config --global;
  • per agent the user instructions (~/.claude/CLAUDE.md, ~/.codex/AGENTS.md) and Claude Code's hooks in ~/.claude/settings.json (command hooks; http hooks need nothing);
  • the scripts and files these texts reference below the home folder (~/…, $HOME/…, the absolute home path), and the scripts they in turn source or run, at most 4 levels deep;
  • script folders on PATH below the home folder whose commands those texts call.

A program found on PATH outside the home folder (or a binary inside it) is never copied; the list names it as needed there, with how it came onto this computer where that can be read from its place (brew install x, npm install -g x, pipx install x). Skills, slash commands, plugins and Codex's own hooks are not carried: workers do not load them on this computer either ("What a worker loads"). Gemini CLI has no way to take instructions per session and gets nothing.

Safety. A file is skipped when it lies outside the home folder (also through a link), is over 256 KiB, is not text, looks like a credential by name or holds one (key blocks, token prefixes, NAME=value with a secret-like name), is a state file (caches, backups, logs, locks) or is a private ssh key. At most 400 files and 8 MiB go along.

Which machines. "Take my setup along" in the machine's card is on by default for the same person's machines and off for others. Same person means: the machine's user name or the git user.email there is the same as here (case-insensitive); the machine sends only short SHA-256 fingerprints of both (carry::identity). The switch overrides the default in both directions.

On the worker machine. Everything lives in the state folder, in carried/<source>/ per main host (main_host_id), as content-addressed blobs and a home/ tree built from them. It reaches the workers only through their environment and arguments:

  • git gets a generated GIT_CONFIG_GLOBAL that first includes the machine's own global configuration, then sets the carried core.hooksPath only when the machine has none of its own, and the carried config hooks with the paths rewritten; a worker whose environment already sets GIT_CONFIG_GLOBAL keeps it;
  • Claude Code gets the carried hooks merged into its per-session --settings and the instructions with --append-system-prompt-file; Codex gets them as -c developer_instructions=…;
  • carried script folders come first on the worker's PATH.

The machine's own setup wins where both cover the same thing (its own hooks folder, a hook of the same name); "Carried setup takes precedence" turns that around for one machine. Paths are rewritten for the machine's home (~/, $HOME/, the source's absolute home, with / on Windows as well). A script whose shebang names an interpreter the machine lacks (Windows: also looked up in Git for Windows' usr/bin and bin) is not run there: its hook is left out and the card names what is missing. Everything else that cannot go along stays with the hand-back above.

Updates. The dispatcher discovers again every 5 minutes and when a choice changes. Each poll ends with SetupState; only the blobs the machine lacks travel (in 32 KiB parts, SetupBlob), then the manifest and SetupCommit. A file removed here is gone there with the next commit; unused blobs are removed. Switching the machine off, or removing it from the list, sends SetupDrop, which removes the folder and the credentials. An older satellite refuses SetupState, and nothing is carried to it.

Dropping it from a machine that is away (#1416). Nothing carried stays on a machine that left, also when it was unreachable at that moment:

  • Switched off while unreachable: the dispatcher keeps the choice and drops the setup at the machine's next poll (SetupDrop, or SetupCredentials with a revoke for one credential). Until the machine confirms it, its card says "Will be removed at the next contact." (the status reports held per machine).
  • Removed from the list: the app records the drop in the state folder (carry-revocations.json, carry::revoke: the name, how to reach it, never a password) and tries it at once. The dispatcher tries every open drop every minute until the machine answers; the drop takes back the handed-on sign-ins (Logins with a revoke for Claude Code and Codex) and sends SetupDrop, and only the machine's confirmation settles it. Until then Settings → Worker machines lists it under "Removed machines" with "Will be removed at the next contact." A machine added again under its name or address needs no drop: its own poll follows the switch.
  • Without any message: every contact of a main host (SetupState, any setup request, each poll's Claim) is noted in carried/<source>/contact (at most once an hour). The satellite service checks at its start and every hour: a main host that has not been in touch for 7 days (carry::lifetime::EXPIRY_DAYS) loses its carried folder and its credentials there (log satellite.setup_expired), and a credential file in carried-sign-in/ whose folder is gone goes too. A main host that still uses the machine simply carries everything again with its next poll. The check runs while the service runs; a machine that is switched off checks when its service starts again.
  • By hand on the machine: gitoodo satellite --drop-carried removes what every main host carried there, credentials and the stored Claude Code sign-in (claude-sign-in) included, and prints dropped=<count>.

Credentials. Only those the carried texts reference go along: variables of an env file they source, variables they read that are set in this computer's environment, and CLI logins they call whose CLI takes a token variable (gh → GH_TOKEN from gh auth token). CLIs that cannot take one (tea, az, aws, …) and ssh are listed as "sign in there"; ssh keys never leave this computer. Values travel only in SetupCredentials over the satellite connection, are kept in the machine's system store (a user-only file beside the transferred sign-ins where it cannot be written) and are sent again when their stamp changes. A worker gets them in its environment under their own names, which every language reads. An env file a carried shell script names becomes a temporary file of the worker's own (${GITOODO_CARRIED_SECRETS}/<path>), deleted when the worker ends; only shell texts are rewritten to that placeholder. A Python, Node, PowerShell or other script that reads an env file finds it at its place in the carried folder instead (the reference points there like any other carried file): a user-only file of plain NAME=value lines, written when the first worker of that main host starts and deleted when the last one ends. The card lists credentials by name only, each with its own switch; switching one off revokes it there.

A dispatcher running as a service (LaunchAgent, systemd unit, Windows service) lacks what only the shell profile exports (#1413). A credential variable a carried text reads that the service's environment lacks is looked up where a fresh sign-in sets it, never in another process (carry::login_env): on macOS and Linux the person's login shell is asked once per discovery, as $SHELL -lic, for exactly those names, within 5 s (a hanging profile is stopped and gives nothing); on Windows the user's and the system's environment in the registry. A name set nowhere is listed as "set nowhere on this computer" (SkipReason::NotSet) and named in the card's line (HostStatus::unset) instead of being left out silently.

In the app. The card shows only the switch while all is fine; one line with one action when something blocks ("The setup did not reach “mini”." with "Send again", or the programs the machine lacks with "What goes along", or the credentials set nowhere here with "Look again", which discovers the setup again at once); and the full list (files, credentials, programs needed there, what stays here and why, the precedence switch) on demand.

Coding agents per machine (#957)#

The assistant's check reports every supported agent (Claude Code, Codex, Gemini CLI) with installed, login (yes, no, unknown where it cannot be seen from outside, e.g. Claude Code's macOS keychain, or expired) and version; an agent is ready when it is installed and not known to be signed out or expired. expired (#994) comes from gitoodo worker-check on the machine: Codex's status reads "Logged in", but its usage query (the same as above) says the login no longer works. The row then reads "Sign in again on this machine: the login no longer works. Run codex login there."; a query that only fails or times out leaves the login yes. The only missing piece about agents is no_agent (not one is ready).

The check at setup is not the last word: a login can end later. Each satellite reports in its usage report whether Claude Code, Codex and Gemini CLI are signed out (problem: not_signed_in, read from the agent itself, see docs/agents.md, "Start confirmations and sign-in"); the dispatcher then starts no worker of that agent there (login_expired wait) and lists the agents per machine in its status (signed_out), which the machine's row shows at the agent instead of the stored check. A satellite also reports a silent worker whose screen shows a start confirmation or a sign-in (prompt in its report); the dispatcher stops that worker, pauses the machine with the reason (agent_login or start_failed) and puts the issue back into the queue for another machine or agent.

Each satellite also reports which models its own agent offers (report.agents: per agent the version, the model ids and the recommendation; today Codex). It reads them with the same reader as the main host once the main host first asks it for usage and every 10 minutes after, and logs satellite.agent_models when they change. The main host then starts a worker there only with a model that machine offers, and falls back once on the machine when the agent refuses its model anyway (dispatcher.md, "Worker model per machine"). An older satellite reports no agents; its workers run the agent's own default unless its CLI is at least as new as the main host's list. The field is optional, so the protocol number stays.

A satellite on an older build that is being updated (see "Automatic update") takes no new worker: the host choice skips it up front with the wait reason update_pending ("being updated, goes on by itself") instead of trying a start the old build would refuse.

The last step lists the agents with a switch each. An assistant can be selected before it is installed on the satellite. The install action installs selected assistants; Claude Code and Codex and Gemini CLI then use this computer's sign-in there (see "This computer's sign-ins on worker machines"). Switching saves at once through host_agents_set(name, off) as agents_off on the machine in hosts[] (a deny list: an agent installed later is used without a new setup; absent = all on); adding the same machine again keeps it. The dispatcher treats a switched-off agent like a missing one on that machine (Config::host_allows_agent): with the worker pool the rotation picks among the agents each machine still offers, as it does locally, and a fixed agent waits for a machine that allows it.

The same step sets "Workers at once" for the new machine (host_max_workers_set, above), with "Automatic (N)" from the cores the check reported.

The machine list shows the same switches in every satellite's row, with each agent's state from the last check and when it ran. The check's agents are kept in host-checks.json in the app's data folder (gitoodo_core::host_checks, an observation and no setting, so not in orchestration.json; no secrets) and reach the page as checked on each entry of hosts_list (null before the first check, e.g. for a machine added with gitoodo host add: its switches then show the stored choice only). There is no check button: while the page is open it probes every machine's reachability and version on opening and every three minutes. For a machine that is online it then runs the agent check through host_agents_check(name) (satellite_host::machine_check: shell probe, then the check for that shell) once the last check is older than ten minutes, stores the result and saves a shell that changed since. On macOS and Windows machines with Agent Desktop it also reads the permissions there (host_desktop_permissions), so a grant or a revocation shows up on its own; missing ones are named in the UI language. A row shows "Install" only while something is missing there (offline or failed probe aside: no Gitoodo, an older or no Agent Desktop, or a desktop error that is not a permission); otherwise it shows "Set up". Removing a machine drops its check.
