A satellite is another machine that runs workers for the main host's dispatcher (spec 7.9). Network and SSH live only in crates/core; no port is opened. Forge credentials stay on the main host; assistant subscriptions are provisioned separately as described below.

Pieces#

  • gitoodo satellite: persistent service on satellite.sock (0600) holding worker PTYs; on Windows on the named pipe \\.\pipe\gitoodo-satellite-<user> that only this user may open. gitoodo satellite --stdio is a pipe to it (it starts the service when missing, on Windows detached from the SSH session), so workers survive SSH drops. The bridge ends when its stdin closes, the SSH session hangs up (SIGHUP), the service closes the connection, or nothing moved either way for 15 minutes; a subscription sends a sign of life every minute so it never idles out. Bridges of gone sessions used to stay forever (#965).
  • Protocol: JSON lines, the same cmd/reply/frame vocabulary as the dispatcher socket (dispatcher_rpc.rs), plus hello, spawn, kill, subscribe, ask, ask_done, copy_state, copy_receive. A bridge session runs requests in a row; subscribe and attach turn it into a stream.
  • Bridge: system ssh -o BatchMode=yes ... -- <target> gitoodo satellite --stdio (GITOODO_SSH replaces the program, used by tests); on Windows .local\bin\gitoodo.exe satellite --stdio, relative to the home folder the SSH session starts in.
  • gitoodo host add <name> <ssh-target>: detects the remote shell, connects, compares versions, saves {name, ssh, shell, platform} only. platform (macos, windows, linux) is the system the machine reported; the app saves it too when it adds, installs, checks or probes a machine and the system differs from the stored one. A machine set up before the system was stored gets it in the background: 30 seconds after the app starts it checks each machine without one, and again every 10 minutes while one is still unknown (offline). The dispatcher starts every machine with it, so an issue for that system waits as offline while the machine is away, not as no_platform. A version mismatch is a clear error with the check command (ssh <target> gitoodo --version). The handshake also compares builds, see "Build identity" below.
  • Dispatcher: polls every host (20 s), offers satellites as host candidates, starts workers with spawn (the satellite creates the worktree in its own clone). Unreachable host: no new work, leases wait for the grace and are then released (lease_action).
  • Own copies (#965): a satellite keeps its clones under ~/gitoodo/repos/<owner>/<repo> in its own home; the main host never sends one of its own paths. spawn's prepare carries the repository's credential-free forge address (origin). The main host makes and updates the copy itself before each spawn (satellite_copy.rs), so the machine needs no forge access and no network permission for its own git: it fetches the base (and the worker branch, when the forge has it) with the connected account into its own copy, filling in whatever a partial copy lacks, asks the satellite what it holds (copy_state: tracking refs, partial or not) and sends a git bundle of the rest (copy_receive: a header with refs, size and SHA-256, then base64 chunks of 512 KiB; at most 4 GiB). The first copy gets the full history, later starts only what is new (the satellite's heads are the bundle's prerequisites); a copy left partial by an older build gets the full history once and then stops being partial, so no lazy fetch is ever needed there. The satellite checks size and checksum, unbundles, moves origin/<base> (and origin/<branch>, or drops it when the forge no longer has the branch), sets origin to the forge address and starts the worktree from it (prepare.synced); a restarted worker so gets its pushed branch back. The forge's branch wins over what an earlier run left on the machine: a local branch behind it is fast-forwarded, one apart from it (the branch was updated onto the base, or someone pushed) is set to it, and commits of its own the forge lacks stay under refs/gitoodo/kept/<branch>/<sha> (log satellite.branch_kept); a kept worktree that is clean and only behind is fast-forwarded, one with uncommitted work or own commits stays as it is. The token stays on the main host: it is in no bundle, frame, error or log.
  • Satellite paths (#965): the main host sends none of its own paths. The worker's cwd is ~/gitoodo/worktrees/<repo>/<number> (or below a ~-relative worktree root), the hygiene requests name the satellite's own roots, a configured absolute agent path that does not exist there falls back to the agent's name, and the hook and status-line commands in --settings (Claude Code) and in -c hooks.* (Codex) carry a placeholder the satellite replaces with its own gitoodo, quoted as one shell word.
  • Delivery when the forge moved on: the main host fetches the forge's worker branch into the delivery's scratch repository; a bundle that lacks its commits is never pushed (no force). The main host sends them to the satellite's copy as origin/<branch>, and the worker gets a reason that says to rebase or merge origin/<branch> and deliver again. A satellite whose build lacks copy_state is the machine fault outdated (see below) and gets no start; any other failure of the transfer falls back to the machine's own git clone, and its reason is added to the checkout: error.
  • Branch updates (#383) on a satellite go the same way: the main host sends the base first, update_branch with via_host rebases or merges offline and answers with a bundle of the new head, which the main host pushes with the account (--force-with-lease on the old head).
  • Worker PATH (#965): a satellite service started by ssh or launchd has a short PATH; its workers get the agent's folder, the service's PATH, the login shell's folders and the known install folders that exist (~/.local/bin, ~/.cargo/bin, Homebrew, ...), so the agent and the tools it calls are found as in a terminal.
  • Failed remote starts are sorted by who answered (#965): a satellite that answered with a reason was reached, its fault is the reason's class (agent_missing, agent_login, no_checkout, start_failed, outdated); only no answer at all is unreachable. Each class pauses new workers on that machine once (one notice per machine, not per issue) and names the machine, the agent, the repository and one action there ("update Gitoodo there" for an outdated build); "restart the service" is offered only for this computer. An unreachable machine gives no notice: nobody can fix it from here, it is retried by itself, the work goes to the other machines, and Settings → Worker machines shows it offline.
  • gitoodo attach [<host>] <issue>: raw terminal, detach with Ctrl-], the worker keeps running.
  • Questions: gitoodo ask on a satellite (GITOODO_SATELLITE=1) asks the service, which forwards it on the main host's subscription; the main host posts and confirms, then the worker is parked.
  • Hooks: gitoodo hook stop|stop-failure|status-line|activity on a satellite (GITOODO_SATELLITE=1) sends hook to the service instead of a dispatcher socket (see "Hook events" below).

Remote worker lifecycle#

  • The satellite records workers that end on their own and measures output silence. The main host polls with report (exits are drained, so each is delivered once) and applies the same hang policy as for local workers: silence for the timeout restarts the worker (a spawn without prepare, in the worktree that already exists there), after the maximum it is stalled.
  • report also carries the satellite's own subscription usage. The satellite starts reading it (keychain, usage endpoint, codex app-server) with the first report, not at service start, so a satellite no main host talks to stays idle and small (#769).
  • A login that no longer works is reported apart from a reached limit (#994): the agent's usage.problem is not_signed_in and no old values stand for it. The satellite says so only on the agent's own word: Codex's account/rateLimits/read answers with an auth error, or Codex says so in a notification or on its stderr while the query fails ("could not be refreshed", "sign in again", a rejected refresh token, HTTP 401, "authentication required"); Claude's usage endpoint refuses a token that has not expired yet (401/403). A query that only times out or fails otherwise stays unknown. Such a login typically still passes codex login status ("Logged in") after its refresh token was revoked. The main host then waits with login_expired ("the agent's login there no longer works; sign in again on that machine") instead of usage_gate for that agent there; with the worker pool it names this reason over a usage limit of the other agent, because only a person ends it. After signing in again the next query (at most five minutes later) clears it.
  • A worker that exits on its own is handled like a local one (finish/merge flow). A worker killed by the main host leaves no exit record.

Hook events#

A satellite has no dispatcher, so a worker's gitoodo hook <event> there talks to the satellite service (satellite.sock, on Windows its named pipe) with the dispatcher's hook request (issue, event, usage). The service holds the worker's terminal, knows its delivery and reads its own agent login, so it applies the event itself, exactly as the dispatcher does for a local worker (crates/cli/src/satellite_turns.rs; locally Hub::hook and Hub::check):

  • Every hook is a sign of life: report.silent counts from the later of the last output and the last hook, which the main host's hang policy reads.
  • stop without a result (no pull request yet) is looked at after the same 30 s grace: a worker at its usage limit is left to its reset; one a person typed into lately (attached from the main host) is marked idle; the others get the reminder once and end at the next such turn end (satellite.worker_nudged, satellite.worker_idle). activity and stop-failure cancel a pending look.
  • stop after the pull request (gitoodo worker pr confirmed by the main host) ends the worker (Claude Code, Codex; satellite.worker_finished), and its exit record says code 0, so the main host merges at once as for a local worker. A Codex stop asks this machine's Codex limits again (at most every 30 s).
  • stop-failure marks the worker limited and locks this machine's Claude login (Tracker::limit_reached); status-line brings the status line's usage windows. Both go into the next usage round, so they show in report.providers; the lock outlives the next usage query until a report shows room or its end passes. At the end the worker gets continue (satellite.worker_continued).
  • list carries the satellite's idle, limited and limited_until (this machine's lock end). The main host shows them on the worker's tile and does not take a limited worker's silence for a hang (login_locked), as for a local worker. The main host's own usage figures stay its own: a satellite's status line describes the satellite's login.

Robustness: the state lives on the satellite, so nothing is lost while the main host is away; it reads the result with its next list and report. The hook waits at most 3 s for the service and never fails or prints; no service, a busy one or an older one that refuses hook (bad request or "does not handle") is silent, as a missing dispatcher is locally. An older satellite sends nothing and lists no states, so the main host behaves as before; an older main host ignores the states. The events carry an issue key, the event's name and usage percentages, never a token or a path.

  • A run the main host tracks is not released as vanished for 45 s after start, so a slow poll cannot drop a fresh worker. Unreachable satellites keep the lease grace rules above.
  • Run state of remote workers lives in memory only; after a dispatcher restart the lease table and the satellite's worker list decide (listed: renewed, not listed: released).
  • Updating the main host's app or dispatcher does not touch a satellite's workers: they run on the satellite, and the new dispatcher finds them in the satellite's worker list and renews their leases (see dispatcher).
  • Worktrees on the satellite carry the ownership marker; hygiene_scan and hygiene_apply let the main host clean them up, and the satellite runs its own safe round (see repo hygiene).

Updating a satellite (#965)#

A satellite keeps its run state in memory, and its workers are children of the satellite process (not hosted like the main host's). An update therefore never ends the service while a worker runs there: installing replaces only the file, and the long-running service takes up the new build once it is idle (see "Build identity" below). A service that ends anyway (a reboot) loses nothing and runs nothing twice: the worktrees stay on the satellite, the main host no longer finds the runs in the satellite's list and releases their leases (after the 45 s start grace and the unreachable grace while the satellite is away), and the issues go back into the queue with their worktrees and commits kept on the satellite.

Build identity and outdated builds#

Every development build reports the same version (0.1.0), so a version string cannot tell an old build from a new one. A machine that kept an older CLI then failed starts with errors from code it lacked (git fetch origin dev failed: fatal: cannot change to '~/gitoodo/repos/...'). Builds are therefore compared by their identity, the SHA-256 of the executable (crates/core/src/build_id.rs):

  • Each long-running process (satellite service, dispatcher) measures its own build once at start, before an update could replace the file. The app compares with the CLI it installs on machines (the gitoodo next to it), not with its own binary.
  • hello replies carry build (the satellite's running build), arch (its processor) and, while an installed update waits for the workers, installed (that build). All three are optional; older satellites omit them.
  • Comparison (satellite::compare_builds): another version string fails the handshake as before. With the same version on the same system and processor, the builds must match; a satellite that names no build is too old to and counts as outdated. On another system the release build of the version is installed, so the version alone decides there.
  • An outdated satellite stays connected: lists, reports, kills and branch updates of the workers running there go on, but spawn is refused before it is sent, with an outdated build: ... reason. A request an older satellite does not understand (bad request: ...) is reported the same way, never as a git or copy error.
  • The dispatcher sorts that reason as the machine fault outdated: new workers on that machine pause and the retry waits 1, 2, 5, 10 and then 15 minutes (the fault back-off). The dispatcher updates the machine by itself (see "Automatic update" below), so this fault brings no notice of its own; the pause ends with the first start after the update.
  • host_version hashes the installed file too (sha256sum/shasum -a 256, Get-FileHash on Windows) and reports other with other_build: true for the same version with another build on this system; the assistant then says "an older build" instead of naming two equal versions.

Taking up an update without stopping workers:

  • After an install the app runs gitoodo satellite --restart-idle there. It prints one restart=<word> line: none (no service ran), current (it already runs the installed build), done (the idle service ended, the next connection starts the new one), busy (workers run; the service takes it up after them) or unsupported (an older service on Windows that cannot be ended from outside; it takes the update up when it ends).
  • restart_service asks the service to end; it answers ok only while no worker runs and then ends, otherwise a busy: error. An older service that does not know the request is ended with SIGTERM (its peer process id from the socket) after a second hello showed no workers.
  • The service also checks its own file every 60 seconds; once another build is installed it reports it as installed and ends as soon as no worker runs, so a machine updated while busy needs no further step.
  • The machine list shows "Updating automatically …" for such a machine and for every outdated machine the dispatcher updates by itself (no button), "Needs update" with "Update" only where that failed or no dispatcher runs, and "Up to date" otherwise; the version is the chip's tooltip.

Automatic update (#1181)#

Worker machines are kept on the shipped build without a click. The dispatcher's fleet watcher (crates/cli/src/fleet.rs) shakes hands with each satellite every 20 seconds anyway; the decision and its memory live in crates/core/src/satellite_update.rs (pure, tested with a fake ssh/scp and a mocked release download):

  • Trigger: a hello that fails with another build or version (need_of → Update). A machine that already runs this build, or whose service already holds the installed update and waits for its workers (updating), is left alone. A machine that runs a newer version than the app is never downgraded (Newer); "Update" in Settings still lets the user do it by hand.
  • Install: the same verified path as the app (remote_version::update). On the same system the dispatcher copies its own CLI (build_id::own_cli, only while the file still is the build that runs; after an app update the app restarts the dispatcher with the new one); on another system it downloads the release build in Rust and checks its SHA-256 first. Either way the upload goes to gitoodo.upload, is checked by hash on the machine and only then moved over the old file, which keeps serving until then; a failure leaves the installed build untouched.
  • Switch: gitoodo satellite --restart-idle. Workers are never ended; a busy machine takes the installed build up after them (phase waiting, checked again after 5 minutes).
  • The CLI copied is always the file whose hash is the reference build: on macOS the app bundle's Contents/MacOS/gitoodo, not the service helper's own copy, which is signed apart and has another hash. An install that reports success but is followed by another build at the next poll counts as a failure (still_outdated), so it is never repeated in a loop.
  • One install per machine at a time. A failure retries after 1, 2, 5, 10 and then every 15 minutes. The first two failures stay quiet; the third brings one notice that says in plain words what failed (copy, checksum, download, …) and keeps "Update" in Settings → Worker machines as the manual retry. No further notice follows until it works.
  • No build for the machine (an Intel Mac, a system without a release asset, a missing asset): one notice, and no automatic attempt again until the dispatcher restarts.
  • The dispatcher status (machine_updates) lists each machine's phase (updating, waiting, retrying, failed, no_build, newer), reason and next attempt; the app reads it for the machine list. While the update is automatic, the outdated fault is left out of the status page and its notice.

Install and upgrade: gitoodo host install <name>#

Uses the system ssh/scp only (BatchMode, no stored secrets). On a Windows machine every step is the PowerShell equivalent (see "Windows machines" below). Steps: uname -sm must match this build's OS and CPU, upload to .local/bin/gitoodo.upload, compare the SHA-256 computed on the satellite with the local one, only then move it over .local/bin/gitoodo, and finish with a handshake. A mismatch deletes the upload and leaves the installed binary untouched. On a version mismatch host add points to this command as the upgrade.

Version check and other systems in the app (#441)#

host_version runs one command on the machine (uname -sm and gitoodo --version, from PATH or ~/.local/bin) and reports same, missing or other plus where an install comes from (crates/core/src/remote_version.rs):

  • this_build: same system and processor, the app copies its own CLI as above.
  • release: another supported system (macOS on Apple silicon, Linux x86_64/aarch64, Windows x86_64). The app downloads {base}/v{version}/gitoodo-{triple} and gitoodo-{triple}.sha256 in Rust (size capped, no tokens), compares the SHA-256 before anything is copied and then uses the same verified upload. base is GITOODO_RELEASE_URL at build time, by default the GitHub releases download URL. The release pipeline must publish both assets per target triple.
  • intel_mac: a Mac with an Intel processor. Gitoodo for macOS runs on Apple silicon only (docs/release.md), so the assistant explains that and offers no install; update refuses with no_build without downloading. The system is uname -sm, corrected to Darwin arm64 via sysctl hw.optional.arm64 when the login shell runs under Rosetta.
  • none: no build for that system; the error no_build names the system and asks to build Gitoodo there and place it at ~/.local/bin/gitoodo. A missing asset (404) is also no_build, any other download failure download_failed.

The "Add remote machine" assistant runs the check after connecting and offers install or update as its own step, which the user can skip; the machine list offers "Update all" for every machine whose probe reports another version or an outdated build and that the dispatcher does not update by itself (it failed, or no dispatcher runs). On the same system the check also compares the installed file's hash with this build ("Build identity" above), so another build of the same version is offered as an update too.

Machine suggestions and network search (#440)#

The address step of the assistant lists machines the user probably means (crates/core/src/discovery, Tauri commands discovery_known, discovery_search, discovery_cancel in src-tauri/src/discovery.rs):

  • Right away, without network: hosts from ~/.ssh/config (with Include, globs and paths relative to ~/.ssh; HostName, Port, User, IdentityFile; wildcard patterns skipped) and plain entries from known_hosts. Hashed known_hosts entries only mark a suggestion as "connected before", they never add one.
  • Only after "Search network": TCP port 22 on every address of the local subnets, derived from the interfaces and capped at /24 (at most 254 addresses per interface; loopback, link-local and public addresses skipped), with at most 64 probes at once, 500 ms connect and 1.5 s banner timeout; a hit must answer with an SSH- banner. In parallel the search listens 3 s for mDNS _ssh._tcp and _sftp-ssh._tcp announcements. Progress reaches the page through a channel; "Stop search" sets a cancel flag, no new probe starts and the result so far is kept.
  • Suggestions are merged by address and port, keep every source (SSH config, network, connected before) and are marked "already added" when a saved machine uses that host. Picking one fills name, address, port and user of the manual entry; nothing is saved before the usual steps.

Forge access and assistant subscriptions#

The satellite has no forge account configuration. Questions reach the forge only through the main host (ask forwarding), tested in crates/cli/tests/satellite_bridge.rs.

“Install” also provisions enabled coding assistants, the bundled question skill and Agent Desktop with its version-matched skills (desktop control, permissions). The app keeps Agent Desktop there current by itself (at start and daily); a failure shows on the computer's card, and on a Mac the person there approves its permissions once. On macOS, Claude Code and Codex subscription credentials travel through SSH stdin and are stored in the destination login keychain. They never pass through the frontend or temporary files. Codex uses its keyring credential store. Gemini and automatic credential transfer to other operating systems are not supported by this setup path yet; preflight rejects them before changing the remote installation. Install needs an unlocked destination login keychain and access to the official Node.js download service and package registry. The destination does not need GitHub access when the app carries a matching satellite executable.

New hosts and hosts undergoing setup remain excluded from worker dispatch until setup succeeds. A failed setup can be retried using “Install”. Existing assistant launchers are backed up before replacement; modified skills are protected rather than overwritten.

App: Settings → Satellite hosts (#357)#

The page calls the same core functions as the CLI (crates/core/src/satellite_host.rs: probe, install) through the Tauri commands hosts_list, host_probe, host_add, host_install and host_remove (src-tauri/src/hosts.rs); the frontend never runs ssh itself.

  • Every host is checked when the page opens, per row or all at once. A probe always returns a state (online, version_mismatch, unreachable, protocol); an offline host is not an error.
  • Adding saves the host only when it answers online with this version, optionally after a first install. Remove only drops the entry; nothing changes on the host.
  • Failures carry a stable reason (CmdError::Host), e.g. invalid_name, duplicate, unreachable, platform_mismatch, checksum_mismatch; the page shows a translated title and the technical text under details.
  • The store build cannot run ssh: hosts_list reports supported: false and the page shows a hint to the direct build.

Workers per machine (#967)#

Every machine, this one and each satellite, has its own "Workers at once" field in its row: "Automatic (N)" (default, one worker per dispatch.cores_per_worker cores; for a satellite N shows once a check reported its cores) or a smaller number for a less powerful machine. A number at or above the automatic value would change nothing, so the field offers only smaller ones, and a machine that runs one worker automatically shows no field. The choice saves at once through host_max_workers_set(name, max) (name = a satellite or local, max = null for automatic), also in the store build, and the dispatcher uses it from its next round.

  • Stored as max_workers on the satellite's entry in hosts and on local_host in orchestration.json; absent means automatic, 0 is refused (invalid_max; validate refuses a hand-written 0 too). Adding the same machine again keeps its value.
  • The machine's capacity is the smaller of the automatic value and the maximum (dispatch::host::capped_capacity); the dispatcher's host choice, the load order and the fair share use it (docs/orchestrator/dispatcher.md).

Desktop tests per machine (#995)#

Next to "Workers at once", each machine has "Desktop tests": not allowed, when nobody worked there for 1/2/5/10/30 minutes (default 2), or any time. It shows on this machine's row when Agent Desktop can run here (not in the store build) and on a satellite's row once its setup reported Agent Desktop. The choice saves at once through host_desktop_use_set(name, desktop) (name = a satellite or local; refused with unknown_host or invalid_desktop) as desktop on the machine's entry; adding the same machine again keeps it. A satellite worker reaches only its own desktop, because the satellite has no SSH sign-in for the other machines (docs/orchestrator/dispatcher.md, "Test desktop for desktop checks"). A worker on this machine that waits 3 minutes for a desktop moves once to a satellite of the same system whose desktop is free under that satellite's own setting; its work is committed and pushed first ("Moving to a free desktop elsewhere" there).

Windows machines and the remote shell (#958)#

Windows OpenSSH runs commands in PowerShell (usual DefaultShell) or cmd.exe, not sh. So the first command on every machine is a probe that runs in all three, echo gitoodo-shell %OS% $PSEdition (remote_machine::SHELL_PROBE): sh prints %OS% as it is, cmd expands it to Windows_NT, PowerShell prints each word on its own line and its edition. The result is stored with the machine (shell in hosts[]: absent = POSIX, powershell or cmd), and every later command is written for it:

  • Windows commands go out as powershell -NoProfile -NonInteractive -ExecutionPolicy Bypass -EncodedCommand <base64 UTF-16LE>, which needs no quoting in PowerShell or cmd (the check is about 4 KB, below cmd's 8191-character limit). Progress output is off, and a stopping error leaves as one plain line on stderr with status 1.
  • Check (assistant): os=Windows x86_64, cores, git, and per agent the program (Get-Command, then ~\.local\bin, ~\.claude\local, %APPDATA%\npm, ~\.npm-global, ~\.bun\bin, ~\.volta\bin), the first line of its --version and whether its credential file exists.
  • Install: New-Item for ~\.local\bin, scp to .local/bin/gitoodo.exe.upload, Get-FileHash, then the running gitoodo.exe (a service may hold it) is renamed to gitoodo.exe.old-<id> and the upload moved in; old copies are removed once their service has ended. The release asset is gitoodo-x86_64-pc-windows-msvc (docs/release.md); Windows on arm64 has no build (none).
  • Version check: the same lines from PowerShell for ~\.local\bin\gitoodo.exe.
  • Service: the named pipe above, created with a descriptor for the current user only; the bridge starts it with DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP and, where allowed, out of the SSH session's job, so it outlives the connection. The state folder is %LOCALAPPDATA%'s app folder.

ssh itself fails with status 255 (no route, refused, host key, sign-in). Any other failing status means the machine was reached and a command failed there: the assistant reports command_failed ("The check failed on the machine") with the last lines of the command's stderr, the install steps do the same, and a bridge that does not start on a reached machine is a protocol state ("was reached, but gitoodo satellite did not start there"), never "unreachable".

Coding agents per machine (#957)#

The assistant's check reports every supported agent (Claude Code, Codex, Gemini CLI) with installed, login (yes, no, unknown where it cannot be seen from outside, e.g. Claude Code's macOS keychain, or expired) and version; an agent is ready when it is installed and not known to be signed out or expired. expired (#994) comes from gitoodo worker-check on the machine: Codex's status reads "Logged in", but its usage query (the same as above) says the login no longer works. The row then reads "Sign in again on this machine: the login no longer works. Run codex login there."; a query that only fails or times out leaves the login yes. The only missing piece about agents is no_agent (not one is ready).

The last step lists the agents with a switch each. An assistant can be selected before it is installed on the satellite. The install action provisions selected supported assistants using the local subscription; unavailable subscriptions need to be connected locally first. Switching saves at once through host_agents_set(name, off) as agents_off on the machine in hosts[] (a deny list: an agent installed later is used without a new setup; absent = all on); adding the same machine again keeps it. The dispatcher treats a switched-off agent like a missing one on that machine (Config::host_allows_agent): with the worker pool the rotation picks among the agents each machine still offers, as it does locally, and a fixed agent waits for a machine that allows it.

The same step sets "Workers at once" for the new machine (host_max_workers_set, above), with "Automatic (N)" from the cores the check reported.

The machine list shows the same switches in every satellite's row, with each agent's state from the last check and when it ran. The check's agents are kept in host-checks.json in the app's data folder (gitoodo_core::host_checks, an observation and no setting, so not in orchestration.json; no secrets) and reach the page as checked on each entry of hosts_list (null before the first check, e.g. for a machine added with gitoodo host add: its switches then show the stored choice only). There is no check button: while the page is open it probes every machine's reachability and version on opening and every three minutes. For a machine that is online it then runs the agent check through host_agents_check(name) (satellite_host::machine_check: shell probe, then the check for that shell) once the last check is older than ten minutes, stores the result and saves a shell that changed since. On macOS and Windows machines with Agent Desktop it also reads the permissions there (host_desktop_permissions), so a grant or a revocation shows up on its own; missing ones are named in the UI language. A row shows "Install" only while something is missing there (offline or failed probe aside: no Gitoodo, an older or no Agent Desktop, or a desktop error that is not a permission); otherwise it shows "Set up". Removing a machine drops its check.
