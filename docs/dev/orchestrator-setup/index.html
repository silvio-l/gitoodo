The app guides you through the orchestrator setup and does each step for you. On first start the onboarding offers orchestrator mode (preselected) next to the plain to-do list. With orchestrator mode, the onboarding sets up every repository picked in its repo step in one go, right after that step: you choose once what happens to issues that are already open and press Set up now. Gitoodo then installs the background service (the signed release reads tokens through the service helper without any keychain step; other builds grant the services access once, macOS may ask: choose Always Allow), renames legacy labels and creates missing ones, switches each repo on, clones missing local copies into the clone folder, installs the skill for the worker agent and starts the dispatcher. Each part and each repository shows its own state; Try again repeats only what failed. Own label names, single repositories and agent instructions stay in the settings.

First run (#337)#

The onboarding leads a first-time user from the account to a running worker:

  • Repos to work on: every repository Gitoodo reads starts switched off. The step lists them with the already active ones checked (none on a first run), with search and "All"/"None"; only the checked ones are set up and switched on. A repository switched off here (or later in the settings) does not show in the sidebar.
  • Setup: one confirmation sets up all checked repositories. Each shows its label preview (kept, renamed old → new, created) before anything is written, then its progress; Try again repeats only what failed. Legacy labels are read under their catalog meaning; nothing is deleted. The open-issue choice defaults to Check existing issues and ask: open contributions of other authors are never trusted on their own, the intake asks for an approval, which "Asked of me" answers per group or all at once. The merge style is preselected from what the repositories allow (Forgejo repositories that only allow fast-forward get fast-forward-only).
  • Workers: this machine is listed as a worker with its capacity (default 2, editable) and the agent found on it; machines named in host: labels that do not exist are listed with the issues waiting for them and can be made an alias of this machine.
  • How it goes on: the live state (dispatcher, workers, ready issues), then either **Release an issue** (sets the ready label on an open issue of a switched-on repository) or **Create a test task** (a small issue that is ready at once), and where progress shows (board, sidebar, status).

Switching a repository on records adopted_at. Every switched-on repository can be paused and switched on again where it shows: the play/pause button on its sidebar row (on hover and in the "…" menu) and in the board's repository header. Both write the same state as Settings → Repositories (active/paused in orchestration.json); pausing lets running workers finish. A short message confirms each switch.

The emergency stop keeps its state across restarts: what ran when the app ended runs again, what was halted stays halted (a banner says so, with "Fortsetzen", which lets every repo continue in its own state). "Alles anhalten" in the title bar, in the tray menu, Cmd/Ctrl+Shift+H or gitoodo stop-all stops everything at once (see dispatcher.md, "Emergency stop"). Switching on more than three repositories at once asks first and names the count and how many workers run in parallel (dispatch.max_workers, default 2).

The sidebar picks several repositories at once: Shift-click picks a range, Cmd-click (macOS) or Ctrl-click (Windows, Linux) adds or drops one, Shift+arrow extends from the keyboard, Cmd/Ctrl+A picks every shown repository and Escape lets go. A bar at the foot of the list and the "…" menu then pause, switch on, star or move all picked repositories ("Pause 3 repos").

Groups nest: "New group inside" in a group's "…" menu, dragging a group onto the middle of another one, Alt+Right/Left (into the group above, out one level) or "Move to group …" (also M) put a group inside another, shown with the path ("Clients › Web"). A group never moves into itself or a group inside it. Each level is indented, keeps its folded state and counts what its subgroups hold. Groups can be picked like repositories; pausing or switching on a picked group acts on every repository inside it. Deleting a group moves what it holds up one level.

The assistant below covers the same steps one by one, for a skipped onboarding step, later changes and single repositories. Open it from Settings → Setup assistant, or from Settings → Mode once orchestrator mode is selected.

The assistant stores no progress of its own. Each time it opens, and whenever you press Check again, it checks the real state of the service, the accounts, the labels, the repository state and the dispatcher. It then continues at the first step that is still open. You can stop at any point and resume later, or run it again on a finished setup: steps that are already done stay done and are skipped.

The assistant opens in its own window, shows one step per page with Back and Next and a progress bar of all steps, and moves on by itself once a step is done (#589).

Everything the assistant does is also possible by hand. Each step below names the manual way.

Without a desktop (headless Linux, #1208)#

On a server without a graphical session there is no app and no assistant; the command line does every step, without editing settings.json or orchestration.json by hand and without a token file of your own:

gitoodo account add --forge forgejo --url https://git.example.org --token-stdin   # 2.
gitoodo repo list <account>
gitoodo repo activate <account> owner/repo                  # 3. + 4.: preview, writes nothing
gitoodo repo activate <account> owner/repo --backlog ask    # labels, then switched on
gitoodo service install all                                 # 1. + 7.
gitoodo doctor                                              # final check

The token goes in on stdin only (typed hidden, or piped). Where no system keyring answers it is kept as a systemd credential that both services load: a file only you can read in Gitoodo's state folder and one drop-in per service, which account add writes and account remove removes (daemon.md, "Headless setup"). gitoodo doctor names the command line there, never the app, and a token only the services read is no warning. The worker agent needs its own sign-in on that machine (for example the agent CLI's login); the first worker starts once an issue of the active repository is ready.

0. Install#

Install the app from the download on the landing page (macOS DMG, Windows setup). On macOS, curl -fsSL https://gitoodo.com/install.sh | bash installs the app and the gitoodo command; on Windows, irm https://gitoodo.com/install.ps1 | iex does the same. Then open Settings → Setup assistant. The matching uninstall.sh / uninstall.ps1 removes the services and everything else again (see the README).

1. Background service#

Check: the classifier answers on its local socket and reports its version, its secret backend and whether its first poll has finished. Accounts the last poll could not read are shown as a hint.

Assistant: registers the classifier with the system service manager and waits until it answers. This is launchd on macOS, a systemd user unit on Linux and a scheduled task on Windows. When the service is registered but silent, Set up service again restarts it. If the gitoodo command line program is missing (it is looked for next to the app, then on PATH), the step says so.

The assistant first copies the bundled CLI to a per-user folder and the services run that copy, so moving or updating the app does not break them; both services restart on their own after a crash or a reboot. The step shows the app and installed CLI versions; when they differ from each other or from the running classifier, Reinstall aligns them. Classifier and dispatcher each have Start, Stop and Remove. The store builds install no services.

By hand: gitoodo service install|uninstall|start|stop [classifier|dispatcher|all], gitoodo --version. On a system without a service manager, run gitoodo classifier in a terminal. gitoodo doctor checks the result.

2. Account and token#

Check: at least one account is connected and no account's token lacks a permission or has expired.

Assistant: opens the account wizard. A token that needs renewing is replaced in the Replace token … dialog of that account. Tokens go to the system keychain only.

By hand: Settings → Accounts. Without the app: gitoodo account add --forge forgejo|gitea|github|gitlab --url <url> --token-stdin (token on stdin; keyring, or a systemd credential on headless Linux), gitoodo account token <account> --token-stdin to replace a token, gitoodo account list|remove.

Orchestrator account (#764): per forge host the orchestrator acts as a chosen account. The onboarding step "Worker-Konto" recommends a separate worker account and guides through it per forge: create the account, give it write access to the repos (Forgejo/Gitea: collaborator with write or a team; GitHub: collaborator or team with Write; GitLab: Developer, Maintainer for protected branches), sign in as the worker account and create a token with the rights listed there (the orchestrator's rights without repository settings), and allow it to merge under branch protection. The token goes through the normal account wizard, so it lands in the system keychain only. The check then shows the worker account's login, missing scopes and every activated repo it cannot work in, with a link to grant access. Using the own account stays possible; the history then shows the user's name. Change and check it later under Settings → Accounts → Orchestrator-Konto.

In orchestrator mode the onboarding step "Konto" says which account belongs there: the user's own account, with admin/owner rights for the setup; the worker account follows in the step "Worker-Konto".

Automatic worker account (#764): where the own account may create accounts, the step "Worker-Konto" offers "Create worker account automatically" above the guide. Nothing is written before the user has seen a summary and confirmed it. Then four steps run in order, each with its state; a failed step is run again and continues where it stopped (every step is idempotent):

  1. Account. Forgejo/Gitea: needs a site administrator (GET /user → is_admin) and a token with write:admin. POST /admin/users with the chosen login and email, restricted: true (sees only what it is added to), must_change_password: false, full name "Gitoodo worker" as marker. GitLab self-managed: an administrator with the api scope (and Admin Mode, where it is on); POST /users with skip_confirmation, force_random_password, external: true, projects_limit: 0, no group creation, and an admin note as marker. The login is checked (letters, digits, -, _, ., at most 39 characters); the email defaults to a plus address of the own email (alice+gitoodo@…), Gitoodo never invents a domain. A login that already exists is used again only if it carries Gitoodo's marker; anyone else's account is never changed.
  2. Access. Per activated repo (or every listed repo when none is active yet) the worker becomes a collaborator with write (Forgejo/Gitea), or a member as Developer (GitLab; Maintainer only where a protected branch lets only Maintainers merge). Organisation repos get a per-repo collaborator as well, not a team: Gitoodo creates no teams and changes no organisation membership, so the worker only reaches the repos the user switched on. A failed repo fails the step with its reason; the retry skips what is already in place.
  3. Merge. Forgejo/Gitea: on protected branches with a merge allowlist the worker is added to merge_whitelist_usernames. GitLab: a protected branch where nobody may merge is listed for the user. Anything that cannot be done is listed under "Still for you" with the repo.
  4. Token. Forgejo/Gitea: the token endpoint only accepts basic auth (Sudo does not apply), so Gitoodo sets a random one-time password as admin, creates the token gitoodo-<time> with exactly the worker scopes (read:user, write:repository, write:issue) by basic auth and immediately sets another random password nobody knows. GitLab: POST /users/:id/personal_access_tokens with api and an expiry of 364 days. The token is stored through the normal account path (system keychain only, rights recorded, service access granted) and chosen as the host's worker account; the check below then runs as usual.

The step leads with that card ("Create the worker account automatically") wherever it is possible; the manual guide sits behind "Set it up myself instead", the reasons behind a collapsed "Why a worker account?". A line under the step title says which way applies ("Gitoodo creates the worker account for you" or the guide).

Admin without admin scope. Where the own account is a site administrator but its token lacks the admin scope, the card stays and asks to confirm admin rights once:

  • Forgejo/Gitea: the user enters the own password (and, if the forge asks, the code of the authenticator app). The core creates a short-lived token with basic auth (POST /api/v1/users/{login}/tokens, scopes write:admin, write:repository, write:user; the one-time code goes out as X-Forgejo-OTP and X-Gitea-OTP), runs the setup with it and deletes it right after (DELETE /api/v1/users/{login}/tokens/{id}), also when the setup fails. If that delete fails (a one-time code may have expired), the step names the token so the user can delete it under Settings › Applications. Accounts with security keys cannot use basic auth; the step then offers the token way.
  • Alternatively (and on self-managed GitLab only): paste a temporary admin token (Forgejo/Gitea scopes as above, GitLab api, with Admin Mode also admin_mode). It is used for this one run and not stored; the user deletes it afterwards.
  • Or "Renew token with admin rights": the Replace token … dialog of the own account opens over the step and asks for the admin scope; once the new token is saved, the step checks again and shows the plain card.

The onboarding's account step offers "Replace token …" and "Connect another account" (disconnect, then the wizard) for a connected account; in orchestrator mode its wizard mentions that the admin scope lets Gitoodo create the worker account later.

Where the own account is no admin, the step says so in one line and shows the guide. gitlab.com and GitHub always use the guide (no account API). On GitHub, once the worker token is connected, "Give access to all repos" in the check invites the worker as collaborator (Write) from the own account and accepts the invitations with the worker token (PATCH /user/repository_invitations/{id}); the same button adds missing collaborators on the other forges. Merge rules (GitHub rulesets, branch protection bypass lists) stay manual on GitHub.

3. Map labels#

Check: the target repository has every catalog label (see spec.md, section 5.1) and no legacy label names the migration would rename (#591). The target is the first active repository of a connected account; if there is none, you pick an account and a repository.

Assistant: shows the labels the repository lacks. For each one you can use a label the repository already has, or have it created. The mapping applies to all repositories and is written to profile.names in Gitoodo's own orchestration.json. Missing labels are created only after you confirm the list. Legacy labels (for example prio:1, status:*) are listed as old → new and renamed by the same click (the #567 migration), so no English duplicates appear beside them; issues and pull requests keep their labels. Labels already in use under their catalog name are listed as "stay as they are". Where a legacy name and its catalog name both exist, both stay and are named as a pair; Gitoodo merges nothing, and the step does not wait on such a pair. The same holds for two legacy names of one catalog label (an:mensch and ready-for-human): the first in the list is renamed, the second stays beside it as a pair, since Forgejo and Gitea would accept a second label of the same name. Other existing labels are never changed or deleted.

The onboarding's setup step and Adopt several repositories … show the same preview for every picked repository before anything is written: a total line (kept, renamed, new) and per repository the labels it keeps, renames (old → new) and gets created. It is read from the forge without writing; a repository whose labels cannot be read says so and can be read again.

By hand: set profile.names in <config>/orchestration.json (catalog name to your label name, see daemon.md) and create the labels on the forge. The classifier also recreates missing catalog labels in active repositories on its next run.

4. Activate a repository#

Check: the target repository is listed in orchestration.json with the state active and is not switched off in the settings.

Assistant: sets the repository to active. This means the orchestrator may take issues labelled ready (or your mapped name) and set labels in that repository. Before a repository writes for the first time, the assistant (and Settings → Repositories) shows a preview read from the forge without writing: how many issues are open, how many would become ready, how many would get an approval or clarification question and to whom, how many labels and milestones would be set (#598). You pick what happens to the issues that are already open:

  • Only handle new issues: issues and pull requests opened before this moment get no labels, comments or milestones and never become ready on their own.
  • Take existing issues as ready: they become ready without a question.
  • Check existing issues and ask (recommended; the default in the onboarding, in Settings → Repositories and for the sidebar's switch, #1115): the normal intake; questions go out at most five per repository and run, the rest is logged as "N more questions pending".

Questions mention the configured person of the repository, else the connected account, never the owning organisation. The choice is stored as backlog (new, ready, ask) with adopted_at in the repository's rule; rules written before #598 behave like ask. If no suitable repository exists yet, Create a new project or Adopt an existing repository open the project wizard inside the assistant.

Adopt several repositories … (#590) lists the account's other repositories with a search field and "All of <owner>" per owner or organisation, plus its own choice for open issues (default: only new issues). Nothing is written until Adopt N repositories; until then any repository can be deselected, and the label preview above the button lists what each selected repository keeps, renames and gets created. The onboarding's repo step offers the same "All of <owner>" switch when an account reaches repositories of several owners or organisations. The repositories are then handled one after the other, each with its status (waiting, setting up, turned on, failed): legacy labels are renamed and missing ones created, then the repository is switched on. A failed repository does not stop the others; retry it under Settings → Repositories. The local-copy step then lists every repository adopted in this run (see below).

By hand: Settings → Repositories. Without the app: gitoodo repo activate <account> <owner/repo> prints the label preview and the open-issue counts per choice and writes nothing; --backlog new|ready|ask then renames and creates the labels and switches the repository on (--paused for paused). gitoodo repo pause|observe switch it back, gitoodo repo list <account> shows every repository's state.

Removing a repository again#

Aus Gitoodo entfernen … (sidebar actions menu of a repository, Settings → Repositories in a repository's detail and for a multi-selection) takes repositories out of Gitoodo's management (src-tauri/src/repo_remove.rs, crates/core/src/repo_remove.rs):

  • The repository is switched off in the settings, so lists, counts and notifications skip it.
  • Its rule leaves orchestration.json. The dispatcher assigns nothing new there and, in its next round, stops its running and parked workers rather than letting them finish (enforce_control). Unfinished changes stay in the worktree; forge labels and issues stay as they are.
  • Its leases are released: by the app while no dispatcher holds the state folder (the app takes the dispatcher's instance lock for the edit), otherwise by the dispatcher in its next round.
  • Optionally, Gitoodo's own worktrees of the repository are removed through the hygiene's guarded removal: only folders with Gitoodo's ownership marker for exactly this repository, none with a live lease or unsaved work. The user's own checkout is never removed.
  • Nothing changes on the forge. The toast offers Undo for about 30 seconds (the app keeps the removed rule for 10 minutes); afterwards the repository comes back through Settings → Repositories or Repos hinzufügen.

Auch auf der Forge löschen (endgültig) additionally deletes the repository on its forge. The dialog names what is lost (code, issues, pull requests, wiki, releases) and whether the forge can restore it: Forgejo/Gitea have no trash; GitHub keeps most deleted repositories for 90 days (not forks); GitLab may only mark the project for deletion (delayed deletion, usually 7 days, depending on version and settings). Before the button is enabled, the core checks with the connected account's token whether it may delete (Forgejo/Gitea: repository admin and scope write:repository, for a repository of an organisation also write:organization, asked with a write the forge refuses (docs/token-permissions.md); GitHub: scope delete_repo and admin; GitLab: scope api and the Owner role) and names a missing right with Token ersetzen …. When a delete still fails, the toast says the repository left Gitoodo and why it was not deleted on the forge ("Removed from Gitoodo; not deleted on the forge: …"). The user types the full name owner/repo, or for several repositories their count or "löschen". The delete itself runs in the core against DELETE /api/v1/repos/{owner}/{repo}, DELETE /repos/{owner}/{repo} or DELETE /api/v4/projects/{path}; see docs/security.md.

5. Local copy#

Check: the dispatcher has a local copy of the target repository.

Each worker works in its own worktree of this copy: it creates a branch there, opens a pull request and merges it into the base branch.

The dispatcher uses, in this order: the folder set for the repository, a clone found by its origin in the projects folders or the clone folder (any layout), else <dispatch.clone_root>/<owner>/<repository> (#592; default clone folder ~/gitoodo/repos, a folder of Gitoodo's own, #735). In a copy of yours Gitoodo only fetches and creates its <prefix>/… branches and worktrees (under dispatch.worktree_root); it never checks out, resets or cleans your working tree. The worktree folder must lie apart from the clone and projects folders. The step shows the clone folder with Change…, which opens the native folder picker (Finder, Explorer, the desktop portal) and applies to every repository. The assistant lists the target and every repository adopted with it in this run (#590), one row each with its folder and state:

  • No clone yet (nothing there or an empty folder): ticked, Clone N repositories clones it with the connected account. The token reaches only that one git clone through GIT_ASKPASS, as with gitoodo worker push; origin is the plain HTTPS URL and no token lands in .git/config, a file, a log or an error text.
  • Clone present: origin points at the repository on the account's server (HTTPS or SSH).
  • Clone of another repository, **repository without origin, not a repository**: shown and left as it is. Move the folder away or fix origin, then check again.

Later fetches of the dispatcher (base branch, branch updates) and the workers' pushes use the connected account the same way, so a fresh device needs no git credential helper and no SSH key, also for private repositories. A missing or expired token is reported in the dispatcher log and the app ("reconnect the account") instead of a git prompt.

Instead of cloning, Other folder… points the assistant to the folder where the repository already lives. The folder is checked before it is saved: a clone of this repository is used; a missing or empty folder is saved and offered for cloning there; a clone of another repository, a repository without origin or a folder with other files is refused with that reason and nothing is saved.

Several repositories (#590): every repository without a copy is ticked; untick it, or use Select all / Select none, to skip it. The target cannot be skipped, the first worker needs its copy. Use the clone folder drops a folder set with Other folder…. Nothing is cloned before Clone N repositories; the clones then run in the background (at most two at a time, as in the onboarding), each row with its state (will be cloned, skipped, waiting, cloning with its share, cloned, failed) and an overall progress bar below the list. A failed clone shows its reason with Try again and does not stop the others. The step is done once the choice is confirmed and every ticked repository has its copy.

By hand: clone the repository yourself into the clone folder.

6. Skill and agent instructions#

Check: the AGENTS.md in the local copy holds the current Gitoodo section.

Assistant: installs the Gitoodo skill on this computer if it is missing, and on request writes or updates the marked Gitoodo section of AGENTS.md in the local copy. Text outside the markers stays as it is, and nothing is committed: you review and commit the change yourself. This step does not hold back the first worker.

By hand: Settings → Skill, and copy the section shown there into AGENTS.md.

7. First worker#

Check: the dispatcher is registered as a background service (where the build may install one) and answers on its control socket and reports running workers.

Assistant: installs the dispatcher as a background service and starts it unless one already answers, so it keeps running after the app quits; the store build cannot install services and starts it from the app. The dispatcher logs to dispatcher.jsonl in the log folder (see logging). The assistant then waits for a worker. A worker starts as soon as an issue in an active repository carries the ready label. The setup is complete once a worker runs.

On Windows the dispatcher has no scheduled task yet (#355): the assistant starts gitoodo dispatcher from the app as its own process, which answers on a named pipe of the current user (#354) and keeps running after the app quits, but not across a new login.

By hand: gitoodo dispatcher in a terminal, then give an issue the ready label. Details: dispatcher.md.

Final check#

The last page and the success page list the live state of everything the orchestrator needs (#601): classifier running as a service, every token readable by the services without a prompt, the classifier polling without errors, the local copy present with a matching origin, the dispatcher registered as a service and running. Each red item has one Fix button that opens the step that fixes it. The service step counts as done only once no token needs a keychain prompt, so the assistant never says "ready" while the services cannot work.

What the assistant never does#

  • It never commits and never writes configuration that is versioned in your repositories. It writes Gitoodo's own settings.json and orchestration.json, and only on request the marked Gitoodo section of AGENTS.md in the local copy.
  • It never shows a token, writes one to a file or log, or sends one to the app's frontend. (Only gitoodo account add on a machine without a keyring keeps it as the services' systemd credential, a file only you can read.)
  • It never deletes or renames labels on the forge.
  • It never deletes a repository on the forge; only the removal dialog does, after a typed confirmation (see "Removing a repository again").
