让编程智能体自动处理 GitHub 议题

本页内容
  1. 你需要什么
  2. 从议题到合并
  3. 一次性设置
  4. GitLab：议题与合并请求
  5. 开始使用

有了 Gitoodo，一个就绪的 GitHub 议题无需你启动会话就能变成已合并的拉取请求：一个工作进程接手议题并创建拉取请求，等你的仓库要求的检查通过后，调度器就会合并它。本页展示其中每一步，以及你只需设置一次的内容。GitLab 上的流程相同，只是用合并请求。

你需要什么#

  • 一个 GitHub 账户和一个令牌。令牌助手会打开 GitHub 的经典令牌页面并预先选好权限，同时解释每一项；细粒度令牌也可以，权限需手动选择。权限列表见代码托管平台令牌（英文）。
  • 一个你已在用并已登录的智能体命令行工具：Claude Code、Codex 或 Gemini CLI。工作进程使用你的订阅运行；Gitoodo 不需要 API 密钥。
  • 处于编排器模式的 Gitoodo；入门会带你完成设置。

从议题到合并#

  1. 议题变为就绪。 来自你信任的人（你自己、拥有写权限的人、所属组织的成员、你的受信任的作者）的议题，在描述完整后，或者一旦带上 ready 标签，就会变为就绪。其他任何人的议题会先收到一个批准问题，绝不会自行启动工作进程。
  2. 工作进程启动。 调度器为每个就绪的议题启动一个工作进程，各自在独立的 worktree 和分支中运行，例如 gitoodo/42-login-fix。它在侧边栏中显示为仓库下面的一个会话，你随时可以接管。
  3. 缺少决定时，智能体会提问。 它把问题写进议题；Gitoodo 会在问我的中把它显示为一张回答卡片，并预先选中推荐项。你的回答会以一条简短评论发回，工作进程随即继续。参见问题。
  4. 创建拉取请求。 工作进程推送它的分支，并创建一个带有 Closes #42 的拉取请求。它自己不持有令牌：Gitoodo 用已连接的账户替它推送。议题随之转为 in-review。
  5. 由检查决定。 Gitoodo 从目标分支的分支保护和规则集中读取必需的检查。如果某项检查失败，拉取请求会带着失败信息退回给它的工作进程；如果分支已落后，Gitoodo 会更新它。
  6. 合并。 Gitoodo 以你的仓库允许的方式合并（默认为 squash），合并的正是经过检查的那个提交，然后关闭议题并移除 worktree。

一次性设置#

  • 必需的检查。 如果没有任何检查，Gitoodo 会等待三分钟看是否出现检查，然后合并。请添加一个 CI 工作流，并在分支保护或规则集中把它设为必需。安全的自动合并列出了合并前必须满足的全部条件。
  • 合并账户。 如果你的规则限制了谁可以推送，合并账户必须在该名单上。允许合并账户可以添加用户；团队则需要你在 GitHub 上修改。详情见分支规则（英文）。
  • 合并方式。 默认值在“设置 → 调度器”中设置，单个仓库自己的方式在该仓库设置的合并下设置；参见合并与发布。

GitLab：议题与合并请求#

在 GitLab 上，工作进程创建的是合并请求。启用 "Pipelines must succeed" 时，由头部流水线决定；在使用快进或半线性合并的项目中，GitLab 会自行变基分支。合并账户需要在受保护的目标分支上拥有 Allowed to merge。Gitoodo 目前还不读取 GitLab 的分支规则：如果合并被拒绝，会有一张卡片链接到相应设置。

开始使用#

下载 Gitoodo，然后按照入门从安装一直走到第一个已合并的拉取请求。
